Implement the plan documented at the path / reference in `$ARGUMENTS` **directly in Claude Code, one phase at a time, driving the whole project to completion and activation the way the AI orchestrator does**: open a **project branch** `claude/implement-plan-<slug>` from the default branch (the orchestrator's `orchestrator/project-<N>` equivalent) with a draft **final PR** into the default branch, ship each phase of the plan's **Phases & Merge Strategy** as its own PR against the project branch, and let the review-autofix workflow review it and auto-merge it. On these PRs the workflow runs in **Claude-fixer mode**: its reviewer panel writes the findings, and a fresh Claude stage session fixes them (or rejects them with reasons) instead of the GPT editor, resolves merge conflicts instead of the GPT resolver, and the workflow re-reviews every push until no valid finding is left and then auto-merges. The waits are an hourly low-effort Sonnet check-in, never a CI or review-comment babysit. After the last phase merges, run the **conformance audit** (`/verify-activation — scope conformance`, the judge that checks the merged code against the plan), then the repo's **security audit** workflow and then the **runtime validation** workflow against the project branch — the orchestrator's `ai:security-pass → ai:validating` order — looping each until it is clean (and re-auditing conformance when validation needed Claude-written fixes), then land the completion PR that moves the plan doc into `docs/completed/`, then mark the final PR ready so the whole project is reviewed once more and auto-merges into the default branch, then run **`/verify-activation — scope activation`** on the finished project and, when it reports DORMANT, start **`/deploy-activate`** for you. Nothing reaches the default branch before every stage passed. **Every stage runs in its own fresh session** (see [Stage Sessions](#stage-sessions)) so no step re-sends the whole history; progress is persisted to `docs/implement-plan/<slug>.md` and to the stage-session prompts so any later session resumes where the last one stopped, and the lessons each stage records there are ingested into AI memory when the PR carrying them merges. This is the **in-session** variant — Claude writes the code. To hand the plan to the unattended **AI orchestrator** instead (which decomposes the work into a dependency DAG of issues and ships each phase as its own PR), use `/implement-plan-ai`. `$ARGUMENTS` is **free-form prose** that must resolve to a single plan markdown doc — typically a path like `docs/plans/<slug>-plan.md`, but it may also be a slug, a topic that matches one plan filename, or a GitHub reference (issue / PR) that links to the plan. Optional trailing prose (focus areas, a phase to start with) is allowed, and a trailing `— source revision <ref>` makes every stage and checker session check out `<ref>` instead of the default branch (only for testing an unmerged change to this command; normal runs omit it); a stage session started by this command also receives a trailing `— resume.` block (see [Stage Sessions](#stage-sessions)).
**Questions never stall the chain:** after the start-up checks (steps 0, 1, and 3), every intent or design question a stage would stop to ask is answered with its RECOMMENDED option and recorded as an auto-decision (CLAUDE.md §28, see [Auto-Decisions](#auto-decisions)); the full list is shown for your review, never re-asked, at the verify-activation and deploy-activate stages, so a human is needed only once the project is complete.
**Issue mode:** a plan whose header carries a `Source issue:` line was written by `/implement-issue-claude` for one standalone issue. The chain is the same, with the differences in [Issue Mode](#issue-mode) — most importantly, nobody is at the keyboard, so the start-up checks are auto-decided too (CLAUDE.md §28.A) and every stop is reported on the issue.

3a. **Open the project branch and the draft final PR** (project mode, first stage only; in [Issue Mode](#issue-mode) the branch forks from and the final PR targets `<issue base>`, and the plan doc is committed with the log). `git checkout -B claude/implement-plan-<slug> origin/<default>` (on a name collision with an unrelated branch, stop and ask), create `docs/implement-plan/<slug>.md` with `Project branch: claude/implement-plan-<slug>` and the phase checklist, commit it as `docs(implement-plan): start <slug>`, and `git push -u origin claude/implement-plan-<slug>` — GitHub refuses a PR with no commits, so the log is the branch's first commit. On a merge or a review round the checker starts the next stage session, and that session archives this one and the checker. On a block it **hands the PR back to this session** instead (see [Hand-back](#hand-back)), because the session that armed the wait last worked on the PR and holds the context the intervention and the action-needed report need.
   - **Merged** (next stage session) → tick the phase in the log and go to step 4 for the next phase from the freshly merged base branch. After the last phase, go to step 8.
   - **Review round** (`state: review-round` or `state: conflict`; next stage session) → step 7a, then arm the wait again with the same three next stages.
   - **Blocked** (the definition in [Check-in Loop](#check-in-loop); handed back to the session that armed the wait, or a fresh `… — blocked PR` stage session only when the hand-back fails) → this is the one case where Claude touches the PR outside a review round: check out the branch, resolve the block under CLAUDE.md §12 (merge the base branch and resolve the conflict, address the remaining findings, fix the failing check, or re-open / re-create the PR if it was closed unmerged), verify, commit as `[claude-intervention] <summary>` (this subject ends the run of `[claude-autofix]` rounds, so the workflow's `MAX_AUTOFIX_ITERATIONS` count starts over, as a `[judge-fix]` commit does for GPT PRs), push, remove the `ai:review-blocked` label from the PR **before** arming the next wait (read its labels with `mcp__github__issue_read`, then `mcp__github__issue_write` `update` with that list minus `ai:review-blocked`; a routine §23.B label write — `gh api` writes stay behind the `permissions.ask` prompt), or the checker routes straight back to a blocked stage, record the intervention in the log, and arm the wait again. Cap: **3 interventions per PR**; on the fourth blocked stage stop and ask in Q/A format instead of pushing again. In Claude-fixer mode the workflow never runs the GPT review-blocked judge: when the rounds reach `MAX_AUTOFIX_ITERATIONS` (default 5) it labels the PR itself `ai:review-blocked`, which routes here.

7a. **Review round — Claude fixes what the reviewer panel found.** The workflow's hand-off is the last comment carrying `<!-- ai:claude-fixer-handoff:v1 kind=<findings|conflict> head=<sha> round=<r> -->` for the PR's current head; read it and, for `kind=findings`, the reviewer ledger comments the workflow posted just before it (the consensus findings, task gaps, and per-reviewer findings) plus any failing check it names. Check out the PR head branch at `<sha>` (if the head moved since, the hand-off is stale: arm the wait and end).
   - **`kind=conflict`** → `git merge origin/<base branch>`, resolve keeping both sides' intent (stop and ask when the right resolution is not evident), run the repo's checks, commit as `[claude-merge-resolve] merge <base branch>`, push. The push starts the next review round.
   - **`kind=findings`** → judge **every** finding against the actual code, exactly as the GPT editor would: a finding is valid when re-reading the code confirms the defect, invalid when it misreads the code, duplicates a fixed one, or asks for out-of-scope change (§5 still binds, and §6 / §10 are never overridden by a reviewer). Fix the failing checks it names too.
     - **At least one valid finding** → fix all the valid ones, verify per step 5, and push **one** commit whose subject starts with `[claude-autofix] review round <r>: <summary>` (one commit per round: the workflow counts consecutive `[ai-autofix]` / `[claude-autofix]` commits toward `MAX_AUTOFIX_ITERATIONS`). Before pushing, reply once on the PR listing each finding as fixed or rejected with a one-line reason. The push starts the next review round.
     - **No valid finding left** → read the latest workflow-owned findings hand-off for this head, including its `<!-- ai:claude-fixer-handoff:v2 head=<sha> round=<r> ledger=<64hex> -->` marker. A dedicated GitHub App bot, distinct from the review workflow's GH_PAT account, must post one separate PR comment listing each rejection with a reason and ending with BOTH `<!-- ai:claude-fixer-verdict:v1 head=<sha> -->` and `<!-- ai:claude-fixer-verdict:v2 head=<sha> round=<r> ledger=<64hex> -->`. `CLAUDE_FIXER_VERDICT_BOT_LOGIN` must be configured to that bot's GitHub login in the repo and checker environment. The bot must use privately provisioned installation credentials with Issues or Pull requests write permission. Claude Code Web may replace authorization headers to api.github.com: do not assume `gh` or a Web session can post as the bot. If a verified bot-authenticated posting path is unavailable, leave the verdict unposted and report `Status: BLOCKED`; never post as a collaborator or use GH_PAT. Then dispatch the review workflow with the convergence input: `gh workflow run review_autofix.yml -R <owner>/<repo> -f pr_number=<N> -f claude_fixer_converged_head=<sha>` in this library (directly, not through `internal-review.yml`, which calls `review_autofix.yml@main` and so cannot forward an input `main` may not have yet), `gh workflow run ai-review.yml -R <owner>/<repo> -f pr_number=<N> -f claude_fixer_converged_head=<sha>` in consumer repos. The gate authenticates the bot and ledger and launches **one fresh reviewer panel on that head**, not auto-merge. Only a clean result and fresh ready same-head check-run snapshot can enable auto-merge; further findings block the PR for intervention, not another same-head verdict cycle. Invoking this command *is* the §23.C approval for this dispatch — do not re-ask.
   - Record the round in the log (`review rounds: <r>`), add a `[source:intervention]` lesson when a finding revealed a reusable pattern, and arm the wait as in step 7. A round never merges anything itself and never disables a check.

8. **Conformance audit — the judge, before security and validation.** In the `conformance <k>/3` stage session, `Read` `.claude/commands/verify-activation.md` and follow its procedure with `docs/plans/<slug>-plan.md — scope conformance — unattended` (plus the merged PR list from the log) as its `$ARGUMENTS`: it maps every acceptance criterion in the plan to the merged code, audits that code for correctness, and opens one fix PR for the EVIDENCE-BASED defects it can fix. `— unattended` makes it auto-decide the findings that need a decision (§28), applying the RECOMMENDED fix in its fix PR; copy the auto-decisions it reports into the log's `## Auto-decisions` section. Two overrides apply to that procedure inside this chain: it audits the **base branch** (in project mode, check out the synced project branch and read the code there, not the default branch), and its fix branch is `claude/implement-plan-<slug>-conformance-fix-<k>` from the base branch with the PR opened against the base branch, so the fix PR runs in Claude-fixer mode like every other PR of the project. Record the run in the log's `## Conformance` section (verdict, fix PR, date). Running it before the security pass means every conformance fix is security-audited and validated afterwards. Then act on its result:
   - **Fix PR opened** → arm the wait on that PR as in step 7 (next stage `conformance <k+1>/3`, review rounds via step 7a); the next stage re-audits the merged fixes.
   - **CONFORMANT with no fix PR** → if no clean security pass is recorded yet, or a conformance fix PR merged after the last clean security pass, go to step 9 (security, then validation); otherwise (the post-validation re-run found nothing to fix) go to step 11.
   - **INCOMPLETE with no fix PR** (the run auto-decided every decision it could, so what remains is a finding it could not verify or has no §28-safe option) → stop with `Status: BLOCKED` and ask the Q/A questions `/verify-activation` produced.
   - **Cap: 3 conformance runs per project**, shared by the pre-security runs and the post-validation re-run in step 10. A fourth run is never started: stop with `Status: BLOCKED` and ask.

9. **Security pass (orchestrator order: security before validation).** In [Issue Mode](#issue-mode), a plan whose header says `Security pass: skip` skips this step: record `Security: skipped (<reason from the plan header>)` and go to step 10. Otherwise dispatch the security audit workflow — `security-audit.yml` in this library, `ai-security-audit.yml` in consumer repos (pick the one that exists; if neither exists, record `Security: not wired` in the log and continue to step 10) — with `gh workflow run <file> -R <owner>/<repo>` plus, in project mode, `-f ref=claude/implement-plan-<slug>` (or `mcp__github__actions_run_trigger` with the same inputs). With `ref` the audit covers the project branch's changes since its merge-base with the default branch, its follow-up issues carry `Integration branch: claude/implement-plan-<slug>` so the AI pipeline's fix PRs target the project branch, and the tracker's default-branch marker is left alone. The audit files a follow-up issue for every new finding (there is no weekly cap). A consumer wrapper that predates `ref` rejects the dispatch (`Unexpected inputs provided`): record it, set `Status: BLOCKED`, and ask (the wrapper needs the next `@stable` sync) — never dispatch without it in project mode, because a default-branch audit never sees the project's code. Find the run id (`gh run list -R <owner>/<repo> --workflow=<file> -L 1 --json databaseId`), record it (`Waiting on: run <id>`), arm the wait on the run (next stage `security-pass <k>/5 — read result`), and end the turn. Invoking this command *is* the §23.C approval for these dispatches — do not re-ask. In the next stage session, **first read the run's conclusion** (`gh run view <id> -R <owner>/<repo> --json status,conclusion`; the `— resume.` block's `Checker observed:` line carries it too) — only a `success` run has audited anything; then read the result: the run log's `security-audit: tracker=#… findings=… followups_created=…` line, the new dated section on the `AI Security Audit Tracker` issue (label `ai:security-audit`, marker `<!-- ai:security-audit-tracker:v1 -->`), and the `ai:security` follow-up issues it opened (marker `<!-- ai:security-finding:<id> -->`), or the log-only skip when `SECURITY_AUDIT_SKIP_IF_UNCHANGED` found the default branch already audited (legacy mode only; a branch audit never skips).
   If step 8 returned INCOMPLETE without a fix PR, never continue to step 9 on your own.
   - **Conclusion is not `success`** (`failure`, `cancelled`, `timed_out`, `startup_failure`, …) → the audit did not run to completion, so an empty tracker section and zero follow-ups prove nothing: this is the *run failed* case below, never a clean pass.
   - **Conclusion `success` and no follow-up issues opened, or the run skipped as unchanged** → the pass is clean; go to step 10.
   - **Follow-up issues opened** → this session writes **no** security fix. The follow-ups enter the repo's standalone-issue pipeline on their own (that is how the orchestrator's security pass fixes findings too): by default the Claude issue implementer (`AI_ISSUE_IMPLEMENTER`), which builds each one as its own issue-mode project on the branch its `Integration branch:` line names — the project branch here — and skips its own security pass; in a repo set to `codex`, clarify → plan → implement → review, whose PRs target the project branch and take the normal GPT autofix path. Either way the follow-up is closed and labelled `ai:merged` once its fix is on the project branch. Record them in the log, arm the wait on the issue list (next stage `security-pass <k+1>/5`), and re-dispatch the audit in that stage. Each re-dispatch is one **security cycle**; cap **5 cycles** (the orchestrator's `MAX_SECURITY_PASS_CYCLES` default). On exhaustion, or if a follow-up is closed without a merged PR, stop with `Status: BLOCKED` and ask in Q/A format.
   - **Run failed** (any non-`success` conclusion: workflow error, missing secret, a crashed audit step) → record the run id, conclusion, and the failing step from `gh run view --log-failed <id> -R <owner>/<repo>` in the log, set `Status: BLOCKED`, and ask in Q/A format (re-dispatch after a fix lands, or skip the security pass); do not loop on an infrastructure failure and never continue to step 10 on your own.

10. **Runtime validation.** Dispatch the validate workflow — `internal-validate.yml` here, `ai-validate.yml` in consumers (if neither exists, record `Validation: not wired` and continue) — in standalone mode: `-f tracking_issue=0`, plus `-f pr_number=0` for `internal-validate.yml` only (the consumer wrapper has no `pr_number` input and rejects the dispatch when it is passed), plus `-f target_ref=claude/implement-plan-<slug>` in project mode so the run validates the project branch instead of the default branch. With no orchestrator tracking issue the workflow neither comments nor opens fix-up issues; its verdict is in the run. A consumer wrapper that predates `target_ref` rejects the dispatch: record it, set `Status: BLOCKED`, and ask (the wrapper needs the next `@stable` sync) — never validate the default branch in its place. Record the run, arm the wait on it (next stage `validation <k>/3 — read result`), end the turn. In the next stage session, first read the run's conclusion as in step 9; a non-`success` run with no `validation_status.json` and no `VALIDATION_FAILURE_SUMMARY` line failed before validating and is handled like the terminal classes below (record, `Status: BLOCKED`, ask). Otherwise read the verdict from these sources, in order, and stop at the first that answers: (1) `validation_status.json` in the `ai-validation-<run-id>-<attempt>` artifact (`gh run download <run-id> -R <owner>/<repo> -n ai-validation-<run-id>-<attempt>`; the file sits nested in the download, e.g. `tmp/codex-validate-<run-id>-<attempt>/validation_status.json` — `find` it; fields `status`, `raw_status`, `summary`, `fix_issues`); (2) the `STATUS_VALUE` / `RAW_STATUS_VALUE` env of the workflow's record step in the run log (`gh run view --log <run-id> -R <owner>/<repo>`); (3) the `VALIDATION_FAILURE_SUMMARY` line (`status=… raw_status=… summary=… failure_summary=…`), which the workflow emits **only on a failing verdict** — its absence on a `success` run is normal, not an error. If none of the three answers, treat it as an unknown payload (below).
    - **Validation target trust boundary:** In project mode, keep the draft final project PR open into the default branch, with a same-repository head and base and a trusted OWNER, MEMBER, or COLLABORATOR author association. `validate.yml` authorizes that PR and pins its head SHA before checkout; a missing or ambiguous binding fails the run before validation. All four validation workspace hooks run tokenless and without network or host `.git` access; do not depend on credentials or network in them.
    - **`status=pass`** → if a validation-fix PR (the `needs_fixes` branch below) merged after the last conformance run, the audited code changed: continue with step 8 in this session as stage `conformance <k+1>/3` (the shared cap applies). Otherwise go to step 11. A project with no conformance run recorded (it reached validation before this command gained step 8) always goes to step 11; step 12 then runs the full-scope check.
    - **`raw_status=needs_fixes`** → Claude fixes it: branch `claude/implement-plan-<slug>-validation-fix-<cycle>` from the base branch, implement the fixes the diagnosis describes (the `fix_issues` proposals), verify per step 5, push, open the PR against the base branch, wait for its review rounds and merge exactly as in step 7 (next stage `validation <k+1>/3`), then re-dispatch validation. Each re-dispatch is one **validation cycle**; cap **3 cycles** (`MAX_VALIDATE_CYCLES` default). On exhaustion stop with `Status: BLOCKED` and ask.
    - **`harness_error`, `infeasible`, `codex_failure`, or an unknown payload** → these are terminal in the orchestrator too; record the summary and ask in Q/A format rather than guessing at a fix.

11. **Completion PR — move the doc only now.** From the base branch, `git mv docs/plans/<slug>-plan.md docs/completed/<slug>-plan.md` (create `docs/completed/` if missing; use `git mv` so history is preserved), set the log to `Status: COMPLETE`, `Activation: pending verify-activation` (project mode: `Stage: final-merge`), with the merged PR list and conformance, security, and validation evidence, and land any `README.md` / `agents.md` update the phases did not already ship. Branch `claude/implement-plan-<slug>-complete`, push, open the PR against the base branch (§19 discipline applies). `lint-plan-archival.yml` fails an archival PR whose body references no `#N` at all, so the body must carry `Refs #N` lines: the plan's tracking issue when it has one — the gate then requires that issue's checkboxes to be ticked or a `## De-scoped phases` section; never de-scope silently — and otherwise every merged phase, conformance-fix, validation-fix, and verify-fix PR of this project (`Refs #<phase PR>` …), which trace the archival and carry no checkboxes. The lint only runs on PRs into `main` / `stable`, so in project mode it checks the final PR (step 11a), which carries the same `Refs` lines. Arm the wait as in step 7 (next stage `final-merge 1/1` in project mode, `verify-activation 1/3` in legacy mode).

11a. **Final merge into the default branch** (project mode, stage `final-merge 1/1`, once the completion PR merged into the project branch). Sync the project branch (step 2), update the final PR's body (`mcp__github__update_pull_request`) with the merged PR list, the conformance / security / validation evidence, and the step 11 `Refs #N` lines, then mark it ready for review (`mcp__github__update_pull_request` with `draft: false`). The `ready_for_review` event runs the reviewer panel over the whole project in Claude-fixer mode: arm the wait on the final PR as in step 7 (next stages `verify-activation 1/3` on merge, `final-merge — review round` on a hand-off, `final-merge — blocked PR` on a block) and handle its rounds and blocks with steps 7a and 7 — their fixes land on the project branch, which is the final PR's head. The workflow auto-merges it into the default branch once no valid finding is left. Record `Final PR: #F merged <date>` in the log (the log update rides the verify-activation fix PR, or stays in the report). In [Issue Mode](#issue-mode) the final PR merges into `<issue base>`; how the issue closes, and whether steps 12–13 run, depends on that base.

12. **Verify activation.** In the `verify-activation <k>/3` stage session, `Read` `.claude/commands/verify-activation.md` and follow its procedure with the completed plan (`docs/completed/<slug>-plan.md`, plus the merged PR list from the log) as its `$ARGUMENTS`, appending `— scope activation` when the log's `## Conformance` section records a CONFORMANT run, and always ending with `— unattended` (§28) (step 8 already graded implementation and correctness). This runs against the default branch, which now carries the whole project. A project with no conformance run recorded — one that passed its security and validation stages before this command gained step 8 — runs the full-scope check instead, exactly as before. If an activation-scope run stops because code the project needs is missing outright, re-run it at full scope in this session. Its fix branch is `claude/implement-plan-<slug>-activation-fix-<k>` from the default branch (the project branch has merged), so fix PRs run in Claude-fixer mode. Its report carries the `Auto-decisions (for review)` list — every `## Auto-decisions` entry in the log plus any this run made — and that list is shown, never asked (§28.E). Then act on its result:
    - **Fix PR opened** (its Step 7 found fixable defects) → arm the wait on that PR as in step 7 (next stage `verify-activation <k+1>/3`, review rounds via step 7a); the next stage re-runs verification on the merged fixes. Cap **3 verify cycles**; if the third cycle still opens a fix PR or ends INCOMPLETE, stop with `Status: BLOCKED` and ask.
    - **LIVE** → record `Activation: LIVE`, report, send one `PushNotification` (`<plan title>: complete and LIVE — <n> auto-decisions to review`, dropping the suffix when there are none), and stop. `/deploy-activate` is not needed. This final session stays open for the report; a `change AD-<n> → <letter>` or `confirm` reply there is handled per [Auto-Decisions](#auto-decisions).
    - **DORMANT** → go to step 13.
    - **INCOMPLETE with no fix PR** (full scope only; every remaining finding is one the run could not auto-decide) → stop with `Status: BLOCKED` and ask the Q/A questions `/verify-activation` produced.

13. **Start `/deploy-activate`.** `/deploy-activate` is interactive — it gives you one step at a time and waits for your pasted output — so it gets its own fresh session: `create_session` with `source_url` = the repo, `model` = the stage model, `permission_mode` = this session's mode, `title` = `implement-plan <slug> — deploy-activate`, and `prompt` = `/deploy-activate docs/completed/<slug>-plan.md`. Record `Activation: deploy-activate started (<session id>)`, send one `PushNotification` (`<plan title>: ready to activate — open "implement-plan <slug> — deploy-activate"`, adding `; <n> auto-decisions to review` when there are any; `/deploy-activate` lists them in its opening message), report, and archive this session with `archive_session` as the last action.

14. **Report.** Emit the [Output Format](#output-format) in chat at every hand-off point: after each PR is opened, after each stage that changed state, and at completion.

## Issue Mode

`/implement-issue-claude` turns one standalone issue into a single-phase plan `docs/plans/issue-<N>-<topic>-plan.md` whose header carries:

```
Source issue: <owner>/<repo>#<N> (<issue url>)
Base branch: <issue base>
Security pass: run | skip (<label>: automation-produced issue)
```

`<issue base>` is the branch the issue names in an `Integration branch:` or `Target branch:` line (the same parsing as `scripts/resolve_integration_ref.sh`, `Integration branch:` winning), otherwise the default branch. That session then runs this command from step 0 with the plan path. Everything above applies, with these differences:

- **Start-up checks are auto-decided** (CLAUDE.md §28.A): the plan is fixed by the issue, the plan is always one phase, and a non-`auto` permission mode is recorded, not asked. A project branch name that already exists is this project when its log names the same `Source issue:`; otherwise append `-2`, `-3`, ….
- **Always project mode, based on `<issue base>`.** Step 3a forks `claude/implement-plan-<slug>` from `origin/<issue base>` and commits the plan doc together with the log; the final PR's `base` is `<issue base>`; step 2 syncs from `origin/<issue base>`. The security audit (`ref`) and validation (`target_ref`) still run against the project branch.
- **Security pass.** `Security pass: skip` skips step 9 (recorded in the log). It is set for issues labelled `ai:security`, `ai:check-triage`, or `ai:workflow-heal`, whose own audit could open follow-ups of follow-ups.
- **Closing the issue.** Phase, fix, and completion PRs use `Refs #<N>`. When `<issue base>` is the default branch, the final PR's body carries `Fixes #<N>`, so the issue closes and `issue_pr_status.yml` labels it `ai:merged` when the whole project merges. For any other base, GitHub does not close issues on the merge, so the `final-merge` stage session closes it explicitly once the final PR merged: `mcp__github__issue_write` `update` with `state: closed`, `state_reason: completed`, and `ai:merged` added to its labels. That is the signal a parent project's security-pass checker waits for. §19 still applies: an `ai:orchestrator-tracking` issue never reaches this command.
- **Activation.** When `<issue base>` is the default branch, steps 12–13 run as usual. For any other base (another project's branch, `stable`, a pull request's head branch) the change goes live with that branch's own lifecycle, so the project ends after the final merge: record `Activation: n/a (base <issue base>)`, `Status: COMPLETE`, and report.
- **Stops are reported on the issue** (CLAUDE.md §28.C): every place this file stops at `Status: BLOCKED` and asks, the session instead posts **one** comment on the source issue starting `<!-- ai:claude-blocked:v1 -->` naming the blocker, the options, and the recommended one, adds the `ai:claude-blocked` label, sends one `PushNotification`, and ends. A human answers there and comments `/reclarify`; the next session removes the label and resumes from the log.
- **Progress comment.** At each stage hand-off, edit (`mcp__github__update_issue_comment`) the one issue comment starting `<!-- ai:claude-issue-progress:v1 -->` with the current `Stage:`, `Waiting on:`, and PR links; when the project completes it also lists the `## Auto-decisions` entries for review (§28.E). One comment per issue, never one per stage.

## Stage Sessions

Waking one long-lived session re-sends its whole conversation on every wake, and the gap between check-ins outlives the prompt cache, so each wake pays for the full history at full price. This command therefore never wakes the session that did the previous stage, with one exception: a blocked, closed, or stuck PR is handed back once to the stage session that armed that wait (see [Hand-back](#hand-back)), which runs the blocked-PR intervention itself. Review rounds are not handed back: they are routine and frequent, and each runs in a fresh session. Each **stage** — one phase, one review round, one conformance audit, one security or validation read, the completion PR, the final merge, one verify-activation cycle — runs in a **fresh session** started by the checker, whose only inputs are this command file, the progress log, and a short `— resume.` block. The expensive model only ever reads what the current stage needs.

- **Started by** the checker with `create_session`: `source_url` = the repo, no `source_revision` (the default branch; the stage reads the project branch per step 2; only a `— source revision <ref>` run passes `<ref>`), `model` = the stage model, `permission_mode` = the mode the checker was given, `title` = `implement-plan <slug> — <next stage>` (for example `implement-plan heal-autofix — phase 2/4`, `… — phase 2/4 — review round`, `… — conformance 1/3`, `… — security-pass 1/5`, `… — validation 2/3 — read result`, `… — final-merge 1/1`, `… — verify-activation 1/3`), and `prompt`:
  ```
  /implement-plan-claude <plan path> — resume.
  Stage: <next stage>   Checker observed: <verdict reason>
  Previous stage session: <id>   Checker session: <id>   Safety-net trigger: <trig_… id>   Hand-back trigger: <trig_… id | none>
  Waiting on was: <PR #N | run <id> | issues #a, #b>   Stage model: <model>   Project branch: <claude/implement-plan-<slug> | none (legacy)>
  <Uncommitted auto-decisions: <AD-n entries>, only when a stage recorded one with no PR in flight>
  <— source revision <ref>, only when the run carries one>
  ```
- **Names say where the project is.** Titles always carry the plan slug and the stage, so the session list reads as the project's timeline.
- **Archiving** (step 0): each stage session archives the previous stage session and the checker, never one that is waiting on the user. **Only the chain archives its own sessions.** A `… — waiting: …` checker holds the chain's only pending check-in (`send_later` into itself); archiving it from outside kills that check-in and the project stalls silently until the safety net fires. To stop a project on purpose, delete its safety-net trigger and archive its checker together; to nudge a stalled one, start the next stage session by hand with a `— resume.` block. The final LIVE report and the `/deploy-activate` session stay open. In steady state you see one open session per plan: the current stage (or its Sonnet checker while waiting).

## Check-in Loop

The wait between "PR opened" and "review round handed off / PR merged" (and between "workflow dispatched" and "run finished", and "follow-ups opened" and "follow-ups merged") is an **hourly check-in by a low-effort Sonnet checker session**, not a watch. It never uses `subscribe_pr_activity`, which §25 forbids and a hook blocks; it is the scheduled check-in §25.C allows and this plan's §26 check-in.

**Why a checker session and not a Routine.** A Routine created with `create_new_session_on_fire` starts a session with **no MCP tools and no repository** (connectors are not carried over), so it can neither read the repo nor start the next stage — a checker built that way can never report and the project stalls silently. A session started with `create_session` gets the repository, `gh`, and the claude-code-remote tools, inherits the creator's permission mode, and can re-arm itself with `send_later`.

**Arming the wait** (the stage session, at the end of its stage):
0. **Sweep, then the hand-back Routine.** Run the stale Routine sweep (CLAUDE.md §26.G). For a PR wait (a run or issue-list wait has no hand-back), `create_trigger` a Routine bound to **this** session: `persistent_session_id` = this session's id, `run_once_at` = now + 7 days, `name: implement-plan <slug>: hand-back`, `initiation: own_followup`, and `prompt`: `Hand-back for /implement-plan-claude <plan path>, PR #N (<PR URL>). Continue with the Hand-back section of .claude/commands/implement-plan-claude.md in this session.` The prompt never changes: the checker only moves `run_once_at`, renewing it 7 days ahead at every check-in (a dead-man's switch) and pulling it to one minute out on a block. A stage session woken by its hand-back deletes the fired Routine and creates a new one when it re-arms. The hand-back trigger id goes into the checker instructions (step 2).
1. **Checker** — `create_session` with `source_url` = the repo (plus `source_revision` for a `— source revision <ref>` run), `model: claude-sonnet-5`, `permission_mode` = this session's mode (Auto; see step 0), `title` = `implement-plan <slug> — waiting: <PR #N | run <id> | issues #a, #b>`, and the prompt `/effort low` **and nothing else**: `create_session` takes no effort parameter, and `/effort low` is only applied when it is the whole prompt (CLAUDE.md §26.B). The checker runs on Sonnet in Auto mode, never Haiku: outside Auto mode the claude-code-remote write tools (`send_later`, `create_session`, `archive_session`, `create_trigger`, `update_trigger`, `delete_trigger`) ask for approval on every call whatever `permissions.allow` says, and Haiku 4.5 cannot run in Auto mode, so a Haiku checker stops at a prompt on every re-arm.
2. **Checker instructions** — `create_trigger` with `persistent_session_id` = the checker's session id, `run_once_at` = two minutes from now, `name` = `implement-plan <slug>: checker instructions`, `initiation: own_followup`, and the standalone prompt built from the [Checker prompt](#checker-prompt) template. The one-shot trigger disables itself after it fires; the checker keeps low effort for the rest of its life.
3. **Safety net** — `send_later` into **this** session with `delay_minutes: 1440`, `initiation: own_followup`, `name: implement-plan <slug>: safety net`, and a message: `Safety net for /implement-plan-claude <plan path>: the next stage never started. get_session <checker id>; if it is blocked, archived, or idle with no pending check-in, run .claude/scripts/check_in_status.py yourself, then either start the next stage session per the Stage Sessions template or arm a fresh checker, and re-arm this safety net.` The next stage session deletes it (step 0), so it only fires when the chain has stalled — one wake of this session per stalled day, never in the normal path.
4. Record the ids (`Checker:`, `Safety net:`, `Hand-back:`) in the log and the report, then end the turn.

**What counts as "done waiting"** is decided by `.claude/scripts/check_in_status.py`, never by the checker model:
- *PR* — merged; closed without merging; labelled `ai:review-blocked`, `ai:review-autofix-failed`, or `ai:needs-human`; a **review round** (`state: review-round` / `state: conflict`): the configured workflow comment account posted a correctly formed hand-off for the current head, its linked review workflow run completed successfully, no other run is queued or active on the branch, and no matching dedicated-bot verdict answers the findings; or the PR is conflicted with no workflow run queued or in progress (even without a hand-off). A collaborator's marker, an incomplete/failed linked run, or an unset hand-off author cannot authorize a hand-off; the checker keeps waiting. **Stuck**: a check run on the head commit failed, **and** the head commit is older than 6 hours, **and** no workflow run on the head branch is queued or in progress. Red checks or open threads on a younger head, or while a run is active, are the review workflow's business — the checker stays quiet.
- *Workflow run* — `status` is `completed` (any conclusion); a non-`success` conclusion reports `state: failed`, which routes to the block stage (for steps 9–10, `security-pass <k>/5 — run failed` / `validation <k>/3 — run failed`).
- *Issue list* — every issue is closed or labelled `ai:merged`.

The script issues one REST call in terminal-only mode. Non-terminal PR checks paginate check runs in 100-item pages and use at most three further calls once an old failure is found; a Claude-fixer PR adds one call per 100 PR comments and at most one linked run read, plus up to three branch-run reads (queued, in progress, pending) before waking. It never uses GraphQL (§15), and prints one JSON line (`done`, `state`, `reason`); exit 2 means the read failed.

### Hand-back

A blocked, closed, or stuck PR wakes the stage session that armed that wait (the session that last worked on the PR) instead of a fresh `… — blocked PR` session, so the intervention and any action-needed report come from the session holding the context. The wake is a **scheduled** fire of that session's hand-back Routine: the checker pulls its `run_once_at` forward to one minute out (`update_trigger`, never touching the prompt: `update_trigger` tells models not to rewrite a prompt because another session asks, and checkers asked to do so refused, observed 2026-09-25). A scheduled fire runs in the session the Routine is bound to; `fire_trigger` is never used, because a manual fire ignores the binding and starts a fresh session with no repository and no context (verified 2026-09-25). A merged PR, a review round, a finished run, and a resolved issue list never use the hand-back: they start a fresh next stage session exactly as before, so the normal path costs no more than it did.

When its hand-back fires, the stage session first runs `check_in_status.py --repo <owner>/<repo> --pr N` itself (the Routine carries no verdict), then renames the checker (its id is in this session's report) to `implement-plan <slug> — handed back: PR #N <state>` and archives it (`archive_session`), and only then deletes the fired Routine (`delete_trigger`, ignore not-found). The order matters: the checker's 10-minute hand-back check reads a missing Routine as a failed hand-back, so the checker must be gone first; the wake itself proves the hand-back arrived. If the PR is merged, or a review round is waiting, the checker stopped before starting the next stage: start that stage session per [Stage Sessions](#stage-sessions) as the checker would. If it is not done, the checker stopped renewing the Routine for 7 days: re-arm the wait per [Check-in Loop](#check-in-loop). If it is blocked, closed, or stuck, the stage session:

1. Deletes its pending safety net (`delete_trigger`, ignore not-found).
2. Renames itself (`set_session_title`, own id from `session_${CLAUDE_CODE_REMOTE_SESSION_ID#cse_}`) to `implement-plan <slug> — <stage> — blocked PR`, re-reads the progress log and its PR branch, and sends one `PushNotification` (`<slug>: PR #N <state> — handed back to <new title>`).
3. Runs the **Blocked** intervention of step 7 in this session (the `[claude-intervention]` commit, removing `ai:review-blocked` before re-arming, 3 interventions per PR; on the fourth, stop with `Status: BLOCKED` and ask in Q/A format — that question is the action-needed report, or under CLAUDE.md §28 an auto-decision recorded for review), then re-arms the wait per [Check-in Loop](#check-in-loop) with a new hand-back Routine, a new checker, and a new safety net, and ends the turn.

A stage session that is later archived by the next stage (step 0) takes its hand-back Routine with it: the next stage deletes the `Hand-back trigger` its `— resume.` block names, and the stale Routine sweep (CLAUDE.md §26.G) catches any that were missed. When the hand-back fails (the Routine was deleted, or the session was archived, in which case the scheduled fire ends with `auto_disabled_session_gone`), the checker's hand-back check falls back to starting a fresh `<next stage on block>` stage session, as before.

### Fallbacks

- **No `create_session`** (a local CLI, desktop, or IDE session without the claude-code-remote MCP server): arm `send_later` into this session with `delay_minutes: 60` and a message that repeats the checker steps, and on each wake delegate the check to a Sonnet subagent (Agent tool, `model: "sonnet"`; the Agent tool takes no effort level) that runs `check_in_status.py` and returns its JSON; when done, continue in this session. If `send_later` is missing too, use `CronCreate` (every hour, deleted with `CronDelete` when done) and say once that it lives only as long as the session. If neither exists, say so, leave the log at the current stage, and tell the user that re-running `/implement-plan-claude <plan>` resumes from the log — never poll with `sleep`.
- **A checker that is blocked** on a permission prompt (a stage started in a non-Auto mode) shows as `blocked` in the session list; approving its prompt lets it continue, and the safety net catches it after 24 hours either way.

## Auto-Decisions

The chain has nobody to answer a question mid-project, so CLAUDE.md §28 replaces the §0/§2 stop with a recorded pick. This section is how this command applies it.

- **When.** From the end of step 3 onward, in the invoking session (phase 1 included) and in every `— resume.` stage session. Steps 0, 1, and 3 still ask: you are at the keyboard for them.
- **What.** Intent and design questions: an ambiguous or under-specified plan step, an edge case or interface choice the plan does not settle, and `/verify-activation` findings that need a decision (the chain always passes it `— unattended`). Write the question in the §2 format, take its RECOMMENDED option (the first one on a single-choice question with several), and keep working. The pick must obey §1, §5, §6, and §10 (§28.B); a question with no such option is not auto-decidable.
- **Never auto-decided** (§28.C): the start-up checks, every failure escalation this command already stops on (intervention, conformance, security, validation, and verify-activation caps; a security or validation run that did not succeed; a terminal validation class; a security follow-up closed unmerged), and every §22.B / §23.C / §24.D operation. Those still stop at `Status: BLOCKED` and ask.
- **Record.** One `AD-<n>` line per decision in the log's `## Auto-decisions` section (format in [Progress Log](#progress-log)); numbers run across the project and are never reused. The PR in flight carries the entry and lists it in its body under `## Auto-decisions`. A stage that opens no PR puts the entry in its report and in the `Uncommitted auto-decisions:` line of the `— resume.` block it hands on, and the next stage commits it. No notification per decision; each stage report carries a count.
- **Review at the end.** The step-12 report prints every entry under `Auto-decisions (for review)`; `/deploy-activate` prints them in its opening message next to Step 1. Neither asks. A `change AD-<n> → <letter>` reply in the final LIVE session or the `/deploy-activate` session is implemented as one PR on `claude/implement-plan-<slug>-decision-changes` (under §12, verified like any fix, with the entry set to `changed to <letter> (<date>, PR #N)`), and the §26 check-in is armed for it; `/deploy-activate` holds its runbook until that PR merges. Unchanged entries become `confirmed (<date>)` when `/deploy-activate` reaches LIVE, or, on the LIVE path, on a `confirm` reply (a docs-only PR on the same branch). Unanswered entries stay `pending review`, which blocks nothing.

## Progress Log

`docs/implement-plan/<slug>.md`, one file per plan, committed in the repo so that a fresh session — new machine, re-cloned container, or a later day — resumes at the exact stage instead of restarting. In project mode it lives on the project branch (first committed in step 3a) and reaches the default branch with the final PR; in legacy mode it lives on the default branch. It rides in each phase PR, each review-round and validation-fix PR, each verify-activation fix PR (conformance or activation), and the completion PR, so the copy on the base branch can lag the live session by one step; the `— resume.` block carries the current stage in the meantime, and step 2 re-verifies `Waiting on:` against GitHub before acting.

- **Read first (mandatory).** Never open a PR before reading this file. `Status: BLOCKED` → restate the recorded blocker and ask before continuing.
- **Update at every hand-off**: PR opened, review round handled, PR merged, intervention pushed, auto-decision recorded, conformance audit run, run dispatched, run read, cycle counter incremented, checker / safety net armed, session handed off. Refresh `Last updated` and `Last note` each time; use the date from the session context.
- **Persist by committing it** on the branch of the PR that is in flight (its own `docs:`-scoped commit). A log change with no PR in flight (e.g. "validation dispatched, run 123") waits for the next branch — the checker and stage-session prompts carry the same facts in the meantime.

### Lessons

The `## Lessons` section is how the project teaches the AI pipeline. When a stage hits a **surprise**, it adds one line there before it commits the log: a conformance finding (`conformance`), a security follow-up issue (`security`), a validation `needs_fixes` diagnosis (`validation`), a blocked-PR intervention or a review-round finding that revealed a reusable pattern (`intervention`), a place where the phase had to depart from the plan (`plan-deviation`), or an activation gap fixed in an activation-scope fix PR (`activation`). A clean stage adds nothing.

- **Format, one lesson per line** — `- [source:<source>] <lesson> (files: <path>, <path>)`. `<source>` is one of the six values above; the `(files: …)` suffix is optional and lists repo-relative paths the lesson is about. Lines that do not match are ignored by ingestion.
- **Write a reusable lesson, not a story.** One or two sentences a future planner can act on (`A workflow reading a new repo-var must default it in both the reusable workflow and the consumer wrapper`), not what happened in this PR. Never include secrets, tokens, or credential values.
- **Ingestion.** When a PR from a `claude/implement-plan-*` or `claude/verify-activation-*` branch merges (into the project branch or the default branch), `.github/workflows/issue_pr_status.yml` reads every `docs/implement-plan/*.md` at the merge commit and writes each lesson to the `ai-memory` branch as a `lessons_learned_record.v1` record (phase `implement_plan`, kind `project_retrospective`, tags `source:<source>`, `plan:<slug>`, and `file:<path>`). Record ids derive from the slug, source, and text, so re-ingesting a log changes nothing. Ingestion is fail-open and honours `AI_MEMORY_ENABLED` / `LESSONS_LEARNED_ENABLED`.
- **Only what a PR carries reaches memory.** Lessons ride the PR in flight. The activation stage's lessons reach memory only when that stage opens a fix PR; otherwise they stay in its report.

## Rules

- **One phase per PR, in the plan's order, and never the next phase before the current one merged.** The plan's Phases & Merge Strategy is the unit of delivery, exactly as the orchestrator ships one PR per phase issue. Do not fold two phases into one PR to save a cycle, and do not start phase `n+1` on top of an unmerged phase `n` branch.
- **Project branch first, default branch last (project mode).** Phase, review-round, conformance-fix, validation-fix, and completion PRs target `claude/implement-plan-<slug>`; security and validation run against it; only the final PR — reviewed once more as a whole — merges into the default branch, after every stage passed. The project branch is synced with the default branch at the start of every stage (step 2) and is never force-pushed.
- **One stage per session.** Never wait inside the session that did the work: arm the checker and end the turn. Never wake a finished stage session to continue — the checker starts a fresh one; the only wake is the [Hand-back](#hand-back) of a blocked, closed, or stuck PR to the session that armed that wait.
- **Wait, don't babysit.** Between PR-opened and the next hand-off or merge the only activity is the low-effort Sonnet checker, hourly. No `subscribe_pr_activity` (§25 — a hook blocks it), no polling loop, no `sleep`, no CI fixing, no review replies while the review workflow is working on the PR. `review_autofix.yml` owns the reviewer panel, the round loop, the iteration cap, and auto-merge for these PRs; it hands each round to a fresh stage session (step 7a).
- **Claude is the fixer, the reviewer panel is the reviewer.** On `claude/implement-plan-*` PRs the GPT editor, the GPT conflict resolver, and the GPT review-blocked judge never run. Every review round is judged finding by finding against the code (§12 PR Review Mode, with §5 / §6 / §10 still binding), fixed in one `[claude-autofix]` commit, or answered by the dedicated bot with a ledger-bound verdict plus the convergence dispatch; conflicts are resolved by a `[claude-merge-resolve]` merge; the round loop stops only when a fresh reviewer run finds nothing and the checks are ready on that head. Never dispatch the convergence input for a head whose findings were not all answered.
- **Intervene only on a blocked PR, and only under §12.** "Blocked" is the definition in the [Check-in Loop](#check-in-loop): the workflow gave up (`ai:review-blocked` — in Claude-fixer mode that is the `MAX_AUTOFIX_ITERATIONS` cap — `ai:review-autofix-failed`, `ai:needs-human`), the PR was closed unmerged, or it has sat red for 6+ hours with no workflow run active. Then fix it as PR Review Mode work, commit as `[claude-intervention]`, push, remove `ai:review-blocked`, and go back to waiting. At most 3 interventions per PR before asking.
- **Conformance before security, re-audited after Claude-written validation fixes.** The conformance audit (step 8) is the project's judge: it runs once all phases merged and before the security pass, so its fix PRs go through security and validation. When validation needed a Claude-written fix, it runs again before completion; a fix from that re-run sends the project back through security and validation. At most 3 conformance runs per project.
- **Security before validation, both from the repo's own workflows, both bounded.** Security findings are fixed by the `ai:security` follow-up issues flowing through the AI pipeline — never by a Claude-authored security patch — and the audit re-runs after they merge (cap 5 cycles). In project mode the audit is dispatched with `ref` = the project branch, and a pass is clean only when it opened no follow-up. Validation failures with `needs_fixes` are fixed by Claude in a validation-fix PR and validation re-runs (cap 3 cycles). Terminal validation classes (`harness_error`, `infeasible`, `codex_failure`) and any workflow that fails before doing its job are asked about, not looped on.
- **Never move the doc before the gates pass.** `docs/completed/` is the "project done" signal. It moves in the completion PR only after every phase merged, the conformance audit is CONFORMANT, the security pass is clean, and validation passed — with `git mv` so the plan's history follows it. A partial project leaves the doc in `docs/plans/` and the log at `IN_PROGRESS` / `BLOCKED`.
- **Activation follows completion.** The activation-scope `/verify-activation` runs only after the completion PR merged — in project mode, after the final PR merged into the default branch (full scope for a project with no recorded conformance run); `/deploy-activate` starts only on a DORMANT verdict, in its own session, and waits for you there — this command never runs a deploy step itself.
- **Never archive a session that waits on the user.** A session asking a Q/A question, blocked on a permission prompt, or holding the final report stays open.
- **Verification is evidence-based.** Run the tests and linters; read the code; confirm the wiring. Do not assume a step is done because you wrote it — confirm it against the repo, with `file:line` / test citations in the PR body and the report.
- **Record surprises as lessons.** Every stage that hits a conformance finding, security follow-up, validation fix, blocked-PR intervention, reusable review-round finding, or plan deviation adds one line to the log's `## Lessons` section (see [Lessons](#lessons)); the merged log feeds AI memory.
- **The log is the resume point.** Read it before acting, update it at every hand-off, commit it with the PR in flight. A session that cannot start stage sessions or schedule check-ins leaves an accurate log so the next invocation continues instead of restarting.
- **Honor the project rules while implementing:** §5 (minimal change set), §6 (naming immutability — add aliases, never rename in place), §7 (update `README.md` / `agents.md` on behavior change), §9 (style), §10 (MongoDB contracts + index registry), §14 (consumer-repo registry if templates/`.claude` assets change), §15 (GitHub API hygiene — terminal checks use one REST call; non-terminal checks paginate check runs and PR comments and add at most three old-failure reads), §18 (automation bias + future-removal registry), §19 (PR-body auto-close discipline), §20 (changelog fragments, never `CHANGELOG.md` directly), §21 (never commit onto a merged PR's branch — every phase gets a fresh branch from the base branch), §25 (no PR watching), §26 (this command's checker is the PR's check-in).
- **Branch + push + PR; never push to the default branch.** Each PR is the deliverable for its phase; this command never merges anything itself.
- **If a plan step belongs in the upstream workflow library rather than this repo**, do not edit the upstream from this session — implement the parts that belong here and surface the upstream-bound step in the report instead of guessing.
- **If the plan is ambiguous or under-specified** such that implementing a phase correctly would require guessing intent, auto-decide it per [Auto-Decisions](#auto-decisions) (CLAUDE.md §28): write the Q/A question, take the RECOMMENDED option, record it as an `AD-<n>` entry, and continue. The chain stops at `BLOCKED` only for what §28.C excludes: the start-up checks (a plan with no Phases section, step 3, still asks), failure escalations, ask-first operations, and a question with no option that honours §1 / §5 / §6 / §10.
- **Auto-decisions are shown, not asked, at the end.** Never re-ask a recorded decision; the verify-activation report and `/deploy-activate` list them, and only a human `change` reply reopens one.
- **In-session only — for orchestrator hand-off use `/implement-plan-ai`.** This command implements the plan itself, phase by phase, with Claude as the implementer and the review fixer, and the review-autofix workflow as the reviewer and merger. `/implement-plan-ai` dispatches the unattended orchestrator, which decomposes the plan into issues and runs the same security → validation → completion lifecycle from the poller instead.
