## Lessons
- [source:conformance] When a new check gates a push, name it in every step that pushes the same merge: a step that says "push" and only cross-references the section holding the check is a sibling path a literal reader skips. (files: .claude/commands/implement-plan-claude.md)
- [source:intervention] Decode subprocess output of a UTF-8 file (`git show <rev>:settings.json`) with an explicit `encoding="utf-8"`, never `text=True` alone: `text=True` uses the locale encoding, so under `LC_ALL=C` with UTF-8 mode off a valid UTF-8 file fails to decode. (files: .claude/scripts/loaded_settings_check.py)
- [source:plan-deviation] Check the harness's documented reload behaviour before designing around "read only at session start": Claude Code's file watcher hot-reloads `settings.json` (hooks and permissions) and runs `ConfigChange` per detected change, so a load check must follow `ConfigChange`, not just SessionStart. (files: .claude/hooks/settings_load_recorder.py, .claude/commands/implement-plan-claude.md)
- [source:conformance] A hook that must observe a settings change cannot rely on `ConfigChange` alone: Claude Code runs it with the hooks loaded before the change, so a checkout whose settings lack the hook never records the next change. Design load checks for the transition from un-wired settings. (files: .claude/hooks/settings_load_recorder.py, .claude/scripts/loaded_settings_check.py)
- [source:intervention] A fail-closed check that reports a cause-specific reason must pick that reason on every early-return path, above all "no record": the case the reason was written for usually never wrote a record, so a test that seeds a record exercises the wrong branch. (files: .claude/scripts/loaded_settings_check.py, tests/test_settings_load_recorder.py)
- [source:intervention] A check that reads "the branch before the merge" from `HEAD^1` needs every merge feeding it to use `--no-ff`: a plain `git merge` fast-forwards when it can, and `HEAD^1` is then the parent of the last upstream commit, which misses a change in an earlier one. Prove it by running the documented command on a fast-forwardable branch in a scratch repository. (files: .claude/commands/implement-plan-claude.md, tests/test_claude_asset_sync_command.py)
- [source:intervention] A review re-run dispatched with `workflow_dispatch` from the default branch attaches its check runs to that branch's commit, not to the PR head, so a check that failed on the head (an outage, a cap) stays red there; only a new head or a re-run of that job clears it. (files: .github/workflows/review_autofix.yml)
- [source:intervention] A check that gates work after a merge must run before a conflicted merge is resolved, not after its commit: during an unfinished merge `HEAD` is still the pre-merge tip and the cleanly merged files are on disk, so `--before HEAD` checks the same state that `HEAD^1` checks after the commit. (files: .claude/commands/implement-plan-claude.md, .claude/commands/fix-claude-pr.md)
