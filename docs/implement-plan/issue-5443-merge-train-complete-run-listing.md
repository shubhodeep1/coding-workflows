## Lessons
- [source:plan-deviation] Fake `gh` fixtures for paged `actions/runs` listings need a distinct `id` per run: a listing deduplicated by id collapses id-less runs and reads as incomplete. (files: tests/test_review_merge_train.py)
- [source:conformance] Offset pages over a status-filtered GitHub run listing can skip a run that stays active, even when total_count never changes (one run leaves above it while another enters below the page boundary), so page with a keyset instead: bound each follow-up query by `created=<=<oldest created_at read>` and count a status complete only when one response holds its whole total_count. A time-windowed listing with no status filter only grows at the top and does not need this. (files: scripts/review_merge_train.sh, tests/test_review_merge_train.py)
- [source:intervention] Before accepting a paging-completeness fix, test the membership swap that keeps total_count unchanged (one run leaves, one enters mid-list): count checks alone never detect it. (files: tests/test_review_merge_train.py)
- [source:intervention] Validate every field a listing deduplicates or classifies on (`id`, `path`, timestamps) before trusting it: a missing field silently drops a run instead of failing, and an inclusive time bound must round fractional seconds up, never down. (files: scripts/review_merge_train.sh, tests/test_review_merge_train.py)
- [source:intervention] When a listing query already filters on a field, do not filter the results on that field again: a missing or unexpected value in the response then drops a run the query proved relevant. Validate it instead, and require counts used for completeness to be whole numbers before any rounding. (files: scripts/review_merge_train.sh, tests/test_review_merge_train.py)
- [source:intervention] A guard that must see every active workflow run reads all five non-terminal statuses (`requested`, `pending`, `queued`, `waiting`, `in_progress`): a freshly dispatched run can still be `requested`, and a run held by a deployment environment is `waiting`, so a three-status listing fails open on both. (files: scripts/review_merge_train.sh, tests/test_review_merge_train.py)
- [source:intervention] Sequential status-filtered queries miss a run that leaves a status after it was read and enters one read before it; `waiting` is re-entrant (it can follow `in_progress`), so no lifecycle order is safe. Read every status again after the first read of every other status, and test each status change at every point between two queries. (files: scripts/review_merge_train.sh, tests/test_review_merge_train.py)
- [source:intervention] Never default a response's list field with `// []` before validating it: the default turns a missing or null list into a valid empty one, so the shape check can no longer fail. Pass a non-array value through and let the validator reject it. (files: scripts/review_merge_train.sh, tests/test_review_merge_train.py)
- [source:intervention] A `workflow_dispatch` run's head_branch is the ref the workflow ran from, never the PR it acts on: attribute a dispatch run only by an identifier the dispatcher put in its name (`run-name`), and treat a dispatch without one as unattributed. (files: scripts/review_merge_train.sh, tests/test_review_merge_train.py)
- [source:intervention] Status-filtered queries read in lifecycle order see a run however often it moves forward, so repeat the whole order (every status, the last included) per pass: a pass that stops short of the last status misses a run that moves backward and then forward again. And a run the listing keeps but cannot attribute to any PR makes the listing incomplete, never silently absent. (files: scripts/review_merge_train.sh, tests/test_review_merge_train.py)
