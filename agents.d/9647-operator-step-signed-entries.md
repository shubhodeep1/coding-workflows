- **Operator-step entries signed by the job token (Refs #9647, PR #9643).** Since 2026-11-17 most `<!-- ai:operator-step:entry key=… -->` comments are posted by `github-actions[bot]` with a trailing `<!-- ai-comment-sig:v1 … -->` line. On 2026-11-23 the poller step "Resolve released operator steps" (run 45218670304) had `GH_TOKEN` but not `AI_COMMENT_SIGNING_SECRET`, so the gh shim never loaded, `_authoritative_entry_comments` saw only the PAT-written `pr-9643` entry (done), and the tracker #9647 was closed (comment 7107951108) with 7 signed entries still unticked.
  - **Verification in every read path.** `load_entry_comments` in `scripts/operator_step_issue.py` (used by `tick`, `resolve`, `upsert` and the needs-human claim reads) now passes each signed bot comment through `comment_signature.normalize_comment`, loaded in-process from `scripts/comment_signature.py`, whenever `AI_COMMENT_SIGNING_SECRET` is set. A verified comment reads as the signed PAT login wrote it, exactly as the shim returns it, so the result is the same whether or not the step loaded the shim. No API call is added.
  - **Fail closed.** A signed `github-actions[bot]` entry comment that stays unverified (secret absent, module not loadable, HMAC broken by an in-place edit) and is newer than every trusted entry comment for its key makes the key `unverified`: `resolve` and `tick` never tick it (`outcome=unverified`), and `resolve` never closes the tracker while one exists, on the first read, the pre-close re-read, or (as a reopen, `reason=reopened_after_close`) the read after the close. The close reason is `unverified_signed_entries`, checked before `no_entries`; `op=verify issue= outcome=unverified count= keys= secret=present|absent` lists the keys. A newer trusted entry for the same key (the ticked copy `/deploy-activate` posts) supersedes the unverified one and clears the hold. The `resolve` output adds `unverified` (key count).
  - **Wiring.** The "Resolve released operator steps" step now gets `AI_COMMENT_SIGNING_SECRET` and `AI_COMMENT_JOB_TOKEN` like the other comment-writing poll steps, so its tick and auto-closed comments are also signed job-token posts. The promote cycle's `tick` step (`promote-main-to-stable.yml`) still has no secret: it skips signed entries as `unverified`, and `resolve` ticks the release ones.
  - **`/deploy-activate` ticks.** The command (both `.claude/commands/deploy-activate.md` and the consumer template) looks for entries on closed trackers as well as the open one, counts a signed `github-actions[bot]` comment whose `as=` login is the pipeline account as that account's, and never edits a signed comment or one on a closed tracker: it posts a new comment on the open tracker with the same body minus the signature line and the verified ticks applied, only when the session's login is the pipeline account. Plain PAT entry comments on the open tracker are still edited in place.
