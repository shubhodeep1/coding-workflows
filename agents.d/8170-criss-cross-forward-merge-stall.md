<!-- agents: section="Workflow architecture" -->
Criss-cross merge history no longer leaves a PR conflicted on GitHub forever (#8170). When a PR head and `origin/<base>` have more than one merge base, git's merge folds them into a virtual base and can merge cleanly while GitHub, which merges from a single base, reports `mergeable_state=dirty`. Before, "Detect merge conflicts" (`scripts/review_autofix_step_detect_merge_conflicts.sh`) said "No merge conflicts detected" and pushed nothing, the review-blocked judge's merge never ran (`mergeable` stayed `null`/`false`), and the poller's conflict sweep re-dispatched no-op runs until its attempt cap. Now, when the local merge is clean and still pending (`MERGE_HEAD` exists) and `git merge-base --all` returns more than one commit, the step probes each base with `git merge-tree --write-tree --merge-base=<base>`. If any probe conflicts it sets `MERGE_CONFLICT=true` and the new env `MERGE_CRISS_CROSS_CLEAN=true` (initialised `false`), and `scripts/review_conflict_prepare.sh` commits git's clean merge as `[ai-merge-resolve] resolve merge conflicts` through `_conflict_prepare_commit_deterministic_merge` (no model run; `CONFLICT_RESOLVED=true`, pushed by the existing push step), so `origin/<base>` becomes an ancestor of the head. On `orchestrator/project-*` branches the commit is deferred to the integration fingerprint check like the other deterministic resolutions. A probe error (git without `--merge-base`, a blobless fetch failure) fails open to the old "no conflicts" outcome.

The review-blocked judge (`scripts/review_rb_judge.sh`) merges `auto/forward-merge-stable-*` PRs with `--merge` instead of `--squash` at all three merge sites (`merge`, final-round `fix`, `merge_with_followup`), through `RB_MERGE_METHOD_FLAG` (default `--squash`). A squash strips stable's ancestry from main, which `promote-main-to-stable.yml`'s pre-flight refuses; `scripts/review_enable_auto_merge.sh` already routes these PRs to a merge commit.

`forward-merge-stable-to-main.yml` reuses an open fallback PR instead of opening a duplicate. A release pushes to `stable` (starting the workflow) and `test-and-mark-stable.yml`'s `sync-to-main` job dispatches it again for the same commit; the concurrency group serializes the runs, but each opened its own `auto/forward-merge-stable-<run_id>-<attempt>` PR (#8169 and #8170), and the two separate conflict resolutions produced the criss-cross history above. The fallback step now lists open PRs into `main` once (paginated REST, fallback path only), keeps only same-repository `auto/forward-merge-stable-*` heads (a fork PR with a matching ref name is ignored), fetches each one and, when one already contains `origin/stable`, writes `reused_pr_number=<n>` and exits without pushing a branch or opening a PR. A listing or fetch failure fails open to opening a new PR.
