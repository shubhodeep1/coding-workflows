- **Automatic re-plan of a placeholder-token plan hold (#8339).** `run_plan_auto_approval_gate` in `scripts/files_touched_scope_guard.py` adds `replannable: true` (otherwise the key is absent) only to a `hold` / `path_not_granted` record whose denied paths are all non-exact (end in `/` or contain `*?[`), whose issue is off the heal route (`ai:workflow-heal` label or heal fingerprint marker), and whose remaining protected paths approve with reason `granted` against the grant that produced the hold (the proposed Q108 grant, when that branch held). The `files_touched` plan check is applied as the real gate would. The check is in memory and never changes the decision or writes a grant body; every other reason is ineligible. In stall recovery, `_plan_auto_approval_gate` (phase `ai:awaiting-approval` only) looks for `<!-- ai:automation-path-replan:v1 issue=<N> -->` in a trusted comment (pipeline login, `[bot]`, OWNER/MEMBER/COLLABORATOR). Without it, it runs one `gh issue edit --add-label ai:planning --remove-label ai:awaiting-approval` (plan.yml skips `/answer` otherwise) and posts one `/answer` comment ending with the marker. Logs: `AI_PHASE_GATE_V1 phase=stall_recovery gate=auto_approve reason=path_not_granted outcome=replan|replan_label_failed|replan_comment_failed issue=<N>`. The re-plan waits for the `ai:planning` concurrency cap first (`phase_cap_can_dispatch`; when capped it logs `STALL_SKIP ... reason=phase_capped ... action=automation_path_replan` and returns without a notice, so a later tick retries). A failed edit falls through to the hold notice; a failed comment returns without one and moves the label back to `ai:awaiting-approval`, so the next tick retries the re-plan with its marker (if that rollback fails, the `retrigger_plan` arm recovers `ai:planning`). With the marker present the hold notice runs as before. Tests: `tests/test_files_touched_scope_guard.py`, `tests/test_orchestrate_poll_process.py`.
