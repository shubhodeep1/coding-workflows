**Red-main heal dedupe and the check-triage target guard (2026-11-18, Refs #9650, #9733; Phase 2 of `docs/plans/pipeline-human-wait-elimination-plan.md`).** Both are on by default and add no job.
- **Red-main heal dedupe** (`WORKFLOW_HEAL_RED_MAIN_GROUPING_ENABLED`, default `true`, also defaulted inside `scripts/workflow_failure_heal_intake.sh`). A `workflow_run` report from a `push` on the default branch gets a key from `workflow_failure_heal.py red-main-group-key`: SHA-256 of `red-main|<workflow name, lowercased, [cycle:<id>] stripped>|<first failing job, lowercased>|<branch>`. `_heal_red_main_group_key` reads only local files (the verified run JSON, the run summaries, the intake event's default branch), so it makes no API call. `budget --red-main-group <key>` then returns `{"action": "duplicate", "match": "red_main", "red_main_group": <key>, ...}` for an open heal issue whose header has the exact line `<!-- workflow-failure-heal:red-main-group=<key> -->`. The report becomes a plain occurrence on that issue.
  - **Precedence:** fingerprint > source > red-main group > lineage cap > cause > budget caps. Inside `budget_decision` a re-issue match also ranks above red-main, but the intake's re-issue lookup runs only when the first decision is not a duplicate, so in practice red-main ranks above it.
  - **Header line:** `compose-issue --red-main-group` writes the line after the optional `cause=` line. `validate_heal_issue_body_routing` accepts at most one exact line there, and `_MARKER_RE` does not read it (the key is hyphenated), so `parse_red_main_group_marker` reads it from the header only.
  - **Scope recovery** never replaces a `red_main` match, and drops `--red-main-group` from its budget re-run.
  - **Log line:** `WORKFLOW_HEAL red_main_group key=<key|none> outcome=duplicate|new|skipped reason=<open_group_heal existing_issue=<n>|no_open_group_heal|disabled|ineligible_kind|reconstructed|no_run_info|not_default_branch_push|no_job|helper_failed>`.
  - **Rollback:** `false` (repo variable) restores fingerprint-only dedupe and byte-identical heal bodies.
- **Check-triage target guard** (`CHECK_TRIAGE_TARGET_FILES_GUARD_ENABLED`, default `true`; `CHECK_TRIAGE_TARGET_FILES_GUARD_CHECKOUT_DIR`, default `GITHUB_WORKSPACE`, the PR-head checkout). `triage_target_files_guard` in `scripts/check_failure_triage.sh` runs in the collect stage after the check-run context collector and before `triage_metadata.json`. It acts only when `CHECK_TRIAGE_PR_BRANCH_ROUTING_ENABLED` emitted a `Target branch` route, and never in historical mode.
  - **Inputs:** the failing `tests/` files come from `heal-scope failing-tests` over the collected context. They are untrusted log text: strict charset, no `..`, at most 8. The head is checked with local `git cat-file` at the validated failing SHA. The default branch is checked with one aliased GraphQL `object(expression:)` read, with paths passed only as variables.
  - **Fallback:** when no file is on the head and at least one is on the default branch, the route is cleared (`CHECK_TRIAGE routing outcome=fallback reason=target_branch_lacks_files target_branch=<default> from_branch=<head>`), so the issue is planned on the default branch. Every other case logs `routing outcome=keep reason=<target_files_guard_disabled|no_failing_files|head_commit_unavailable|target_branch_has_files|default_lookup_failed|files_missing_on_default>` and keeps the route (fail open).
  - **Not affected:** the base-branch gate has already run by then and is not re-evaluated after a fallback. The separate PR-head (`CHECK_TRIAGE_PR_HEAD_ROUTING_ENABLED`) and integration-branch routes are unchanged.
- **Tests:** `tests/test_workflow_failure_heal.py` (`red_main` cases) and `tests/test_check_failure_triage_target_files_guard.py`, which `ci.yml` runs in the `Check-failure triage workflow security tests` step.
