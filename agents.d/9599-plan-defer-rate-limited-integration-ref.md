Plan defers a rate-limited CI-triage resolve (#9599, heal of #9582, run 43885930759): when `scripts/resolve_integration_ref.sh` exits 75 while CI-triage routing is on, `plan.yml`'s "Resolve integration ref" step still refuses the default branch but no longer fails the job (which filed `plan_failed` heal reports for a limit that clears by itself). It replays the resolver's `::error::INTEGRATION_REF_RESOLVE outcome=rate_limited` line as a `::warning::`, writes the step outputs `rate_limited_defer=true`, an empty `ref=` and `resolver_status=failed`, sets `SKIP_PLAN=true`, appends one line to `GITHUB_STEP_SUMMARY`, logs `::warning::INTEGRATION_REF_RESOLVE outcome=deferred reason=rate_limited rc=75 ci_triage_routing=on issue=<n>` and exits 0. It makes no `gh` call and changes no label. Every setup step gated on `steps.refctx.outputs.label_missing_hold != 'true'` is also gated on `steps.refctx.outputs.rate_limited_defer != 'true'`, so Checkout never resolves the empty ref to the default branch. The issue keeps `ai:planning`, and standalone stall recovery (`ai:planning` -> `retrigger_plan`) re-posts `/answer`; installs without it (the `core` profile, or `ENABLE_STANDALONE_STALL_RECOVERY=false`) need `/answer` re-posted by hand.
