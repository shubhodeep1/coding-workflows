Plan defers a rate-limited CI-triage resolve (#9599, heal of #9582, run 43885930759): when `scripts/resolve_integration_ref.sh` exits 75 while CI-triage routing is on, `plan.yml`'s "Resolve integration ref" step still refuses the default branch but no longer fails the job (which filed `plan_failed` heal reports for a limit that clears by itself). It replays the resolver's `::error::INTEGRATION_REF_RESOLVE outcome=rate_limited` line as a `::warning::`, writes the step outputs `rate_limited_defer=true`, an empty `ref=` and `resolver_status=failed`, sets `SKIP_PLAN=true`, appends one line to `GITHUB_STEP_SUMMARY`, logs `::warning::INTEGRATION_REF_RESOLVE outcome=deferred reason=rate_limited rc=75 ci_triage_routing=on issue=<n>` and exits 0. It makes no `gh` call and changes no label. Every setup step gated on `steps.refctx.outputs.label_missing_hold != 'true'` is also gated on `steps.refctx.outputs.rate_limited_defer != 'true'`, so Checkout never resolves the empty ref to the default branch. The issue's labels are left as they were, because the skipped "Validate planning phase label" step is what moves `ai:clarification` / `ai:blocked` to `ai:planning`. Standalone stall recovery still re-posts `/answer` for an issue in `ai:planning` (`retrigger_plan`) or `ai:clarification` (`auto_respond_clarify`); `ai:blocked` is a dedicated-handler phase with no stall-recovery action. An `ai:blocked` issue, or any install without stall recovery (the `core` profile, or `ENABLE_STANDALONE_STALL_RECOVERY=false`), needs `/answer` re-posted by hand after the limit resets. Exit 2, exit 3 and the routing-off fallback are unchanged; clarify and clarify-respond still fail closed on exit 75. Tests: `test_plan_rate_limited_refusal_defers_without_failing` and `test_plan_setup_steps_skip_on_rate_limited_defer` in `tests/test_workflow_checkout_integration_ref_audit.py`.
