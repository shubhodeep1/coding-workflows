### Release-gate self-cancel retry and final-CI hold (issue #10266)

- Cancel cause: when the smoke gate ends `cancelled`, `scripts/promote_main_cycle.sh` calls `gate_cancel_cause <gate_run_id>` (1 jobs read of the gate, at most 6 job-log reads of jobs whose cancelled step is a watch step, the same names the heal intake uses; a candidate left unread after 6 gives `unknown`). A line-start `RELEASE_GATE_RUNNER_WAIT outcome=cancel_requested gate_run=<that gate>` gives `runner_wait`, readable data without it `other`, a failed read `unknown`. The skip line is `PROMOTE_CYCLE_SKIPPED reason=smoke_gate_cancelled run=<id> cause=<cause>` and the `cycle` step output is `gate_cancel_cause=<cause>`.
- Marker: the `cycle` job's step "Record runner-wait gate cancel for the poller retry" (a name contract with `PROMOTE_CYCLE_GATE_CANCEL_MARKER_STEP`) runs only on `outcome=skipped:smoke_gate_cancelled` with `gate_cancel_cause=runner_wait`.
- Poller retry: `promote_cycle_retry_check` (`PROMOTE_CYCLE_RETRY_CHECK_ONLY=true`) treats that marker like the `runner_wait_long` one (same 60-minute to 24-hour window, same runner-wait check, one dispatch, lines end `reason=gate_runner_wait_cancel`), and caps it: once `PROMOTE_CYCLE_GATE_CANCEL_RETRY_MAX` (default 3) `[cycle-retry]` runs were created in the last 24 hours on any main tip (a retry runs on the tip of its dispatch, so a per-head count restarts whenever `main` moves; `runner_wait_long` retries count too), read from the runs listing it already makes (`per_page=100`), it logs `PROMOTE_CYCLE_RETRY outcome=cap_reached reason=gate_runner_wait_cancel ...`. A cancel by a person or another run has no marker (`outcome=not_runner_wait`). `runner_wait_long` retries themselves stay uncapped and their lines unchanged.
- Final-CI hold: `_pr_ensure_final_ci` takes an optional `PR_FINAL_CI_RELEASE_GATE_RUNS_JSON` (active runs the caller already holds). Only `_mt_merge_lease_ready_final_ci` sets it, from `_MT_LEASE_RUNS_JSON` when `_MT_LEASE_RUNS_STATE=ok`. A cache nothing filled earlier in the tick (state empty, the free-lease case) is filled there through the tick's one active-run listing pass (`_mt_inflight_review_branches` + `_mt_lease_runs_seed`, as `_mt_lease_pr_runs_active` does), only on this path right before a dispatch and never while the bound is `0`; a failed listing logs `RELEASE_GATE_FINAL_CI_HOLD outcome=runs_unread` and dispatches as before. Right before the full-suite dispatch (docs-only and sync-quick forms are never held) a queued or running `test-and-mark-stable.yml` run younger than `RELEASE_GATE_FINAL_CI_HOLD_MAX_MINUTES` (default 300, `0` off) gives `PR_FINAL_CI_OUTCOME=deferred` / `PR_FINAL_CI_REASON=release_gate_active`; the lease function returns 1 and sets `MT_LEASE_FINAL_CI_GATE_HELD=1`, so both step-3 callers try no later waiter of that base in the tick. The only reads added are that listing pass on a tick that had not made it. The review sweep and the review-end dispatch are not held, so the sweep can still start a deferred head's full final CI.
