- **Clarify-respond runs its helpers from the verified support bundle (#8715, stuck-states plan P2a-3, Refs #8291).** The "Stage workflow support files" step of `orchestrate_clarify_respond.yml` runs `scripts/stage_support_for_phase.sh clarify_respond`. That helper stages every clarify-respond script, plus `clarify_sandbox/Dockerfile`, from the verified `.codex-workflow-src` commit into `SUPPORT_SCRIPTS_DIR` under `RUNNER_TEMP`, and writes no executables into the issue checkout. Before it stages anything, the step runs the read-only `--list` as a capability probe. If the support ref's helper cannot stage `clarify_respond`, or has no helper at all, the step falls back to the legacy copy loop with a warning. Every later call uses `"${SUPPORT_SCRIPTS_DIR:-scripts}/<helper>"`. `orchestrate_parse_and_post_answer.sh` changes into its own parent directory, which inside the bundle is not a git checkout. So the "Parse and post answer" step runs it with `env ${SUPPORT_SCRIPTS_DIR:+"GIT_DIR=${GITHUB_WORKSPACE}/.git"}`, as clarify.yml's auto-decide step does. That keeps its memory claim, loop guard and processed-command ledger bound to this repository's origin. `SUPPORT_SCRIPTS_UNIFIED_ENABLED=false` restores the legacy copy loop and the bare `scripts/` paths.
