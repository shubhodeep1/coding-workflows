- `UNBLOCK_JUDGE` also logs `item= kind= stop= fingerprint= op=invalid_verdict_park outcome=terminal streak=<n>` or `outcome=skip reason=decide_failed|validate_failed` (`scripts/unblock_judge.sh`, tele-funtoken-msg-scoring#4770): the refused answer just recorded was the `INVALID_VERDICT_PARK_AFTER`-th in a row (default 2, `scripts/unblock_ledger.py`) on the same stop and fingerprint, so the judge takes the ledger's terminal `close` with `terminal_reason=invalid_verdicts`, which parks the item in the needs-human digest with one CRITICAL page (or closes it when `NEEDS_HUMAN_DIGEST_ENABLED=false`). The refused-answer marker comment is posted once, never retried (a retry after a lost response could post two markers and park after one refusal); when the write fails it logs `op=invalid_verdict_record outcome=failed reason=record_failed rc=<gh exit code>` and, unless this run parks the item, sends one WARNING, because the streak is counted only from posted markers (a parking run whose write failed and whose park then stops at `decide_failed` or `validate_failed` sends that WARNING instead). A run where the model gave no answer at all (`outcome=model_failed reason=invalid_model_config|isolation_failed`) posts the older uncounted marker without `stop=`/`fingerprint=` and never parks, so a provider or sandbox outage cannot park items. On the parking run the comment no longer says the judge "will try again later".

- **Unblock judge refused answers (tele-funtoken-msg-scoring#4770).** A refused judge answer posts `<!-- ai:unblock-wait:v1 item=<n> reason=invalid_verdict stop=<id> fingerprint=<12 hex> -->` (the older form without `stop=`/`fingerprint=` is still recognised and is neither counted nor a break). It is not a round. `scripts/unblock_ledger.py invalid_verdict_streak` counts the trailing run of these markers for the item's current stop and fingerprint among the pipeline login's unblock markers (any other `ai:unblock:v1` or `ai:unblock-wait:v1` marker for the item ends the run); `decide` returns `invalid_verdict_streak` and `invalid_verdict_park_after`, takes `--pending-invalid-verdicts N` for the refusal the caller has not posted yet, and makes the item terminal with `terminal_reason=invalid_verdicts` (added to `TERMINAL_REASONS`) at `INVALID_VERDICT_PARK_AFTER` (2). Before this, no terminal condition could ever hold for an item whose answers were always refused, and it was retried every `--marker-hours` (6 h) with no page. Verdict text fields no longer refuse `<!--` / `-->`: `_strip_comment_delimiters` removes them, repeating until none is left, so a quoted `<!-- changelog: fixed -->` line no longer voids the verdict and the stored text still cannot form a marker. Text that is only delimiters is refused as empty.
- **Blocked implement verdicts page at WARNING (tele-funtoken-msg-scoring#4770).** When `implement.yml`'s "Comment on issue failure" sets the `ai:blocked` latch for a deliberate `BLOCKED:` verdict, it writes `${RUNTIME_DIR}/implement_blocked_latched.flag`; "Telegram failure notification" then sends `Implementation blocked on issue #<n>: human input required` with the reason, issue and run links at `WARNING` (tracked on the issue) instead of the `DEBUG` failure message, which the default `ALERT_MSG_LEVEL=WARNING` dropped. Every other implement failure keeps the `DEBUG` message.
