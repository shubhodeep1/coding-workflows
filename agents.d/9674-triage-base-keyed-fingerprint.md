<!-- agents: section="Workflow architecture" -->
Check-failure triage keys the issue on a failing default branch (Refs #9674): in `scripts/check_failure_triage.sh`'s base-branch gate, after the success, pending and routed-head-base skips and after the heal-issue skip (`CHECK_TRIAGE_BASE_TRACKED_SKIP_ENABLED`) has fallen through (`failed_jobs_differ` included), a base conclusion of `failure`, `timed_out`, `cancelled`, `startup_failure` or `action_required` on a base ref equal to `base.repo.default_branch` from the PR payload switches `FP` to `sha256("<repo>|base=<ref>|check=<check>")`. The existing open-triage listing (`OPEN_TRIAGE`) is matched against it with the same `contains("fp=…")` rule as the duplicate check: a match logs `skip reason=base_triage_tracked`, reports an unverified PR-head route like the other base-gate skips, writes no step output and runs no supersede logic; otherwise it sets `BASE_KEYED_REF`, logs `base_keyed outcome=file` and records `base_keyed_ref` in `triage_metadata.json` (always present, empty for a per-PR issue). The lineage root stays the per-PR fingerprint. The diagnose stage re-checks the ref (`^[A-Za-z0-9._/-]{1,200}$`, no `..`), that the fingerprint is the base-keyed one, that no routing line sits beside it and that historical mode is off, else `error base_keyed_metadata_invalid` and exit 1. The body keeps its four header lines plus `<!-- check-failure-triage:base=<ref> -->` as line 5, keeps the `- **Pull request:**` line byte-for-byte, and adds ``- **Base branch:** `<ref>` (failing; first seen on PR #<n>)``; the body validator expects that fifth line. The post step titles it `CI failure: <check> on <ref> (first seen on PR #<n>)` (an invalid `base_keyed_ref` is `op=post stage=metadata_invalid`). `scripts/resolve_integration_ref.sh`'s `CI_TRIAGE_PARSE_PY` reads the marker only at line 5 and only after every trust check passed, and prints `base <pr> <ref>`; `resolve_ci_triage_branch` then prints nothing, so the issue keeps the default branch. Unknown base results, non-default bases, integration-branch / PR-head / target-branch routes and historical mode keep the per-PR fingerprint. `CHECK_FAILURE_TRIAGE_MAX_OPEN_ISSUES` (default 5, `0` = no cap, other values warn and use 5; forwarded by `check_failure_triage.yml` as `vars.CHECK_FAILURE_TRIAGE_MAX_OPEN_ISSUES || '5'`) stops the collect stage after the PR-head routing gate, before context collection, once `OPEN_TRIAGE` holds that many issues (`skip reason=open_issue_cap`, one Telegram WARNING); historical mode and a supersede replacement are exempt. No API call is added. Tests: `tests/test_check_failure_triage_base_fingerprint.py`, plus base-keyed cases in `tests/test_resolve_integration_ref_ci_triage.py` and `tests/test_check_failure_triage_post_stage.py`.
