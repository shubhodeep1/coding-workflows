- Managed wrappers are locked in consumer repos. `workflow-templates/ai-workflow-integrity.yml` (in every install profile) calls `.github/workflows/workflow_integrity.yml` on `pull_request_target` (types opened, synchronize, reopened) and on every branch `push`. It reads the base and head trees as git objects (nothing from the consumer runs), lists the managed candidates (`ai-workflow-integrity.yml`, `ai-update-workflows.yml`, and every top-level workflow that calls a `shubhodeep1/coding-workflows/.github/workflows/*` reusable workflow in either tree) and skips when none changed. Otherwise it takes the single 40-hex pin of the head's `ai-workflow-integrity.yml`, fetches that commit in the updater's sparse shape, verifies the signed `sync-manifest.json` (tag, Sigstore identity, commit and file hashes; the inline `SYNC_VERIFY_PY` verifier is a byte copy of `update_workflows.yml`'s, pinned by `tests/test_workflow_integrity.py`), renders the release templates with the release's own `scripts/workflow_wrapper_refs.py`, and requires every managed wrapper in the head (the `WORKFLOW_PROFILE` manifest, the integrity wrapper, and the updater when either tree has it) to be byte-identical. Pull request runs post the commit status `coding-workflows/workflow-integrity` on the head (pending at start; `success`, `failure` or `error` at the end, `github.token` with a `GH_PAT` fallback); push runs only fail the job, so they never overwrite a pull request verdict. Reasons: `no_managed_wrapper_changed` (skip), `integrity_wrapper_missing`, `pin_missing`, `pin_ambiguous`, `pin_not_sha`, `release_commit_missing`, `ERR_SYNC_MANIFEST_*`, `workflow_profile_unknown`, `wrapper_mismatch` (per file `modified`, `missing`, `template_missing`).
- `update_workflows.yml` ignores `allow_workflow_edits: false` / `ALLOW_WORKFLOW_EDITS=false` for managed wrappers in consumers; the job-level `if:` now skips the job only in `shubhodeep1/coding-workflows` itself, so the release gate's smoke dispatch (`allow_workflow_edits=false` against this repository) never syncs consumer wrappers into the source repo. - **Daily consumer drift repair.** `.github/workflows/audit_consumer_drift.yml` now runs daily (`0 8 * * *`) and reads the templates and `scripts/workflow_wrapper_refs.py` from the `stable` tag (`git archive FETCH_HEAD`), not from `main`, passing `--templates-dir` and `--renderer` to `scripts/audit_consumer_drift.py`. With `--repair` (on unless the repo variable `CONSUMER_DRIFT_REPAIR_ENABLED` is `false`), `repair_drifted_repositories` runs `DriftRepairer.repair` for every `drift` and `match` result (the audit compares normalized text, the integrity check exact bytes): a depth-1 git clone and an exact-byte check first (a match costs no REST call and its `no_exact_drift` skip is left out of the summary), then one `GET repos/<r>/pulls?state=open&per_page=100` listing, paginated up to 10 pages (skip with `reason=sync_pull_request_open` when an `auto/update-workflows-*` or `ai-sync/stable` head from the same repo is open; find the existing restore PR by head `auto/restore-managed-workflows` plus body marker `<!-- coding-workflows:restore-managed-workflows:v1 -->`), exact-byte rewrite of every managed wrapper (profile manifest plus `ai-workflow-integrity.yml`, plus the updater whenever the consumer has it (a dangling symlink counts), whatever its profile lists, because the integrity check compares it then; an unresolved `WORKFLOW_PROFILE` or missing manifest skips the repository before the clone with `reason=profile_unknown`, reported only for `drift` results; a symlinked `.github` or `.github/workflows` skips the repository with `reason=unsafe_checkout`), a commit, a `--force-with-lease` push skipped when the tree is unchanged (an existing branch whose tip is not this audit's restore commit is left alone, `reason=restore_branch_not_owned`), then at most one `POST pulls` or `PATCH pulls/<n>`. The git credential is passed through `GIT_CONFIG_*` environment variables, never argv. Failures become `outcome=error reason=repair_failed` for that repository only. The summary JSON gains `repairs`, and the job summary and Telegram alert list them; any repair other than a `sync_pull_request_open` or `no_exact_drift` skip raises the alert to WARNING, also for a repository the audit reports as `match`.
