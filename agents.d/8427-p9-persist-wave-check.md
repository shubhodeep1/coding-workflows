### Check between waves (`PERSIST_ORCH_WAVE_CHECK_ENABLED`, P9 of #8427)

Phase P9 of `docs/plans/persistent-unattended-workflows-plan.md`. Repo variable `PERSIST_ORCH_WAVE_CHECK_ENABLED` (default `false`), defaulted in `orchestrate_poll.yml`, in the poller (`${PERSIST_ORCH_WAVE_CHECK_ENABLED:-false}`) and in `scripts/persist_orchestrator.py` itself; only the exact value `true` turns it on. `PERSIST_ORCH_WAVE_CHECK_MAX_WAIT_MINUTES` (default `90`) falls back to 90 when not a positive integer.

- **Gate.** `persist_orch_wave_check` (`scripts/orchestrate_poll_process.sh`, next to `persist_orch_group_failures`) runs in the managed loop immediately before `SKIP_JUDGE_FOR_CLEAN_WAVE="false"`, and acts only when every clean-wave skip condition holds (`ENABLE_CLEAN_WAVE_JUDGE_SKIP=true`, not stuck, `WAVE_COMPLETE=true`, no failed item, project not complete, `CURRENT_WAVE < TOTAL_WAVES`) and `final_merge_pr` is a positive integer with `final_merge_status == "pending"`. The head SHA comes from the external-finalize block's same-tick read of that PR (`PERSIST_ORCH_WAVE_CHECK_HEAD_SHA` / `PERSIST_ORCH_WAVE_CHECK_HEAD_PR`, set only when the PR is open, reset per tracking issue); there is no fallback read. The first tick that reaches a boundary only records `wave_check_wait_since` / `wave_check_wait_head` and holds (`outcome=pending reason=boundary_first_seen`, no API call), because that head was read before the tick's own sub-issue merges, or the final PR was recorded later in the tick (then `reason=head_sha_unavailable`, also a one-tick hold); the next tick classifies the current head. A head that moved during a hold keeps the wait clock (the wait is bounded per boundary, so a head that keeps moving cannot hold it past `MAX_WAIT`); only `wave_check_wait_head` is updated, by a branch that writes state anyway.
- **Classification.** `persist_orchestrator.py wave-check` (pure) classifies one page of `commits/<sha>/check-runs?per_page=100` with the rules of `scripts/pr_checks_lib.sh`: a newer same-name run supersedes only a `cancelled` run (a check run has no workflow identity), and for the CI check name (`--ci-check-name`, the poller passes `_pr_auto_merge_required_ci_check_name`, `lint` here) only a newer run of the same Actions run does (the same-run half of `PR_CHECKS_JQ_SUPERSEDE_DEFS`; its bound-CI-run half is not applied because no runs listing is read, so a cancelled CI run beside a newer one from another CI run is red); `skipped` / `neutral` are ignored, a pending run always holds (also with an empty required list), a failed run is red only when its name is in `--required-names` (the poller passes `ORCH_FINAL_MERGE_REQUIRED_CHECKS`; `*` every failure, empty none; the branch-protection lookup is not repeated), red wins over pending, and a truncated page (`total_count` above the runs read) is `pending`, never green or `no_checks`, even when no run on it counts. Outcomes: `green` (the skip proceeds), `pending` / `no_checks` (hold: `wave_check_wait_since` is recorded once and the poller `continue`s to the next project), `red` and `timeout` (pending for `>= MAX_WAIT` minutes) set `INVOKE_JUDGE_FOR_STUCK=true` so the existing wave-judge path runs, at most once per head and outcome per `MAX_WAIT` minutes (a repeat holds with `reason=judged_recently`, because the final-PR phase bypasses the judge-cycle cap), `no_checks_timeout` and `unavailable` fail open to the skip.
- **Judge block.** `persist_orchestrator.py wave-check-block` renders `=== BEGIN/END UNTRUSTED WAVE CHECK ===` into `PERSIST_ORCH_WAVE_CHECK_BLOCK`: outcome, failing check names and conclusions, still-pending names and minutes waited (timeout), unmet done-checks of the wave's items (newest pipeline-login journal entry with `acceptance.state == "unmet"`, up to 5 strings, plain `issue N`; `note` is never read), and one log tail (last 8192 bytes of the first failing Actions job's log, else the first failing third-party run's `output.summary`). Every data line has control characters and `<!--` / `-->` removed, runs of `=` broken into `= = =`, `attempt_journal._scrub` applied and an `UNTRUSTED_DATA: ` prefix; the block is capped at 12 KiB with a `- ... truncated` line. The wave-judge prompt prints the block with a short lead, and the "wave is STUCK" paragraph is shown only when no block is present; with the switch off the prompt is byte-identical.
- **State field.** Top-level `wave_check_wait_since` (`YYYY-MM-DDTHH:MM:SSZ`) and `wave_check_wait_head` (the head SHA the clock belongs to, empty when none was known), plus `wave_check_judged` (`<head sha>:<red|timeout>`) and `wave_check_judged_at` (epoch seconds) written when a result is sent to the judge; set on the first tick at a boundary and removed (then `post_state_comment`) on green, every fail-open path, when the gate's conditions no longer hold, and on every incomplete-wave tick (the managed loop's `WAVE_COMPLETE != true` branch runs the `stale` clear before it continues, since `persist_orch_wave_check` is not reached there). Red and timeout keep them, so the next tick classifies the head again. A value that does not parse, or lies in the future, is reset.
- **Journal.** green writes a `wave_check` / `ok` entry and red / timeout a `wave_check` / `fail` entry to the tracking issue's attempt journal through `attempt_journal.py append` (its own `PERSIST_JOURNAL_ENABLED` gate applies), from the tick's tracking comments; skipped when those comments or the pipeline login are unavailable.
- **API budget.** At most two reads per tick: the check-runs page, and one job log (`--allow-escape-sequences`) only for a red Actions run; plus the identity read shared through `PERSIST_JOURNAL_LOGIN_CACHE`, at most once per poller process. The journal append is a separate comment write by `attempt_journal.py`, gated by `PERSIST_JOURNAL_ENABLED`, and not counted in the two reads. A `judged_recently` hold makes only the check-runs read. The first tick at a boundary makes none. The job log is never echoed to the poller's stdout.
- **Failure modes.** Check-runs read fails: `reason=checks_unavailable`, skip as today. Log read fails: the block says `(log unavailable)`. Helper missing or no output: `reason=helper_absent` / `helper_failed`, skip as today. State write fails while pending: `outcome=error reason=state_write_failed`, still held this tick. A persistent red (or still-pending past `MAX_WAIT`) result on one head re-invokes the judge at most once per `MAX_WAIT` minutes while the final PR is pending (the judge-cycle cap is bypassed then), until the head moves or the judge advances the wave or adds fix-ups, which removes the wait fields through the `stale` clear on the next incomplete-wave tick. When the wave judge run for a red / timeout result ends without a verdict (judge checkout failure, isolation unavailable, judge run failed, unparseable output), `_persist_orch_wave_check_unjudge` removes `wave_check_judged` / `wave_check_judged_at` (the wait fields stay), so the next tick runs the judge again instead of holding as `judged_recently`.
- **Switch off.** No Python starts and no API call; one jq check removes a leftover `wave_check_wait_since` (`outcome=cleared reason=switch_off`); with none present there is no write and no log line.
