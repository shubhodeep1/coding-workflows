### Check between waves (`PERSIST_ORCH_WAVE_CHECK_ENABLED`, P9 of #8427)

Phase P9 of `docs/plans/persistent-unattended-workflows-plan.md`. Repo variable `PERSIST_ORCH_WAVE_CHECK_ENABLED` (default `false`), defaulted in `orchestrate_poll.yml`, in the poller (`${PERSIST_ORCH_WAVE_CHECK_ENABLED:-false}`) and in `scripts/persist_orchestrator.py` itself; only the exact value `true` turns it on. `PERSIST_ORCH_WAVE_CHECK_MAX_WAIT_MINUTES` (default `90`) falls back to 90 when not a positive integer.

- **Gate.** `persist_orch_wave_check` (`scripts/orchestrate_poll_process.sh`, next to `persist_orch_group_failures`) runs in the managed loop immediately before `SKIP_JUDGE_FOR_CLEAN_WAVE="false"`, and acts only when every clean-wave skip condition holds (`ENABLE_CLEAN_WAVE_JUDGE_SKIP=true`, not stuck, `WAVE_COMPLETE=true`, no failed item, project not complete, `CURRENT_WAVE < TOTAL_WAVES`) and `final_merge_pr` is a positive integer with `final_merge_status == "pending"`. The head SHA comes from the external-finalize block's same-tick read of that PR (`PERSIST_ORCH_WAVE_CHECK_HEAD_SHA` / `PERSIST_ORCH_WAVE_CHECK_HEAD_PR`, set only when the PR is open, reset per tracking issue); there is no fallback read.
- **Classification.** `persist_orchestrator.py wave-check` (pure) classifies one page of `commits/<sha>/check-runs?per_page=100`: the newest run (highest `id`) per name counts, `skipped` / `neutral` are ignored, red wins over pending. Outcomes: `green` (the skip proceeds), `pending` / `no_checks` (hold: `wave_check_wait_since` is recorded once and the poller `continue`s to the next project), `red` and `timeout` (pending for `>= MAX_WAIT` minutes) set `INVOKE_JUDGE_FOR_STUCK=true` so the existing wave-judge path runs, `no_checks_timeout` and `unavailable` fail open to the skip.
- **Judge block.** `persist_orchestrator.py wave-check-block` renders `=== BEGIN/END UNTRUSTED WAVE CHECK ===` into `PERSIST_ORCH_WAVE_CHECK_BLOCK`: outcome, failing check names and conclusions, still-pending names and minutes waited (timeout), unmet done-checks of the wave's items (newest pipeline-login journal entry with `acceptance.state == "unmet"`, up to 5 strings, plain `issue N`; `note` is never read), and one log tail (last 8192 bytes of the first failing Actions job's log, else the first failing third-party run's `output.summary`). Every data line has control characters and `<!--` / `-->` removed, runs of `=` broken into `= = =`, `attempt_journal._scrub` applied and an `UNTRUSTED_DATA: ` prefix; the block is capped at 12 KiB with a `- ... truncated` line. The wave-judge prompt prints the block with a short lead, and the "wave is STUCK" paragraph is shown only when no block is present; with the switch off the prompt is byte-identical.
- **State field.** Top-level `wave_check_wait_since` (`YYYY-MM-DDTHH:MM:SSZ`), set on the first pending tick at a boundary and removed (then `post_state_comment`) on green, red, timeout, every fail-open path, and when the gate's conditions no longer hold. A value that does not parse, or lies in the future, is reset.
- **Journal.** green writes a `wave_check` / `ok` entry and red / timeout a `wave_check` / `fail` entry to the tracking issue's attempt journal through `attempt_journal.py append` (its own `PERSIST_JOURNAL_ENABLED` gate applies), from the tick's tracking comments; skipped when those comments or the pipeline login are unavailable.
- **API budget.** At most two reads per tick: the check-runs page, and one job log only for a red Actions run; plus the identity read shared through `PERSIST_JOURNAL_LOGIN_CACHE`. The job log is never echoed to the poller's stdout.
- **Failure modes.** Check-runs read fails: `reason=checks_unavailable`, skip as today. Log read fails: the block says `(log unavailable)`. Helper missing or no output: `reason=helper_absent` / `helper_failed`, skip as today. State write fails while pending: `outcome=error reason=state_write_failed`, still held this tick. A persistent red check re-invokes the judge each tick while the final PR is pending (the judge-cycle cap is bypassed then), until the judge advances or adds fix-ups.
- **Switch off.** No Python starts and no API call; one jq check removes a leftover `wave_check_wait_since` (`outcome=cleared reason=switch_off`); with none present there is no write and no log line.
