<!-- agents: section="Workflow architecture" -->
**Check-failure triage re-runs release-download 5xx failures (issue #9120).** In the collect stage, right after the `pr_not_open` and `fork_pr` gates and before routing, dedup and the base-branch gate, `triage_release_download_rerun_gate` (`scripts/check_failure_triage.sh`) re-runs the failed jobs of a first-attempt workflow run instead of filing an issue when every failed job's annotations show a `github.com` release download that returned HTTP 502/503/504. It reads the run once (`GET actions/runs/<run>`; `status` must be `completed`, `run_attempt` 1 and `head_sha` the triaged head) and memoizes `workflow_id`, so the base-branch gate no longer reads the same run again. On the workflow_run path (empty check-run id, details URL `.../actions/runs/<run>`) it lists the attempt-1 jobs and needs 1 to 3 failed jobs; on the check_run path the details URL must name `/job/<CHECK_RUN_ID>`. The gate skips with `reason=pr_unverified` when the PR read did not confirm a head repository equal to this repository (a failed PR fetch leaves it empty and skips the fork guard). Read budget: the check_run path makes 2 reads (run, annotations) and the workflow_run path, which is how Actions failures arrive (`check_run_id: ""`), makes up to 5 (run, attempt-1 jobs, one annotations read per failed job, at most 3); both make at most 1 POST. That is above the issue's 2-read target on the workflow_run path, bounded by the 3-failed-job cap, because Actions failures carry no check-run id. Each failed job's annotations (`GET check-runs/<id>/annotations`) must match in `triage_release_download_classify`: a `failure` annotation with `\b50[234]\b` and a `https://github.com/<o>/<r>/releases/(latest/)download/` URL, or the CodeQL pair (`Unable to download and extract CodeQL CLI: Unexpected HTTP response: 50x` plus any annotation with a release URL and `HTTP status code: 50x`). A match makes one unretried `POST actions/runs/<run>/rerun-failed-jobs` (success is exit 0 and HTTP 201; the response is never printed) and exits 0 without `ready=true`, so diagnose and post do not run. Any read failure, a non-match or a failed POST logs a `RELEASE_DOWNLOAD_RERUN outcome=skip` line and files as before (fail open). The re-run is attempt 2, so a failure that comes back is triaged as usual; each run is re-run at most once. `CHECK_FAILURE_TRIAGE_RELEASE_DOWNLOAD_RERUN_ENABLED` (default `true`, forwarded by `check_failure_triage.yml`) turns it off with `false`; any other value warns and keeps it on. Historical mode skips the gate.

When planning blocks an issue labelled `ai:check-triage`, `plan.yml`'s `Handle blocked planning output` step reads the label from the already-fetched `ISSUE_META_FILE` and sends the Telegram alert at `WARNING` instead of `CRITICAL`, with ` (CI triage; the unblock judge will re-check)` in its first line, and adds one paragraph after the `Reason:` line saying the unblock judge re-checks the failing check and closes the issue once it passes. The first line `Planning blocked: human input required.` and the `Reason:` line are unchanged (`scripts/unblock_judge.sh` reads both); other blocked issues, and a missing metadata file, keep `CRITICAL` and today's text.
