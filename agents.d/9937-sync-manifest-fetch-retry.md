Sync-manifest fetch retry (#9937). In "Verify signed sync manifest" (`update_workflows.yml` `verify_manifest`, and the same step in `workflow_integrity.yml`) the manifest is no longer fetched with `gh release download` (which also sends a GraphQL query and whose stderr was discarded). The block between `# BEGIN sync manifest fetch (byte-identical in update_workflows.yml and workflow_integrity.yml; tests pin it)` and `# END sync manifest fetch` is identical in both workflows (`tests/test_workflow_integrity.py::test_manifest_fetch_block_is_a_copy_of_the_sync_fetch_block`) and stays inline: it sources nothing, because no upstream code may run before verification. It makes two REST calls, `gh api repos/<repo>/releases/tags/<vX.Y.Z>` and then `gh api -H 'Accept: application/octet-stream' repos/<repo>/releases/assets/<id>` for the single asset named `sync-manifest.json` with `state == "uploaded"` (the id must be all digits). Both calls pass `--include`; the response headers land in `<file>.raw`, the body after the header block is split into `<file>.part`, and that is renamed only on success. Each call gets at most 3 attempts:
- rate limited (stderr says `rate limit`, or HTTP 403/429 while `gh api rate_limit` reports `resources.core.remaining == 0`): sleep the numeric `Retry-After` header + 1 s when the response carries one, otherwise until `resources.core.reset` + 5 s, otherwise 60 s for a secondary limit, then retry. All rate-limit sleeps of both calls share the cap `SYNC_MANIFEST_RATE_LIMIT_MAX_WAIT_SECONDS`, set from the caller repository variable of the same name (default `1200`, also the shell default; a value that is not 1-6 digits falls back to `1200`, and values above `1500` are clamped to `1500` so the step rejects well before the 35-min job timeouts). A wait that would pass the cap is not taken; the step rejects at once;
- any other failure retries once after 10 s;
- a 404 on the release lookup is not retried.

Reason codes: `ERR_SYNC_MANIFEST_FETCH_FAILED` (new) with `detail=rate_limited`, `detail=http_<status>` or `detail=unknown` when a call still fails (`detail=unknown` also covers a release lookup whose body is not a JSON object). `ERR_SYNC_MANIFEST_MISSING` now means only that the release does not exist (`detail=release_not_found`), that it has no `sync-manifest.json` asset, or that the downloaded file is absent or a symlink. Both reach `failure_reason_code`, the verification alert and the Summary unchanged. Job timeouts were raised to cover the wait: `update-wrappers` and `integrity` both 35 min.
