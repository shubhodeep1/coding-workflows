- **Unblock judge also closes nothing-to-implement issues with no pending fix-up wait (#9518).** `unblock_main` calls `unblock_nothing_to_implement_close` a second time, with an empty fix-up, after its deterministic exits and before the model verdict. It applies the same checks as the #8470 close (pipeline-login newest block with the exact reason line, no later trusted implementation plan, standalone issue at stop `blocked`) plus one more: when a fix-up wait exists, the block must be newer than the time that wait ended (`wait_ended_at`: the wait comment's last update when it was already `done`, the fix-up's `closed_at`, read by the same fix-up lookup, when it closed without merging, or the current run when the judge times it out). The closed-without-merging run writes that `closed_at` into the done wait comment as `<!-- ai:unblock-wait-ended:v1 at=<ts> -->`, just above the wait marker, and later runs read it back from the item comments (only from the pipeline login, and only when it is earlier than the comment's last update), so a failed or skipped close is retried instead of being compared with the patch time. A wait the judge times out while its fix-up is still open writes `<!-- ai:unblock-wait-unresolved:v1 -->` there instead, and later runs that read it from a pipeline-login wait comment (or find a wait time that is not a UTC timestamp) skip the no-wait close, because that fix-up never resolved. A block filed while the fix-up was still unresolved stays with the judge. The comment says no fix-up is pending, and the marker and the `op=nothing_to_implement` log line carry `fixup=none`; a `fixup=none` marker counts as already posted only when it is no older than the newest block, so a re-block after a reopen gets its own comment. The close itself makes no reads and at most the same three writes (comment, label, close) and does not touch the wait comment; when the run reaches it through the timed-out or closed-without-merging fix-up path, that path has already patched the wait comment `done` earlier in the same run (one more write, as before this change). `UNBLOCK_NOTHING_TO_IMPLEMENT_CLOSE_ENABLED=false` turns off both closes.
