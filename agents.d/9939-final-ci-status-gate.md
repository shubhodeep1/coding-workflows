- **The final CI posts a `ci/final` commit status; synchronous merges refuse blocked PRs (#9939, 2026-11-22).** The default-branch ruleset (25851281) required the check `lint`. Since #9698 renamed the PR-body lint job to `pr-body-lint`, the only `lint` on a pipeline PR head comes from the dispatched final CI (`ci.yml` `workflow_dispatch`, "CI [pr:N]"), and GitHub counts a workflow job's check-run for a PR only when the run's event is push, pull_request, pull_request_target, pull_request_review, deployment or deployment_status. So `lint` read as "expected" forever, and every merge from 2026-11-21 12:23 UTC landed by admin bypass: `_pr_ruleset_required_check_blockers` matches by name and counted the dispatched `lint` check-run as passing, so the direct `gh pr merge` paths went ahead with the owner's admin `GH_PAT`.
  - **`ci/final`.** The `lint` job's last two steps ("Checkout the final CI status script", a sparse checkout of the run's own head into `.ci-final-status`, and "Report the final CI result as a commit status") run `scripts/ci_final_status.sh` with `if: always() && !cancelled()` and `continue-on-error: true`. It POSTs one `repos/<repo>/statuses/<sha>` (context `ci/final`, target_url the run) with `success` only when "Require every CI job to succeed" (`id: ci_require_all_jobs`) succeeded and, in a docs-only run, `docs_only_verify` succeeded too; a cancelled aggregate posts nothing, anything else posts `failure`. It always exits 0: a failed post logs `CI_FINAL_STATUS ... outcome=post_failed` and the missing status keeps the PR blocked, never falsely green. `lint` now declares `permissions:` (`contents: read`, `pull-requests: read`, `actions: read`, `statuses: write`), and `ci_pr_quick.yml` grants `statuses: write` because a caller must grant what a called job declares even when the job is skipped. `static-checks` declares its own read-only `permissions:` (`contents`, `pull-requests`, `actions`), so in quick mode, where it runs PR code, it does not inherit that `statuses: write`. Quick mode never runs `lint`, so it never posts.
  - **Blocked-merge guard.** `_pr_sync_merge_blocked_guard <pr_json|pr_number> [base_ref] [blockers_hint]` (`scripts/pr_checks_lib.sh`) returns 1 when GitHub reports `mergeable_state` `blocked`, `unknown`, null/missing or the PR is unreadable (fail closed), else 0 with no output. It runs right before every direct merge: `rb_judge_sync_merge_guard` in `scripts/review_rb_judge.sh` (the `merge` and `terminal` auto-then-direct chains, the direct retry inside `rb_judge_merge_retry_transient`, and the `merge_with_followup` sync merge), and in `scripts/orchestrate_poll_process.sh` the direct fallback of `_orch_squash_merge_bound` (new outcome `deferred`, return 1), the final integration merge (any `blocked` now defers, not only when the ruleset helper names a blocker; it reuses `pr_json` and the helper's result as `blockers_hint`) and the poller's `merge_with_followup`. After a deferral the judge's transient retry never merges directly: in the `merge` / `terminal` chains it re-tries only `--auto` (at most 3 times, only while the `--auto` stderr is transient), and a failed `--auto` request is logged as `RB_JUDGE_MERGE_ERROR` (auto part only). `rb_judge_deferred_merge_pending` then reads `RB_MERGE_RETRY_GIVEUP` (`non_transient`, `head_moved`, `not_open`, `deferred`, `exhausted`): the run reports `mergeability_pending` when the retry ran out on transient errors, the `--auto` stderr is empty, or `mergeable_state` was not `blocked`, and `merge_failed` (the usual warning) when the PR closed, its head moved, or GitHub refused `--auto` for a non-transient reason on a `blocked` PR. Deferrals reuse existing outcomes (`RB_MERGE_STATUS=mergeability_pending`, `judge_skip_reason=mergeability_pending`, the final merge's "Will retry next poll" with the budget not spent), and `--auto --match-head-commit` stays first wherever a path already tried it, so GitHub merges once the PR is green. `PR_SYNC_MERGE_BLOCKED_GUARD_ENABLED` (default `true`, forwarded by the judge step of `review_autofix.yml` and by `orchestrate_poll.yml`) set to `false` restores the old behaviour for consumers that rely on admin-bypass merges.
  - **Owner steps.** O1: the implementing PR's own final CI posts `ci/final` (creator github-actions[bot]). O2: while it is open and green, the owner makes the ruleset require `ci/final` (integration 15368; drop the pin if it reads "expected") and `ai-review/head-gate`, and removes `lint`; the PR then auto-merges with rule-suite `pass`. O3: after one more PR auto-merges with `pass`, the owner removes the Admin bypass actor. Rollback: restore `lint` in the ruleset and set `PR_SYNC_MERGE_BLOCKED_GUARD_ENABLED=false`.
