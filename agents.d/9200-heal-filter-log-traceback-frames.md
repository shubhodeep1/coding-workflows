Workflow failure heal log filter and Python tracebacks (Refs #9190, #9200): `filter_log` in `scripts/workflow_failure_heal.py` keeps the tail plus `_SOFT_LOG_PATTERNS` lines, and `_traceback_context_indices` adds the lines after each `Traceback (most recent call last)` header: indented frame, source and caret lines, blank lines, the first unindented line (the exception line), then indented continuation lines and a `The above exception was the direct cause of the following exception:` / `During handling of the above exception, another exception occurred:` marker. The next unindented line or the next header ends the block; a chained traceback's header starts its own block. The Actions timestamp prefix is ignored for this, trailing blank lines are dropped, each block keeps its last `_TRACEBACK_CONTEXT_MAX_LINES` (30) lines and is scanned for at most `_TRACEBACK_SCAN_MAX_LINES` (400) lines; a traceback with no exception line by then (uncollapsed mutual recursion) is followed on to its exception line, so that line and the innermost frames are kept. The `max_lines` / `max_bytes` cut is unchanged. Before this, the heal evidence for the Python 3.14 argparse crash in `scripts/render_prompt.py` (plan run 42929246385) held two bare headers and #9190 / #9200 were filed as inconclusive. Tests: `test_filter_log_keeps_chained_traceback_frames_and_exception_lines_outside_tail`, `test_filter_log_keeps_the_innermost_lines_of_a_long_traceback` and `test_filter_log_keeps_the_exception_line_of_a_traceback_longer_than_the_scan_window`.
