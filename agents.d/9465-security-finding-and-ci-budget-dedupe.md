**Security audit: a finding repeated under a new id reuses the open follow-up's id (Refs #9465).** In issues mode `scripts/security_audit.sh` dedupes follow-ups by the `<!-- ai:security-finding:<finding_id> -->` marker, but the audit model invents that id on every run: #9399, #9431 and #9465 were one finding at `scripts/render_prompt.sh:326` on branch `ai/issue-9341`, each filed while the earlier ones were still open. Before the id dedupe, a finding whose id has no follow-up now takes the id of an OPEN `ai:security` follow-up with the same audit scope (its `- Integration branch:` equals `SECURITY_AUDIT_TARGET_REF`; both empty for the default branch), the same `- Location:` file and the same `- Category:` key (the OWASP code `A01`..`A10` when present, else the lower-cased letters and digits) within `SECURITY_AUDIT_SIMILAR_FINDING_LINE_WINDOW` lines (default 25, `0` off); the nearest line wins, then the older issue. From there on it is the existing finding: no issue is filed, the summary line's `finding_ids_b64` names the open issue's id (which is what `scripts/review_single_issue_security_pass.sh` checks follow-ups against), and the tracker report says `Reported this run as <id>; it repeats open follow-up #<n>`. A closed follow-up never matches, so a finding that comes back under a new id after its issue closed, fixed or not, is filed again (the pre-existing exact-id dedupe still covers open and closed follow-ups); a follow-up of another branch never matches either. The data comes from the paginated `ai:security` issue list the dedupe already reads (no extra API call). Findings-json mode (orchestrator security pass) never reaches this code. The tracker report comment stays one comment per audit run: it is posted with the job token, so it starts no `issue_comment` wrapper run, and nothing reads it back.

- `scripts/ci_budget_watch.py` re-file cooldown: when an `ai:ci-budget` issue with the same marker was closed within `CI_BUDGET_REFILE_COOLDOWN_DAYS` (default 7, `0` off), a new issue is opened only once the value reaches `CI_BUDGET_REFILE_URGENT_RATIO` (default 0.9) of its limit; otherwise it logs `CI_BUDGET_ISSUE kind=<kind> subject=<subject> action=cooldown closed_issue=<n> cooldown_days=<d> urgent_ratio=<r>` and only prints the `::warning::CI_BUDGET` line. One open issue per finding is unchanged (`action=exists`). The closed-issue listing (50 most recently updated, one call) is read only when a finding below the urgent ratio has no open issue, and a failed read opens the issue as before. With the default thresholds a workflow-size finding is always above the urgent ratio, so the cooldown applies to job-duration findings.
