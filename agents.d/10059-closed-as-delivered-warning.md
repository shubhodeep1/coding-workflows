- **Closed-as-delivered wave items warn instead of paging (#10059, 2026-11-24).** `orchestrate_lib.py check-wave-status` takes an optional `--issue-state-reasons-json` (`{"<issue>": "completed|not_planned|reopened|duplicate"}`, lowercased; non-object fails with `ok:false`) and marks each wave item `closed_as_delivered` when its status is `closed`, the issue state is `closed`, the reason is `completed`, it carries `ai:closed` and none of `VALIDATION_DISPATCH_BLOCKING_FAILURE_LABELS`. The new top-level `any_failed_blocking` is true only when a `closed` / `implementation-failed` item is not of that kind; `any_failed`, `validation_dispatch_safe_despite_failures`, the statuses and `decision_source` are unchanged. The poller reads `stateReason` from the existing `_fetch_candidate_issue_details_graphql` batch (`state_reason` in the cached detail object) into `ISSUE_STATE_REASONS_JSON`; the REST state fallback, a reissue-adopted successor and the snapshot caller record no reason, so those items fail closed (blocking). Only the completion-status comment and its alert read `ANY_FAILED_BLOCKING`: when it is true the `failed` state, the "closed without merge" list and the once-per-project CRITICAL (`completion_status_failure_alert_sent`) are as before; when only delivered items exist the comment lists them under "Wave issues closed as already delivered" and the poller sends one WARNING per item, deduped by the state-file array `completion_status_delivered_closed_alerted` (it never sets the CRITICAL flag, so a later real failure still pages). Every other `ANY_FAILED` reader and the judge invocation are unchanged.
