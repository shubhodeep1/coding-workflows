<!-- agents: section="Workflow architecture" -->
**Workflow log analysis report delivery via PR (project #9116, P1).** In `workflow-log-analysis.yml`, job `analyze-commit-notify`, step `Commit and push report` (`id: commit_report`) keeps the purge, commit and retry-with-rename loop, but with `WORKFLOW_LOG_ANALYSIS_REPORT_VIA_PR` (default `true`) it rebases onto the dispatch branch and force-pushes only the run-unique `auto/workflow-log-analysis-report-<run_id>-<attempt>` branch (regex-guarded). It then lints a fixed PR body with `scripts/lint_pr_body_auto_close.py`, runs `gh pr create` once (an "already exists" reply is resolved with `gh pr list`), and tries `gh pr merge --squash --match-head-commit <HEAD>`, then the same with `--auto`, and otherwise leaves the PR open with a `::warning::` and exit 0. After `--auto` succeeds it polls the target branch with `git fetch` + `git cat-file` (no API call) for up to `WORKFLOW_LOG_ANALYSIS_REPORT_MERGE_WAIT_MINUTES` (default 10, 0-20, invalid values warn and use 10; the deadline is clamped to 55 minutes after the job started, `WLA_JOB_START_EPOCH`, which the `Resolve AI engine` step records; the poll interval `WORKFLOW_LOG_ANALYSIS_REPORT_MERGE_POLL_SECS`, default 30, is a script-environment override for tests that a repository variable does not reach) and records `pr_merged` once the report is there; otherwise it warns that deep-audit and api-redundancy are skipped and that a caller reading the newest report from the branch (comprehensive-test-and-release.yml Phase 2) sees the previous one. The rename-on-collision loop also treats paths on other pending `auto/workflow-log-analysis-report-*` branches (listed with `git ls-remote`, fetched into `refs/remotes/wla-pending/*`, the run's own branch excluded) as taken. The run-branch push uses `--force-with-lease`: empty on the first push, and on a retry the branch's remote head read with `git ls-remote`, so a push that landed while the client saw a failure does not exhaust the retries. An unrecognized `WORKFLOW_LOG_ANALYSIS_REPORT_VIA_PR` value warns (without printing it) and keeps PR mode. The PR number is read from any `.../pull/<n>` URL, so GitHub Enterprise Server works. When the step fails or is cancelled after the analysis completed, the Telegram step (`WLA_COMMIT_OUTCOME`) sends a WARNING instead of a report link, naming the run branch only in PR mode. A report PR that did not land (`pr_open`, or `pr_auto_merge` after the wait) is also sent at WARNING with the PR link. Report PRs are ordinary pull requests: PR CI and `internal-review.yml` run on them (no head-ref skip exists for this branch prefix). Never `--admin`. After a direct merge it deletes the run branch fail-open. `false`/`0`/`no`/`off` restores the unchanged direct push to `GITHUB_REF_NAME`. The analyze step's `report_file` reaches the step through `env:` (`WLA_ANALYZE_REPORT_FILE`) and must match `^analysis/workflow-optimization-YYYY-MM-DD(-N)?\.md$`. The step outputs `committed` and `report_file` are unchanged; `delivery`, `report_pr_number`, `report_pr_url` and `report_branch` are new, and the job exposes `report_delivery`. `deep-audit` (and so `api-redundancy`) runs only when `report_delivery` is empty, `pushed` or `pr_merged`, because it reads the report from the target branch. The job has its own `permissions:` block (the workflow-level grants plus `pull-requests: write`). Contract tests: `tests/test_workflow_log_analysis_report_pr.py`, collected by `tests/test_workflow_log_analysis_failure_contract.py`.
