<!-- agents: section="Workflow architecture" -->
**Workflow log analysis report delivery via PR (project #9116, P1).** In `workflow-log-analysis.yml`, job `analyze-commit-notify`, step `Commit and push report` (`id: commit_report`) keeps the purge, commit and retry-with-rename loop, but with `WORKFLOW_LOG_ANALYSIS_REPORT_VIA_PR` (default `true`) it rebases onto the dispatch branch and force-pushes only the run-unique `auto/workflow-log-analysis-report-<run_id>-<attempt>` branch (regex-guarded). It then lints a fixed PR body with `scripts/lint_pr_body_auto_close.py`, runs `gh pr create` once (an "already exists" reply is resolved with `gh pr list`), and tries `gh pr merge --squash --match-head-commit <HEAD>`, then the same with `--auto`, and otherwise leaves the PR open with a `::warning::` and exit 0. Never `--admin`. After a direct merge it deletes the run branch fail-open. `false`/`0`/`no`/`off` restores the unchanged direct push to `GITHUB_REF_NAME`. The analyze step's `report_file` reaches the step through `env:` (`WLA_ANALYZE_REPORT_FILE`) and must match `^analysis/workflow-optimization-YYYY-MM-DD(-N)?\.md$`. The step outputs `committed` and `report_file` are unchanged; `delivery`, `report_pr_number`, `report_pr_url` and `report_branch` are new, and the job exposes `report_delivery`. `deep-audit` (and so `api-redundancy`) runs only when `report_delivery` is empty, `pushed` or `pr_merged`, because it reads the report from the target branch. The job has its own `permissions:` block (the workflow-level grants plus `pull-requests: write`). Contract tests: `tests/test_workflow_log_analysis_report_pr.py`, collected by `tests/test_workflow_log_analysis_failure_contract.py`.
