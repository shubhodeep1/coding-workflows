- **Merge-lease forward-merge priority (merge-lease parallel merges Phase 3, Refs #9781).** `_merge_lease_order_key <pr> <labels> [<head_ref>]` in `scripts/pr_checks_lib.sh` returns `0<pr>` (12-digit zero-padded) for a PR carrying a `MERGE_TRAIN_PRIORITY_LABELS` label or, new, a `<head_ref>` starting with an entry of `MERGE_LEASE_PRIORITY_HEAD_PREFIXES` (default `auto/forward-merge-stable-`, set in the helper and wired as a repository variable with the same default (#9821); comma-separated literal prefixes, trimmed, no globs; empty, `none` or `off` turns it off, but an empty repository variable falls back to the default through `||`, so only `none` or `off` turns it off from a repository variable), and `1<pr>` otherwise. With two arguments or an empty ref the output is unchanged. Forward-merge PRs join the label group, and inside it the lowest PR number wins.
  - `_merge_lease_queue_first` projects a fourth row field, the head ref, between the head SHA and the labels: `.head.ref` from the REST `pulls` listing when `.head.repo.full_name` is this repository, or `.head` from the `_mt_list_open_prs` rows when `.head_repo` is (case-insensitive, against `PR_CHECKS_REPOSITORY`/`GITHUB_REPOSITORY`). A fork head or an unknown repository gives an empty ref, so no priority; it never blocks a PR. Both call sites (the update-mode `_merge_lease_gate` and the `_mt_merge_lease_tick` grant) get the order with no extra API call; the tick rows must keep `head` and `head_repo`. Phase 2 grant-time eligibility still applies to a forward-merge waiter.
