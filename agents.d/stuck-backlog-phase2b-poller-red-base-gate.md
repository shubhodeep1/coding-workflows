Poller red-base gate (Refs #9421, stuck-backlog plan Phase 2 step 4; issue #9766): `_plan_auto_approval_gate` in `scripts/orchestrate_poll_process.sh` now runs `_plan_red_base_gate` first, before the trusted-login lookup, the heal-counterfactual check, the Q108 grant write and the test-only marker post. A held plan therefore gets no issue-body write and no comment. This replaces the "poller-side red check is not part of this phase" sentence in `agents.d/stuck-backlog-phase2-red-base-hold.md`: stall recovery's `auto_approve` arms and its `retrigger_implement` arms in `ai:awaiting-approval` no longer approve a plan while the tracked base is red.

Branch checked: the managed callers in `execute_stall_recovery_action` pass the project's `integration_branch` from `STATE_FILE` (a local read) as the gate's optional 5th argument. It is used only when the issue's labels in the batched details map include `ai:orchestrator-managed`. Otherwise, and for the two standalone callers, the default branch is used: `CWS_DEFAULT_BRANCH`, then the shared `_STALL_STANDALONE_DEFAULT_BRANCH` memo, then one `repos/<repo>` read per process.

Trust rule (same as `plan.yml`): `_red_base_gate_load_helper` sources `scripts/plan_base_ci_gate.sh` only when `PLAN_BASE_CI_GATE_STAGED=true`, the file is a regular non-symlinked file, it sources cleanly and it defines `red_base_approval_hold_check`, `_red_base_hold_flag_on` and `_red_base_hold_log`. Otherwise one `::notice::` is printed per process and nothing is held. `orchestrate_poll.yml` "Stage workflow support files" installs the helper from `.codex-workflow-src`, then `.codex-workflow-src-main`, and writes the flag to `$GITHUB_ENV`. When neither source has it, the step removes the checkout copy and writes `false`. The five poller steps that carry `AUTOMATION_PATH_PLAN_AUTO_APPROVAL_ENABLED` also get `RED_BASE_APPROVAL_HOLD_ENABLED` (default `true`) and `RED_BASE_HOLD_WORKFLOWS` (default `.github/workflows/ci.yml`). The script defines the same defaults, plus `PLAN_BASE_CI_GATE_STAGED=false`.

Cache: `RED_BASE_HEALTH_CACHE` is a per-process (one poller step, one tick) associative array keyed by branch. Each value is `status|reason|red|heal|workflow|run_id`, taken from the helper's `RED_BASE_HOLD_*` globals. A cache hit restores those globals and replays the per-issue `RED_BASE_APPROVAL_HOLD` line through `_red_base_hold_log`. Read failures (`runs_lookup_failed`, `heal_lookup_failed`) are cached, so they are not repeated per issue. `disabled`, `heal_issue_exempt` and `input_invalid` results are never cached. API cost: at most 1 runs read per configured workflow plus 1 heal listing per branch per poller step. The poller gate makes no comment read and no post.

Logs on a hold: `RED_BASE_APPROVAL_HOLD outcome=held ...`, then `AI_PHASE_GATE_V1 phase=stall_recovery gate=auto_approve reason=base_ci_red outcome=hold issue=<n> heal=<N> branch=<branch>` and `STALL_SKIP issue=<n> reason=base_ci_red_hold phase=<phase> action=none`. The gate returns 1, so the callers return before `STALL_RECOVERY_SHOULD_INCREMENT` is set and no recovery attempt is counted. Every read fails open. A base that turns green during a tick is picked up on the next tick.

Tests: `tests/test_plan_base_ci_gate.py` (`test_poller_red_base_gate_*`).
