- **Unblock judge protected-path handoff (#7060).** With `UNBLOCK_PROTECTED_HANDOFF_ENABLED=true` (default `false`), a `scope-blocked` issue whose newest pipeline-authored guard comment is an `ai:guard-rejection:v1 ... guard=automation-path` marker (`unblock_ledger.py protected-rejection`, parsed separately from `REJECTION_RE`, so `override_guard` stays unavailable) gets an operator handoff for `descope` / `operator_step` instead of a fix-up. The ops run in this order: the `ai:operator-step` entry, then a comment ending in `<!-- ai:unblock-wait:v1 item=<n> reason=operator_handoff run=<r> -->`, then a WARNING; a failed operator-step write skips the hold comment, so the next run retries. The issue stays blocked. A later run with that trusted marker newer than the rejection skips before `decide` (`reason=operator_handoff_pending`) and refreshes the hold comment in place, so the poller's scan (`UNBLOCK_JUDGE_RETRY_HOURS` on the marker's `updatedAt`) does not re-dispatch it. Other stops ignore the rejection, so an old handoff cannot hold a later, unrelated block. `dormant_until` is set only for an `_UNSET_OPERATOR_STEP` placeholder.
