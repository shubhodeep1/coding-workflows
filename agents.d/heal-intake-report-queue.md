<!-- agents: section="Workflow architecture" -->
Heal intake report queue: `.github/workflows/workflow-failure-heal-intake.yml` no longer serialises intakes with one shared concurrency group. GitHub keeps one pending run per group and cancels it when a newer run is queued, so a burst of `repository_dispatch` reports lost every report but the first and the last before any job started (about 15 cancelled runs on 2026-10-21; nothing was logged, and GitHub keeps no payload for a cancelled run). With `HEAL_INTAKE_QUEUE_ENABLED` on (any value but `false`), the workflow-level group is `workflow-failure-heal-intake-run-<run_id>` and the recovery-scan job's is `workflow-failure-heal-recovery-scan-<run_id>`. Both jobs run `scripts/workflow_failure_heal_queue.sh acquire` from their trusted checkout before any engine setup, and `release` (`if: always()`) right after their work. `acquire` finds the lowest-numbered open `ai:heal-intake-queue` issue by the GH_PAT login, opening one when none is open (a loser of a create race closes its own as a duplicate). It posts a ticket whose last line is `<!-- ai:heal-intake-queue:v1 run=<id> attempt=<n> job=intake|recovery-scan -->` and polls the comments every `HEAL_INTAKE_QUEUE_POLL_SECONDS` (20). It goes once `workflow_failure_heal.py heal-queue position` finds no older live ticket by that login. A ticket is stale, and is deleted by the waiter, when it is older than `HEAL_INTAKE_QUEUE_LEASE_SECONDS` (10800), its run has completed or moved to a later attempt (the holder's run is read at most once per `HEAL_INTAKE_QUEUE_HOLDER_CHECK_SECONDS`, 300), or it is an earlier ticket of the waiting run itself. `acquire` exports `HEAL_INTAKE_QUEUE_ISSUE`, `HEAL_INTAKE_QUEUE_TICKET_ID` and `HEAL_INTAKE_QUEUE_WAITED_SECONDS`, and `scripts/workflow_failure_heal_intake.sh` adds the wait to `WORKFLOW_HEAL_REPORT_MAX_AGE_SECONDS`. The queue fails open and never drops a report. A missing login, issue or ticket, unreadable comments, a lost ticket, or `HEAL_INTAKE_QUEUE_MAX_WAIT_SECONDS` (4800) let the run proceed unlocked with one WARNING. Job timeouts are 130 minutes (intake) and 175 (recovery-scan). `HEAL_INTAKE_QUEUE_ENABLED=false` (any letter case, as GitHub expressions compare) restores the shared `workflow-failure-heal-intake` group for both jobs and turns the steps into no-ops. The recovery scan's `intake_busy` skip stays for that mode.
