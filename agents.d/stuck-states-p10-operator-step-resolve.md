<!-- agents: section="Workflow architecture" -->
- **Operator steps only for real human work; the tracker resolves and closes itself (stuck-states P10, Refs #8291).** Activation verification (`scripts/activation_verify.sh` `activation_normalise_verdict`) marks a gap whose cleaned `dormant_until` is exactly `@stable contains <7-40 hex>` as a release wait: `kind` is forced to `code`, `open_pr` to null, and each normalised gap gains a `release_wait` boolean. Release waits are listed in the verdict comment as `(ships with the next @stable release; nothing to do)`, never go into the activation-fix issue or the `ai:operator-step` issue, and log `op=release_waits count=<n> outcome=left_to_release`; the prompt keeps its "never list promoting `main`, tagging `stable`, or the consumer sync" rule and adds this as the fallback shape. `scripts/operator_step_issue.py resolve --repo OWNER/REPO [--trusted-login LOGIN]` runs from the poller step "Resolve operator steps" (`.github/workflows/orchestrate_poll.yml`, right after "Run worktree registry GC", `if: !cancelled()`, `continue-on-error: true`). It reuses tick's recorded condition (newest trusted entry comment per key with unticked boxes, a `source-sha` line and no `done` marker), reads `commits/stable` once and compares `<source>...<stable commit>`, at most 10 per run, oldest comment first (the rest are `compare_cap`); only `ahead` or `identical` posts tick's superseding comment (`ticked by the poller.`), anything else or a failed call fails closed. When no trusted entry comment and no legacy body section has a `- [ ] ` line left and at least one entry exists, it re-reads the comments (a new entry defers: `close_deferred`), PATCHes `state=closed state_reason=completed`, then re-reads once more and reopens on a new unticked entry or a failed re-read. `upsert` reads the tracker state after posting an entry and reopens a closed tracker (`reason=entry_after_close`). Entries without a source commit (unblock steps, legacy sections) are never auto-ticked. The needs-human digest is never touched. API budget: one listing per tick when no tracker is open; otherwise at most one identity read, one paginated comment read, one `commits/stable` read, at most 10 compares, one POST per ticked key, and when closing two re-reads and at most two PATCHes; `upsert` adds one issue read per posted entry. Kill switch `OPERATOR_STEP_AUTO_RESOLVE_ENABLED` (default `true` in the helper and the workflow): `false` makes `resolve` a no-op with no API call. `upsert`'s reopen check reads the same variable but only where the calling step's environment sets it; the activation-verify steps do not map it, so there it stays on (a failed check only logs `reason=recheck_failed` and never fails the upsert). `tick` (nightly promote cycle) is unchanged.
