- **Per-PR checks are one job (`.github/workflows/pr-checks.yml`, 2026-11-18).** The workflow `PR checks` replaced `lint-pr-body-auto-close.yml` and took over every non-label event of `integration-pr-readiness.yml` (`docs/plans/fold-per-pr-checks-plan.md`, CLAUDE.md §33.A). Its single job `pr-body-lint` runs two step groups on `pull_request` (`opened`, `edited`, `synchronize`, `reopened`, `ready_for_review`) into `main` or `stable`:
  - PR-body lint (CLAUDE.md §19): `scripts/lint_pr_body_auto_close.py` over the PR title, body and, for PRs into the default branch, commit messages. Its verdict is the job result, reported as the check-run `pr-body-lint`, which `ORCH_FINAL_MERGE_REQUIRED_CHECKS_DEFAULT` lists.
  - Integration PR readiness: `scripts/check_integration_pr_readiness.py` posts the commit status `orchestrator/integration-pr-not-ready`. Its verdict is that status. Both readiness steps are `continue-on-error`, so a failed tracking-issue read or status POST (a fork PR's token is read-only) never turns `pr-body-lint` red; before the fold such a failure failed only the `readiness` job, which no gate reads.
  - Every step after the checkout has `if: !cancelled() && …`, so a failure in one group does not skip the other, and a step still waits for the steps of its own group (`steps.<id>.outcome`). The lint step does not run after a failed commit read.
  - Label events stay in `integration-pr-readiness.yml` (`labeled` / `unlabeled` only; its `readiness` job runs for `ai:override-incomplete-merge` and is skipped for any other label). They must not reach `pr-checks.yml`: a job skipped by `if:` reports a `skipped` check-run, GitHub and `_pr_ruleset_required_check_blockers` read the newest check-run of a name, and `skipped` counts as passed, so a label change after a failed lint would hide it. For the same reason the `pr-body-lint` job has no job-level `if:`.
  - The readiness steps skip `edited` (the readiness check never ran on it; an edit changes nothing the script reads), so the status is posted on the same events as before the fold.
  - No `concurrency:` group, like the two workflows the job replaces. With `cancel-in-progress: false` a job for a superseded head that is still waiting for a runner would hold the current head's `pr-body-lint` behind it; with `true` the job could be cancelled while it writes the status; and with either, a newer `edited` run could replace a waiting `synchronize` run, so the readiness steps could no longer skip `edited`.
  - Do not rename the job or give it a `name:`: the job id is the check-run name the merge gate reads. Further per-PR checks with the same trigger, token and trust join this job as another step group. `lint-plan-archival.yml` is still a workflow of its own.
  - Permissions are the union: `contents: read`, `issues: read`, `pull-requests: read`, `statuses: write`. The job takes no secret. Tests: `tests/test_pr_checks_workflow.py`.
