Auto-heal remediation no-code guard (`REMEDIATION_NO_CODE_GUARD_ENABLED`, default `true`). `scripts/implement_commit_changes.sh` runs it on the staged set (`git -c core.quotePath=false diff --cached --name-only --no-renames --diff-filter=ACMDT`, the automation-path guard's query, so a non-ASCII doc or test name stays literal and a code file moved under `tests/` still counts as code) right after the commit-time `files_touched` scope guard and before `git commit`. It calls `scripts/files_touched_scope_guard.py --remediation-no-code-check --issue-body-file "${ISSUE_BODY_FILE}" --staged-file F`, which prints one JSON record (`outcome`, `reason`, `count`, `paths`) and exits 40 only when a body line outside a ``` / ~~~ fence opens (up to 3 leading spaces) with `<!-- auto-heal-remediation:v1` (`is_auto_heal_remediation_body`; a verbatim re-issue copy still matches, a backticked or quoted mention does not; no author check, because the rule only restricts) and every staged path is non-code (`is_remediation_non_code_path`: a `.md` file anywhere, or a path under root-level `tests/`, `docs/`, `changelog.d/`, `agents.d/` or `db/contracts/`). Allow reasons: `not_remediation`, `no_paths`, `code_changed` from the helper, and `prior_pr_baseline` (the run started from a prior PR's branch, `PRIOR_PR_BASELINE_BRANCH` from `steps.baseline_refctx.outputs.branch`, set only when `steps.checkout_baseline.outcome == 'success'` because a failed baseline checkout falls back to the default ref; that branch may already hold the code change) and `helper_error` from the shell. On exit 40 the step writes `scope_violation_blocked=remediation-no-code`, `scope_violation_count` and `scope_violation_files` and exits 1, so nothing is committed or pushed and no PR is opened. `scripts/implement_handle_guard_block.sh` then latches `ai:scope-blocked` (redispatch is refused by "Validate approval phase label") and posts one comment whose first line is `🚨 **Auto-heal remediation guard rejected this implementation run: no code change.**` (listed in `GUARD_REJECTION_HEADERS` of `scripts/unblock_ledger.py`) and whose last line is `<!-- ai:guard-rejection:v1 item=<n> guard=scope reason=remediation-no-code ... -->`; that reason is never `override_guard`-eligible. `scripts/workflow_failure_heal_report.sh` logs `skip reason=remediation_no_code_park` and dispatches nothing when the newest guard-rejection marker for the issue written by the reporter's own login carries that reason; without a readable login, or when a newer guard-rejection comment has no marker, it reports as before. For this reason only, the handler posts the comment before it adds the label (other scope reasons keep label-then-comment), so the `issues: labeled` reporter can already read the marker; the comment states the label is applied next instead of the label read-back, which still logs `::error` and reaches Telegram when the latch fails. The unblock judge treats the parked issue like any other `ai:scope-blocked` item. The guard reads only files already on disk (no API call) and fails open: toggle off, `HEAL_ROUTE=true`, no `ISSUE_BODY_FILE`, an empty staged set, a failed `mktemp`, a missing helper or any helper exit other than 0 or 40 all let the commit proceed. The review gate (`scripts/review_autofix_step_evaluate_gate.sh`) is not involved. Tests: `tests/test_files_touched_scope_guard.py` (`test_remediation_*`, `test_guard_handler_*`, `test_heal_reporter_skips_remediation_no_code_park`), `tests/test_workflow_failure_heal.py` (`test_reporter_skips_remediation_no_code_park`).
