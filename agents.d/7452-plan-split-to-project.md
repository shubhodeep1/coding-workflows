Plan split to a project (Q151/Q152/Q164). The pipeline plan grant covers at most 50 files. When a pipeline-authored issue's plan lists more, `files_touched_scope_guard.py --plan-auto-approval-gate` holds with `reason=plan_too_large_for_grant` and `plan_path_count`, unless the implement-time automation-path check would refuse the plan anyway (for example `ALLOW_WORKFLOW_EDITS=false`, which keeps `reason=workflow_edits_disabled`). The plan stage then runs `scripts/plan_split_dispatch.sh` instead of holding:

- It starts `internal-orchestrate.yml` (this repo) or `ai-orchestrate.yml` (consumers) with `engine=claude`. The `project_description` carries the issue title, the full plan text, and instructions to keep the plan's phases, give every issue at most 50 `files_touched` entries, and put the phase that switches a behaviour on last. The `tracking_comment` starts with `<!-- ai:plan-split-source:v1 issue=N -->`.
- Before the dispatch, the source issue moves from `ai:awaiting-approval` to `ai:split-to-project` and then gets `<!-- ai:plan-split:v1 issue=N wrapper=... -->` from the pipeline account, so the orchestrator run always sees the label. A failed label change or marker comment holds the plan without a dispatch. The step outputs `plan_split=true`, so no "plan awaiting approval" alert is sent. The dispatch is never retried, because a dispatch that timed out may already have started a project. A dispatch rejected with an HTTP 4xx status started nothing: the script removes the label (restoring `ai:awaiting-approval`), then posts a release marker, and holds. Any other dispatch failure may have started a project: the label stays, a release marker with instructions is posted, a WARNING is sent (`outcome=dispatch_unconfirmed`), and a person removes the label and comments `/reclarify` if no tracking issue appears.
- `orchestrate.yml` comments the tracking-issue link on an open source issue that carries `ai:split-to-project`. If its run fails before a tracking issue exists, the "Release plan-split source issue" step removes the label and only then posts `<!-- ai:plan-split-released:v1 issue=N -->`, because the dispatcher checks the label before the markers. A split marker followed by a release marker no longer counts as a split, so a `/reclarify` can hand the plan to a new project.
- When the project's status is `complete`, the poller (`close_plan_split_source_if_needed`) closes the source issue as completed. It acts only on a marker comment from a trusted author (OWNER/MEMBER/COLLABORATOR or `github-actions[bot]`), and only if the issue is open and carries the label. The outcome is kept in the state file as `.plan_split_source`, so this costs one issue read once. A failed project leaves the source issue open.
- The plan is held as before (`exit 3`) when `PLAN_SPLIT_TO_PROJECT_ENABLED=false`, the issue is a project child (`ai:orchestrator-managed` or `Managed by: AI Orchestrator`), it is already split (label or marker), the wrapper is missing or switched off, the description is over 60,000 characters, the source issue cannot be marked, the consumer wrapper predates the `tracking_comment` input, or the dispatch is rejected. Plans held before this change are not split; `/reclarify` re-plans them.
