**Heal occurrence counter comment (Refs #9200).** With `HEAL_OCCURRENCE_IN_PLACE_ENABLED` on (default), the heal intake records repeat reports of a failure in one comment per heal issue and edits it in place (`_heal_record_occurrence` in `scripts/workflow_failure_heal_intake.sh`, `merge_occurrence_comment` in `scripts/workflow_failure_heal.py`). The comment's first line is still `<!-- workflow-failure-heal:occurrence -->`; its second line is `<!-- workflow-failure-heal:occurrence-count:v1 count=<n> first=<UTC> last=<UTC> -->`, followed by the newest 10 reports, newest first, each under `<!-- workflow-failure-heal:occurrence-entry:v1 n=<n> at=<UTC> -->`. Only a counter written by the account the intake posts as is edited (an earlier `/user` result of the run is reused, else one `/user` read); the first counter on an issue starts at the number of single-report occurrence comments already there plus one, with `first=` set to the oldest of them. Run-volume plan D18 left edit-in-place out because readers order markers by `created_at`; the two readers of occurrence comments are adapted instead: `_recovery_occurrence_runs` reads the entries one by one and never combines lines of two reports, and `heal_stale_decision` moves its anchor to the count line's `last=` time as well as to the `created_at` of a trusted occurrence comment. The poller hands `heal_stale_decision` only an issue's newest 20 comments (`comments(last: 20)` in `_fetch_candidate_issue_details_graphql`), so a counter with 15 or more newer comments after it is posted again as a new comment and the old one is deleted (`occurrence_update outcome=reposted`). `_recovery_occurrence_runs` sees only the kept entries, so a report older than the newest 10 can no longer supply the failed run of a marker-less heal issue. Cost (§15): one paginated comments GET per repeat report (also on the heal-scope recovery path, whose earlier read predates the diagnosis), then one `PATCH` (or the one `POST` as before, plus one `DELETE` on a re-post). Every failure falls back to posting a comment. The read-modify-write is not locked: two intakes handling the same issue at the same moment can lose one report's entry and one count.

**Heal-of-heal and fixture reports.** With `HEAL_SOURCE_DEDUPE_ENABLED` on (default), the intake passes `--report-issue <repo>#<n>` to `budget` for a `phase_failure` report; when that issue is an open listed heal issue and there is no fingerprint, source or cause duplicate, the decision is `duplicate` with `match: heal_source` and the report becomes an occurrence on that heal issue. It is neither diagnosed nor escalated: `escalate reason=heal_issue_failed_itself` stays reserved for a run that fails with the issue's own fingerprint (or cause), and stall recovery's budgets bound the retries. A defect that only ever fails on heal issues therefore gets no heal issue of its own. The skip gate `smoke_test_fixture` now also matches the titles `[E2E Orchestrate Smoke ...]` and `[E2E Clarify Negative Test ...]`, whose issues carry no `e2e-smoke-test` label.
