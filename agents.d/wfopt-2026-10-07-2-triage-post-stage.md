Check-failure triage post-step stage codes (Refs #9033): the `Post check-failure triage issue` step of `.github/workflows/check_failure_triage.yml` prints exactly one `CHECK_TRIAGE op=post stage=<code> pr=<n>` line on every exit path except the unchanged `CHECK_TRIAGE op=supersede outcome=skip_create` exit 0 (and `cd`/`source`/check-name sanitiser failures, which have no code). In order: `body_missing` (`${RUNTIME_DIR}/issue_body.md` empty or absent), `marker_invalid` (the redaction/marker/truncation Python check failed; a missing or malformed `triage_metadata.json` also lands here because that check reads the fingerprint), `metadata_invalid` (a `jq -er` read of `fingerprint`, `generation` or `root` failed), `token_missing` (`GH_TOKEN`, i.e. `CHECK_TRIAGE_ISSUES_TOKEN`, is empty; tested for emptiness only, never printed, and checked after the supersede gate so the skip path is unchanged), `create_failed http_class=<4xx|5xx|unknown> attempts=1` (`gh_retry gh issue create` failed; its stderr goes to `${RUNTIME_DIR}/triage_post_create_stderr.txt`, which is never printed or uploaded, and only the class of the first `HTTP NNN` token is logged; `attempts=1` because `gh_retry` makes one attempt for creates), `url_missing` (the create returned no URL) and `created` (printed right after the unchanged `CHECK_TRIAGE created issue=...` line). Every failure code still fails the step with `exit 1`; no lookup call follows an ambiguous create, so find a possible duplicate by the body's `fp=` marker. `tests/test_check_failure_triage_post_stage.py` pins the codes and runs the step against a stub `gh`.
