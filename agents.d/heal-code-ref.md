Heal code-ref routing (P6 step 1 of `docs/plans/heal-evidence-reproduction-and-trends-plan.md`, Refs #8434): behind `WORKFLOW_HEAL_CODE_REF_ROUTING_ENABLED` (default `false` in `scripts/workflow_failure_heal_intake.sh` and in both the `intake` and `recovery-scan` jobs of `.github/workflows/workflow-failure-heal-intake.yml`; only the literal `true` turns it on), `_heal_code_ref_route` runs in the Route block's `workflow-defect|inconclusive` arm after today's target is chosen (failed run branch, mirror mapping, wrapper pin) and before the existing `_branch_exists` check, so the override lands before `_open_issue` renders the routing header. It qualifies only this repository's `workflow_run` reports (`autofix_failure` reports with a `script_ref` get the body line only, never a retarget; anything else is `not_eligible`). `workflow_failure_heal.py code-ref` (pure, never calls `gh`) picks the child run: the last eligible run the failed logs link to (same `select_linked_runs` order, read from `${RUNTIME_DIR}/linked_runs/` and `${RUNTIME_DIR}/code_ref/`), else the newest eligible issue-linked run by `created_at` from P1's `${RUNTIME_DIR}/evidence_pack_api/issue-<n>.json` + `runs-page-<n>.json` (same title and repository filter as `issue_linked_runs`, shared through `_issue_linked_run_matches`). `code_ref_run_eligible` requires the run's `repository.full_name` (and `head_repository.full_name` when the key is present; a null value fails closed) to be the source repository, a valid `head_branch` and `head_sha`, a `.github/workflows/` `path`, a branch that is not an `orchestrator/project-<N>` integration branch, an `ai/issue-<N>` heal fix branch or the `promote-candidate` mirror, and a failed or stalled run (`failure|timed_out|cancelled|startup_failure`, not `completed`, or such a job/step conclusion). It retargets only when the child's branch differs from both the failed run's `head_branch` and the current target, its `path` is in the frozen `scope_inputs_frozen.json` `.self_workflows` (read only), and a routing probe (`validate_heal_issue_body_routing` on the five marker lines plus the `Target branch:` line) accepts it; then `TARGET_BRANCH_SOURCE=code_ref`. If the branch does not exist, the branch-exists block's `code_ref` arm restores the prior target and source and re-checks it with today's logic. A helper failure keeps today's target. API budget (CLAUDE.md §14): 0 calls when P1 is on (its issue-linked data is reused); with P1 off, `code-ref-requests` returns the log-linked ids with no cached `linked_runs/run-<id>.json`, and the intake makes at most 3 single-attempt `GET repos/<repo>/actions/runs/<id>` (`GH_RETRY_MAX_ATTEMPTS=1`, same identity and repository checks as `_heal_fetch_linked_runs`); issue-linked runs are not looked up with P1 off. The body gains `- **Code ran from:** <branch>@<sha>` after the `Head SHA` line (`render_code_ran_from`, re-validated in `compose-issue --code-ran-from`; with no qualifying child, the payload `script_ref` renders `stable@unknown` or `unknown@<sha>`); it is not a routing key. With the switch off nothing runs, no log line is written and the body is byte-identical.
