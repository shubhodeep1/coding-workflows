Engine-fallback heal scope (2026-10-23 design review): an `engine_fallback` report now names its reporting run. `scripts/ai_engine_fallback_report.sh` passes `GITHUB_RUN_ID` and `GITHUB_RUN_ATTEMPT` to `workflow_failure_heal.py build-engine-fallback-payload --run-attempt`, which writes `reporter_run: {run_id, run_attempt}` (attempt 1 when unset). `run_refs` stays empty, so claim binding, provenance and log reading are unchanged. `validate-payload` keeps a well-formed `reporter_run` and drops a malformed one without failing the report. Only on the `open` budget decision, `scripts/workflow_failure_heal_intake.sh` reads the run once (`GET repos/<source_repo>/actions/runs/<run_id>`) and `verify-engine-reporter-run` binds it: same repository, `name` equal to the report's `workflow_name`, `run_attempt` at least the claimed one, and the run still queued or in progress, or (any other status) last updated within `WORKFLOW_HEAL_REPORT_MAX_AGE_SECONDS`. A bound run sets `ENGINE_REPORTER_RUN_REF`, and the frozen scope inputs get that run plus `ENGINE_FALLBACK_SCOPE_PATHS` (`scripts/ai_engine.sh`, `scripts/claude_engine.py`, `scripts/codex_isolated_exec.sh`, `scripts/clarify_isolated_run.sh`, `scripts/review_untrusted_sandbox.sh`, `scripts/ai_engine_fallback_report.sh`, `.github/actions/install-claude/action.yml`, `.github/actions/claude-pool-token/action.yml`; each kept only if it exists at the scope commit). The heal issue is then filed in coding-workflows. A report whose role and reason fingerprint already has an open heal issue is recorded there as an occurrence before any run read. A `consumer-app-defect` verdict is filed as `workflow-defect` (`classification_remapped ... reason=engine_fallback_harness_scope`), because the scope names only harness code; the report has no issue number, so the issue already files here, and the remap gives it the default heal target branch (`stable`). A report with no `reporter_run` (an older reporter), or one whose run does not bind, keeps the quiet `skip reason=scope_unavailable_no_runs`. A bound run whose scope still does not verify is treated like any report that names a run: CRITICAL refusal. Each step logs one line under the existing `WORKFLOW_HEAL` prefix: `engine_reporter_run outcome=verified run=<owner/repo:N> attempt=<n>`, `outcome=rejected reason=run_unavailable|run_id_mismatch|run_not_in_source_repo|workflow_name_mismatch|run_attempt_mismatch|run_stale|no_reporter_run|verifier_error run_id=<n>` or `outcome=absent`, each followed by `fp= source=`.
