- **Security-pass marker re-read and cycle guard (#10176).** `single_pass_gate` in `scripts/review_single_issue_security_pass.sh` decides on `PR_ISSUE_COMMENTS_FILE`, the comments snapshot the `Collect PR metadata` step (`scripts/review_collect_pr_metadata.sh`) took when the job started. A review run can reach the gate long after that (merge-train wait, reviewer models), when an audit has already posted its markers; the gate then saw no marker, dispatched again and reused cycle 1 (PR #10175). Now the gate makes at most one fresh paginated comments read per run (`single_pass_fresh_comments`): when the snapshot is unusable (missing, empty or not an array), and right before a dispatch (after the `audit_throttled` check, so before any `pending` or `failed` marker is posted). A failed fresh read, or an empty one while the PR payload's `comments` count is 1 or more, holds with the existing `hold_reason=markers_unverifiable` and logs `detail=fresh_read_failed|fresh_read_empty`: nothing is dispatched, no marker is posted and no cycle is counted. When the fresh view holds other trusted markers than the snapshot, the gate re-enters itself once on that view (`SINGLE_PASS_GATE_REENTRY=true`; no second comments, `/user` or skip-check read), so a `status=clean` marker for the head ends `clean` and a fresh `pending` one holds `audit_pending`. The cycle guard then numbers the next marker `max(next cycle, highest trusted cycle + 1)` (`single_pass_next_free_cycle`); it reads, then posts, with no reservation, so two overlapping review runs on one PR can still pick the same number (pre-existing race, narrowed but not closed). Switches, both default `true` in the script (§8) and forwarded from repository variables to the "Single-issue security pass" step and the deterministic-skip-merge security-pass step, listed in `scripts/stage_switches.json`: `SECURITY_PASS_MARKER_REREAD_ENABLED` (fresh read, re-entry and the hold; `false` keeps the job-start snapshot only) and `SECURITY_PASS_CYCLE_REUSE_GUARD_ENABLED` (renumbering; with the re-read switch `false` the guard still reads once before a dispatch and continues on a failed read). The collect step writes a sidecar `${PR_ISSUE_COMMENTS_FILE}.source` with one line `<cache_hit|cache_miss|fallback|cache|direct|synthesized> <epoch>` (fail-open). `gh_pr_cached_read` records which path served the read when `GH_PR_CACHED_READ_SOURCE_FILE` names a file (default unset, nothing written): `cache_hit` with the epoch the cached entry was fetched, `cache_miss`, or `fallback` (live read, cache unavailable); `cache` is left only by an older staged helper. `sig_shim=on` means a `*/ai_comment_sig_shim.*` dir with an executable `gh` is anywhere on PATH (the gh call counter stays first). The gate's own comment posts (pending and failed markers) capture stderr and echo only the signing shim's allow-listed `AI_COMMENT_SIG` lines. Cause (issue change 4): the in-repo part, a gate deciding on the job-start snapshot where an empty or unreadable file looked like "no markers", is fixed by the above. The job-token fallback seen on the failing runs (comments posted by the PAT without a signature line) left no reason in their logs; the candidate the evidence points to (job-token refusal or the repository-wide job-token rate limit) is an external limit. `scripts/comment_signature.py` now logs every fallback reason so the next occurrence names it.

- `SINGLE_ISSUE_SECURITY_PASS` gate keys for the comments view (#10176, `scripts/review_single_issue_security_pass.sh`): `mode=gate pr= head= outcome=markers_read comments=<n|unreadable> markers=<n> author=<login> source=<cache_hit|cache_miss|fallback|cache|direct|synthesized|fresh|unknown> age_s=<n|unknown> sig_shim=<on|off>` once per view decided on, including the view a `markers_unverifiable` hold rejects (`markers=0`) (the snapshot, then `source=fresh age_s=0` for a fresh read; a re-entry logs its fresh view once; `source=unknown` when the `.source` sidecar is missing or not in that fixed set, with `age_s` from the file's mtime); `outcome=hold reason=markers_unverifiable detail=fresh_read_failed|fresh_read_empty [cycle=<used>]`; `outcome=reread reason=markers_changed` before the one re-entry; `outcome=cycle_renumbered from=<n> to=<m>`; `outcome=cycle_guard result=unverified detail=<...>` when only the guard switch is on and the fresh read fails. No token or secret is logged.
- `AI_COMMENT_SIG` fallback reasons (#10176, `scripts/comment_signature.py` and its embedded copy in `scripts/gh_helpers.sh`): every post that falls back to the caller's token logs `outcome=fallback reason=post_switch_off|job_token_missing|repo_mismatch|job_token_refused_cached|job_token_rate_limited|job_token_refused issue=<n>`; `job_token_rate_limited`, `job_token_refused` and `outcome=failed` add `status=<3 digits>` when the error names an HTTP status. `identity_unknown` and `body_too_long` keep `outcome=skip`.
