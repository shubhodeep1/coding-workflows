- **Failure-fingerprint markers (stuck-states P3a, producer side, Refs #8291).** The "Comment on issue failure" step of `.github/workflows/plan.yml` and `.github/workflows/clarify.yml` appends exactly one `<!-- AI_FAILURE_FINGERPRINT_V1 phase=<plan|clarify> fp=<12 hex> run=<run_id> -->` line to the end of the failure comment it already posts; the body prefixes in `PHASE_FAILURE_COMMENT_PREFIXES` are unchanged. The marker comes from `python3 "${SUPPORT_SCRIPTS_DIR:-scripts}/workflow_failure_heal.py" phase-failure-fingerprint` (`phase_failure_fingerprint`, pure): the failed step is the first `conclusion == "failure"` step of the jobs-API job whose `runner_name` is `$RUNNER_NAME` (same lookup as `review_autofix_step_assemble_failure_evidence.sh`), the error is the first failure-level check-run annotation that does not match `_GENERIC_ERROR_RE`, normalized with `normalize_error_line` (fallback `no-error-line` when the fetched annotations hold no usable line; a supplied annotations file that is missing, unparseable or not a list gives `reason=annotations_unavailable` (`step_unknown` when no failed step matches the runner) and no marker), and `fp = sha256("<phase>|<lowercased step>|<error>")[:12]`. `PHASE_FAILURE_FINGERPRINT_MARKER_RE` is a verbatim copy of `orchestrate_lib.FAILURE_FINGERPRINT_MARKER_RE` (orchestrate_lib.py is not staged for plan/clarify); a test pins the two patterns, and both Python and the step's bash re-check the marker before posting. The subcommand prints only `marker=` / `fp=` / `error_present=` / `reason=` and always exits 0. A marker is written only when `job.status == failure` and `STALL_FINGERPRINT_BREAKER_ENABLED` (default `true`) is truthy (`1|true|yes|on`, any letter case, matching the poller's `is_truthy`); the failed job's check-run id is taken from its `check_run_url`, falling back to `.id`; every error path fails open and posts the comment without a marker. Cost: 2 REST reads on a failed run, 0 otherwise.
