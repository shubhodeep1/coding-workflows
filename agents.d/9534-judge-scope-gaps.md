Judge scope gaps (issue #9534, Refs #9503): two changes stop a narrow judge-written `files_touched` list from stalling planning. (1) Scope companions: before `gh issue create`, the poller passes the body of a judge addition (`NEW_BODY`) or judge fix-up (`FIX_BODY`, `create_judge_fixup_issues_from_verdict`) through `apply_judge_files_touched_companions` in `scripts/orchestrate_poll_process.sh`. That helper calls `add_files_touched_companions`, a `python3 -I -B` program that imports `PIPELINE_PLAN_GRANT_COMPANIONS`, `extract_files_touched` and `normalize_path` from `scripts/files_touched_scope_guard.py`. It appends whichever of `tests/**`, `changelog.d/*` and `agents.d/*` is missing to the first `files_touched:` block, at that block's indent, including a list written flush with the key. Entries the judge wrote keep their text and order, and a body with no block is unchanged. Fails open (body unchanged, `reason=helper_failed`); 0 API calls; `JUDGE_FILES_TOUCHED_COMPANIONS_ENABLED=false` (default `true`, passed by every `orchestrate_poll.yml` step that runs the poller) disables it. The judge prompt also requires that a new issue reusing an existing workflow job or step list every script that job runs. (2) Planning scope routing: when the planner's only blocker is files outside `files_touched`, it emits `BLOCKED:` and then one `SCOPE_MISSING: <path>` line per file (`prompts/mode-plan.txt`, its template, and the inline prompt of `scripts/run_plan_codex.sh` that the plan run sends; keep the three in step). The router strips one surrounding pair of backticks and refuses any other backtick, quote or `$`. `plan.yml`'s "Route planning scope block" step (`id: route_scope_block`, same `if:` as "Handle blocked planning output", `continue-on-error: true`) runs `scripts/plan_scope_block_route.sh`. It finds the script in `SUPPORT_SCRIPTS_DIR` or else the support checkout; the legacy staging copies it as optional, and without the script the step logs `reason=helper_absent`. The script routes the block only when the switch `PLAN_SCOPE_BLOCK_ROUTING_ENABLED` (default `true`) is not `false`, the answer is not a `WAITING:` answer, the item is an issue and not a PR (from `ISSUE_META_FILE`), and there are 1-20 deduplicated, fence-free paths (a scope line after an unclosed fence opener logs `reason=unclosed_fence`). Each path must pass the `unblock_ledger._clean_path` rules with no trailing `/`, the body must have a `files_touched:` block, and no path may already be covered (`entry_matches`). A routed block writes `<!-- ai:guard-rejection:v1 item=<n> guard=scope reason=out-of-scope run=<run> count=<n> truncated=false paths=<b64> -->`, built like `guard_rejection_marker()`. The handler then opens the blocked comment with `🚨 **files_touched scope guard rejected this planning run.**` (now in `GUARD_REJECTION_HEADERS`, so a broken marker reads as `malformed`), keeps every existing line, puts the marker last, and adds `ai:scope-blocked` in the same `gh issue edit` as `ai:blocked` (its `ensure_label_exists` may make one `gh label create`; when that create fails the handler posts the unrouted comment and logs `reason=label_unavailable`). The label also starts the workflow-failure-heal report (`internal-workflow-failure-heal.yml`), as an implement-time scope block does. It never routes the open-PR wait reason. A person's `/answer` on the routed block removes `ai:scope-blocked` together with `ai:blocked` in the plan.yml transition edit, since implement.yml refuses to run while it is present. The unblock scan then picks stop `scope-blocked`, and `override_guard` keeps its path bans and 20-path cap. In `scripts/unblock_actions.py` an `override_guard` grant with a plan still posts `/approved`, except on a routed planning block (`ai:blocked` beside `ai:scope-blocked`; the implement-time guard never adds `ai:blocked`), where an older plan is never approved. Without a plan, or on that routed block, it follows the `reset_ops` guard-stop rule: `/reclarify`, remove the stop label, and for `scope-blocked` also remove `ai:blocked`, which `/reclarify` never clears. `reset_ops` itself applies the same routed-block rule, so `retry_budget`, `accept_with_followup`, a regrant and hold follow-ups also re-plan instead of approving the older plan, and drop `ai:blocked`. Tests: `tests/test_plan_scope_block_route.py`, the `judge_companions` tests in `tests/test_orchestrate_poll_process.py`, the planning-scope tests in `tests/test_unblock_judge.py` and `tests/test_plan_clarify_blocked_output.py`.
