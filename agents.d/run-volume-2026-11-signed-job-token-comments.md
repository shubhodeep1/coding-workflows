<!-- agents: section="Workflow architecture" -->
Signed job-token comments (run-volume plan item 15, decision D16, `docs/plans/reduce-actions-run-volume-plan.md`). Opt-in by the repository secret `AI_COMMENT_SIGNING_SECRET`. With it unset, nothing changes and every rule in the job-token comments note above still holds. With it set, the author-trusted kinds that note keeps on `GH_PAT` (security-pass markers, attempt journal, autofix editor summary, orchestrator state, merge-base sync, phase markers) move to the job token too, and so do all other pipeline comments that cannot start work.

- **Where it hooks in.** `scripts/gh_helpers.sh` (`_ai_comment_sig_activate`, run when the file is sourced) writes a `gh` shim and an embedded copy of `scripts/comment_signature.py` into `${RUNNER_TEMP}/ai_comment_sig_shim.*` and puts the shim first on `PATH`. Inside Actions it also appends that dir, and nothing else, to `GITHUB_PATH`, so every later step of the job goes through it, including Python scripts run straight from a step. The shim finds the real `gh` and its signer itself, and passes every call through in a step that does not hold the secret. `tests/test_comment_signature.py` keeps the embedded copy byte-identical to the `.py` file: edit the `.py`, then re-embed it. Every `gh` call that is not a comment create, a comment body edit or a comments read execs the real binary.
- **Create.** `POST repos/<this repo>/issues/<n>/comments` (any of `-f/-F body=`, `--input`, `gh issue|pr comment --body/--body-file`) whose body contains none of `/approved`, `/answer`, `/reclarify`, `Clarification required`, and no `(?im)^\s*implementation\s+plan\b` line, is posted with `AI_COMMENT_JOB_TOKEN` (`github.token`). It carries a last line `<!-- ai-comment-sig:v1 repo=<owner/repo> issue=<n> as=<GH_PAT login> type=<User|Bot> sig=<hmac> -->`, where the HMAC-SHA256 covers repository, issue number, login, account type and body. The body match ignores case, like the wrappers' `contains` / `startsWith`. Everything else keeps the caller's token, unchanged: those comments are what start the `issue_comment` wrappers, and the hardened plan-approval jobs in `ai-implement.yml` / `ai-plan.yml` read plan comments by the approver login with their own inline code. A refused job token (401/403) falls back once to the caller's token and is remembered for the job; any other failure is not resent.
- **Read.** Every `GET .../issues/<n>/comments`, `.../issues/comments[/<id>]` and every `gh api graphql` response is normalized before `--jq` runs (`jq -rcS`, per page, like `gh`; a `jq` error exits 1). A REST comment by `github-actions[bot]`, or a GraphQL node whose `author.login` is `github-actions`, with a valid signature comes back as the signed account: `user.login`/`user.type` (GraphQL: `author.login`, `author.__typename`), `author_association`/`authorAssociation` `OWNER` (repository owner) or `COLLABORATOR`, and the signature line removed from `body`. The signed repository and issue must match the object's own `issue_url` or `url` when it has one. Readers that trust the `GH_PAT` login, over REST or GraphQL, therefore need no change. A bot comment with no or a bad signature is returned unchanged, so it stays untrusted. The create response is normalized the same way.
- **Edit.** A body edit of a validly signed bot comment is re-signed for the same account (one extra `GET issues/comments/<id>`). An edit of any other comment is passed through.
- **Plumbing.** The reusable workflows that post or read comments declare the optional `workflow_call` secret `AI_COMMENT_SIGNING_SECRET`. Every step or job `env` map that sets `GH_TOKEN`, `GH_PAT` or `GITHUB_TOKEN` from `secrets.GH_PAT` also sets `AI_COMMENT_SIGNING_SECRET` and `AI_COMMENT_JOB_TOKEN` (`github.token`), so exactly the steps that hold the PAT hold the key and nothing else does. `AI_COMMENT_SIGNING_POST` is workflow-level `env`. The same applies to the release, sweep, heal-intake, validation-intake and log-analysis workflows here. The hardened check-failure triage workflow (`check_failure_triage.yml`, its callers and `ai-check-failure-triage.yml`) never gets the secret, so its PAT-holding collect stage still exports nothing to later steps; its few comments stay on `GH_PAT`. The consumer templates forward the secret. `update_workflows.yml` and `ai-update-workflows.yml` are left out: the updater template's secrets stay pinned so a template synced ahead of a release still starts the updater (`tests/test_update_workflows_template_gate.py`), and `scripts/propagate_consumer_secrets.sh` copies it to every consumer when it is set (`CONSUMER_OPTIONAL_SECRET_NAMES`), so all repositories share one value and cross-repository reads verify. `ci.yml` and the `pull_request` workflows never get it. Both model engines run in the `env -i` container of `codex_isolated_exec.sh`, so a model never sees it. `tests/conftest.py` strips the variables and the shim's `PATH` entry for the test session.
- **Rollback.** Repository variable `AI_COMMENT_SIGNING_POST=false`: new comments go back to `GH_PAT`, and signed comments keep verifying. Deleting the secret instead turns every signed comment, orchestrator state included, into an untrusted bot comment.
- **Replay.** The signature is not bound to the comment id or time. Anyone who can post as `github-actions[bot]` in the repository can re-post an exact copy of a signed comment on the same issue, which then reads as a newer trusted comment. Moving it to another issue or repository breaks the signature.
- **Not covered.** Comment calls made with `curl` (`curl_gh_api`, the Telegram cleanup tracker in `scripts/tg_helpers.sh`) and steps that run before the first `gh_helpers.sh` source in a job keep using the PAT as before. Those steps post and read their own comments with the PAT, so they stay consistent. `test-and-mark-stable.yml` sources the helpers right after checkout in its e2e jobs, because their wait loops read pipeline comments before any other step does.
