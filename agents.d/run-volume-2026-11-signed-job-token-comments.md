<!-- agents: section="Workflow architecture" -->
Signed job-token comments (run-volume plan item 15, decision D16, `docs/plans/reduce-actions-run-volume-plan.md`). Opt-in by the repository secret `AI_COMMENT_SIGNING_SECRET`. With it unset, nothing changes and every rule in the job-token comments note above still holds. With it set, the author-trusted kinds that note keeps on `GH_PAT` (security-pass markers, attempt journal, autofix editor summary, orchestrator state, merge-base sync, phase markers) move to the job token too, and so do all other pipeline comments that cannot start work.

- **Where it hooks in.** `scripts/gh_helpers.sh` (`_ai_comment_sig_activate`, run when the file is sourced) writes a `gh` shim and an embedded copy of `scripts/comment_signature.py` into `${RUNNER_TEMP}/ai_comment_sig_shim.*` and puts the shim first on `PATH`. Inside Actions it also appends that dir to `GITHUB_PATH` and the shim variables to `GITHUB_ENV`, so every later step of the job goes through it, including Python scripts run straight from a step. `tests/test_comment_signature.py` keeps the embedded copy byte-identical to the `.py` file: edit the `.py`, then re-embed it. Every `gh` call that is not a comment create, a comment body edit or a comments read execs the real binary.
- **Create.** `POST repos/<this repo>/issues/<n>/comments` (any of `-f/-F body=`, `--input`, `gh issue|pr comment --body/--body-file`) whose body contains none of `/approved`, `/answer`, `/reclarify`, `Clarification required`, and no `(?im)^\s*implementation\s+plan\b` line, is posted with `AI_COMMENT_JOB_TOKEN` (`github.token`). It carries a last line `<!-- ai-comment-sig:v1 as=<GH_PAT login> type=<User|Bot> sig=<hmac> -->`, where the HMAC-SHA256 covers repository, issue number, login, account type and body. Everything else keeps the caller's token, unchanged: those comments are what start the `issue_comment` wrappers, and the hardened plan-approval jobs in `ai-implement.yml` / `ai-plan.yml` read plan comments by the approver login with their own inline code. A refused job token (401/403) falls back once to the caller's token and is remembered for the job; any other failure is not resent.
- **Read.** Every `GET .../issues/<n>/comments`, `.../issues/comments[/<id>]` response is normalized before `--jq` runs (`jq -rcS`, per page, like `gh`): a `github-actions[bot]` comment with a valid signature comes back with `user.login`/`user.type` of the signed account, `author_association` `OWNER` (repository owner) or `COLLABORATOR`, and the signature line removed from `body`. Readers that trust the `GH_PAT` login therefore need no change. A bot comment with no or a bad signature is returned unchanged, so it stays untrusted.
- **Edit.** A body edit of a validly signed bot comment is re-signed for the same account (one extra `GET issues/comments/<id>`). An edit of any other comment is passed through.
- **Plumbing.** The reusable workflows that post or read comments declare the optional `workflow_call` secret `AI_COMMENT_SIGNING_SECRET` and set it, `AI_COMMENT_JOB_TOKEN` and `AI_COMMENT_SIGNING_POST` in workflow-level `env`. So do the release, sweep, heal-intake, validation-intake and log-analysis workflows here. The consumer templates forward the secret, and `scripts/propagate_consumer_secrets.sh` copies it to every consumer when it is set (`CONSUMER_OPTIONAL_SECRET_NAMES`), so all repositories share one value and cross-repository reads verify. `ci.yml` and the `pull_request` workflows never get it. Both model engines run in the `env -i` container of `codex_isolated_exec.sh`, so a model never sees it. `tests/conftest.py` strips the variables and the shim's `PATH` entry for the test session.
- **Rollback.** Repository variable `AI_COMMENT_SIGNING_POST=false`: new comments go back to `GH_PAT`, and signed comments keep verifying. Deleting the secret instead turns every signed comment, orchestrator state included, into an untrusted bot comment.
- **Not covered.** Comment calls made with `curl` (`curl_gh_api`, the Telegram cleanup tracker in `scripts/tg_helpers.sh`) and steps that run before the first `gh_helpers.sh` source in a job keep using the PAT as before. Those steps post and read their own comments with the PAT, so they stay consistent. `test-and-mark-stable.yml` sources the helpers right after checkout in its e2e jobs, because their wait loops read pipeline comments before any other step does.
