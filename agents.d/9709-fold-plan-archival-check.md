<!-- agents: section="Workflow architecture" -->
- **The plan-archival lint is a step group of `pr-checks.yml` (2026-11-18).** The workflow file `lint-plan-archival.yml` (workflow `Lint plan-archival completeness`, job `lint`) is gone; its work is the third step group of the `pr-body-lint` job (`docs/plans/fold-per-pr-checks-plan.md`, OD2). Only `ci.yml` now has a job named `lint`, the check-run name the `main` ruleset requires (`tests/test_lint_pr_body_auto_close.py` pins that).
  - When it runs: the old `paths: docs/completed/**` trigger filter is a step. "Enumerate added files in PR" runs on every event of the workflow and lists the files the PR adds; "Write PR body to file" and "Run plan-archival completeness lint" run only when one of them is under `docs/completed/` (step output `needed`). A PR that only edits or deletes files there started the old workflow too, but its lint had nothing to check.
  - How the added files are found: `git diff -z --name-status --find-renames HEAD^1 HEAD` on the merge commit GitHub checks out for a `pull_request` run. Its first parent is the base tip, so the diff is what the PR adds, with no API call and no history beyond the job's `fetch-depth: 2`. Added means status `A`, plus a rename whose destination is under `docs/completed/` and whose source is not: a plan moved there with `git mv` is an archival. The old `BASE_SHA HEAD_SHA` diff reported such a move as a rename and `--diff-filter=A` dropped it, so a moved plan was never checked. A rename inside `docs/completed/` is still not an archival.
  - Fail closed: the enumerate step fails when `HEAD` is not a two-parent merge commit (`outcome=not_a_merge_commit`), when the merge commit's second parent is not the event's head SHA (`outcome=stale_merge_commit`), and when the diff fails or cannot be parsed, or a file added under `docs/completed/` has a line break or a non-UTF-8 byte in its name (`outcome=enumerate_failed`).
  - Verdict: the job result. A violation (script exit 1) or an unreadable tracking issue (exit 2) fails `pr-body-lint`, which `ORCH_FINAL_MERGE_REQUIRED_CHECKS_DEFAULT` lists; before the fold it failed a check-run named `lint`, which that list also has. The steps are not `continue-on-error`.
  - Telling the two lints apart: a red `pr-body-lint` no longer always means a CLAUDE.md §19 violation. The failed step is either "Run auto-close keyword lint" or one of "Enumerate added files in PR" / "Run plan-archival completeness lint", and every failing exit of the plan-archival group prints `::error title=Plan-archival completeness lint (not the PR-body lint)::[lint_plan_archival] outcome=<not_a_merge_commit|stale_merge_commit|enumerate_failed|failed> …`. Success lines are `[lint_plan_archival] outcome=enumerated added_files=<n> lint_needed=<true|false>` and `[lint_plan_archival] outcome=passed`.
  - The `main` ruleset does not list `pr-body-lint`, so GitHub's own merge button does not wait for the plan-archival lint (it did only by accident before, through the shared name `lint`). Adding `pr-body-lint` to the ruleset is an operator decision.
  - Permissions and trigger of `pr-checks.yml` are unchanged; the job still takes no secret. The gate-list entry `Lint plan-archival completeness` stays (it matches no check-run, like the other two workflow-name entries).
