**`.gitleaksignore` union (#9659).** `scripts/review_conflict_prepare.sh` resolves an unmerged root `.gitleaksignore` on the trusted runner, on PR conflicts and on `orchestrator/project-*` integration sync, in the `# >>> .gitleaksignore union` block (after the deterministic-merge commit helper, before the manifest union-merge and the host-only take-base). The resolver sandbox excludes root dotfiles, so this conflict used to fail closed with `sandbox_path_host_only` (shubhodeep1/binance-blessings PR #585). The base branch's file (MERGE_HEAD, index stage 3) is kept byte for byte, and each fingerprint line the PR side (stage 2) added that is not already present is appended with the `#` comment lines it added directly above it. It resolves only when the stages are `1 2 3` or `2 3`, every stage is a regular `100644` blob, stage 3 is MERGE_HEAD's blob, neither side deleted a merge-base line, and every added non-blank, non-comment line fully matches `^[0-9a-f]{40}:[^:\n]+:[A-Za-z0-9_.-]+:[0-9]+$`; any other shape stays unmerged and fails closed as before. Blobs are read from the index only. The staged blob must start with the stage-3 bytes and carry every fingerprint of both sides, or the step exits 1. When nothing else is unmerged the merge commits at once, or on integration sync after the fingerprint check (`_det_commit_scope=gitleaksignore-only`); a verified `.gitleaksignore` is exempt from fingerprint re-expansion, while every other violated path keeps the verifier's guard: like the `.ai` take-base, the deferred commit is then cancelled and those paths go to the resolver (which records retry state) instead of the prepare step exiting 1. Switch `CONFLICT_GITLEAKSIGNORE_UNION_ENABLED` (default `true`, defaulted in the script).

**`.gitleaksignore` fingerprint suggestion (#9659).** The autofix editor never writes `.gitleaksignore`. When a sandbox-excluded finding in the editor summary names it, `scripts/review_autofix_step_post_editor_summary.sh` adds up to 10 gitleaks `Fingerprint:` lines from the failed checks' `log_tail` blocks in `PR_CHECK_RUNS_CONTEXT_FILE` to the step's existing comment, as a fenced ready-to-paste block ahead of the trailing markers, with a note that a human or the main-branch pipeline decides. A line is used only when it matches the fingerprint shape, has no backtick, angle bracket or control character, and names a commit that is an ancestor of the PR head. A fingerprint whose commit is not in the shallow checkout is dropped, never fetched, and counted as `missing=<m>`. No extra API call; only the counts are logged.

**Superseded check-triage issues (#9659).** `scripts/unblock_judge.sh` `unblock_triage_superseded_note` runs after the Q129 check-triage resolution gate for a standalone `ai:check-triage` issue whose newest trusted "Planning blocked" comment gives `work is already on the planning ref; nothing to implement` (the #8470 predicate, shared as `unblock_nothing_to_implement_blocked`). It reuses this run's cached `triage_resolution.json`: `resolved` / `already_resolved` means the gate closed it; an `unverified` verdict posts one trusted note ending in `<!-- ai:unblock-triage-superseded:v1 item=<n> -->` and stops without `/answer` or `/approved`; a note older than `UNBLOCK_JUDGE_WAIT_MAX_DAYS` first records one trusted `close` round marker (`unblock_ledger.py fingerprint` + `marker`, once after the note, skipped while `NEEDS_HUMAN_DIGEST_ENABLED=false`) so `scripts/unblock_scan.py`'s parked skip applies, as after the judge's own close, then parks the item in the needs-human digest (`operator_step_issue.py needs-human park`, one CRITICAL page when newly parked) and never resumes it; a failed marker write or a failed or disabled park holds and retries next run. Any other verdict (`not_triage`, `disabled`) or no cached verdict judges as usual. A failed note write holds the item and retries next run. Switch `UNBLOCK_TRIAGE_NOTHING_TO_IMPLEMENT_GATE_ENABLED` (default `true`, forwarded by `unblock_judge.yml`).
