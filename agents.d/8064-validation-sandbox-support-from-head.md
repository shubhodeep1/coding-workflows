- **Support files from `HEAD` in the screened copy (#8064, heal of #7913).** Self-repo support staging writes trusted copies over tracked support files so the host runs only trusted code (#6865), but the screened copy must test the branch's own committed files. `cmd_run` passes a fixed `support_from_head_args` list to `STAGE_PY` as `HEAD:<path>` arguments (`scripts/validate_process.sh`, `scripts/validation_harness_sandbox.sh`, `scripts/codex_isolated_workspace.py`, `scripts/templates/slot_manifest.schema.json`); nothing inside the sandbox executes them, because `STAGE_PY` imports `codex_isolated_workspace` from `SANDBOX_HELPER_DIR`. For each listed name that `git ls-files` lists and `readonly_allowed` admits, `stage_from_head` stages the `HEAD` blob (`git ls-tree -z HEAD` mode `100644`/`100755` only, then `git cat-file blob <oid>`, with the hardened git env, so no filter runs) with the blob's mode, and logs `VALIDATION_HARNESS_SANDBOX phase=stage outcome=ok reason=support_from_head path=<path>`. It falls back to the working-tree read, with no log, when the working-tree entry is not a regular file, the path is untracked, `HEAD` is unborn, the `HEAD` entry is a symlink or submodule, or git fails. A `HEAD:` argument that is empty, absolute or has a `..` segment is ignored, and a `dest=src` overlay always wins over a `HEAD:` entry. `scripts/validate_driver.sh` is not in the list: the sandbox runs it, so it stays the trusted overlay, and a branch that changes it together with tests that read it still sees the trusted driver. A tracked file with uncommitted working-tree edits in that list stages its `HEAD` bytes; validate checkouts are clean commits apart from the support overwrite.
