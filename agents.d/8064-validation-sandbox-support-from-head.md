- **Support files from `HEAD` in the screened copy (#8064, heal of #7913).** Self-repo support staging writes trusted copies over tracked support files so the host runs only trusted code (#6865), but the screened copy must test the branch's own committed files. While `VALIDATION_SANDBOX_SUPPORT_FROM_HEAD_ENABLED` is on (the #8065 switch, which gates this list and the `head-support:` list together, so `false` restores working-tree staging for every path), `cmd_run` passes a fixed `support_from_head_args` list to `STAGE_PY` as `HEAD:<path>` arguments (`scripts/validate_process.sh`, `scripts/validation_harness_sandbox.sh`, `scripts/codex_isolated_workspace.py`, `scripts/templates/slot_manifest.schema.json`, `scripts/render_validation_templates.py`, and every tracked file under `workflow-templates/validation-harness/` through a `HEAD:<dir>/` prefix entry); the sandbox machinery itself does not run them, because `STAGE_PY` imports `codex_isolated_workspace` from `SANDBOX_HELPER_DIR` and the harness tests are rendered on the host before staging; only the branch's own tests, inside the credential-free sandbox, read or run them, so widening the list still needs review. The four names also on the #8065 `head-support:` list are staged by its `head_blob` first (which logs `reason=support_from_head` or `outcome=skip reason=support_from_head_unavailable`) and are never read from `HEAD` a second time. For each other listed name that `git ls-files` lists and `readonly_allowed` admits, `stage_from_head` stages the `HEAD` blob (`git ls-tree -z HEAD` mode `100644`/`100755` only, then `git cat-file blob <oid>`, with the hardened git env, so no filter runs) with the blob's mode, and logs the same `VALIDATION_HARNESS_SANDBOX phase=stage outcome=ok reason=support_from_head path=<path>` line #8065 introduced. Each git call has a 60-second timeout; a timeout, or a git call that cannot start, counts as a git failure (logged, working-tree copy staged), as in `head_blob`. It falls back to the working-tree read, with no log, when the working-tree entry is not a regular file, the path is untracked, `HEAD` is unborn, the `HEAD` entry is a symlink or submodule, or git fails; a git failure while `HEAD` exists logs `outcome=skip reason=support_from_head_git_failed`, and a `HEAD` blob over 8 MiB (read with `git cat-file -s`, because the blob is buffered whole) keeps the streamed working-tree read and logs `outcome=skip reason=support_from_head_too_large`. A `HEAD:` argument that is empty, absolute or has a `..` segment is ignored, and a `dest=src` overlay always wins over a `HEAD:` entry. `scripts/validate_driver.sh` is not in the list: the sandbox runs it, so it stays the trusted overlay, and a branch that changes it together with tests that read it still sees the trusted driver. A tracked file with uncommitted working-tree edits in that list stages its `HEAD` bytes; validate checkouts are clean commits apart from the support overwrite.
