- **Standalone `ai:ready-to-merge` with a merged linked PR (issue #9482).** A PR merged into an integration branch (`orchestrator/project-*`) never sets `willCloseTarget`, so both GraphQL linked-PR lookups miss it. `run_standalone_stall_recovery` therefore runs the `_resolve_issue_implementation_pr` fallback for `ai:ready-to-merge` as well as `ai:done`, and `attempt_merge` reuses the PR it resolved. When that PR has merged, `_check_merged_pr_guard` skips recovery without touching the stall counters and hands the issue to `_reconcile_standalone_merged_pr_issue`. Each skip logs exactly one `STALL_SKIP` line: the reconcile's `reason=merged_non_target_base` line for a non-target base, otherwise `STALL_SKIP issue=<n> reason=linked_pr_merged pr=<p> phase=<phase> action=<action>` from the caller (gated by `_STALL_STANDALONE_NT_SKIP_LOGGED`). The stall judge's `linked_pr` diagnostics carry `merged` and `merged_at` from the payload `_fetch_pr_json` already returned, and `state` reads `merged` for a merged PR. A judge `escalate_human` is kept, not normalised to `attempt_merge`, only when the linked PR is closed or merged and `_pr_json_is_issue_implementation_pr` accepts it; a closed mention-only cross-reference keeps the old normalisation. This keep applies even with `ENABLE_STALL_HUMAN_TERMINALIZATION=false` (the default), so it is a second exception to that flag's downgrade alongside the `MAX_JUDGE_REPLAY` backstop: the issue gets `ai:needs-human` because `attempt_merge` cannot act on a closed or merged PR.
- **Standalone stall state is author-filtered (security finding #9718).** `_extract_standalone_state_comment_id_from_comments` and `_extract_standalone_state_json_from_comments` in `scripts/orchestrate_poll_process.sh` accept an `AI_STANDALONE_STALL_STATE_V1` comment only when its `user.login` is the pipeline's own login (`UNBLOCK_TRUSTED_LOGIN`, the GH_PAT user that `write_standalone_state_json` posts as). This is the same author filter `extract_latest_valid_orchestrator_state` applies to `ORCHESTRATOR_STATE_V1`. A marker comment from any other commenter is ignored, so it cannot reset or inflate `stall_recovery_count` and the other counters, and the writer never PATCHes it. An empty login trusts no comment. `run_standalone_stall_recovery` resolves the login once per tick in its own shell, and skips a candidate whose state cannot be verified (fail closed: counters untouched, no state comment posted). The tick-level identity gate at the top of the sweep normally skips the whole sweep first.
