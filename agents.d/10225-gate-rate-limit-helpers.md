- **Release-gate reads wait out rate limits (#10225).** Raw `gh api` reads in `scripts/stable_e2e_step_verify_cancel_on_close.sh`, `scripts/stable_e2e_step_deep_verify.sh`, `scripts/stable_e2e_step_wait_plan.sh` and the inline steps of `.github/workflows/test-and-mark-stable.yml` go through `gh_api_retry` (`scripts/gh_helpers.sh`); the step scripts source the workspace copy when `gh_api_retry` is not defined (a missing helper fails the step), `wait_plan` sources it inside the command substitution so its own shell is unchanged, and each routed inline step starts with `declare -F gh_api_retry >/dev/null || source scripts/gh_helpers.sh`. Each of the seven PAT jobs sets `GH_RETRY_MAX_ATTEMPTS: "3"` and `GH_RETRY_RATE_LIMIT_MAX_WAIT_SECS: "600"`, so a read waits at most (3 - 1) x 600 s for a reset (within `E2E_FINALIZATION_RESERVE_MINUTES` for `e2e-smoke-test`); `orchestrate-decompose-test` (81 to 101, on top of #10205's 3000 s watch + 1500 s dispatch cap + 360 s budget), `clarify-rejects-unsolvable-test` and `e2e-alt-model-test` got 20 more minutes of `timeout-minutes` for it (`workflow-log-analysis-test`, `orphan-workflows-test` and `validate-standalone-test` read through neither helper, so they keep their limits and the env only bounds a future read). Phase 7 reads use `phase7_gh_api_read`, which caps each wait at `min(600, (job_cap - now) / 2)` with `job_cap = E2E_JOB_STARTED_EPOCH + (E2E_JOB_TIMEOUT_MINUTES - E2E_FINALIZATION_RESERVE_MINUTES) * 60`. `scripts/stable_e2e_step_deep_verify.sh` uses the same cap through `deep_verify_gh_api_read`, stops its outer retry rounds and skips the indexing-delay recheck on rc 75 (rate-limit give-up) or rc 2 (permanent answer), and fails closed (`deep_passed=false`, `jobs listing unavailable`) when no read of a run's jobs listing succeeded (a read that returned an empty listing still counts as read), instead of passing it as a spurious re-trigger. The always() steps `Cleanup test artifacts` and `Cleanup alt-model artifacts` source the helper fail-soft and fall back to a plain `gh api` read that prints the reply only on success (so an error body never reaches the PR-body PATCH) when it is missing; `Cleanup test artifacts` reads through `cleanup_gh_api_read`, which sets `GH_RETRY_RATE_LIMIT_MAX_WAIT_SECS` = min(600, job time left / 8) afresh for each read (its PR-body and dispatch-review reads moved off `_safe_gh_jq`, which never waits for a reset). Writes keep their single attempt. `tests/test_test_and_mark_stable_gh_rate_limit_routing.py` fails on any raw read (`gh api` without a write flag, `gh run view|list|watch`, `gh pr view|list|checks|diff`, `gh issue view|list`, a `_safe_gh_jq` call) outside its allowlist, where every entry carries a reason and a stale entry fails (each command between unquoted `||`, `&&`, `;` or `|` is classified on its own flags, so a GET joined to a continued `-f` POST still counts as a read); `tests/test_test_and_mark_stable_deep_verify_fail_closed.py` runs those deep-verify verdicts against a stubbed `gh_api_retry`; `tests/test_test_and_mark_stable_phase7_rate_limit_wait.py` replays the run 46009933351 rate limit against a fake `gh`.
- **Gate `GH_PAT_BUDGET` lines carry numbers (#10225).** The start step of each PAT job makes one `gh api rate_limit --jq '[.resources.core.remaining, .resources.core.reset] | @tsv'` read (it does not use up the core allowance), prints `remaining=<n> reset=<epoch>` when the reading matches `^[0-9]+[[:space:]][0-9]+$` and stores it in `${RUNNER_TEMP}/gh_pat_budget_<job>`; otherwise it prints `unknown`. The end step calls `gh_pat_budget end test-and-mark-stable <job> <snapshot>` when the checkout's `scripts/gh_helpers.sh` defines it (so `used_in_job` and the gh call counter keys come from the helper) and otherwise prints the old `unknown` line. Neither step can fail the job. `validate` holds no PAT and keeps `unknown`. No new log prefix.
