- **Support code from the protected `promote-candidate` branch (#7746, phase 1 of `docs/plans/pin-promote-cycle-to-candidate-plan.md`, Refs #7745).** In this repository, the support-ref resolve steps of `cancel_on_pr_close`, `check_failure_triage`, `clarify`, `implement`, `issue_pr_status`, `memory_maintenance`, `orchestrate`, `orchestrate_clarify_respond`, `orchestrate_poll`, `plan`, `review_autofix`, `validate` and `workflow_failure_heal` check the job `workflow_ref`. Only when it is exactly `shubhodeep1/coding-workflows/.github/workflows/<this file>.yml@refs/heads/promote-candidate` do they make one `GET branches/promote-candidate` read per resolve step, not per run. `clarify`, `plan`, `orchestrate` and `orchestrate_poll` have two such steps and `implement` has four, and each reads the branch on its own, so if the branch moves or one read fails, two steps of one run can pick different sources. Only `validate.yml` shares the result between its steps: "Fetch workflow support files" reuses the result of "Resolve integration ref" through its `promote_candidate_sha` / `promote_candidate_checked` outputs, and reads the branch itself only when that step exited early with no tracking issue. They take its tip as the support ref only when the branch is protected and the tip is 40 hex, and log `SUPPORT_REF source=promote_candidate sha=<sha>`. Otherwise they keep the previous source and log `SUPPORT_REF source=promote_candidate_unprotected`. These lines are a second `SUPPORT_REF` shape alongside the consumer `ref=<pin|stable> workflow_ref=<ref>` line. `review_autofix.yml` also accepts `refs/heads/promote-candidate` as a review support ref. The gh-retry bootstrap steps (`validate.yml` included) still clone `main`, because `tests/test_workflow_gh_retry_fallback_contract.py` requires them to stay byte-identical across workflows (one of them is in `security-audit.yml`). Consumer pins and `@main` runs are unchanged.
