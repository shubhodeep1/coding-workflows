The stall-recovery `skip` close-out also honours the owner hold (issue #9733, where `skip` closed held PR #9744 on an `ai:awaiting-approval` issue). The hold log line now carries the action it replaced: `STALL_SKIP issue=<n> reason=pr_ai_hold pr=<m> detail=draft|skip_ai_title phase=<phase> action=none requested_action=<action>`, where `phase` can be any phase. Four more checks back up the guards above when the batched linked-PR payload lacks `draft`/`title`:
- `execute_stall_recovery_action skip` (managed path) re-checks the REST implementation-PR payload its healthy-PR guard already resolves (`STALL_RECOVERY_EFFECTIVE_ACTION=skip_skipped_pr_ai_hold`; returns 1; nothing closed).
- `close_linked_pr` reads `draft` and `title` from the `pulls/<n>` request it already makes and never closes a held PR. It logs `close_linked_pr: skipping PR #<n> for issue #<m> (owner hold: reason=pr_ai_hold detail=…)` and records the PR in `CLOSE_LINKED_PR_HELD_PRS` (space-separated) and `CLOSE_LINKED_PR_HELD_DETAIL`, which are reset on every call.
- The early-phase open-PR guard in `recover_stalled_issue` re-checks the `_opr_json` payload it already resolves (REST `pulls/<n>` on a cache hit) before the retired-host-only reissue, the conflict resolver and the changes-requested autofix (`STALL_RECOVERY_EFFECTIVE_ACTION=<action>_skipped_pr_ai_hold`; returns 1).
- Both re-issuing `close_and_reissue` arms (the managed one in `execute_stall_recovery_action`, which the stall judge also reaches, and the standalone one) re-check the hold before the replacement issue is created, on the REST payload from `_resolve_issue_implementation_pr` (1 `gh pr list --head` + 1 `pulls/<n>` on the common path, on this arm only, because the cached payloads are the ones that lacked the fields). A held PR logs the hold line with `requested_action=close_and_reissue source=reissue_precheck`, creates no replacement, closes nothing, counts no attempt and keeps the stall clock (managed: `STALL_RECOVERY_EFFECTIVE_ACTION=close_and_reissue_skipped_pr_ai_hold`, returns 1). A failed lookup fails open to the legacy flow.
- When `close_linked_pr` reports a held PR, the managed `skip` arm, the standalone exhausted-close arm and the managed and standalone ancestor-chain no-op cap arms of `close_and_reissue` leave the issue open with no `ai:closed` label. They log the hold line with `requested_action=skip` (or `close_and_reissue`) `source=close_linked_pr`, count no attempt and keep the stall clock.

Only when that lookup fails too does the re-issuing path reach `close_linked_pr` with a held PR: the replacement issue already exists then, so the held PR is left open and logged but the source issue is still closed.

The three retired-host-only reroutes into `close_and_reissue` (the `resolve_merge_conflict` and `dispatch_rb_judge` arms of `execute_stall_recovery_action`, and the early-phase open-PR guard in `recover_stalled_issue`) keep a nested `close_and_reissue_skipped_pr_ai_hold` marker instead of overwriting it with `close_and_reissue`. `invoke_stall_judge` treats that marker like `resolve_merge_conflict_skipped_pr_ai_hold` and runs no fallback action. `execute_stall_recovery_action dispatch_rb_judge` also checks the hold on the REST payload `_resolve_issue_implementation_pr` already returned (0 extra calls) before the retired-host-only check and `_dispatch_rb_judge_for_pr`. A held PR logs the hold line with `requested_action=dispatch_rb_judge`, sets `STALL_RECOVERY_EFFECTIVE_ACTION=dispatch_rb_judge_skipped_pr_ai_hold`, counts no attempt and returns 1. Tests: `tests/test_stall_retired_conflict_reissue.py`.

The standalone `dispatch_rb_judge` rung of `run_standalone_stall_recovery` runs the same check on the REST payload its pre-resolve block already fetches (0 extra calls). The check runs before the retired-host-only reroute and the case arm's `_dispatch_rb_judge_for_pr`. A held PR logs the hold line with `requested_action=dispatch_rb_judge`, counts no attempt, keeps the stall clock and skips to the next issue.
