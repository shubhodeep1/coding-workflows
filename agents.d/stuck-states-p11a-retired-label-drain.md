- Retired-label drain (`RETIRED_LABEL_DRAIN_ENABLED`, default `true` in `scripts/ai_labels.py` and in `.github/workflows/sync_ai_labels.yml` as `vars.RETIRED_LABEL_DRAIN_ENABLED || 'true'`): before `sync-labels` deletes a retired label, `_drain_retired_label` lists the open issues and PRs that carry it (`GET repos/{repo}/issues?labels=<label>&state=open&per_page=100&page=1..2`). It posts one comment on each, starting with the durable marker `<!-- ai:retired-label-drain:v1 label=<quoted label> -->`. Before posting, it reads the item's last comment page (and the page before it when needed), and a marker from an OWNER, MEMBER or COLLABORATOR, or from `github-actions[bot]`, means it skips the comment; a forged marker from anyone else is ignored. It then closes the item through `PATCH repos/{repo}/issues/{n}`: `state_reason=not_planned` for issues, plain `closed` for PRs. At most 10 items are handled per run, shared across all retired labels. The label is deleted only after a complete listing shows no open items: either the first listing was already complete and empty, or a final listing after every item was closed is. A failed or incomplete listing (200+ items), a failed marker read, comment or close (an item is never closed without its comment), an exhausted budget, or a non-empty final listing keeps the label until the next run, and is reported in `errors[]` (`drain_list`, `drain_marker_check`, `drain_comment`, `drain_close`, `drain_final_list`) or as `LABEL_SYNC_RETIRED_DRAIN_DEFERRED`. The drain never changes the exit status or the output keys. `--dry-run` reads only the label and the first listing and logs `LABEL_SYNC_RETIRED_DRAIN action=plan`. The warn-then-delete behaviour described above (`LABEL_SYNC_RETIRED_IN_USE`, where the delete still proceeds) applies only when the switch is `false`, `0`, `no` or `off`. `sync_ai_labels.yml` keeps `permissions: contents: read, issues: write`, because consumer callers grant no `pull-requests` scope. That block caps the job token whatever the caller grants, so the `github.token` fallback never has `pull-requests` scope: draining PRs needs `GH_PAT`, and without it each PR item fails as `drain_comment` / `drain_close` and keeps the label. The drain comment `POST` makes one attempt (`_github_api_request(..., retry_transient=False)`), so a 5xx or timeout after GitHub applied it cannot post a second comment; the next run re-checks the marker. Only an HTTP 429 is retried, because GitHub does not apply a rate-limited write. The marker check reads the item's last comment page and, when that page has no trusted marker, the page before it. In this repository the sync runs from `.github/workflows/internal-sync-ai-labels.yml` (weekly, Monday 05:23 UTC, plus `workflow_dispatch` with a `dry_run` input). It calls the local `./.github/workflows/sync_ai_labels.yml`, grants `pull-requests: write` (which does not reach the called job's token), and forwards `GH_PAT` and `TG_BOT_SECRET` explicitly. Tests: `tests/test_ai_labels_retired.py`.
