**Final-CI local merge and pinned base (2026-11-18, Refs #9690, #9681).** Under a long Actions queue GitHub left `refs/pull/<n>/merge` unrecomputed for over an hour, so every job of runs 44277478295 (#9690) and 44285991274 (#9681) failed with `outcome=stale reason=not_refreshed` and tested nothing. `scripts/ci_final_merge_ref_fresh.sh` (step "Verify the final-CI merge ref is current") now:
- **Pins the run's base.** The time bound is the event payload's `repository.pushed_at` (`GITHUB_EVENT_PATH`: the same file in every job and attempt, no API call and no token scope; every base push before the dispatch is at or before it), or, when the payload lacks it, the run's `created_at` from one `GET actions/runs/<GITHUB_RUN_ID>` (`pin_source=event_pushed_at|run_created_at`). The pin is the live tip when its committer date is not after that bound (a depth-1 fetch of the tip, skipped when the object is local). Otherwise it is the newest first-parent commit of the base whose committer date is not after the bound, from a fetch of the base `CI_FINAL_MERGE_REF_MERGE_DEPTH` deep (default 200, 1-1000, never below `--depth`). Every job and every re-run attempt computes the same pin, so a run's jobs test one base even when the base moves between job starts. If the pin cannot be computed (`pin_reason=run_id_invalid|run_created_unreadable|base_fetch_failed|beyond_depth`), the job falls back to the live tip as before. The pin assumes committer date close to push time, which holds for GitHub merges and the pipeline's own pushes. Known gap: a commit pushed to the base after dispatch but with an older committer date (a direct push of a commit made locally earlier) is pinned by jobs that start after that push, while earlier jobs pin the older tip. Closing the gap needs a push-time signal that costs an extra API read per job, so it is left open.
- Treats a merge ref whose first parent is the pin as fresh (`reason=base_tip`, or `pinned_base` when the base moved since the run was created). The refresh attempts run only when the pin is the live tip, and they accept only a merge into the pin. A `mergeable: false` answer after the tip moved past the pin is about that newer tip (the tip is re-read after the answer, so a move just before the first attempt counts), so the job goes on to the local merge into the pin instead of failing. When that re-read fails, it is unknown which tip GitHub judged, so the local merge into the pin decides as well (a real conflict with the pin still fails as `merge_conflict`).
- **Merges locally** when the attempts do not refresh the ref, or when the base moved after the run was created (GitHub's ref can never match the pin then, so no attempt is made). It fetches `GITHUB_SHA` and the pin `CI_FINAL_MERGE_REF_MERGE_DEPTH` deep, runs `git merge-tree --write-tree` with attributes read from the empty tree (a `.gitattributes` merge driver such as `CHANGELOG.md merge=union` cannot hide a conflict GitHub would report), writes the commit with `commit-tree` (parents: pin, head; fixed identity, dates and message; no signing, `core.hooksPath=/dev/null`), checks it out and appends `CI_FINAL_MERGE_REF_LOCAL_MERGE=<sha>` to `GITHUB_ENV`. The commit is a pure function of (pin, head), so every job that merges locally builds the same commit. The fresh, refreshed and merged_locally lines all carry `tree=`.
- Fails the job on a local conflict (`outcome=conflict reason=merge_conflict`) and on a merge it cannot build (`outcome=stale reason=merge_base_too_deep|merge_fetch_failed|merge_tree_unsupported|merge_failed`; `merge_tree_unsupported` means the runner's git predates `--attr-source`, 2.41). `merge_base_too_deep` means the merge base lies more than the fetch window below the head or the pin: the head is far behind, and the sweep's base sync updates it after the `final-ci-failed` hand-back, as before.
- The three "Fetch base commits for the shallow checkout" steps and the agents.md direct-edit check fetch the merge's parents (`HEAD^1`, `GITHUB_SHA`) instead of HEAD when `CI_FINAL_MERGE_REF_LOCAL_MERGE` names HEAD, because origin does not have the local commit.
- Why #9690 got no new final run for hours: the failed run itself finished at 11:25 UTC (dispatched 09:36, queued). `final-ci-failed` handed the head back to review (`REVIEW_FINAL_CI_FAILED ... outcome=redispatched`), and `_pr_ensure_final_ci` never re-dispatches a head whose run failed. The sweep's base sync then skipped it as `too_recent` (11:42) and `review_in_flight` (12:32, 12:56) while the hand-back's review runs waited in the queue. A head that is not behind its base would never be synced (`up_to_date`). The local merge removes that dependency for a merely stale merge ref.
- Tests: `tests/test_ci_final_merge_ref_fresh.py` (local bare origin with fixed commit dates: pin, local merge, determinism across jobs, conflicts, depth), `tests/test_ci_shallow_checkout_contract.py` (a locally built HEAD fetches its parents).
