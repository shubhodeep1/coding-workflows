<!-- agents: section="Workflow architecture" -->
- **Merge lease grants only to ready waiters and releases a conflicting holder once (issue #10098, Phase 1 of `docs/plans/merge-lease-short-critical-section-plan.md`; Refs #10097).** Before this change the tick granted on the head-gate alone, so a waiter whose `ci/final` was still pending, or that conflicted with its base, held a slot for 4-5 hours.
  - `_merge_lease_pr_eligible` (`scripts/pr_checks_lib.sh`) keeps its statuses response in `MERGE_LEASE_ELIGIBLE_STATUSES_JSON` together with the head it belongs to (`MERGE_LEASE_ELIGIBLE_STATUSES_HEAD`). `_merge_lease_pr_ready <pr> <head> <base>` is called only for a waiter accepted with `MERGE_LEASE_GATE_CONFIRMED=true`. It returns 1 with `MERGE_LEASE_NOT_READY_REASON=final_ci_pending` when `REVIEW_FINAL_CI_WORKFLOW` is set and the newest `ci/final` (any creator) is not `success`; the check reads only the kept response, never a response for another head. It returns 1 with `not_mergeable` when `_merge_lease_pr_mergeable` (one `GET pulls/<pr>`; the open-PR listing has no `mergeable`) reads `mergeable == false` or `mergeable_state == "dirty"`. It returns 0 otherwise and on any read failure (fail-open).
  - `_mt_merge_lease_tick` and `_mt_merge_lease_tick_multi` (`scripts/review_merge_train.sh`): a waiter that is not ready keeps its wait label, gets no skip entry, and logs `MERGE_LEASE pr=<n> base=<ref> mode=tick outcome=skipped reason=final_ci_pending|not_mergeable` (plus a metric `skipped` line). The multi-holder tick checks readiness after `holder_shares_paths`. For an absent `ci/final` whose head has no final-CI run at all (`PR_FINAL_CI_JQ_DECISION_DEF` reads `dispatch no_run`), `_mt_merge_lease_ready_final_ci` calls `_pr_ensure_final_ci` with that listing: one dispatch per base per tick at most, and never for a fork head.
  - Liveness: suppose no waiter is ready, no holder was released or granted this tick, a slot was free when the record was read, and `MERGE_LEASE_IDLE_MINUTES` (0 means 60) have passed. For the multi-holder tick that time is counted from the newer of the record's `updated=` and the holder rows' newest acquired/updated time. Then the first eligible waiter that was not ready is granted with `outcome=granted reason=ready_fallback`.
  - Conflict release: suppose a holder kept by today's checks reads `mergeable == false`, a labelled waiter exists in the listing, `_mt_merge_lease_ready_waiter_exists` finds a ready waiter (holders excluded), and the holder lacks `MERGE_LEASE_CONFLICT_RELEASED_LABEL`. Then the label is added first, and only after that succeeds is the holder released with `outcome=released reason=released_conflict` and a hard skip entry `<pr>:<head>:released_conflict`. A labelled holder keeps its slot, so a PR is released for a conflict at most once. When the release write then fails or loses the race (`outcome=write_failed|lost_race reason=released_conflict`), `_merge_lease_unlabel_conflict_released` removes the label again, because the holder was not released. The multi-holder tick runs the waiter scan once per base (`tm_rwe_result`). Readiness results are cached per `<pr>:<head>` for the tick (`_mt_merge_lease_pr_ready_cached`, `_MT_LEASE_READY_CACHE`), so the scan and the grant loop read `pulls/<pr>` once per waiter. D4 (handing a skip-held waiter back to the sweep) does not run while a waiter skipped as not ready still carries its wait label.
  - Switches (default `true`, defaults also in the library): `MERGE_LEASE_READY_GRANT_ENABLED`, `MERGE_LEASE_CONFLICT_RELEASE_ENABLED`; label `MERGE_LEASE_CONFLICT_RELEASED_LABEL` (default `ai:merge-lease-conflict-released`). Both switches at `false`, or a staged library without the helpers, keep the lease record, the log lines and the API calls exactly as before. The record format is unchanged. The `MERGE_LEASE` prefix is reused; the new tokens are `final_ci_pending`, `not_mergeable`, `ready_fallback` and `released_conflict`.
  - Workflows: the three variables sit next to every `MERGE_LEASE_IDLE_MINUTES` env line. The `orchestrate_poll.yml` backstop and standalone-sweep ticks and the `cancel_on_pr_close.yml` tick also set `REVIEW_FINAL_CI_WORKFLOW` (`vars.REVIEW_FINAL_CI_WORKFLOW`, else `ci.yml` in this repository and empty elsewhere). `review_autofix.yml` keeps its workflow-level `inputs.final_ci_workflow` value.
