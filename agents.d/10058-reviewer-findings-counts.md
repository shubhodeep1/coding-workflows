- **Per-reviewer finding counts (Refs #10058).** `scripts/review_findings_record.py` (the existing "Write review findings record" step of `review_autofix.yml`; no workflow change) prints, right after building the record and before writing it, one line per reviewer that ran (slot `status == ok`; name = slot slug, else safe name): `REVIEWER_FINDINGS pr=<n|unknown> round=<r|unknown> reviewer=<name> raised=<a> lone=<b> lone_rejected=<c> lone_accepted=<d> shared=<e>`. Counts come only from the record: each `=== ISSUE n ===` block's `FLAGGED_BY` entries are matched to reviewers by slug, or by safe name after stripping a leading `review_` / `pass1_` (`unknown` is skipped). `duplicate-of:<id>` issues fold their reviewers into the target when it is in the record. A finding with one matched reviewer is `lone`, otherwise `shared`; `raised = lone + shared`. A lone finding is `accepted` when the editor result is `applied` without override (takes precedence), else `rejected` when `CLASSIFICATION: non-actionable` with a `REJECTION_KIND` other than `out-of-scope` (missing kind counts), or the editor result is `already_satisfied` / `ignored` (including `CONSOLIDATOR_OVERRIDDEN`). Every reviewer instead gets `outcome=unavailable reason=<code>`: `consolidator_disabled` (lite tier or `REVIEW_CONSOLIDATOR_ENABLED=0`), `consolidator_missing` (warning `issues_file_missing`, `issues_file_no_blocks`, `issues_file_refused`, `issues_file_oversized`, `consolidator_parse_failed` or `issues_truncated`), or `flagged_by_missing` (any counted issue in the issues file has a `FLAGGED_BY` entry other than `unknown` that matches no reviewer that ran, such as a `reviewer_N` token, even when another entry matches). The guard sees only entries that reach the issues file: `sanitize_flagged_by` in `scripts/review_parse_consolidator.sh` silently drops unknown tokens when at least one known token survives, so a finding shared with a dropped token can still count as `lone`; a parser-side partial-drop signal is a follow-up. An empty issues file gives zeros when there is no parse failure, or when the only failure is the parser's clean-round result (`parse_error=no_issue_markers` in `PARSER_STATS_FILE` with `REVIEW_PARSER_FAILOPEN` not `0`, and a non-blank `CONSOLIDATOR_RAW_FILE`, default `${RUNTIME_DIR}/consolidator_raw.txt`; `scripts/review_consolidate.sh` empties that file on every failure, so an empty or missing raw file stays `consolidator_missing`, as does a raw file carrying the `[TRUNCATED_BY_OUTPUT_CAP]` marker that script appends when it caps the output); the record's warnings are unchanged. Known limitation: a non-blank consolidator answer without ISSUE markers that ignores the format (prose, a refusal) and leaves no passthrough block still reads as a clean round with zeros, because the record cannot tell it from a real zero-finding round. "Lone" depends on the consolidator's merge of duplicate findings and on the parser's `FLAGGED_BY` sanitising. `scripts/collect_workflow_logs.py` parses the lines (anchored regex, optional Actions timestamp, bounded widths; first copy per `(pr, round, reviewer)`; max 64 per run) only from archives it already downloads, only for trusted-origin runs, into the optional run-row field `reviewer_findings` (kept in cached rows; older cached rows are not re-fetched; cleared by the untrusted-origin exclusion). `scripts/analyze_workflow_logs.py` counts entries only from `workflow_family == review_autofix` runs and adds `analysis_context.json` key `reviewer_findings` (`review_runs`, `runs_with_lines`, `unavailable_runs`, `unavailable_lines`, `reviewers[{reviewer,runs,raised,lone,lone_rejected,lone_accepted,shared}]`). The "Run workflow log analysis" step of `workflow-log-analysis.yml` then runs `scripts/check_workflow_analysis_report.py --insert-reviewer-findings --context "${ANALYSIS_CONTEXT_FILE}" --report "${REPORT_FILE}"` (after the data-gap block, fail-open), which appends `<!-- reviewer-findings-table v1 -->` + `## Reviewer Findings` (a no-op only when the report already ends with the same rendered section; a marker elsewhere in the model-written report draws a `::warning::` and the table is still appended; a coverage sentence "X of Y review runs in the window" that says the lines come from the capped, failure-weighted log sample; columns Reviewer / Runs / Findings raised / Lone / Lone rejected / Lone accepted; `n (p%)` only when lone >= 20, `REVIEWER_FINDINGS_PERCENT_MIN_LONE`). The table is code-built, never a model tally, and is not a `REQUIRED_HEADINGS` entry. Contract tests: `tests/test_review_chatgpt_findings_record.py`, `tests/test_collect_workflow_logs.py`, `tests/test_analyze_workflow_logs.py`, `tests/test_check_workflow_analysis_report.py`.
