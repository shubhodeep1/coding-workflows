- **Failure-signature breaker and stall exhaustion (stuck-states P3b, Refs #8291).** `scripts/orchestrate_poll_process.sh` runs `_failure_fingerprint_breaker_check` on every tick, before the stall threshold and capacity-wait checks, in `run_standalone_stall_recovery` and in `run_managed_failure_fingerprint_breaker` (called before `check-stalls` for the current wave). The decision comes from `python3 scripts/orchestrate_lib.py failure-fingerprint-breaker` (`evaluate_failure_fingerprint_breaker`): only comments by the pipeline's verified login (`unblock_trusted_login`) count, each needs exactly one valid `<!-- AI_FAILURE_FINGERPRINT_V1 phase=<p> fp=<12 hex> run=<id> -->` marker, repeated run ids collapse, and the newest trusted `<!-- AI_FAILURE_FINGERPRINT_BREAKER_V1 ... -->` comment is the consumption point. `STALL_FINGERPRINT_REPEAT_MAX` (default `2`, minimum 2) identical consecutive (phase, fp) markers trip `ai:plan-failed` / `ai:clarify-failed` on a standalone issue (other phases, and every managed wave issue, `ai:needs-human`, since the two failure labels are `TERMINAL_PHASES` that `reconcile_wave_issue_status` would store as a permanent `closed`); the label is verified before the breaker comment is posted. A failed breaker-comment POST removes the label again and returns 1 (`outcome=comment_failed rollback=done`), so a later resume cannot re-trip on unconsumed markers; a removal that is still visible (`rollback=failed`) or a failed label read (`rollback=unverified`, or `label_failed reason=label_read_failed` after the add; `_ffb_read_issue_labels` reports a failed read instead of `[]`) returns 2: the standalone loop skips the ladder for that issue, and the managed loop adds the label to `LABELS_JSON` so `check-stalls` skips it that tick. A `label_failed` result with a successful read that shows the label missing returns 1 and falls through to the legacy ladder. Comment history is authoritative; the `failure_fingerprints` key in standalone state and in managed wave issue entries is an observation mirror only. With `STALL_FINGERPRINT_BREAKER_ENABLED=true` (default) stall exhaustion (`skip`) never closes an issue or its linked PR in either loop: it adds and verifies `ai:needs-human` and leaves the issue open for the unblock judge (the managed healthy-PR redirect to `dispatch_rb_judge` still runs first). An unverified label leaves state untouched so the next tick retries. `false` restores the legacy skip-and-close and disables the breaker.
