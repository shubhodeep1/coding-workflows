Check-failure triage skips a base failure a heal issue tracks (Refs #9215): in `scripts/check_failure_triage.sh`'s base-branch gate, the existing `GET actions/runs/<id>` read now returns `[(.workflow_id // "" | tostring), (.path // "")] | join(" ")`. Any `@<ref>` suffix on the path (`.github/workflows/ci.yml@refs/heads/main`) is stripped first, and the path is kept only when it matches `^\.github/workflows/[A-Za-z0-9_.-]{1,100}\.ya?ml$` with no `..`. When the base run's conclusion is `failure`, the PR's base ref equals `base.repo.default_branch` from the PR payload, and `CHECK_TRIAGE_BASE_TRACKED_SKIP_ENABLED` is not `false` (default `true`; any value other than `true`/`false` turns it off with a `::warning::`), `triage_base_failure_heal_issue` makes one `GET repos/<repo>/issues?state=open&labels=ai:workflow-heal&sort=created&direction=asc&per_page=100` read. It takes the oldest issue that is not a pull request, is authored by OWNER/MEMBER/COLLABORATOR, has `<!-- workflow-failure-heal:source=<repo>#run -->` as its fourth line, has `<!-- workflow-failure-heal:workflow=<path> -->` among its first seven lines, and has the exact line ``- **Target branch:** `<base>` ``. On a match, it writes `${RUNTIME_DIR}/triage_base_tracked.json` (`heal_issue`, `pr_number`, `head_sha`, `run_id`, `base_ref`, `workflow_path`), sets the step output `base_failure_tracked=<n>`, logs `skip reason=base_failure_tracked`, reports an unverified PR-head route like the other base-gate skips, and exits 0 with no issue. A failed read logs `base_tracked outcome=fail_open reason=heal_lookup_failed` and files as before. When a heal issue matches but the note metadata cannot be written (no valid 40-hex head SHA, or a failed write), the skip does not happen: the run logs `base_tracked outcome=fail_open reason=metadata_write_failed` and files the per-PR issue as before, so the failure is never dropped. The new `check_failure_triage.yml` step "Note PR failure on its base-branch heal issue" (`if: steps.collect_triage.outputs.base_failure_tracked != ''`, `continue-on-error: true`, only `CHECK_TRIAGE_ISSUES_TOKEN`) runs the new stage `CHECK_TRIAGE_STAGE=base-tracked-note`. That stage re-validates the file, reads the heal issue's comments (`--paginate`, first lines only) and skips with `reason=already_noted` when one already opens with the same marker (a failed read posts as before), and otherwise posts one comment opening with `<!-- check-failure-triage:base-tracked pr=<n> head=<sha> run=<id> -->`, a marker that `orchestrate_lib.py`'s unrouted-reply check already treats as pipeline bookkeeping. Tests: `CheckFailureTriageBaseTrackedTests` and `CheckFailureTriageBaseTrackedNoteTests` in `tests/test_check_failure_triage_workflow_security.py`.

Planning blocks that wait on an open PR (Refs #9215): `plan.yml`'s "Handle blocked planning output" matches `BLOCKED_REASON` against `^work is delivered by open PR #([1-9][0-9]{0,8}); resume once it is merged$` (the #8335 planner self-check). On a match, the issue comment opens with `Planning blocked: waiting on open PR #<N>.` (the `Planning blocked:` prefix `orchestrate_lib.py` reads as automation stays), keeps the `Reason:` line, and says the unblock judge resumes the issue after PR #<N> merges. The Telegram message goes out at `WARNING` and the step logs `PLAN_BLOCKED_WAIT issue=<n> pr=<N> level=WARNING`. The step forwards `UNBLOCK_JUDGE_ENABLED` (default `true`); when it is `false` nothing resumes the issue, so the wait reason keeps the old comment and the `CRITICAL` page. Every other reason, including `work is already on the planning ref; nothing to implement` (whose exact `Planning blocked: human input required.` header `scripts/unblock_judge.sh` matches), keeps the old comment and the `CRITICAL` page. Tests: `tests/test_plan_blocked_wait_on_pr.py`.
