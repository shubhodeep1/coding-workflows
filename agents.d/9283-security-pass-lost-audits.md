- Single-issue security pass: lost head attempts and the once-per-head hold alert (issue #9942, refs #9283). Past the cycle or attempt cap, `scripts/review_single_issue_security_pass.sh` (gate and `status` modes) classifies each post-cap pending head attempt with `single_pass_marker_audit_lost <created> <next_created>`: the same "lost" rule as `single_pass_pending_audit_state` (at least one run titled `... (PR #<n>)`, all completed at least 10 minutes ago, no result marker for that cycle) over the window `[created - 120s, next later-cycle head marker - 120s)` (unbounded for the last one), so the next attempt's run, dispatched before its marker, is never credited to the earlier one. It reads only the cached `single_pass_audit_runs` listing (still one request per run); before any fetch the gate sets `SINGLE_PASS_AUDIT_RUNS_FROM` to the oldest post-cap pending head marker, and the listing's `created>=` start moves to 120s before it when that is earlier than 24 hours ago (`SINGLE_PASS_AUDIT_RUNS_SINCE_EPOCH` records the start used). Fail closed: a failed or empty listing, a window that starts before the listing, an incomplete listing (`total_count` missing or above the returned runs) whose oldest returned run is newer than the window start, or no matching run counts the attempt; a cycle with any `failed` marker always counts. Up to `SECURITY_PASS_LOST_AUDIT_RETRIES` (default `2`, `0` restores the old counting and the 24-hour listing) lost attempts per head are forgiven; lost ones beyond that count toward `SECURITY_PASS_EXHAUSTED_HEAD_AUDIT_ATTEMPTS` again, so a consistently cancelled audit is bounded. A forgiven retry logs `outcome=retry reason=lost_audit_not_counted head_attempts=<n> lost_attempts=<m>`; the `exhausted_without_completed_audit` hold log ends with `lost_attempts=<m>`. The workflow passes `SECURITY_PASS_LOST_AUDIT_RETRIES` to the "Single-issue security pass", "Single-issue security pass (deterministic skip)" and "Review-blocked judge decision" steps. The "Telegram review-blocked judge decision" step pages `security_hold_exhausted_without_completed_audit` once per head: unless `tg_alert_configured` reports that Telegram cannot send (then the reads are skipped and the log says `repeat=unchecked`, since no marker is ever posted), it reads the newest comment page through `_tg_newest_comments_json`, and a `tg_trusted` comment whose body ends with `<!-- rb-judge-security-hold:v1 head=<sha> reason=exhausted_without_completed_audit -->` on its own line drops the alert to DEBUG; otherwise it pages CRITICAL through `tg_send_msg` and posts that marker comment only when Telegram returned a message id, with `AI_COMMENT_SIGNING_SECRET=""` so the signing shim posts it unsigned with `GH_TOKEN` (the author and last line the read expects). An unconfirmed send or a failed POST only warns, so the next round pages again; a failed read pages `repeat=unchecked`. Only the newest page of 100 comments is read: a marker pushed off it pages once more and is re-posted. A `/re-run` on the same head does not page again; only a new push does. Other hold reasons are unchanged. Tests: `tests/test_single_issue_security_pass.py`, `tests/test_review_autofix_rb_judge_crash_alert.py`.
