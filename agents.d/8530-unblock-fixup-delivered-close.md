- **Unblock judge closes a heal issue whose fix-up already delivered its fix (#8530).** When a fix-up wait ends with the fix-up merged and the judge would post the stop's resume command (after the protected-path handoff, the operator-step hold and the #8470 nothing-to-implement close), `unblock_fixup_delivered_close` in `scripts/unblock_judge.sh` checks a standalone issue (no tracking issue) first without the network: `scripts/unblock_actions.py fixup-delivered-body` requires the `ai:workflow-heal` label, the pipeline login as the item's author, exactly one `Target branch:` line (`TARGET_BRANCH_LINE_RE`, matched per line) and an `## Affected files` section whose every non-blank line is a `- owner/repo: `path`` entry for this repository (at most 50; any other line resumes as `affected_files_unparsed`). Then two reads: the merged `ai/issue-<fixup>` pull request (base must be `base.repo.default_branch`, and the target branch must differ from it), and its paginated file list, which must contain every listed path. Only then it posts one comment ending in `<!-- ai:unblock-fixup-delivered:v1 item=<n> fixup=<f> pr=<pr> -->` (not posted again when a trusted copy exists), adds `ai:closed`, closes the issue as completed and marks the wait `done`. Resuming such an issue planned on `stable`, which did not have the fix-up yet, and proposed the same change again (#8481 after fix-up #8484 / PR #8486). Any read failure resumes as usual; a failed comment, label or close write keeps the wait open so the next scan retries. `UNBLOCK_FIXUP_DELIVERED_CLOSE_ENABLED=false` (default `true`, read from the script environment; `.github/workflows/unblock_judge.yml` does not forward it) restores the resume.
