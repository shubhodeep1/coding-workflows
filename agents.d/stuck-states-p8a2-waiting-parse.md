<!-- agents: section="Workflow architecture" -->
- **Clarify and plan park `WAITING:` dependency answers (stuck-states P8a-2, Refs #8291).** The clarify and plan prompts (the `prompts/` copies, the inline `clarify.yml` prompt and the `scripts/run_plan_codex.sh` heredoc) tell the agent to answer a pure sequencing wait with exactly one line `WAITING: pr=<owner>/<repo>#<N>`, `WAITING: release=shubhodeep1/coding-workflows@stable contains=shubhodeep1/coding-workflows#<N>` or `WAITING: issue=<owner>/<repo>#<N>` instead of `BLOCKED:`.
  - **Parse order.** clarify "Parse Codex output" (unfenced lines of `CODEX_OUTPUT_FILE`) and plan "Parse planning output" (`CODEX_OUTPUT_PARSE_FILE`) look for a `WAITING:` line before the `BLOCKED:` scan and run `dependency_wait_resume.py parse-waiting` from `SUPPORT_SCRIPTS_DIR` (regular file, not a symlink). The helper validates with the scan's own `_validate_wait`: `pr` names this repo or `shubhodeep1/coding-workflows`, `release` must contain an upstream PR, `issue` names this repo and never this issue, N is 1-10 digits, a self-reference is rejected, one pair of backticks is stripped. A wait is a sub-case of `blocked=true`: the step sets `blocked=true`, `needs_clarification=false` and `waiting=true` with `waiting_kind`, `waiting_repo` and `waiting_number`. A valid wait wins over a `BLOCKED:` line (reason `WAITING: <target>`); any other `WAITING:` line keeps the `BLOCKED:` reason or becomes the reason, with `waiting=false`.
  - **Park.** The existing blocked handler steps run `park --phase clarify|plan` first when `waiting=true`: one aliased GraphQL target read (plus one `compare/<sha>...stable` for a merged release PR), then one comment `Waiting on dependency: <target>` with `<!-- AI_DEPENDENCY_WAIT_V1 {"kind","repo","number","since"} -->` (no `"source"`), then `ai:waiting-on-dependency`. On `parked` the step removes `ai:clarification`, `ai:planning`, `ai:awaiting-approval` and `ai:blocked`, sends the CRITICAL Telegram page and exits; P8b's poller scan resumes the issue. Any other status (`already_resolved`, `invalid_target`, `read_failed`, `comment_failed`, `label_failed`, `disabled`, `invalid_args`, `error`, `helper_missing`) appends ` (dependency wait not parked: <status>)` to the reason and takes the unchanged `ai:blocked` path. The `/answer` gate in `plan.yml` is unchanged.
  - **Helper missing and switch.** `dependency_wait_resume.py` is an optional staged script for clarify and plan; without it (older support ref, legacy staging) the step logs `::warning::DEPENDENCY_WAIT_PARK op=parse outcome=skip reason=helper_missing` and the line takes the `BLOCKED:` path, so a WAITING-only answer never reads as clear. `DEPENDENCY_WAIT_RESUME_ENABLED=false` does the same. The clarify BLOCKED-verify retry (P9b) also accepts a `WAITING:` answer as terminal.
