- `AUTOFIX_SKIP_CLEAN_SAME_HEAD` (default `true`, issue #8952) lets the review gate skip a full review of a head that already had a clean one. Writer: the "Post editor summary comment" step ends the "AI autofix editor summary" comment with `<!-- review-autofix-clean:v1 head=<40-hex> base=<40-hex base SHA> support=<REVIEW_SUPPORT_SHA|none> run=<run id> -->` as its last line only when the editor wrote a real summary (not the fallback), `Change status` is `not-edited`, nothing was committed (`DID_COMMIT` not `true` and the committed-files file holds only placeholder lines), no `sandbox-excluded path` finding was declined, and the head (`AUTOFIX_FAILURE_HEAD_SHA`), base (`AUTOFIX_CLEAN_MARKER_BASE_SHA`, from the new gate output `base_sha`) and run id are valid. Gate: after the terminal same-head block and before the fingerprint cap, every event with a numeric PR (except `pull_request` `reopened`) skips with `skip_reason=clean_same_head` when the newest trusted marker for the current head matches the current base SHA and support SHA, the PR is `mergeable=true`, the base was not retargeted, neither `force_rb_judge` nor `post_sync_test_repair` is set (the poller dispatches the integration test repair once per head), and no invalidator applies. Trust: the comment author must be the `GH_PAT` login (`GET /user`), the body must start with `AI autofix editor summary`, and the marker must be the last non-empty line. Invalidators: a comment with no valid `created_at` (`comment_time_unavailable`, order unknown); any trusted `ai:freshness-ci-failed:v1` marker for the head; a newer trusted `ai:single-issue-security-pass:v1` result (`clean`, `findings` or `failed`, not `pending`) for the head (`newer_security_pass_result`), because the security-pass report re-dispatches the review with only `pr_number` and that run must merge or start the next cycle; a newer trusted failure, partial, no-op or changes-lost comment (provider-outage resumes and failed post-summary tails land here); a newer comment or submitted review from anyone who is neither the `GH_PAT` login nor a `Bot`. Bot-submitted reviews deliberately do not re-arm the skip, like Bot comments, so reviewer bots (for example Copilot) cannot re-arm a full review on every unchanged head. `[force-review]` and the `force-review` label force one full review per head but do not bypass this skip once the head has a marker (decision Q8: A). API cost: the comments come from the shared `gate_fetch_marker_comments` read, which now also keeps `ai:single-issue-security-pass:v1` bodies and a body-less `{id, author_login, author_type, author_association, created_at, body: "", activity_only: true}` record for every other non-Bot comment, in the same call and order; one paginated `GET pulls/{n}/reviews` runs only when a trusted marker survives every comment-based invalidator. Provider-outage recovery dispatches (`scripts/provider_outage.py` resume) carry only `pr_number`, so the gate has no separate precheck for them: a resume for a `provider_unavailable` failure re-arms through `newer_failure_marker`, and a label-marker resume on a clean head would only repeat the clean review, because the review-blocked judge is reachable on such a head only through `force_rb_judge`, which bypasses the skip. Every lookup or parse failure logs `AUTOFIX_GATE_CLEAN_SAME_HEAD_CHECK outcome=error` and runs the review. Set the repo variable to `false` to turn the skip off.
