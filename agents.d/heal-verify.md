Post-merge heal verification (P7 of `docs/plans/heal-evidence-reproduction-and-trends-plan.md`, Refs #8434): the `heal-verify` job of `.github/workflows/workflow-failure-heal-intake.yml` runs `scripts/workflow_failure_heal_verify.sh` on the existing hourly `schedule` trigger when `WORKFLOW_HEAL_VERIFY_ENABLED` is `true` (default `false`, defaulted in the workflow and the script; `WORKFLOW_HEAL_VERIFY_MAX_PER_TICK` default 3, clamped 1-10). One GraphQL query per tick returns `viewer{login}`, the closed `ai:workflow-heal` issues updated in the last 7 days (closing pull requests via `closedByPullRequestsReferences(includeClosedPrs:true)`, last 30 comments) and the open heal issues. A heal is kept only when the pipeline login wrote it, it has `fp=`/`root=` markers and `source=<this repo>#run` (D3: consumer and PR-branch heals log `unsupported_source`), it was closed as completed within 7 days by a merged same-repo pull request (the latest one merged before the close), its target branch is valid, and its first `Failed run` workflow name matches the `name:` of exactly one release / CI / scheduled-check workflow file of the checkout (else `workflow_unresolved`), and its body records a failing step (else `step_unknown`). Marker `<!-- workflow-failure-heal:verified:v1 outcome=<held|recurred|recurred_lineage|inconclusive> run=<id> -->` counts only as the last line of a comment by the pipeline login; one posted at or after the closing PR's `mergedAt` means already verified (D1), earlier `outcome=recurred` markers count toward escalation. Per kept heal (at most 3 REST reads, D4): the workflow's runs on the target branch created since the merge, sorted oldest first and limited to completed same-repo non-`pull_request*` runs on that branch (D5; when the list is cut off at 100 runs it is read once more, into its own file, for `created=<mergedAt>..<oldest run on the cut-off page>`, and the two lists are joined, de-duplicated by run id, so together they hold every run since the merge; that read counts toward the 3, so a failed run on a descendant commit, which needs a compare and a jobs read, waits as `read_budget`; if that read is also cut off the heal stays `pending`, reason `runs_truncated`; a failed window read logs `runs_window_failed`); the oldest `success`/`failure`/`timed_out` run on the merge commit, or on a descendant (`compare` `ahead`/`identical`, at most 2, only while a failed run still leaves room for the jobs read), decides. No decisive run: `pending`, retried next tick. Success: `held` marker comment. Failure: one jobs read, the intake's step derivation (`select-evidence-jobs`, first failed step per job); a different step posts `inconclusive` (D6); the same step with an open pipeline-written heal of the same `root=` filed after the merge posts a `recurred_lineage` comment linking it and does not reopen; otherwise the heal is reopened (PATCH first; a failed reopen writes nothing) with a `## Fix did not hold` comment, and with an earlier trusted recurred marker it also gets `ai:workflow-heal-escalated` and a CRITICAL Telegram alert (numbers and URLs only). Run-derived text is sanitised (`single_line`, `neutralize_untrusted_routing`, backticks removed, inside code spans); URLs are built from validated ids. If the comment cannot be posted after a reopen (one retry), the script reads the comments posted since the merge once (one error-path read beyond the 3 per-heal reads); when the `recurred` marker by the pipeline login landed anyway, the heal stays open and the escalation path runs; when that read fails, is malformed or returns a full page of 100 comments without the marker, the heal also stays open (`warn issue=<n> reason=comment_failed reclosed=false` and a WARNING; the second-recurrence escalation still runs), because re-closing a heal whose marker landed would make the next tick skip it as `already_verified`; only a successful read without the marker closes the heal again as completed so the next tick redoes the check. Each run starts one window further through the candidates (`GITHUB_RUN_NUMBER` times the cap), so pending heals cannot hold every slot. Every API error fails open and the script always exits 0. Known limits: a heal whose workflow never runs on its target branch stays `pending` until it leaves the 7-day window, and so does a heal whose runs list is cut off when its deciding run failed on a descendant commit (`read_budget`) or when more than 100 runs fall between the merge and the oldest run on the cut-off page (`runs_truncated`); an intake gen+1 filed while the heal is reopened can leave two open heals in one lineage, which the next intake's dedup handles.
