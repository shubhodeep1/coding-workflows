<!-- agents: section="Workflow architecture" -->
- Updater PR stall alarms (#9483). Consumer-updater PRs (`auto/update-workflows-<sha12>`) no longer stall silently:
  - The "Commit and push updates" refresh writes the PR body with REST `PATCH repos/<repo>/pulls/<n>` (body via `jq --rawfile`, `--input -`), not `gh pr edit`, which needs the `read:org` scope `GH_PAT` lacks. A failure still logs `UPDATER_PR_DELIVERY outcome=failed reason=pr_edit_failed`.
  - The `verify` job's step `verify_merge_blocked` ("Fail when auto-merge could not be enabled") runs only when `verify_publish` succeeded with `auto_merge=failed`. It logs `::error::UPDATER_PR_VERIFY outcome=merge_blocked reason=auto_merge_failed pr=<n> head=<sha>`, sends a raw Telegram alert (`curl --fail`) gated by a step-level `ALERT_MSG_LEVEL` that defaults to `WARNING`, not the workflow's `SILENT`, so it fires when nothing is configured and an explicit `SILENT` still mutes it (skipped with a log line when `TG_BOT_SECRET`/`TG_ADMIN_CHAT_ID` is unset) and exits 1. It never touches the `ai-update-workflows/verify` status, so a human can still merge; "Mark verify failure" keeps its `verify_publish.outcome != 'success'` condition.
  - `scripts/review_head_gate.sh` `review_head_gate_updater_exempt <repo> <pr> <sha> <head ref hint> [live pr json]` posts `ai-review/head-gate` = `success` for an updater PR only when the head ref matches `^auto/update-workflows-[0-9a-f]{12}$`, the PR is open and not from a fork, the live head equals the gated SHA, and the combined status of that SHA has `ai-update-workflows/verify` and `coding-workflows/workflow-integrity` both `success` (integrity is a commit status from `workflow_integrity.yml`, not a check run). Anything else keeps the gate pending (fail closed). Callers: `review_head_gate_main` (late `head_gate` step, which passes `GATE_HEAD_REF`; the early gate call passes none and makes no API call), the updater branch of `scripts/review_enable_auto_merge.sh`, which passes its own fresh PR read, and the review-blocked judge's `updater_verify_hold` branch in `scripts/review_rb_judge.sh`, which runs late enough to see verify and integrity on non-clean reviews. A status POST that fails logs `outcome=skipped reason=post_failed`. The judge step (`rb_judge`) passes `REVIEW_HEAD_GATE_UPDATER_EXEMPT_ENABLED` like the other two review callers. Because all review callers can run before verify succeeds, the updater's `verify` job re-checks the same rules in step `verify_head_gate` ("Post review head gate for the verified updater PR", after `verify_publish` succeeds): up to `UPDATER_HEAD_GATE_POLL_ATTEMPTS` (6) combined-status reads `UPDATER_HEAD_GATE_POLL_SECONDS` (20) apart while verify or integrity is missing or pending, then one PR read and one status post with `GH_PAT` (job-token fallback). It logs `REVIEW_HEAD_GATE mode=updater_exempt source=verify_job ...` and never fails the job. `REVIEW_HEAD_GATE_UPDATER_EXEMPT_ENABLED` (and `REVIEW_HEAD_GATE_STATUS_ENABLED`) default to `true`; `false` restores the old behaviour on every path.
  - `audit_consumer_drift.yml` runs every 6 hours (`0 */6 * * *`). For each drifted consumer, `scripts/audit_consumer_drift.py` reads the coding-workflows pins from the wrappers it already fetched, maps them to `vX.Y.Z` tags (`--release-tags-file`, a `git for-each-ref` TSV of this repo's annotated tags) and counts from the tag time of the first release newer than the oldest pin. At `--pin-max-age-seconds` (`CONSUMER_PIN_MAX_AGE_SECONDS`, default 86400) or more, or when the pin or tag time is unknown, `results[].pin_age.stale` is true, `totals.pin_stale` counts it, and the report raises WARNING with a "Behind stable for <threshold> or more" section (`behind_stable`; "24 hours" at the default) or a "Behind stable, pin or release tag time unknown" section (`pin_unknown`, `tag_time_unknown`), even when an open update PR covers the drift. `SYNC_PR_STALE_AFTER_SECONDS` is unchanged.
