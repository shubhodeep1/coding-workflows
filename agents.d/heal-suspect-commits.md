<!-- agents: section="Workflow architecture" -->
Heal suspect commits (P3 steps 4 and 5 of `docs/plans/heal-evidence-reproduction-and-trends-plan.md`, Refs #8434): behind the same `WORKFLOW_HEAL_TREND_ENABLED` switch (default `false`), `_heal_build_suspect_commits` runs right after `_heal_build_run_time_trend` and before the diagnosis and calls `workflow_failure_heal.py suspect-commits` once (`GH_RETRY_MAX_ATTEMPTS=1`; the step itself makes no `gh` call). It acts only on the shapes the trend step classified as `stall` or `timeout`, read from `${RUNTIME_DIR}/trend/summary.json` (the trend step now also writes its summary JSON there); any other or missing shape logs `skipped reason=shape_<shape>` with no call. The baseline is the failing workflow's last green run on its branch: `_heal_run_reproduction` writes its `last-green-run` result (only while the switch is on) to `${RUNTIME_DIR}/last_green_run.json` (`HEAL_LAST_GREEN_CACHE_FILE`, keyed by repo, workflow id, branch and failing SHA), and the suspect step reuses it only when every key matches (`last_green=cached`); otherwise `suspect_commits` calls `last_green_run` itself (`last_green=fetched`). It then makes one `GET repos/<repo>/compare/<green>...<failing>` and, only when the trend's machine line says `regression=true`, one `GET repos/<repo>/commits?sha=<default>&since=<day>T00:00:00Z&until=<day+1>T00:00:00Z&per_page=50` for the first slow day (skipped with `reason=default_branch_unavailable` when the default branch is unknown, and always for a consumer report, because the intake passes its own default branch only when `SOURCE_REPO` is this repository; it never falls back to `main`). Without the failing run's `created_at` the step makes no unbounded last-green lookup, and a compare whose `status` is `behind` (a baseline newer than the failing SHA) is not used; both give `partial/no_last_green`. So the suspect step makes at most 3 GETs and P3 in total at most 9 per report (6 trend pages, last green, compare, commits), counted in `GH_PAT_BUDGET`. The `## Suspect commits` section follows `## Run-time trend` inside the body `compose-issue --suspect-commits-file` checks with `validate_heal_issue_body_routing`; it lists the newest 15 commits of the range (subject, short SHA, `#N` parsed from a squash subject's trailing `(#N)`); the compare is not paginated, so when GitHub lists fewer commits than `total_commits` (only the oldest page of a long range) the caption says the last 15 of the listed oldest commits are shown and the newest are not listed and, separately, the range's aggregate pipeline files under `scripts/`, `.github/workflows/`, `workflow-templates/` and `prompts/` (at most 20, never attributed to single commits, since the compare response has no per-commit file list). Commit subjects and file names are attacker-writable: they go through `sanitize_text`, `single_line` and `neutralize_untrusted_routing` (`<!--` becomes `&lt;!--`, routing keys are defused), and the section never contains a `regression=` token. The parsed compare `files[]` (`filename`, `status`, `changes`; removed entries kept) is written to `${RUNTIME_DIR}/suspect_commits/compare_files.json` and exposed as `SUSPECT_COMPARE_FILES_FILE` so the later suspect-scope phase needs no second compare call. Everything fails open. With the switch off the intake makes no call, writes no file and logs no line, so the body, API calls and output are byte-identical.
