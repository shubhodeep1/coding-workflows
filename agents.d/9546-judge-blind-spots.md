**Both orchestrator judges see work that is waiting on review (issue #9546, Refs shubhodeep1/tele-funtoken-msg-scoring#5241).** The stall judge read only the in-progress Actions runs blob (`_load_actions_runs_cached`), so a review queued for a runner or already finished looked like "no review ever ran", and it escalated three reviewable PRs to `ai:needs-human`. The unblock judge never saw a blocked issue's open PR, so it decided the work "never landed" and ordered a re-implementation (`retry_budget` on tele-funtoken-msg-scoring#5258).
- **Stall judge** (`invoke_stall_judge` in `scripts/orchestrate_poll_process.sh`, switch `STALL_JUDGE_LIVE_REVIEW_RUNS_ENABLED`, default `true`). With an open linked PR, `_stall_judge_review_runs_for_pr` makes one branch-scoped `gh run list --branch <head_ref> --limit 20 --json databaseId,name,workflowName,status,conclusion,headSha,createdAt` per judge call. It uses the review-name filter of `_direct_inflight_review_run_on_branch`. The runs are merged into `recent_review_workflow_outcomes`: de-duplicated by `id`, newest first, at most 5, each with `head_sha`. `review_waiting_for_runner` is true when a `requested` / `queued` / `waiting` / `pending` run on the PR's current `head_sha` (or a cached, trust-filtered PR-named `workflow_dispatch` run, which carries the default-branch SHA) is younger than `REVIEW_RUN_MAX_RUNTIME_MINUTES`. While it is true, a judged or effective `escalate_human` or `close_and_reissue` (including the replay-cap forced escalation, and a judged escalation that `ENABLE_STALL_HUMAN_TERMINALIZATION=false` normalized to the ladder action) is shown as `wait (review_waiting_for_runner)`; the comment is posted, `STALL_SKIP ... reason=review_waiting_for_runner` is logged, `STALL_RECOVERY_EFFECTIVE_ACTION=review_waiting_for_runner` is set, and the judge returns 1, so no recovery attempt is counted. A judged `escalate_human` on such a tick leaves `judge_escalate_streak` unchanged. Every `fallback_action` path (judge failure, unparseable output, `resolve_merge_conflict` fallbacks, unknown action) goes through `_stall_judge_review_wait_hold`, which holds an `escalate_human` / `close_and_reissue` fallback the same way. A listing failure, no open PR, or the switch off keeps today's 3-entry list without `head_sha`; `review_waiting_for_runner` is added to the diagnostics only when it was computed (listing and merge succeeded and the clock was read), so it is absent with the switch off, without an open PR and on a listing or merge failure, and the prompt reads an absent flag as unknown rather than as "queued entries are stale".
- **Unblock judge** (`scripts/unblock_judge.sh`, switch `UNBLOCK_JUDGE_LINKED_PR_ENABLED`, default `true`). For an issue item, `unblock_linked_open_pr` runs once before the fingerprint. It makes one `pulls?state=open&head=<owner>:ai/issue-<item>&per_page=1` read and, only when a PR is returned, one `pulls/<n>` read, which re-checks `state == open`, the exact head ref, a same-repository head (case-insensitive) and a 40-hex head SHA. It writes `${RUNTIME_DIR}/linked_pr.json`: `null`, or `{number, head_ref, head_sha, base_ref, changed_files, additions, deletions}`; titles and bodies are never stored. When a PR is found, the evidence gains `linked_pr` (the number only, so a new head does not change the fingerprint), the context gains `linked_open_pr`, and the PR's diff fills `pr_diff.txt` (one diff read, 120 KB cap). These are success-path counts: the list, detail and diff reads go through `gh_retry` (CONSIST-001), so a transient error is retried up to `GH_RETRY_MAX_ATTEMPTS` times. Every `unblock_ledger.py validate` call then gets `--linked-pr-file`: `retry_budget`, `reissue` and `descope` must name `#<number>` (`(?!\d)` boundary), or they are refused with `linked_pr_unreferenced:<n>`. That refusal gets the run's single re-ask (shared with the sandbox re-ask, `op=linked_pr_check outcome=reasked|refused_after_reask`); a second refusal takes the existing `invalid_verdict` / park path. Any lookup failure writes `null`: context, fingerprint and validation stay as before. A failed diff read (`reason=diff_failed`, including GitHub's 406 for a diff too large to render) leaves `pr_diff.txt` empty but keeps `linked_pr.json`, so the judge still gets `linked_open_pr` and validation still requires `#<number>`. A failed context merge (`reason=context_merge_failed`) writes `null` before validation, because the judge was not shown the PR; the fingerprint keeps the PR number.
- Tests: the `_sjr_*` cases in `tests/test_orchestrate_poll_process.py` and the `linked_pr` cases in `tests/test_unblock_judge.py`.
