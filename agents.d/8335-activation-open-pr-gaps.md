- **Activation gaps an open PR already fixes get no fix issue; plans never wait on another PR (#8335, refs tele-funtoken-msg-scoring#4992).** `scripts/activation_verify.sh` (`activation_open_prs_json`) adds `open_pull_requests` to the model context: the 50 most recently updated open PRs from one `GET repos/<repo>/pulls?state=open` call, keeping only same-repository heads authored by `github-actions[bot]` or an OWNER/MEMBER/COLLABORATOR, with number, title and head ref (200 characters each), draft flag and body (1500 characters). The list is merged into the context through a file (`--slurpfile`), not an argument. A failed lookup logs `::warning::ACTIVATION_VERIFY open_pull_requests unavailable reason=lookup_failed` (`reason=parse_failed` when the call succeeded but returned no usable list) and passes an empty list; a failed merge logs `reason=context_merge_failed`. A plan whose work is already on the planning ref emits `PLAN_SELF_CHECK: BLOCKER: work is already on the planning ref; nothing to implement` with `STATUS: NOT_CLEAR`, so an edit-free plan is never auto-approved. `prompts/mode-activation-verify.txt` lets the model set `open_pr` on a `code` gap that one of them already fixes. `activation_normalise_verdict` keeps it only when it is an integer in that list, and sets it to null otherwise or on an `operator` gap. A tagged gap is listed in the verdict comment as `- [code] <title> (fix in progress in open PR #N)`, is left out of the `ai:activation-fix:v1` issue, and is logged as `ACTIVATION_VERIFY mode= item= op=in_flight_gaps count= prs= outcome=left_to_open_prs`. When every code gap is tagged, no fix-issue search or create runs. `prompts/mode-plan.txt` and the live planner prompt (the inline heredoc in `scripts/run_plan_codex.sh`, pinned by `tests/test_plan_codex_step_extraction.py`) say implement only writes files. When another open PR already delivers an issue's work, the plan emits `PLAN_SELF_CHECK: BLOCKER: work is delivered by open PR #<N>; resume once it is merged` with `STATUS: NOT_CLEAR`, which `plan.yml` routes to `ai:blocked`, where the unblock judge's `pr_on_branch` hold can resume it after that PR merges. `prompts/mode-clarify-respond.txt` ("Pipeline-capability rule") forbids execution steps that post comments, close issues, or check or wait for another PR. Limitation: a gap tagged to a PR that is then closed unmerged is recorded only in the verdict comment.
