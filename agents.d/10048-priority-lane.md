- **Priority lane at the merge-lease grant (issue #10048).** Corrected premise: `_merge_lease_order_key` used to rank a PR first only by its own `MERGE_TRAIN_PRIORITY_LABELS` labels or a same-repository `MERGE_LEASE_PRIORITY_HEAD_PREFIXES` head; a priority label on the linked issue did not count. New optional trailing inputs, where an empty value gives byte-for-byte the earlier output: `_merge_lease_order_key <pr> <labels> [<head_ref>] [<linked_priority>]` (only `1` ranks first), `_merge_lease_queue_first <pulls> [<cand>] [<skips>] [<exclude>] [<priority_csv>]` and `_merge_lease_queue_order <pulls> [<skips>] [<exclude>] [<priority_csv>]`. Only the merge train fills `<priority_csv>`. `_mt_priority_lane_prepare` (`scripts/review_merge_train.sh`) runs once per process, only when some PR waits for a lease. It makes one aliased GraphQL call through `_mt_pr_meta_prefetch` and keeps the PRs `_mt_pr_is_priority` returns 0 for in `_MT_PRIORITY_LANE_PRS`; a return of 2 (unknown) gives no priority. The update-mode gate callers in `scripts/pr_checks_lib.sh` pass nothing.
  - Hold at the grant: `_mt_priority_lane_defer_for_base` reads the tick's run cache (`_MT_LEASE_RUNS_JSON`, shared with `_mt_lease_pr_runs_active`, so at most one listing pass per tick). It feeds `_pr_priority_lane_pressure` with the `_merge_lease_wedged_queued_seconds` cutoff and sets `_MT_PRIORITY_LANE_DEFER_CSV`. Those waiters are added only to a separate exclude list given to `_merge_lease_queue_first`, never to `tick_excluded` / `tm_excluded`. A queue that is empty only because of them sets `tick_priority_deferred` / `tm_priority_deferred`: the lease stays free, the waiters keep `ai:merge-lease-wait`, and neither the queue-empty (D4) handling nor the `no_waiter` lines run.

- **Priority lane (issue #10048; `PRIORITY_LANE_ENABLED`, `PRIORITY_LANE_WAIT_MINUTES`, `PRIORITY_LANE_MAX_DEFER_MINUTES`).** The helpers are in `scripts/pr_checks_lib.sh` and make no API call: `_pr_priority_lane_enabled`, `_pr_priority_lane_settings`, `PR_PRIORITY_LANE_JQ_DEF` (`pr_priority_lane_verified`, the rules of `_mt_pr_is_priority`; `pr_priority_lane_run_pr`, which matches only `workflow_dispatch` runs titled `Internal: AI Review & Autofix [pr:N]` / `AI Review [pr:N]` from the default branch, `Security Audit (PR #N)` or `CI [pr:N]`), `_pr_priority_lane_pressure` and `_pr_priority_lane_decide`.
  - Review sweep: `review_sweep_annotate_head_gate` sends `REVIEW_SWEEP_HEAD_GATE_PRIORITY_QUERY` (the same call, with extra fields) and sets `priority_lane` on each row. It reorders the snapshot priority-first and creates `ai:priority` once if it is missing. `review_sweep_priority_lane_hold` makes one paginated `actions/runs?status=queued` read, only while a priority PR is open, and writes `${RUNNER_TEMP}/priority-lane-hold.txt` (`hold=`, `priority=`). The dispatch loop calls `_pr_priority_lane_decide sweep` after every other skip; `AUTOFIX_SWEEP_END` gains `skipped_priority_lane=`.
  - Final-CI sweep (`scripts/review_final_ci_sweep.sh`): priority gate-success heads are checked first. `FINAL_CI_SWEEP_PRIORITY_LANE_FILE` (missing or malformed means no hold) defers both the final-CI ensure and the base sync; the summary lines gain `deferred_priority_lane=`.
  - Each deferral is capped at `PRIORITY_LANE_MAX_DEFER_MINUTES`, counted from the hold start: `_pr_priority_lane_pressure` prints `<pr> <age_min> <hold_since_epoch>` (the run's `created_at` plus the wait), the sweep passes it on stdout and as `since=` in the hold file, the merge train keeps it in `_MT_PRIORITY_LANE_HOLD_SINCE`, and `_pr_priority_lane_decide` takes it as an optional 7th argument (the PR's `updated_at` is the fallback). A final-CI head deferred before its status read spends no per-tick slot, and the base-sync pass takes priority heads first; `0` keeps the ordering and turns the hold off. With the lane off, the query string, the order and every decision are the same as before.
