- **Review-blocked judge holds orchestrator integration PRs (#8232).** Right after the consumer-updater hold, `scripts/review_rb_judge.sh` (block between `# BEGIN/END rb-judge orchestrator integration hold (#8232)`) holds `merge`, `merge_with_followup`, final-attempt `fix` (`IS_FINAL=true`) and `close_and_reissue` when the PR head ref matches `ORCH_INTEGRATION_BRANCH_PATTERN` (default `^orchestrator/project-`; an empty or invalid ERE warns and falls back to `^orchestrator/project-([0-9]+)$`, the same rule as `_orch_is_integration_pr` in `scripts/review_enable_auto_merge.sh`), unless the PR is already merged. The hold posts one PR comment, logs `AUTOFIX_AUTO_MERGE_HEAD_BOUND pr= head_sha= action=skip reason=orchestrator_integration_pr judge_action=<action>`, writes `judge_handled=true`, `judge_action=orchestrator_integration_hold` and `judge_skip_reason=orchestrator_integration_pr`, and exits 0. For merge-type actions it first runs `rb_security_merge_gate` (which skips integration PRs) and, only when it passes, posts `ai-review/head-gate` `success` on the 40-hex judged head, as `review_enable_auto_merge.sh` does after its security pass and before its own suppressor; a held gate leaves the status alone and the hold still applies, and `close_and_reissue` gets no status. It never swaps a phase label, adds `ai:ready-to-merge`, creates an issue, merges or closes. A non-final `fix`, `skip` and every other action are not held. The "Telegram review-blocked judge decision" step reports `orchestrator_integration_hold` at `DEBUG`; `finalize_integration_merge_if_needed` merges the PR once the current integration head carries a runtime-validation pass. Tests: the `test_integration_hold_*` cases in `tests/test_review_rb_judge_head_binding.py`.
- **Unvalidated heads in external finalize (#8232).** `mark_validation_complete` records the passed integration SHA in the state field `validation_last_passed_sha`. When the external-finalize path completes a project whose final PR was merged outside the orchestrator, `external_finalize_validation_notice` (in `scripts/orchestrate_poll_process.sh`) runs `validation_history_gate_decision_for_sha` (the per-SHA body of `validation_history_gate_decision_for_current_sha`, which now delegates to it) on the merged final-PR head. An unvalidated head (`missing_pass`, `later_non_harness_failure`) appends a warning naming the merged SHA and the last validated SHA (or "none recorded") to the completion comment and the CRITICAL Telegram message; an unavailable history appends "could not be confirmed" (the state field never confirms a pass on its own; it only names the last validated SHA, and a project validated before this change shows "none recorded"). With `ENABLE_VALIDATION` off nothing is appended (`outcome=skipped reason=validation_disabled`). Completion and `ai:merged` proceed either way. No GitHub API call.
