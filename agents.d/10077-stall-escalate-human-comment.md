**Stall escalate_human issue comment (#9821, re-implemented in #10077; Refs #9853).** `_post_stall_escalate_human_comment <issue> <phase> <minutes> <local_id>` in `scripts/orchestrate_poll_process.sh` sits just above `execute_stall_recovery_action`. That function's `escalate_human)` arm calls it only after `has_label` reads `ai:needs-human` back on the issue; when the label is not confirmed, no comment is posted. It posts one comment on the stalled issue containing: the heading `## Stall recovery: human input needed`; the reason (`STALL_ESCALATE_HUMAN_JUSTIFICATION`, or `Stall recovery ran out of automatic actions for this phase.` when it is empty or unset); the phase and stall minutes; `Tracking issue: #<TRACKING_NUM>` when `local_id` is set; the resume step (remove `ai:needs-human`); and the marker `<!-- ai:stall-escalate-human:v1 issue=<N> phase=<P> -->`. The reason has `<!--` / `-->` neutralised, because the judge's justification is model output. The judge dispatch arm of `invoke_stall_judge` sets `STALL_ESCALATE_HUMAN_JUSTIFICATION` to the judge's justification before `execute_stall_recovery_action`, unsets it afterwards, and keeps that call's return code. When the variable is set the comment logs `source=stall_judge`, otherwise `source=stall_recovery`. The helper is fail-open: it always returns 0, so a failed write never changes the recovery result. Nothing reads the marker yet. Tests: `test_stall_escalate_human_comment_*` in `tests/test_orchestrate_poll_process.py`.
