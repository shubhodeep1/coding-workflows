<!-- agents: section="Workflow architecture" -->
- **Stale `ai:review-blocked` clear after a clean review (#9369, re-issued as #9716).** The identical-failure cap job in `review_autofix.yml` adds `ai:review-blocked` to a PR with no linked issue, and before this change no review path removed it (PR #9218 and PR #9229 kept it after the harness fix until it was removed by hand). `scripts/review_autofix_step_post_editor_summary.sh` now calls `review_blocked_stale_clear_after_clean` right after the editor summary posts, only when that comment carried the `review-autofix-clean:v1` marker. Order: label present in `PR_PAYLOAD_FILE` (`label_absent` otherwise); at least one comment in `PR_ISSUE_COMMENTS_FILE` with an own-line `<!-- review-autofix-failure-cap:v1 head=<sha> ... [support=<sha>] -->` (`no_cap_marker`). A marker is stale when its head differs from the clean head (`cap_head_mismatch`) or, when the clean support is a SHA, its `support=` is missing or differs (`cap_support_mismatch`), else `same_head_same_support`, and it must say it labelled `this pull request (no linked issue found)` (`cap_not_pr_label`). When no marker from any author is stale and labelled the PR, the label is kept with the newest marker's reason and no call is made. Otherwise one retried `gh api user` call (`marker_author_unavailable`) picks the newest marker whose author matches case-insensitively (trust first, then newest, so a newer marker from another author cannot shadow it; `untrusted_cap_author` when none matches), and that trusted marker's own stale and PR-label checks decide; then one `DELETE repos/<repo>/issues/<pr>/labels/ai%3Areview-blocked`, where 2xx or an `HTTP 404` error is `removed` and anything else is `error reason=delete_failed` with a `::warning::`. A missing or unreadable snapshot file falls back to one PR or paginated comments read (`snapshot_unavailable` when that fails). The usual clean run makes no new call; the stale path makes at most two (`GET /user`, the DELETE). Linked issues are untouched. The function always returns 0, so the step never fails on it.
