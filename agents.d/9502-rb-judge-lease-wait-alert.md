<!-- agents: section="Workflow architecture" -->
- Review-blocked judge base-freshness deferral alert (#9502, `.github/workflows/review_autofix.yml`). When `scripts/review_rb_judge.sh` defers `merge_with_followup` with `judge_skip_reason=base_freshness_unknown`, `rb_judge_emit_lease_blocker` also writes `judge_merge_lease_blocker=<PR>` when `PR_BASE_FRESHNESS_LAST_REASON` is `merge_lease_*` and `MERGE_LEASE_BLOCKER` (set by `_merge_lease_gate` in `scripts/pr_checks_lib.sh`: the lease holder, or the first queued PR for `queued_behind`) is numeric; no API call. The "Telegram review-blocked judge decision" step sends this reason at WARNING (not the catch-all CRITICAL "autofix exhausted"), names the PR the lease is "held by or queued for" and gives lease guidance only when that output is numeric; other freshness reasons (`compare_failed`, `pr_files_failed`, ...) get neutral "check the run log" guidance. `scripts/review_autofix_step_post_review_blocked_comment.sh` writes the matching comment text, appends `<!-- rb-judge-base-freshness:v1 head=<sha> -->` (head only; the #9249 crash marker wins on a crash run, no marker on a provider outage) and reuses the #9249 dedupe read, writing `rb_judge_freshness_repeat=true|false` (fail open). `RB_BLOCKED_FRESHNESS_REPEAT=true` makes the alert step log and send nothing. Known residual: on a security-pass-only run the comment step does not run, so the output is empty and the WARNING is sent on every same-head re-fire. Tests: `tests/test_review_autofix_rb_judge_crash_alert.py`.
