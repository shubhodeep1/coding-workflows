### The review sweep caps dispatched review rounds per PR

`.github/workflows/review_autofix_sweep.yml` dispatches `internal-review.yml` every 30 minutes for each open non-draft PR without an active review run. Every mechanism inside a review run has its own cap (`MAX_AUTOFIX_ITERATIONS`, `MAX_SECURITY_PASS_CYCLES`, the fingerprint cap), but nothing bounded the number of runs per PR. Between 2026-11-10 and 2026-11-17 `Internal: AI Review & Autofix` ran 3,778 times over 398 PRs (median 4 per PR, 90th percentile 26, 81 on PR #9178, 74 on #9134, 70 each on #9010 and #9180); 2,430 of those runs were `workflow_dispatch` runs, and sweep ticks such as run 44153959393 show the sweep as their dispatcher. PR #9134 was dispatched every two to five hours for four days, each round ending without a merge (run 44153595157: autofix count 5 of 5, security pass cycle 14).

`scripts/review_sweep_round_cap.sh` is sourced by the sweep's "Enumerate open PRs and dispatch internal-review.yml" step from the trusted default-branch checkout (`.ci-rerun-support`), next to `scripts/review_sweep_head_gate.sh`. When it is missing the step behaves as before.

- **Count.** `review_sweep_round_counts <owner/repo> <default branch> <window hours>` makes one paginated listing per tick for all PRs: `actions/workflows/internal-review.yml/runs?event=workflow_dispatch&created=>=<cutoff>&per_page=100`, `ceil(runs in window / 100)` calls (about 7 at 350 dispatched runs a day and the default 48 hours), each page projected to the six fields the count needs, through `gh_api_retry` when the step defined it. It prints a JSON object mapping PR number to count. A run counts when it is a `workflow_dispatch` run on the default branch (or with a null `head_branch`), its path is `internal-review.yml` and its title is exactly `Internal: AI Review & Autofix [pr:<N>]`, the provenance rule of the sweep's active-run snapshot (issue #6629). Every dispatcher counts; cancelled runs and `pull_request`-event runs do not. Only runs created since the current head's commit count: the sweep's snapshot (the helper's optional fourth argument, by default the step's `prs_json`) carries `head_committed_at`, the head commit's committer date in UTC, which `scripts/review_sweep_head_gate.sh` reads in its existing GraphQL query. A PR without it is not counted, and when no row has it (the head-gate read failed) the listing is skipped (`outcome=read_failed reason=head_date_unavailable`). The count starts at the committer date, not at the push: a commit made well before it was pushed keeps the rounds dispatched in between. Without this scope the cheap same-head dispatches an approved head drew while it waited (about 48 a day) counted against the next push, which was then escalated before any round on it. GitHub returns at most 1,000 runs for a filtered listing: beyond that the oldest are missing, the counts are lower bounds and the log line carries `truncated=true`. The listing is skipped when the active-run snapshot is incomplete, because no PR is dispatched that tick.
- **Cap.** In the per-PR loop, after the active-run skip and before the approved-head final-CI check, a PR whose snapshot row carries a `head_gate_state` other than `success` and that has `SWEEP_REVIEW_MAX_ROUNDS` (default `10`) or more rounds in the last `SWEEP_REVIEW_ROUND_WINDOW_HOURS` (default `48`) is not dispatched: `AUTOFIX_SWEEP_SKIP pr=#<N> reason=review_round_cap rounds=<n> max=<n> window_hours=<n>`, counted as `skipped_round_cap` on the `AUTOFIX_SWEEP_END` line. The loop makes no API call for this. An approved head is never capped: while it waits for CI or a merge every tick's dispatch ends at the gate's cheap same-head skip, which the run listing cannot tell from a full round, and `ai:needs-human` on it would stop the merge train's final-CI resume (`blocked_by_ai:needs-human`). A row without the annotation (the head-gate read failed) is not capped either.
- **Escalation.** `review_sweep_round_cap_escalate` posts one comment ending `<!-- ai:review-round-cap:v1 -->` and then adds `ai:needs-human`, only when the PR does not carry the label yet; a capped PR that is already labelled costs no write per tick. `dry_run` writes nothing. `ai:needs-human` is the pipeline's existing hand-over label, so the escalation reaches its usual consumers: the workflow-failure-heal reporter (`pull_request: labeled`), the unblock scan (`scripts/unblock_ledger.py` `BLOCK_LABELS`) and the merge train. Nothing in the sweep removes the label; a person does.
- **Ways forward for a capped PR.** A new push is reviewed as usual (its `pull_request` run is not a sweep dispatch), `Internal: AI Review & Autofix` can be dispatched by hand, and the sweep resumes by itself once fewer than the limit fall inside the window. Removing the label while the PR is still over the limit makes the next tick add it back with a new comment. The cap is a rolling window, not a latch: a PR that stays stuck is dispatched again as rounds age out, about five rounds a day at the defaults.
- **Failure modes.** A listing that fails on any page, an unparseable listing, or an invalid repository or branch name logs `REVIEW_SWEEP_ROUND_CAP outcome=read_failed` and applies no cap that tick. A failed comment write adds no label, so the next tick retries both; a failed label write after the comment makes the next tick post the comment again with the label. Either way the PR is not dispatched that tick. Other dispatchers (the poller, the security pass, the merge train) are not blocked by the cap; their runs count toward it.
- Switch: `SWEEP_REVIEW_ROUND_CAP_ENABLED=false`.

### Generated chore PRs skip the reviewers and the security pass

Two generators reach the default branch through a pull request only because that branch requires status checks: the nightly validation self-test status (`.github/workflows/nightly-validation-selftest.yml`, branch `auto/validation-selftest-status-<run>-<attempt>`, file `analysis/validation-selftest-status.json`) and the workflow log analysis report (`scripts/workflow_log_analysis_deliver_report.sh`, branch `auto/workflow-log-analysis-report-<run>-<attempt>`, files `analysis/workflow-optimization-<date>[-N].md`). The status file is `*.json`, so the gate's protected-path rule kept a two-line generated change on the full reviewer path (PR #9570: ten dispatched review rounds in 26 hours, run 44035838206 with a 59-minute `codex-agent` job). The report took the docs-only skip and then waited on security-audit cycles of a generated document (PR #9636, runs 44023811452 and 44060663206).

`scripts/review_autofix_step_evaluate_gate.sh` now marks such a PR as a `generated_chore` skip candidate when all of these hold: same-repository head into the default branch; the head ref is the generator's branch name; the validated `/files` list holds nothing but that generator's file or files, with no rename; the PR's author is the pipeline login; and the PR does not carry `ai:security-pass-failed`. The check fetches the file list for a generator's head ref itself, so it does not depend on `AUTOFIX_SKIP_DOC_ONLY` or the small-diff limits. The candidate is exempt from the protected-path suppression and from the single-issue security pass, and goes to `deterministic-skip-merge` with `det_skip_reason=generated_chore`, which waits for CI and merges as for every other deterministic skip. Everything else is reviewed as before: a hand-written PR with the same title, another branch, another author, one more file, a status file on the report branch. `[force-review]`, the `force-review` label, a merge conflict, a failed freshness or final CI marker and the materiality check still send a candidate to review. The exemption adds no API call: the author comes from the gate's PR read, the file list and the pipeline login from reads the skip evaluation already caches. The decision is by branch, paths and author together because the pipeline login is also the repository owner's login, so the author alone proves little. Switch: `AUTOFIX_SKIP_GENERATED_CHORE=false`.

Forward-merge PRs (`chore: forward-merge stable into main`) and consumer wrapper syncs (`chore: update AI workflow wrappers`) change real code and are not exempt; wrapper syncs keep their own verified managed-sync skip (#7128).
