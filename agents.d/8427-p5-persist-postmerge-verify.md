### Check after merge (`PERSIST_POSTMERGE_VERIFY_ENABLED`, P5 of #8427)

Phase P5 of `docs/plans/persistent-unattended-workflows-plan.md`. Repo variables `PERSIST_POSTMERGE_VERIFY_ENABLED` (default `false`), `PERSIST_POSTMERGE_WINDOW_HOURS` (default `24`, clamped to 1..168) and `PERSIST_POSTMERGE_MAX_PER_TICK` (default `3`, clamped to 1..10), defaulted in `orchestrate_poll.yml`, `issue_pr_status.yml` and `scripts/persist_postmerge_verify.py` itself. The helper also reads `PERSIST_MAX_APPROACHES` (default `3`), `PERSIST_BUDGET_ENABLED` (default `false`, P6) and `WORKFLOW_HEAL_VERIFY_ENABLED` (default `false`, #8409 P7) with defaults.

- **Arm.** `issue_pr_status.yml` step "Arm check after merge" (`if: merged && vars.PERSIST_POSTMERGE_VERIFY_ENABLED == 'true'`, `continue-on-error: true`, every value through `env:`) runs after the label/close step, only for a default-branch merge whose orchestrator classification is complete, over `LINEAGE_FINALIZE_ISSUE_NUMBERS` minus `MANAGED_ISSUES` (partial-delivery and tracking issues are already excluded). `persist_postmerge_verify.py arm` reads the done-check from the newest pipeline-authored plan comment (`acceptance_check._plan_comment` + `parse_marker`). With a `post_merge` workflow it posts `### Check after merge pending` carrying the marker, adds `ai:verify-pending` and journals `stage=postmerge outcome=ok`; with `post-merge none` or no done-check it only journals. A PR labelled `ai:skip-activation-verify` is skipped; with `WORKFLOW_HEAL_VERIFY_ENABLED=true` an `ai:workflow-heal` issue is skipped (`heal_owned`). Re-running the step for the same merge re-adds the label without a second comment. The support fetch stages `persist_postmerge_verify.py acceptance_check.py attempt_journal.py gh_api_retry.py targeted_file_context.py` only when the switch is on (`targeted_file_context.py` because `acceptance_check.py` imports it; the plan listed four files).
- **Marker.** One per comment, never edited: `<!-- AI_POSTMERGE_VERIFY_V1 {"pr":N,"merge_sha":"40hex","workflow":".github/workflows/<file>.yml","job":str|null,"branch":"...","merged_at":"...Z","state":"pending|recurred|unverified"} -->` (`<`/`>` escaped). Trusted only from the pipeline login (`attempt_journal.resolve_login`) when the comment's first line is the header of the marker's state (`### Check after merge pending`, `## Check after merge failed`, `### Check after merge unverified`); every field is validated. The active marker is the newest `pending` with no later outcome marker for the same `pr` and `merge_sha`; the re-plan count is the number of trusted `recurred` markers.
- **Check.** `run_persist_postmerge_verify` in `scripts/orchestrate_poll_process.sh` runs right after `run_standalone_stall_recovery` on the idle-tick `STANDALONE_RECOVERY_SWEEP_ONLY` path and in the full poller's post-loop block. `check` lists `ai:verify-pending` issues (`state=all`) and grades at most `MAX_PER_TICK`, oldest `updated_at` first: orchestrator-managed body (`**Orchestrator metadata**`) or heal-owned → label removed; no trusted active marker (hand-applied or forged label) → label removed, nothing reopened. The run is the oldest completed run of the workflow on the branch created at or after the merge (cancelled/skipped/neutral/stale/action_required ignored; a run on the merge commit wins), from the tick's `_load_actions_runs_cached` blob first, else one `actions/workflows/<file>/runs?branch&status=completed&created=>=` read. A run on another head needs `compare/<merge>...<head>` status `ahead` or `identical`. A named job (exact, or matrix `job (`...) decides; otherwise the run's conclusion. `held` removes the label; `unverified` (window passed) removes it and comments; `recurred` reopens the issue with one `PATCH` that drops every phase label and `ai:verify-pending` and adds `ai:planning` (`ai:needs-human` once the re-plan count reaches `PERSIST_MAX_APPROACHES`), comments the run link, and journals `outcome=fail` with a failure text so P1 computes `failure_key`. With `PERSIST_BUDGET_ENABLED=true` and the P6 budget helper (`persist_budget.py`, not yet in the repository) present beside the script, P6 owns the re-plan (`reason=budget_owner`); without it the fallback cap applies (`reason=budget_absent`). The shell posts the existing bare `/answer` retrigger_plan comment for each re-plan issue, honouring `phase_cap_can_dispatch` / `phase_cap_note_dispatch`; a capped issue stays open in `ai:planning` for standalone stall recovery.
- **Switch off.** `arm` makes no call. `check` still lists the label once per tick and removes it (at most `MAX_PER_TICK`) where `closed_at` (or `updated_at` for an open issue) plus the window has passed, so a rollback leaves no stale labels.
- **API budget.** `arm`: at most 1 identity read (cached), 1 issue read (heal verify on only), 1 comments read and 3 writes. `check`: 1 list read plus, per candidate, 1 comments read, 1 workflow-runs read (cache miss only), 1 compare (head is not the merge commit), 1 jobs read (named job), at most 4 writes: at most 1 + 8 x `MAX_PER_TICK` per tick. The plan assumed the run cache was enough (1 + 6 x); it keeps only the 20 newest completed runs repo-wide, so the documented per-candidate runs read is needed.
- **Fail-open.** Every path exits 0. A failed read skips the candidate (`outcome=error reason=gh_read`); a failed label removal or reopen `PATCH` skips every later write for it, so the next tick retries.
- **Plan conflicts.** The existing `retrigger_plan` posts a bare `/answer` (not `/answer [auto-answered-by-orchestrator]`); P5 reuses the bare body. The release-gate replay fixture (`tests/fixtures/persist/postmerge_release_gate_runs.json`) is synthetic.
