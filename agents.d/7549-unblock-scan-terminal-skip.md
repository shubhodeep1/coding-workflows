- **Unblock scan leaves unchanged terminal items alone.** `scripts/unblock_scan.py select` reports two more `skipped` reasons in the existing `UNBLOCK_SCAN ... skipped={...}` line (no new log prefix). `fixup_escalated`: the item has a trusted `<!-- ai:unblock-fixup-escalated:v1 item=<n> -->` comment (`unblock_escalate_fixup` in `scripts/unblock_judge.sh`, after which every judge run only logs `reason=fixup_escalated`); the scan lets one judge run through per `--escalated-recheck-hours` (`UNBLOCK_JUDGE_ESCALATED_RECHECK_HOURS`, default 24, `0` turns the skip off), taken from the `Unblock judge #<n>` runs list the scan already reads, so a scope-blocked fix-up still gets its automation-path re-grant check (`unblock_try_regrant`) when the guard changes. A run that fell out of the 50-run window dispatches. `terminal_unchanged`: the newest trusted `ai:unblock:v1` marker for the item is a `close` for the item's current stop (`unblock_ledger.stop_for_labels`), an `ai:needs-human` `labeled` event follows it (the digest park ran) but the label is gone (on an `ai:orchestrator-managed` issue the poller's label repair, `reconcile_managed_issue_labels`, keeps `ai:blocked` over `ai:needs-human` in the phase group, which also prunes the digest entry), the newest block-label event is not newer than the marker, and no comment newer than the marker comes from anyone but the judge's own `ai:unblock` markers, orchestrator state comments or a `[bot]` login. The fingerprint of an issue or project is a function of its stop and its newest pipeline comment (`unblock_evidence`), so those are the inputs the scan checks instead of recomputing it. Pull requests (their fingerprint holds failing check names), failed projects and `NEEDS_HUMAN_DIGEST_ENABLED=false` (the judge then really closes the item) are not covered. An item still labelled `ai:needs-human` but missing from the digest is judged again, as before. No new API call (§15): the scan reads only the label events, comments and runs it already fetched.
