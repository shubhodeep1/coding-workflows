Heal intake linked runs (#8248): after the heal-scope freeze, `_heal_collect_linked_runs` in `scripts/workflow_failure_heal_intake.sh` follows same-repository `actions/runs/<id>` links found in the failed jobs' filtered logs (`workflow_failure_heal.py linked-runs`, reusing `extract_run_refs`; runs already in `run_refs` excluded, at most `WORKFLOW_HEAL_MAX_LINKED_RUNS`, default 4, `0` off, newest mention last). For each it reads the run (identity: same id and `repository.full_name` equal to the source repository, case-insensitive, before the jobs read), its jobs (`per_page=100`), and the log of the job holding the longest step. `linked-run-timeline` renders one line per non-skipped step (start, end, duration, conclusion; `[LONG]` at 600 seconds or longer than the shortest stall window the parent logs name, `stall_window_minutes`), and the log goes through `redact-stream`, `log-window` (the step's time window, whole log when nothing matches) and `filter-log --max-bytes WORKFLOW_HEAL_LINKED_RUN_LOG_BYTES` (default 30000). Output goes to `${RUNTIME_DIR}/linked_run_timelines.txt` (files under `${RUNTIME_DIR}/linked_runs/`, never `${LOG_DIR}`) and becomes the prompt section `=== LINKED RUN TIMELINES (UNTRUSTED) ===` before `=== FAILED RUN LOGS (UNTRUSTED) ===`, only when non-empty. Linked data never feeds the `ai:workflow-heal-scope:v1` marker, the ownership inputs or the fingerprint. API budget: at most 3 REST calls per linked run, none without a link. Fail-open log: `WORKFLOW_HEAL warn linked_run_skipped run=<id> reason=run_unreadable|run_malformed|other_repository|jobs_unreadable|jobs_malformed|timeline_failed|log_unavailable` (a `log_unavailable` run keeps its timeline), and `warn linked_runs_failed` when the collector itself fails. The release gate's wait-implement step and `scripts/stable_e2e_step_wait_review.sh` print `↳ Watching <Implement|Review> run <id>: <url>` once per scoped run id they already hold (`e2e_note_watched_run`, newest 5 kept) and append ` (watched runs: <url> ...)` (`e2e_watched_run_urls`) to their stall and timeout `::error::` lines; the Clarify and Plan waits hold no run id while polling and are unchanged.
