<!-- agents: section="Workflow architecture" -->
- **Red-main heal dedupe and triage target-files guard (issue #9823, plan Phase 2 of `docs/plans/pipeline-human-wait-elimination-plan.md`).** No new log prefix (`WORKFLOW_HEAL` and `CHECK_TRIAGE` already exist).
  - *Red-main group key.* `red_main_group_key(workflow_name, failing_job, branch, *, default_branch, event, workflow_path)` in `scripts/workflow_failure_heal.py` is pure (no API call, no I/O). It returns sha256 over `red-main|<workflow name without [cycle:<id>], lower-cased>|<failing job, lower-cased>|<branch>` only for a `push` run of a `CI_WORKFLOW_FILES` workflow on the default branch, else `""`. The `red-main-group-key` subcommand prints `{"key","reason"}` (`ok|not_default_branch_push|not_ci_workflow|no_job`) and always exits 0.
  - *Precedence.* `budget_decision(..., red_main_group=, red_main_grouping_enabled=True)` checks the group first, ahead of fingerprint, source, heal-source, re-issue, cause, lineage and budget rules: an OPEN listed heal issue whose leading header block has the exact line `<!-- workflow-failure-heal:red-main-group=<64 hex> -->` (read by `parse_red_main_group_marker`, because `_MARKER_RE` only reads `[a-z_]+` keys) returns `action=duplicate match=red_main_group`, and the unchanged `compose-occurrence` path records the new head and run. When any open group issue's own `fp` marker equals the report's fingerprint, the fingerprint rule matches it instead (`match=fingerprint`), so inline heal-scope recovery still applies. `_cmd_budget` also reads `WORKFLOW_HEAL_RED_MAIN_GROUPING_ENABLED` as a second gate. `compose_issue_body(red_main_group=)` writes the line after the optional `cause=` line for a `workflow_run` source only; `validate_heal_issue_body_routing` accepts at most one exact such line there.
  - *Intake.* `_heal_red_main_group_key` in `scripts/workflow_failure_heal_intake.sh` runs after `_heal_cause_key`, reads the run's `.event`, `.head_branch` and `.path` from the provenance-verified `PROVENANCE_RUNS`, the failing job from `SUMMARIES_FILE` and the default branch from `PROVENANCE_DEFAULT_BRANCH` (local files only), and logs `WORKFLOW_HEAL red_main_group key=<k> outcome=duplicate|new|skipped reason=<open_group_heal|fingerprint_match|other_match|no_open_group_heal|scope_recovery|budget_decision|disabled|ineligible_kind|reconstructed|no_verified_run|not_default_branch_push|not_ci_workflow|no_job|helper_failed>` (`other_match`: recorded on another heal issue, re-issue matches included; `scope_recovery`: a scope-recovery replacement issue; `budget_decision`: escalated or budget-capped, no new issue). The outcome line is logged from the final decision, after the re-issue lookup and scope recovery. Scope recovery strips `--red-main-group` from its budget re-run and never replaces a `match: red_main_group` issue.
  - *Triage target-files guard.* `triage_target_files_guard` in `scripts/check_failure_triage.sh` runs once after routing set `ROUTING_TARGET_BRANCH="${HEAD_REF}"` and the check-run context was collected, before the collect-stage metadata hand-off. The trusted support helper (`heal-scope failing-tests`, credentials unset, under `timeout`) extracts the failing files (strict path shape, no `..`, at most 20); `git cat-file -e` checks them on `refs/remotes/origin/<head>` (else the checked-out `HEAD_SHA`, only while it is still the PR's current head; otherwise `reason=target_head_advanced` keeps the route) and on `refs/remotes/origin/<default>` / `refs/heads/<default>` of the workspace, else of `CHECK_TRIAGE_DEFAULT_BRANCH_TREE_DIR`. No API call and no fetch in the script: the triage job's `Checkout default branch for target-files guard` step (only while PR-branch routing and the guard are on, `continue-on-error`, `persist-credentials: false`) takes a depth-1 checkout of `github.event.repository.default_branch`, and the next step moves it to `${RUNNER_TEMP}/check-triage-default-branch` and exports that path. When none exist on the head and all exist on the default branch, the route is cleared (no `Target branch:` line) and it logs `CHECK_TRIAGE routing outcome=fallback reason=target_branch_lacks_files target_branch=<default>`; otherwise `routing outcome=keep reason=<target_files_guard_disabled|default_branch_invalid|helper_missing|helper_failed|no_failing_files|files_truncated|target_head_advanced|target_ref_unavailable|default_ref_unavailable|files_on_target|files_absent_on_default> target_branch=<head>`. Without a resolvable default ref the guard keeps the route (fail open). The base gate is `triage_base_gate_check`; a PR-branch route skips it (`reason=target_branch_route`, sets `BASE_GATE_TARGET_ROUTE_DEFERRED`), so when the guard clears the route the script runs it then (`base_gate outcome=recheck reason=target_files_fallback`), before the collect-stage hand-off.
  - *Switches / rollback.* `WORKFLOW_HEAL_RED_MAIN_GROUPING_ENABLED` (intake and recovery-scan jobs of `workflow-failure-heal-intake.yml`) and `CHECK_TRIAGE_TARGET_FILES_GUARD_ENABLED` (`check_failure_triage.yml` triage job) both default `true` in the scripts and the workflow env; only `false` (any case) turns them off.
