### Grouping repeated failures (`PERSIST_ORCH_FAILURE_GROUPING_ENABLED`, P8 of #8427)

Phase P8 of `docs/plans/persistent-unattended-workflows-plan.md`. Repo variable `PERSIST_ORCH_FAILURE_GROUPING_ENABLED` (default `false`), defaulted in `orchestrate_poll.yml` and in `scripts/persist_orchestrator.py` itself; only the exact value `true` turns it on. `PERSIST_ORCH_GROUP_WINDOW_HOURS` (default `24`) and `PERSIST_ORCH_GROUP_MAX_HOURS` (default `12`) fall back to their defaults when not a positive integer.

- **Decision.** `persist_orchestrator.py group` (pure: no subprocess, no network) reads the open items of `state.waves[WAVE_IDX].issues[]` (integer `github_issue`, status not `merged` / `closed` / `skipped` / `not_created`) and, from the per-tick `_current_wave_details_json` cache, each item's attempt journal (`attempt_journal.parse`, pipeline login only; `note` is never read). An item's key is the `failure_key` of its newest entry when that entry is `fail` / `partial` / `blocked`, the key is 12 hex characters and the entry is no older than the window (the boundary is included); a newer `ok` entry means no key. Two or more items with the same key form a group. The owner is the item with the earliest failing entry of that key in the window (ties: lower issue); an existing `grouped_under.owner` still in the group is kept even when another member's failure is earlier, so the owner (and its comment) does not flap from tick to tick; a member held this tick (unknown cache entry) still counts for that rule. The group key is the journal `failure_key` (`fingerprint(workflow, step, error_signature)[:12]`); `workflow_failure_heal` has no `cause_key` on this ref.
- **State fields.** `grouped_under: {owner, key, since}` on each paused item (`since` kept while owner and key stay the same) and `persist_group_released_key` (cooldown). A field is released when the item is no longer open (`item_inactive`), its key changed or aged out (`key_changed`), no member has a trusted journal (`journal_absent`), the owner left the wave (`owner_gone`), merged / closed / has `persist_merged_pr` (`owner_merged`) or changed key (`owner_key_changed`), the owner of its group changed (`owner_changed`), the field is malformed, including a stored key that is not 12 hex characters (`field_invalid`), or `now - since >= MAX_HOURS` (`max_hours`). A `max_hours` release stores the key in `persist_group_released_key`, and the item is not grouped again on that key until its key changes (then the field is removed), so the 12 h bound does not flap. A released item is not regrouped on the same tick. An item, or its owner, whose details-cache entry is missing or unreadable (a dropped GraphQL batch, or the whole cache reset to `{}`) is unknown, not failure-free: its `grouped_under` stays as it is, its cooldown is not cleared, and only the `max_hours` bound applies.
- **Poller.** `persist_orch_group_failures` (`scripts/orchestrate_poll_process.sh`, before `invoke_stall_judge`) runs at the top of the managed loop's not-stuck branch, before the P6 governor. It applies the decision to `STATE_FILE` in one jq write (no write when nothing changed), and only after that write lands posts one `## Paused: same failure as another project item` comment (marker `<!-- AI_PERSIST_GROUPED_V1 key=<key> owner=<n> -->`, plain `issue N`, never `#N`) per newly grouped item, unless the cached comments already hold that marker (matched with its `<!-- ` opener, so journal note text cannot match) from the pipeline login with a `created_at` no earlier than the episode time (`newest_failure_ts` in the helper output: the later start of the item's and its owner's newest unbroken run of same-key failing entries, so an owner that keeps failing with the same key does not move it), which happens after a tick whose `post_state_comment` failed; a marker from an earlier grouping episode does not count, so a regrouped item gets a fresh comment once it or its owner has failed again since. Known limit: a regroup with no new journal entry on either side (the switch turned off and on inside the window, or a reshuffle back to the same owner) reuses the earlier comment; the pause is still bounded by `PERSIST_ORCH_GROUP_MAX_HOURS`. A failed post is not retried. Scratch files are `mktemp` files under `RUNTIME_DIR` (else `/tmp`). `PERSIST_ORCH_GROUP_STATE_CHANGED` joins the `post_state_comment` condition. Tick-local maps: `PERSIST_ORCH_GROUPED_ISSUES_JSON` (`{member: owner}`) adds `ai:needs-human` to members in P6's stall-check label view (`PERSIST_BUDGET_STALL_LABELS_JSON`, so `check-stalls` skips them; no label is written) and makes the P6 governor skip them; `PERSIST_ORCH_GROUP_DIAG_JSON` (`{owner: [{issue, id, key}]}`) adds `grouped_items` (`issue`, `id`, `title`, `key`) to the owner's stall-judge diagnostics (managed items only). The title comes from the details cache, which now selects `title` on the existing aliased issue query (no extra call); control characters, `<!--` / `-->`, `#` and `@` are stripped, runs of three or more `=` become `= = =` so a title cannot imitate a prompt section header, it is capped at 120 characters, and a non-empty title is prefixed `UNTRUSTED_DATA: ` so the stall judge and its semble query read it as data. Releasing a field resumes normal stall recovery on the same tick.
- **Failure modes.** No helper output (helper missing, crash, switch mismatch): state unchanged, nothing paused. Failed state write: `outcome=error reason=state_write_failed`, no comment, nothing paused. The stuck-wave branch (`INVOKE_JUDGE_FOR_STUCK=true`) neither applies nor releases groups that tick.
- **API budget.** Zero reads (comments come from the GraphQL details cache), at most one identity read shared through `PERSIST_JOURNAL_LOGIN_CACHE`, and one comment write per newly grouped item.
- **Switch off.** No Python starts and no API call; one jq check removes leftover `grouped_under` / `persist_group_released_key` fields from every wave (`outcome=released reason=switch_off`); with none present there is no write and no log line, and the governor, stall view and diagnostics are unchanged.
