Heal suspect-commit scope (P4 of `docs/plans/heal-evidence-reproduction-and-trends-plan.md`, Refs #8434): behind `WORKFLOW_HEAL_SUSPECT_SCOPE_ENABLED` (default `false` in the script and in both the `intake` and `recovery-scan` jobs of `.github/workflows/workflow-failure-heal-intake.yml`; only the literal `true` turns it on), `_heal_scope_suspect_paths` runs inside the scope-freeze block, after `_heal_scope_linked_paths` and before the freeze `jq`, and calls `workflow_failure_heal.py suspect-scope` once (`GH_RETRY_MAX_ATTEMPTS=1`; the step itself makes no `gh` call). It adds the files changed between the failing workflow's last green run and `HEAD_SHA` to `scope_inputs_frozen.json` as a separate `suspect_files` key (present only when non-empty, frozen before any untrusted evidence, 0444 like the rest). The files come from the GitHub compare `files[]`, authenticated API metadata, never from logs or the diagnosis. `heal_suspect_scope_paths` reads only `filename` (a rename's `previous_filename` never enters), drops `removed` rows, keeps a path only when it passes `_safe_heal_path`, sits under `scripts/`, `.github/workflows/`, `workflow-templates/` or `prompts/`, is not under a top-level `.github/ai/` or `.claude/` (the prefixes are anchored at the repository root, so `workflow-templates/.claude/hooks/...` is under `workflow-templates/` and allowed), and is a regular file at the scope commit; it keeps at most 8 (`HEAL_SUSPECT_SCOPE_MAX`), ranked by `changes` (stable ties), and a missing path never takes a slot. Eligibility: the report is of this repository (`consumer_report` otherwise), `HEAD_SHA` is a 40-hex SHA (`invalid_input`), the verified run at `HEAD_SHA` has a saved run JSON (`run_unavailable`) whose `head_repository` is `SOURCE_REPO` (`foreign_head`: a fork's compare range must never pick the pipeline files a healer may edit), and the commit resolves locally (`scope_commit_unavailable`); each skip makes no call. API budget (CLAUDE.md §14): 0 calls when P3's `SUSPECT_COMPARE_FILES_FILE` is present (`source=p3`); otherwise the last-green lookup and one `GET repos/<repo>/compare/<green>...<failing>` (`source=fetched`, 2 calls). P3's suspect step runs after the freeze, so in today's order P4 makes the 2 calls and writes `${RUNTIME_DIR}/suspect_scope/handoff.json` (`{repo, workflow_id, branch, failing_sha, green_sha, last_green, compare}`, the compare trimmed to the fields `parse_suspect_compare` reads, no patches); `_heal_build_suspect_commits` reuses it when every key matches (`--last-green-json`, whose file the handoff's baseline overwrites even after the reproduction cache wrote it, and the new `suspect-commits --compare-json`, which `suspect_commits(compare_cache=...)` uses only when its green and failing SHAs match the resolved baseline), so on that success path P3 plus P4 stays at most 9 calls per report; when the P4 compare fails, is malformed or is `behind`, no handoff is written and the reproduction and P3 steps repeat their own lookups, so that fail-open path can exceed 9. When the handoff matches (its `branch` is the validated branch), its baseline replaces any reproduction-cache copy, so the baseline and the cached compare always come from the same lookup; the reproduction step (`_heal_run_reproduction`) also takes its last-green result from a matching handoff instead of calling `last-green-run`. Suspect paths are checked at `HEAD_SHA`, which is the render ref only for `workflow_run` reports; for other source kinds the render drops a suspect path missing at its ref, so the scope can only shrink. `_open_issue` passes `suspect_files` to `heal-scope render` for a self-repo scope only; `render_heal_scope_marker(suspect_files=...)` ranks them after the 8-slot subject reserve and before `changed_files` (`crash, workflow_paths, subjects[:8], suspect_files, changed_files, subjects[8:]`), under the unchanged 20-path cap; they are never step globs. The marker format, `verify_heal_scope` and already-filed markers are unchanged, and with the switch off no call, file or log line is made, so the snapshot and marker are byte-identical. Everything fails open to `[]`. Stacking with `docs/plans/heal-scope-linked-runs-script-closure-plan.md` (#8290): its P1 linked-run inputs (`self_workflows` via `_heal_scope_linked_paths` and the linked scope file) and its P2 render-time script closure are separate inputs; `suspect_files` is its own frozen key, and all of them share the one 20-path marker cap, so when #8290's P2 closure reserve lands it must rank itself relative to `suspect_files`. Linked paths that fill their room plus a full subject reserve can truncate suspect paths (`heal_scope_truncated`); that is accepted.
