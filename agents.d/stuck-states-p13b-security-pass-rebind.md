**Security-pass rebind across clean sync merges (stuck-states P13B, convergence plan D4, Refs #8291).** When a recorded clean pass (`security_pass_status=passed`) no longer matches the integration head, `run_security_pass_inline` still runs the `SECURITY_PASS_CYCLE_BUDGET_RESET` step first, then refreshes the default branch and resolves the merge base, and then calls `security_pass_rebind_if_no_new_project_lines <head> <merge_base> <prior_status>` before the audit worktree is prepared. The pass is rebound to the new head without a model run only when every gate holds: `SECURITY_PASS_REBIND_ENABLED` is on (default `true`; `false`/`0`/`no`/`off` turns it off, any other value warns and keeps it on); `security_pass_last_audited_sha` (legacy fallback: `security_pass_head_sha`) is a 40-hex SHA equal to `security_pass_head_sha` and different from the head; the head and merge base are 40-hex SHAs; the last audited commit exists and is an ancestor of the head; and every commit in `git rev-list <head> ^<last_audited> ^<merge_base>` (non-empty) has two or more parents and an empty `git show --no-color --no-ext-diff --no-textconv --format= --cc` output. On success one jq write sets only `security_pass_status=passed`, `security_pass_head_sha` and `security_pass_last_audited_sha` to the head (`.status`, labels, the cycle and the findings memory are untouched, the same contract as the "already valid" return), followed by `reconcile_tracking_body_after_security_pass_transition` and `post_state_comment`. Any failed gate, git error or state-write failure falls through to the existing audit unchanged. The gate checks use local git only; the success path makes the same hash-gated body reconcile and state comment a clean audit already makes, and no other GitHub API call. Accepted edge: a merge whose resolution takes the default branch's version of a project-touched file has an empty `--cc` and is rebound, because the resulting lines are default-branch code (consistent with line ownership); the weekly audit covers the default branch.
