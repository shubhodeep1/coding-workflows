<!-- agents: section="Workflow architecture" -->
Unchanged-state write skip (`ORCH_STATE_SKIP_UNCHANGED`, default `true`). `post_state_comment` in `scripts/orchestrate_poll_process.sh` posts nothing when the state's content hash (sha256 of `jq -cS .`) matches the record for the tracking issue: the hash of the newest complete chain read at the start of that tracking issue, or of the last chain the run wrote. Readers pick the newest complete chain by author and manifest, so they read the same state either way. The record is the file `RUNTIME_DIR/state_persisted_sha_<tracking>`, so writes made in subshells update it. It is cleared before each read, and set only from a verified full read (`COMMENTS_FETCH_OK`) that did not fall back to an older chain, so a partial thread cannot hide a newer chain and the healing write still posts. A failed or torn write keeps the previous record, which still matches the newest complete chain. Only the poller writes state chains after the initial post in `orchestrate.yml`, and one poller runs per repository, so no other writer can make the record stale. Without `RUNTIME_DIR` or a hash, the write posts. Measured on 2026-11-17: tracking #8291 (a 12-part, 567 KB state) re-posted all 12 parts with content identical to the previous chain, and one run wrote it three times in 70 seconds; 450 KB of it is `merged_issue_fingerprints`.
