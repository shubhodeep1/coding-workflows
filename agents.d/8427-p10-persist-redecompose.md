### Re-decompose remaining waves (`PERSIST_ORCH_REDECOMPOSE_ENABLED`, P10 of #8427)

Phase P10 of `docs/plans/persistent-unattended-workflows-plan.md`. Repo variable `PERSIST_ORCH_REDECOMPOSE_ENABLED` (default `false`), defaulted in `orchestrate_poll.yml`, in the poller (`${PERSIST_ORCH_REDECOMPOSE_ENABLED:-false}`) and in `scripts/persist_orchestrator.py` itself; only the exact value `true` turns it on. `PERSIST_ORCH_MAX_REDECOMPOSE` (default `2`, falls back to 2 when not a positive integer) caps revises per project through the state's `redecompose_count`.

- **Judge option.** `persist_orch_revise_option_block` appends `prompts/mode-judge-revise-option.txt` to the wave-judge task (right after `mode-judge.txt`) only when the switch is on, the fragment and helper are staged, `CURRENT_WAVE < TOTAL_WAVES` and `redecompose_count` is below the cap. The fragment documents two optional verdict fields, `revise_remaining` (boolean) and `revise_reason` (string, at most 500 characters), for `status: in_progress` only. Switch off: no output, no Python, byte-identical judge prompt.
- **Trigger.** `persist_orch_redecompose` runs in the judge's `in_progress)` arm, on the branch where the judge added no current-wave issues, immediately before `# Advance to next wave`, and only when `CURRENT_WAVE < TOTAL_WAVES` and the verdict has `revise_remaining == true`.
- **Flow.** `persist_orchestrator.py revise-input` (pure) renders five `=== BEGIN/END UNTRUSTED <NAME> ===` blocks: PROJECT SPEC (`project_body_snapshot`), PENDING ISSUE DEFS (the not-created items of the waves after the current one, plus `frozen_ids`), SINCE DECOMPOSED (`since_lines` / `render_since`, also with P7 off), JOURNALS (newest pipeline-login journal step per current-or-earlier item; `note` is never read) and JUDGE REASON. Every data line has control characters and `<!--` / `-->` removed, `=` runs broken, `attempt_journal._scrub` applied and an `UNTRUSTED_DATA: ` prefix; at most 48 KiB, and nothing is written when the pending defs would be cut (`input_too_large`). The prompt is `${RUNTIME_DIR}/judge_static.txt`, `=== REVISE TASK ===`, `prompts/mode-orchestrate-revise.txt`, then the blocks. One `poller_claude_judge WAVE_JUDGE` run (gated by `_judge_isolation_should_run WAVE_JUDGE`; no retries, no host fallback, no isolation-failure record) writes the model output.
- **Validation.** `persist_orchestrator.py revise-validate` (pure) takes the last JSON object with a `pending_issue_defs` key and writes nothing unless every check passes: 1..50 items; ids `^[a-z0-9_-]{1,64}$`; item keys only `title` (1-256), `body` (1-12000), `priority` (1-10), `files_touched` (at most 50 paths of at most 512 characters) and the required `implementation_minutes_estimate` (integer 1-60, stripped before storing; `.github/ai/orchestrate_schema.v1.json` itself is unchanged); no reuse of a created, current-wave, mapped or other pending id; edges only between new ids; no `Orchestrator metadata` or `<!--` in titles or bodies; then `validate_decomposition`, `compute_waves` (auto-serializing file overlaps with `load_hot_files()`) and `validate_wave_file_partition` from `scripts/orchestrate_lib.py`. A revise is refused when any entry of a later wave is already created (`created_in_remaining`).
- **State fields.** On success `waves[current_wave:]` (entries `{id, github_issue: null, status: "not_created", files_touched}`), `pending_issue_defs` (revised ids replaced, other defs kept), `dependency_edges` (old edges touching a revised id dropped, new and serialization edges added), `total_waves` and `total_issues` are replaced, `redecompose_count` is incremented, `pending_issue_defs_previous` keeps the old revised defs verbatim and `persist_redecompose_previous_layout` keeps `{waves, dependency_edges, at}` of the old layout. Created items, the current and earlier waves, `issue_number_map` and `project_body_snapshot` never change. The new state replaces `STATE_FILE` with `mv`, `TOTAL_WAVES` is refreshed, and the arm's existing `post_state_comment` persists it; the next wave's deferred creation reads the revised defs.
- **API budget.** One tracking comment (`## Remaining waves re-decomposed (n/max)`: removed and added titles, at most 20 each, scrubbed, no `#N`) per successful revise; the model call runs on the wave-judge runner. Zero calls otherwise.
- **Failure modes.** Helper or prompt missing, isolation unavailable, no model output, validation reject or a failed write: the state is untouched and the wave advances on the old defs. A comment post failure only loses the human-readable comment. A rejected revise does not count against the cap.
- **Rollback.** Turn the variable off. `pending_issue_defs_previous` and `persist_redecompose_previous_layout` hold what a manual restore of the latest revise needs.
