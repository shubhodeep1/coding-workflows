- **Verdict-wait dispatch skip (issue #9991, re-issued as #10243; Refs #9987, #9939).** A PR head that already has a verdict and only waits to merge is not re-reviewed or re-judged. Review sweep (`review_autofix_sweep.yml`, enumerate step): `review_sweep_annotate_head_gate` (`scripts/review_sweep_head_gate.sh`) reads, in the same GraphQL query, `mergeable`, `autoMergeRequest`, the head-gate status's `createdAt`, and the `ai-review/judge-merge-pending` and `ai-review/verdict-wait-alert` contexts. `review_sweep_verdict_wait_reason` (pure jq) skips a head-gate-success head that GitHub reports `MERGEABLE` (a conflicted or not yet computed head is dispatched) and carries `ai:final-ci-merge-pending` or has auto-merge enabled; an approved head whose final CI is `in_flight` is skipped with the existing runs read, which every approved head without the label still gets first, so a `failure` keeps its own `approved_head_final_ci_failed` skip (or, with `SWEEP_SKIP_APPROVED_FINAL_CI_FAILED=false`, its re-review) even with auto-merge on; `success`, `none` and `read_failed` dispatch unless the snapshot names a wait. Each skip follows only its own switch. The existing `merge_lease_wait` skip is unchanged. `review_sweep_round_cap_applies` (`scripts/review_sweep_round_cap.sh`) now only decides the escalation: a head with `ai-review/judge-merge-pending` success is still skipped past the cap (and by the infra backoff) but not labelled (`AUTOFIX_SWEEP_SKIP ... reason=review_round_cap ... label=skipped_verdict`). `review_sweep_verdict_wait_alert` raises one Telegram WARNING per head once the verdict is `VERDICT_WAIT_ALERT_HOURS` (default 6, `0` off) old, naming the blocker (the merge lease holder, `final CI queued or running`, or `_pr_ruleset_required_check_blockers`' summary such as `ci/final (missing)`). Only a delivered send (a message id) posts the head-bound `ai-review/verdict-wait-alert` success status, which the next tick reads back. With no Telegram sender it reads nothing. Stall recovery: `_dispatch_rb_judge_for_pr` (`scripts/orchestrate_poll_process.sh`) calls `_rb_judge_verdict_wait_check` after its cycle dedupe and the read-only phase-cap check, and returns rc 4 to skip. The check makes no read unless the PR carries the lease-wait or final-CI-pending label, or has auto-merge on. Then one GraphQL read: it skips only when the head is unchanged, the verdict status was posted by the pipeline login (`PERSIST_JOURNAL_LOGIN_CACHE`), no required check run completed and no required non-`ai-review/` status was posted after the verdict (`isRequired(pullRequestNumber:)` in the same query; an unknown flag counts), and, for a judge verdict, the `base=<sha>` its description records (`_pr_judge_merge_pending_mark`'s optional fourth argument, passed `PR_BASE_FRESHNESS_BASE_SHA` by `rb_judge_mark_merge_pending`) is the current base or the base moved only outside the PR's files (one compare plus `_merge_lease_pr_paths`). All three call sites log `STALL_SKIP ... reason=rb_judge_verdict_wait` and count no attempt. `VERDICT_WAIT_DISPATCH_SKIP_ENABLED=false` (default `true`, read in both workflows) restores the old dispatches and round-cap rule, and sends no alerts. Every failed read dispatches as before. Tests: `tests/test_review_sweep_verdict_wait.py`, `tests/test_stall_rb_judge_verdict_skip.py`, `tests/test_rb_judge_verdict_status.py`, `tests/test_review_sweep_round_cap.py`.
