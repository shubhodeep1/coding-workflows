### Heads with a verdict that only wait to merge are not re-dispatched (issue #9991)

On 2026-11-23 the sweep dispatched 181 re-reviews across 47 PRs in seven hours (#9984: 12 runs on one unchanged approved head whose ruleset check was missing), and stall recovery re-ran the review-blocked judge on unchanged heads whose `merge` decision was deferred by a busy lease (#9573 x21, #9637 x20). Those runs also counted as review rounds, so the round cap labelled waiting heads `ai:needs-human` (#9515, #9839).

- **Judge verdict marker.** When `scripts/review_rb_judge.sh` decides `merge`, `merge_with_followup` or a final-attempt `fix` and the merge is deferred for a reason a re-run cannot change, it sets `RB_MERGE_WAIT_TOKEN` (`lease_wait`, `blocked` for the #9939 blocked-merge guard, `checks_not_ready`, `auto_merge` for an enrolled auto-merge on a still-open PR) and `rb_judge_record_verdict_wait` posts the commit status `ai-review/rb-judge-verdict` (always `success`) on the judged head through `review_rb_judge_verdict_post_status` (`scripts/review_head_gate.sh`), description `decision=<d> wait=<w> base=<base sha> ms=<mergeable_state>`. `deferred_base_moved`, `checks_failed`, `merge_failed`, unknown freshness, conflicts and merged PRs record nothing. Cost: one PR read and one status POST per deferred verdict.
- **Relevant change.** `_pr_rb_judge_verdict_waiting` (`scripts/pr_checks_lib.sh`) returns 0 (still waiting) unless: the lease-wait label is gone for a lease wait (`lease`), the merge state differs (`checks`), auto-merge was disabled for an auto-merge wait (`auto_merge`), or the base moved and `_pr_base_freshness` reports `overlap` (`base`; `unknown`/`disabled` give `base_unknown`, which dispatches). A new head has no verdict status. A malformed description is `parse` (dispatch).
- **Sweep.** `scripts/review_sweep_head_gate.sh` reads the verdict, an `ai-review/merge-wait-alert` marker, the head-gate `createdAt`, base sha/ref, `mergeStateStatus` and `autoMergeRequest` in its existing GraphQL query (no new call). After the active-run skip, `review_sweep_verdict_wait_reason` gives `final_ci_merge_pending`, `auto_merge_checks_pending`, `auto_merge_checks_missing` (gate success, auto-merge enabled, final CI in flight or succeeded, read once and shared with the failed-head skip) or `rb_judge_merge_deferred`; the step logs `AUTOFIX_SWEEP_SKIP pr=#<n> reason=verdict_waiting wait=<reason> head_ref=<ref> head_sha=<sha>` and adds `skipped_verdict_waiting=<n>` at the end of `AUTOFIX_SWEEP_END`. A skipped dispatch creates no run, so it is never a review round, and the round cap leaves out heads with a judge merge verdict.
- **Alert.** `review_sweep_verdict_merge_wait_alert` raises one Telegram WARNING per head once its verdict is `VERDICT_MERGE_WAIT_ALERT_HOURS` (default `6`, `0` = off) old, naming the lease holder and `_pr_ruleset_required_check_blockers`' summary (for example `ci/final (missing)`). It posts the `ai-review/merge-wait-alert` status first, so a failed marker write sends nothing and the alert never repeats per tick; at most 5 alerts per tick.
- **Stall recovery.** `_dispatch_rb_judge_for_pr` (`scripts/orchestrate_poll_process.sh`) calls `_stall_rb_judge_verdict_unchanged` after the cycle-local dedupe: it uses `STALL_IMPL_PR_JSON` only for the same PR, pre-filters without a call (open, and lease-wait label, final-CI merge-pending label, auto-merge, or `mergeable_state=blocked`), then reads `commits/<head>/status` once. An unchanged verdict returns `4`; all three callers treat it like the phase cap (no recovery-count increment) and log `STALL_SKIP issue=<n> reason=rb_judge_verdict_unchanged pr=<n> phase=<phase> action=dispatch_rb_judge wait=<w>`. Any read or parse failure dispatches as before.
- Switch: `VERDICT_WAIT_DISPATCH_SKIP_ENABLED=false` (both the sweep and the poller; default `true`) restores every dispatch, the previous round cap, and stops the judge from posting the verdict status.
