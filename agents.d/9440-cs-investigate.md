### CS ticket investigation (`cs_investigate.yml`, #9440)

`.github/workflows/cs_investigate.yml` is a `workflow_call`-only reusable workflow for tele-funtoken-msg-scoring's repo-owned `ai-cs-investigate.yml` wrapper (CS hub `workflow_dispatch`). It is **not propagated**: no `workflow-templates/` entry and no install profile. Permissions are exactly `contents: read` and `id-token: write`; it takes only the optional `OPENROUTER_API_KEY` secret (codex fallback) and holds no `GH_PAT`, provenance secret or repair key. The support commit comes from the `job` context (`workflow_ref` / `workflow_sha`, no API call), checked out with `github.token`; the caller's default branch is checked out read-only into `target/`.

`scripts/cs_investigate.sh` validates the inputs (invalid inputs fail the job with no verdict), fetches `GET <hub>/api/tickets/<id>` and photos `.../files/<n>` (n = 0..4, stop at the first 404, `CS_PHOTO_MAX_BYTES` cap, image magic bytes required) with a `cs-hub` OIDC token, then runs the `CS_INVESTIGATE` role (read profile) through `claude_run_selected` with `GH_TOKEN`, `GITHUB_TOKEN` and `ACTIONS_ID_TOKEN_REQUEST_*` unset. The agent has no shell: it asks for database reads by replying `{"bridge_requests":[...]}` (1-5 objects, each at most 4 KB), and the runner sends each one on stdin to `scripts/cs_bridge_query.sh` (fixed host `mongo-explorer-5iucg.ondigitalocean.app`, path `/claude-db/query`, `agent-db-bridge` OIDC token in a 0600 header file), for at most 3 rounds. Ticket JSON, photos and bridge results enter the prompt only inside `BEGIN/END UNTRUSTED` blocks with every line prefixed `UNTRUSTED_DATA: ` (`scripts/cs_verdict.py compose`). The final reply is checked by `scripts/cs_verdict.py validate` against `scripts/templates/cs_verdict.v1.schema.json` (stdlib validator that fails closed on unknown schema keywords, `ticket_id`/`mode` must match, verify-only outcomes only in verify mode, at most 32 KB); any failure after valid inputs emits `{"ticket_id":"<id>","outcome":"invalid_verdict"}` and the job stays green. The workflow sets `AI_ENGINE_FALLBACK_POLICY: 'always'` (fixed, not from vars), so Claude being unavailable (no credential, a broker-refused token, isolation unavailable, every account usage-limited or failed) runs the isolated codex command; a Claude timeout (124/137) or crash (other non-zero) is not retried on codex and gives `invalid_verdict` (`engine_timeout` / `engine_failed`). The broker refuses `refs/tags/stable`, so an `@stable` caller runs on codex; pin `cs_investigate.yml@<40-hex>` (or `@main`) to get the Claude pool. `CS_HUB_ALLOWED_HOSTS` (caller repo variable, space-separated `host` for port 443 or `host:port`; `host:443` is the same as `host`) is required inside Actions: empty, or a hub host/port not on it, fails the job before any `cs-hub` OIDC token is fetched. Each engine round runs under `timeout` (`CS_ENGINE_TIMEOUT_SECS`, default 780; exit 124/137 is `engine_timeout`) and no round or bridge request starts after `CS_RUN_DEADLINE_SECS` (default 2700) from script start, so the 60-minute job timeout never cuts off the verdict.
