- **PID namespace for the harness (#7349, finding `validation-harness-credential-inheritance`).** `scripts/validation_harness_sandbox.sh` starts the harness (`run`, and so `checked-run`) through `as_sandbox_in_pidns` only. Root runs `unshare --pid --fork --mount-proc --propagation private --kill-child` and only then drops to the sandbox user with the unchanged `env -i` allowlist, so a test sees a private `/proc` and cannot list runner processes or read their `cmdline` / `environ`. `provision`, `selfcheck` and `run` first prove a namespace can be created; when it cannot, they fail closed with `reason=pid_namespace_unavailable` (exit 3, `harness_error`), and nothing runs without the namespace. Root writes the host pid of `unshare` and a launch marker (written inside the namespace before the privilege drop) to `${VALIDATION_HARNESS_SANDBOX_PIDNS_STATE_DIR}/<run>-<attempt>.pid` / `.started` (default `/run/ai-validation-harness`, created root-owned `0700`; it must be absolute, have at least two components, contain no `//` or trailing `/`, and lie outside the sandbox home, else `invalid_pidns_state_dir`; an existing path is used only when it is already a root-owned 0700 directory, never passed to `install -d`, which would chmod/chown it; otherwise, or when the create fails, `pidns_state_dir_failed`). A missing marker after the launch is `pid_namespace_launch_failed`. `selfcheck` runs a second probe inside a namespace created the same way and fails with `pid_namespace_shared`, `caller_pid_visible` or `host_init_visible` (`pid_namespace_unverifiable` when the host namespace id cannot be read). `start_rootless_dockerd` passes `DOCKERD_ROOTLESS_ROOTLESSKIT_FLAGS=--pidns`, so the daemon and every container it starts (including `--pid=host` ones) get rootlesskit's PID namespace. `selfcheck` then requires at least one of the sandbox uid's `dockerd` processes, read as root by host pid with `pgrep`, never from the sandbox-written `docker.pid`, and requires every one of them to be outside the helper's PID namespace (`docker_pidns_isolated`); otherwise it fails with `docker_pid_namespace_shared`. `cleanup` no longer reads `${work}.pgid` (written by the sandbox user; still removed): root kills only the recorded pid, after checking the pid file is a root-owned regular file, the pid is greater than 1, and the process is still a uid-0 `unshare`, and kills its forked child (the namespace's init) first. In `auto` cgroup mode the sandbox user's systemd user manager (`loginctl enable-linger`) runs in the host PID namespace, and `systemd-run --user` through its sockets would start commands outside the namespace. So, before the privilege drop and before the launch marker, root bind-mounts `/dev/null` over every socket under `/run/user/<uid>` except `docker.sock` (found with `find -xdev -type s`, so renaming `systemd/` does not hide `private`) inside the new mount namespace (explicit `--propagation private`, so the daemon outside keeps its bus). A symlink at the runtime dir, `bus` or `systemd/private`, a failed mount on a path that still exists, or any socket other than `docker.sock` still unmasked when root lists them again after the mask (one renamed between `find` and `mount`), exits 125 without the marker (`pid_namespace_launch_failed`); a path removed before its mount is skipped, and the namespace probe fails with `user_manager_reachable` when any socket other than `docker.sock` is still there. Residual: in systemd mode a container started through the rootless daemon can bind-mount the unmasked socket and reach the manager with a hand-crafted D-Bus client (a process it starts runs as the sandbox uid, so runner `environ` stays unreadable; process listing and `cmdline` do not); `VALIDATION_HARNESS_SANDBOX_CGROUP_MODE=cgroupfs` never starts the user manager. `validate_process.sh`, `validation_refresh_runner.py` and the workflows are unchanged; the daily `harness-sandbox-check` job reports a runner image where `unshare` stops working.
