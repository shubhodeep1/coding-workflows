- **PID namespace for the harness (#7349, finding `validation-harness-credential-inheritance`).** `scripts/validation_harness_sandbox.sh` starts the harness (`run`, and so `checked-run`) through `as_sandbox_in_pidns` only. Root runs `unshare --pid --fork --mount-proc --kill-child` and only then drops to the sandbox user with the unchanged `env -i` allowlist, so a test sees a private `/proc` and cannot list runner processes or read their `cmdline` / `environ`. `provision`, `selfcheck` and `run` first prove a namespace can be created; when it cannot, they fail closed with `reason=pid_namespace_unavailable` (exit 3, `harness_error`), and nothing runs without the namespace. Root writes the host pid of `unshare` and a launch marker (written inside the namespace before the privilege drop) to `${VALIDATION_HARNESS_SANDBOX_PIDNS_STATE_DIR}/<run>-<attempt>.pid` / `.started` (default `/run/ai-validation-harness`, created root-owned `0700`; it must be absolute and outside the sandbox home, else `invalid_pidns_state_dir`; a failed create is `pidns_state_dir_failed`). A missing marker after the launch is `pid_namespace_launch_failed`. `selfcheck` runs a second probe inside a namespace created the same way and fails with `pid_namespace_shared`, `caller_pid_visible` or `host_init_visible` (`pid_namespace_unverifiable` when the host namespace id cannot be read). `cleanup` no longer reads `${work}.pgid` (written by the sandbox user; still removed): root kills only the recorded pid, after checking the pid file is a root-owned regular file, the pid is greater than 1, and the process is still a uid-0 `unshare`, and kills its forked child (the namespace's init) first. `validate_process.sh`, `validation_refresh_runner.py` and the workflows are unchanged; the daily `harness-sandbox-check` job reports a runner image where `unshare` stops working.
