Heal-route counterfactual gate (issue #8249). On the heal route (`HEAL_ROUTE=true` in `plan.yml`, or `workflow_failure_heal.py heal-route` on the live issue or the poller's batched details map: the `ai:workflow-heal` label or the `workflow-failure-heal:fp=` body marker) `scripts/run_plan_codex.sh` appends `prompts/mode-plan-heal-counterfactual.txt` after the heal evidence (a missing prompt only warns). The plan must contain a `## Counterfactual check` ending with exactly one unfenced line at the start of a line: `HEAL_COUNTERFACTUAL: PASS`, `HEAL_COUNTERFACTUAL: PARTIAL: <job>[, <job>...]`, `HEAL_COUNTERFACTUAL: FAIL: <text>` or `HEAL_COUNTERFACTUAL: UNVERIFIED: <text>`. `scripts/partial_delivery.py heal-counterfactual --plan-file F [--gate-flag V]` (`python3 -I -B`, exit 0 for every parse outcome, 2 for I/O errors) decides: `PASS` approves; `PARTIAL` approves only when each comma-separated job (at most 20, 200 characters each) appears as a whole token (case-insensitive; `build` does not match `build-image`) in a `- ` bullet `parse_plan` returns for `## Deferred scope`, otherwise it is `FAIL` (`partial_jobs_not_deferred`, `deferred_scope_missing`, `partial_job_list_invalid`); `FAIL`, `UNVERIFIED`, no line, a second line, a malformed line or a line outside the `## Counterfactual check` section (only a level-2 heading opens it; `result=missing`, reason `outside_counterfactual_section`) hold. Text inside code fences, lines indented by 4+ spaces or a tab (indented code blocks) and mid-line mentions are ignored. `plan.yml`'s "Auto-approve clear plan" step and the poller's `_plan_auto_approval_gate` (all four stall-recovery arms: managed and standalone `auto_approve` and `retrigger_implement`) run it before the automation-path gate, so a held heal plan never gets a Q108 grant. A hold keeps `ai:awaiting-approval`, writes `auto_approve_hold_reason=heal_counterfactual_hold` (plan.yml) or `STALL_SKIP ... reason=heal_counterfactual_hold` (poller, no recovery attempt counted), and posts one comment ending `<!-- ai:heal-counterfactual-hold:v1 issue=<n> plan_comment=<id|unknown> result=<PASS|PARTIAL|FAIL|UNVERIFIED|missing> source=<plan|poller> -->` plus a WARNING; a trusted marker (pipeline login, `[bot]`, OWNER/MEMBER/COLLABORATOR) for the same issue, plan comment and result suppresses another comment. `plan.yml` keeps the plan comment id as `PLAN_COMMENT_ID`. In the poller a `heal_route_unknown` hold (no usable details-map entry this tick) only logs and is re-checked next tick. Logs: `AI_PHASE_GATE_V1 phase=plan|stall_recovery gate=heal_counterfactual outcome=approve|hold result=<...> reason=<...> issue=<n>` (non-heal issues log nothing). `HEAL_COUNTERFACTUAL_GATE_ENABLED` defaults to `true` in `plan.yml`, `orchestrate_poll.yml` (the five steps that set `AUTOMATION_PATH_PLAN_AUTO_APPROVAL_ENABLED`) and the poller script; `false` turns it off (decision `approve`, reason `gate_disabled`, also for an unknown heal route), any other value (also on an unknown heal route) is treated as `true` with `::warning::HEAL_COUNTERFACTUAL_GATE_ENABLED has invalid value; treating as true`. A `PARTIAL` heal plan also carries `## Deferred scope`, so partial-delivery tracking (#7657) keeps the issue open after the merge. The heal intake prompt (`prompts/mode-workflow-failure-heal.txt`) writes a `## Would the suggested fix have passed?` subsection (`<job>: yes|no|unknown` per failing job) that the planner starts from but re-derives. `plan.yml` and `orchestrate_poll.yml` stage `partial_delivery.py`; `plan.yml` stages the prompt (optional).
