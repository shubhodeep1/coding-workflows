<!-- agents: section="Workflow architecture" -->
- **Dependency wait resume scan (stuck-states P8b, Refs #8291).** `scripts/dependency_wait_resume.py scan --repo <owner/repo>` runs from the `orchestrate_poll.yml` step "Resume dependency waits" on every poller tick, after "Release merge-queued PRs (merge train backstop)" and before "Find active tracking issues", so standalone issues resume without an active project. It runs from `.codex-workflow-src` (a missing or symlinked helper logs `::notice::DEPENDENCY_WAIT_RESUME op=scan outcome=skip reason=helper_missing`), with `continue-on-error: true`, and always exits 0.
  - **Label lifecycle.** An issue parked in `ai:waiting-on-dependency` carries a trusted `<!-- AI_DEPENDENCY_WAIT_V1 {"kind":"pr|release|issue","repo":"o/r","number":N,"since":"<ISO8601>"[,"source":"seed"]} -->` marker. A PR merged, an issue closed with `ai:merged`, or a release whose PR merge commit `stable` contains (`compare/<sha>...stable` status `ahead` or `identical`) gets one `/answer [auto-answered-by-poller]`; a PR closed unmerged or an issue closed without `ai:merged` gets one `/reclarify`. Both carry `<!-- AI_DEPENDENCY_WAIT_RESUMED_V1 issue=<n> target=<t> since=<since> outcome=answer|reclarify -->`; before `/answer` the scan adds `ai:blocked` (which `plan.yml`'s `/answer` gate moves to `ai:planning`) and keeps `ai:waiting-on-dependency` until the comment has posted; a failed post removes `ai:blocked` again (a failed removal logs `detail=rollback_failed` and leaves both labels, so the issue stays in the waiting scan). After either comment posts the scan removes the wait label (clarify adds `ai:clarification` after `/reclarify`); a failed removal is retried on later ticks. A seed whose marker posted but whose label change failed is finished on the next tick without a second marker, only when that marker is a `"source":"seed"` `issue` wait for the same `Depends on: #N` and the marker is still the issue's newest pipeline-login comment (any later one means the seed was applied) and the issue's events show no pipeline-login `labeled` event for `ai:waiting-on-dependency`. Such an event means a person moved it back on purpose: the scan posts one `<!-- AI_DEPENDENCY_WAIT_SEED_DECLINED_V1 issue=<n> -->` note, so later ticks skip it without an events read; a failed events read writes nothing. No Telegram is sent. After `DEPENDENCY_WAIT_ESCALATE_DAYS` (default `7`, 1-9999) a still-open wait gets one latch comment `<!-- ai:needs-human-latch reason=dependency_wait target=<t> since=<since> -->` and `ai:needs-human`; `ai:waiting-on-dependency` stays, so a later merge still resumes it. `plan.yml` ignores `/answer` while only the wait label is set, so the latch comment tells a person to swap it for `ai:blocked` before replying `/answer`. On resume the scan removes `ai:needs-human` only when the newest pipeline-login latch is this wait's and the newest `labeled` event came from the pipeline login.
  - **Targets and trust.** `pr` targets name the current repo or `shubhodeep1/coding-workflows`; `release` targets name `shubhodeep1/coding-workflows`; `issue` targets name the current repo and never the issue itself. A `since` in the future, a wrong typename, a null node or a GraphQL error is never satisfied (`invalid_marker` / `read_failed`); an invalid target still ages into the escalation. Markers count only when authored by `viewer.login` of the `GH_PAT`.
  - **Seeding.** Each tick the 50 most recently updated open `ai:blocked` issues with exactly one `Depends on: #N` line (not `ai:security`, `ai:needs-human`, `ai:orchestrator-managed`, no `<!-- ai:security-finding:`, no existing trusted wait marker) get a wait marker with `"source":"seed"`, then `ai:waiting-on-dependency` is added and `ai:blocked` removed.
  - **Switch off.** `DEPENDENCY_WAIT_RESUME_ENABLED=false` moves each waiting issue to `ai:blocked` with one `<!-- AI_DEPENDENCY_WAIT_DISABLED_V1 issue=<n> -->` note and reads no targets.
  - **Call budget.** One GraphQL call (viewer, waiting pages of 50 up to 5 pages, one blocked page) when nothing is waiting or seedable; otherwise one aliased GraphQL call for every distinct target and one REST compare per distinct release SHA. A paginated comments read only when a write is due or the wait marker is outside the 30-comment window; one events read only when clearing a latch, or when a blocked issue's newest pipeline-login comment is its seed marker (at most once per issue, because a deliberate move back gets the decline note).
  - **Failure modes.** A failed call 1 logs `op=scan outcome=read_failed`; an empty login logs `identity_unavailable`; a failed post leaves no resume marker so the next tick retries; every exception logs `op=scan outcome=error` and exits 0.
