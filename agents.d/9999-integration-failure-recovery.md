<!-- agents: section="Workflow architecture" -->
`INTEGRATION_CONFLICT_LIFETIME_MAX` counts conflicts that are still open, not every dispatch a project ever made. Each resolver or judge dispatch records the default-branch commit it was asked to merge in (`integration_conflict_episode_base_sha`). When `heal_integration_branch_conflict` next runs and the integration branch contains that commit, `integration_conflict_reset_on_progress` sets the total, per-episode dispatch and unresolved-tick counters back to `0` and logs `INTEGRATION_CONFLICT_EPISODE_RESOLVED`. A conflict the resolver never lands keeps counting and still ends the project at the cap.

The two terminal paths (lifetime cap, failed judge escalation) save the status the project failed from as `integration_failed_from_status`. Each tick, `recover_failed_integration_if_mergeable` checks a failed project whose `integration_sync_status` is `failed`: when the final PR has been merged (finalize then records it and the project completes), or is open, reported mergeable by GitHub and a local `git merge-tree` of the default branch into the integration branch is clean, the saved status is restored (or, for a failure from before the field existed, the status of the newest trusted state snapshot that is not `failed`, found with `scripts/orchestrate_state_v2.py extract --skip-status failed`). Only `in_progress`, `validating`, `validation-fixing`, `security-pass` and `security-pass-fixing` are restored. The counters start from `0`, the completion-status comment returns to `in-progress`, and the project's tick ends there; the next tick continues from the restored status. One REST read of the final PR per tick, only for a project in that failed state.
