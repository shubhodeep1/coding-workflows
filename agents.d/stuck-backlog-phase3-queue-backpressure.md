Issue run linkage and queue backpressure (Refs #9421, stuck-backlog plan Phase 3):
- **Run-name convention.** `internal-clarify.yml`, `internal-plan.yml`, `internal-implement.yml` and the templates `ai-clarify.yml`, `ai-plan.yml`, `ai-implement.yml` set a `run-name` on the line after `name:` that renders `<workflow name> [issue:N]` (`format('<workflow name> [issue:{0}]', github.event.issue.number)`). All six trigger only on `issues` / `issue_comment`, so the number is always set. Exception: an issue whose title starts with `[E2E ` keeps the issue title as its run title, because the stable release gate (`test-and-mark-stable.yml`, `find_latest_scoped_run_field` in `scripts/comprehensive_test_and_release_gh_api.sh`) finds smoke runs by `display_title == issue title`. Drop the exception only after those readers also accept the tagged form. The prefix is not reserved, so any issue titled `[E2E ...` falls back to the legacy, untagged run title and its runs link only through `head_branch` (no privilege is gained; that is the pre-Phase 3 behaviour). The plan also names `internal-orchestrate-clarify-respond.yml` and its `ai-orchestrate-clarify-respond.yml` template; this phase leaves them untagged because the issue's scope lists only the six files above, so clarify-respond runs still link only through `head_branch` until a follow-up adds the run-name there. `tests/test_poll_issue_run_linkage.py` pins the strings and checks that every gate smoke title starts with `[E2E `.
- **Linkage.** `build_active_issue_set` unions the head_branch matches with tagged runs. A run is tagged only when `.event` is `issues` or `issue_comment` and `.display_title` equals `.name + " [issue:N]"` exactly, with N matching `^[1-9][0-9]{0,9}$`. A pull-request title carrying a forged tag never links. Tagged runs come from the fresh in-progress and queued runs, plus tagged queued runs younger than `QUEUED_RUN_ZOMBIE_MINUTES` (default 1440; a value that is not a positive integer falls back to `STALL_THRESHOLD_MINUTES`). Untagged runs are unchanged.
- **Queue depth.** `_load_actions_runs_cached` keeps `total_count` from its existing `status=queued&per_page=50` read in `ACTIONS_QUEUED_TOTAL`. The fresh path also stamps each queued row with `_poller_queued_total` and `_poller_queued_total_at` (epoch seconds), and every path that reuses the `ai_memory.py` cached rows without the queued read (the in-TTL cache hit, the 304 reuse, and the cache-hit side of the `reason=mktemp_failed` and `reason=fetch_unconfirmed` fallbacks) restores the depth from that stamp through `_actions_queued_total_from_cached_runs` when it is under 1800 seconds old. The 304 is keyed on the in-progress read's ETag, which rarely changes while the queue is jammed, so without the stamp the hold would stay off on most ticks. The depth is empty (unknown) when no fresh stamp exists (including after a fresh read that saw zero queued rows, which leaves the same no-hold result as a known 0), or when a mktemp failure or an unconfirmed fetch has no cache hit to fall back to; an in-process ready-cache hit returns before the reset and keeps the value from the tick's first fetch. The 1800-second bound keeps a queue that drained without any run starting (so the ETag never changed) from holding dispatch indefinitely. The cache schema allows extra run fields, readers ignore the two stamp fields, and no API call is added.
- **Backpressure.** `queue_backpressure_holds_dispatch` runs first in `phase_cap_can_dispatch`, so it covers stall-recovery re-dispatch, wave issue creation, validation dispatch and the review-blocked judge. It holds (the caller sees 1) when `ACTIONS_QUEUED_TOTAL >= ACTIONS_QUEUE_BACKPRESSURE_HIGH` (default 150, set in the script). Callers keep their existing skip line, so a held capped action also logs the caller's `reason=phase_capped` (for example `STALL_SKIP ... reason=phase_capped`); the adjacent `QUEUE_BACKPRESSURE outcome=held` line names the real cause. Stall actions with no phase-cap state (`retrigger_review`, `resolve_merge_conflict`, `close_and_reissue`) never reach `phase_cap_can_dispatch`, so the three stall guards (`execute_stall_recovery_action`, `run_standalone_stall_recovery`, `recover_stalled_issue`) call `queue_backpressure_holds_uncapped_stall_action` when the state is empty; a hold logs `QUEUE_BACKPRESSURE outcome=held state=none ...` and `STALL_SKIP issue=<n> reason=queue_backpressure phase=<p> action=<a>`, counts no recovery attempt, and leaves phase-cap accounting unchanged. The open-linked-PR conflict-resolver and changes-requested autofix dispatches (`_dispatch_review_for_conflicts` in `recover_stalled_issue` and the merge-conflict branch of `run_standalone_stall_recovery`) return or continue before those guards, so each calls `queue_backpressure_holds_dispatch "none" dispatch_conflict_resolver|dispatch_autofix <issue>` right before dispatching; a hold logs `STALL_SKIP issue=<n> reason=queue_backpressure pr=<pr> phase=<p> action=<a>` and touches neither `conflict_override_count` nor the stall budget. `run_stall_judge` is not held. Exempt actions: `attempt_merge`, `escalate_human`, `skip`. Fail open: an unknown depth, a threshold below 1, or a non-integer threshold (one `::warning::`) keeps the legacy result. The check is stateless at HIGH; hysteresis and passing the variables through `orchestrate_poll.yml` are not part of this phase, so `ACTIONS_QUEUE_BACKPRESSURE_HIGH` and `QUEUED_RUN_ZOMBIE_MINUTES` are read only from the poller process environment and a repository variable does not reach them yet.
- **Heal readers.** `_issue_linked_run_matches` (`number=`), `_trend_issue_linked_runs` and `select_failed_runs` (through `tracking_issue`) in `scripts/workflow_failure_heal.py` also accept the tagged title of an `issues` / `issue_comment` run, so heal reports keep these runs.
- **`display_title` reader audit (plan Phase 3 step 5).** Readers in `scripts/` that match runs of the run-named wrappers: `build_active_issue_set` (new tagged parse) and the heal readers above (adjusted). Readers that never see these runs, unchanged: `scripts/gh_helpers.sh` and `_pr_named_review_trust_jq_def` / the default-branch review lookup in `scripts/orchestrate_poll_process.sh` (`[pr:N]` review titles), the `[tracking:N]` parse in the poller and `_TRACKING_RUN_TITLE_RE` / `_PR_RUN_NAME_RE` in `scripts/workflow_failure_heal.py`, `build_workflow_run_payload` (release, promotion and CI runs), `scripts/unblock_scan.py` and the unblock-dispatch read in the poller (`Unblock judge #N`), `scripts/unblock_judge.sh` (`[pr:N]` / `[tracking:N]`), `scripts/pr_checks_lib.sh`, `scripts/review_final_ci_sweep.sh`, `scripts/ci_sync_quick.sh`, `scripts/ci_cancelled_rerun.py` (CI and `[sync-quick]` titles), `scripts/promote_main_cycle.sh` (Test & Mark Stable), `scripts/review_merge_train.sh`, `scripts/review_single_issue_security_pass.sh` (`(PR #N)` titles) and `scripts/evidence_pack.py` (never matches on it). `find_latest_scoped_run_field` in `scripts/comprehensive_test_and_release_gh_api.sh` and the smoke-run lookups in `test-and-mark-stable.yml` do read clarify, plan and implement runs by issue title; they keep matching only because of the `[E2E ` run-name exception.

- `QUEUE_BACKPRESSURE` (`scripts/orchestrate_poll_process.sh` `queue_backpressure_holds_dispatch`). Format: `QUEUE_BACKPRESSURE outcome=<on|off|unknown> queued=<n|unknown> high=<h>` (once per shell, stderr), `QUEUE_BACKPRESSURE outcome=held state=<s> action=<a> issue=<n> queued=<total>` (stdout, per held dispatch), and `::warning::QUEUE_BACKPRESSURE outcome=off reason=invalid_threshold`. `issue=` carries the caller's third argument verbatim: an issue number, or `validation` / a local id for the validation and wave-creation callers. For the open-PR conflict-resolver and autofix holds the PR number is only on the adjacent `STALL_SKIP ... reason=queue_backpressure pr=<pr>` line.
