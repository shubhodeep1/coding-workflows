**Final-merge exhaustion auto-resume (issue #8984).** `mark_validation_complete` in `scripts/orchestrate_poll_process.sh` writes `final_merge_failure_kind="final_merge_exhausted"` and `final_merge_failure_head_sha` (final PR head, 40-hex or `""`) in the same state write that sets `status=failed` after `MAX_FINAL_MERGE_ATTEMPTS`; the success write clears the kind. In the terminal-state block, after the `ai:force-merge` bypass and only for `status=failed`, `maybe_auto_resume_final_merge_exhaustion` checks, in order: switch `FINAL_MERGE_AUTO_RESUME_ENABLED` (default `true`, both poller env blocks in `orchestrate_poll.yml`), the marker, no validation-origin failure label (`project_is_validation_origin_terminal_failure`; reachable only when such a label is present while the marker is still set, for example applied by hand, because `/judge_resume` clears the marker), no aborted comprehensive cycle (`comprehensive_release_callback.handled` with a status other than `complete`, because the exhaustion park already released it), a 40-hex `validation_last_passed_sha`, a numeric `final_merge_pr`, the PR read (open, not merged, not a draft, 40-hex head), the head not already in `final_merge_auto_resume_head_shas` (last 200 kept, a bound on the state comment size well above any realistic number of resumes per project), `mergeable=true` + `mergeable_state=clean`, `_pr_checks_completed` with the base ref (required checks only), and `compute_cycle_integration_ahead_by` > 0. On success it writes `status=validating`, `final_merge_status=pending`, `final_merge_attempt_count=0`, clears the kind, records the head, persists the state comment (a failed persist restores the saved state and skips as `lookup_failed detail=state_persist`, so the head ledger is never lost after a retry starts), then sets the phase label (which drops `ai:blocked` / `ai:needs-human`; a failed label write restores the saved state with the head kept in the ledger, so that head's one retry is spent and later ticks skip as `already_resumed_on_head` instead of re-writing state every tick, re-persists it and skips as `lookup_failed detail=label_write`, or `detail=label_write_repersist_failed` when that re-persist also fails), posts a `<!-- final-merge-auto-resume:<sha> -->` tracking comment and sets `FINAL_MERGE_AUTO_RESUME_MODE`. When the head equals `validation_last_passed_sha` the mode is `merge`: the label is `ai:validated` and the caller runs `mark_validation_complete` in the same tick. When the head moved after validation passed the mode is `revalidate` (issue #9320 item 4): the write also sets `validation_last_dispatch_cycle=0` and `validation_last_dispatch_ts=now` (so the old head's successful run cannot trip the success fallback), the label is `ai:validating`, and the caller runs `dispatch_validation_if_needed`; the merge happens only after that head passes validation, so an unvalidated head is never merged on an older pass. Any failed lookup skips with the state unchanged; the one exception is the failed label write above, which keeps the head in the ledger. `/judge_resume` clears the marker. State parked before this change has no marker and is never resumed.
