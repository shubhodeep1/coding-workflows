**Final-merge exhaustion auto-resume (issue #8984).** `mark_validation_complete` in `scripts/orchestrate_poll_process.sh` writes `final_merge_failure_kind="final_merge_exhausted"` and `final_merge_failure_head_sha` (final PR head, 40-hex or `""`) in the same state write that sets `status=failed` after `MAX_FINAL_MERGE_ATTEMPTS`; the success write clears the kind. In the terminal-state block, after the `ai:force-merge` bypass and only for `status=failed`, `maybe_auto_resume_final_merge_exhaustion` checks, in order: switch `FINAL_MERGE_AUTO_RESUME_ENABLED` (default `true`, both poller env blocks in `orchestrate_poll.yml`), the marker, a 40-hex `validation_last_passed_sha`, a numeric `final_merge_pr`, the PR read (open, not merged, not a draft, 40-hex head), the head not already in `final_merge_auto_resume_head_shas` (last 20 kept), head == validated SHA, `mergeable=true` + `mergeable_state=clean`, `_pr_checks_completed` with the base ref (required checks only), and `compute_cycle_integration_ahead_by` > 0. On success it sets `ai:validated` (which drops `ai:blocked` / `ai:needs-human`), writes `status=validating`, `final_merge_status=pending`, `final_merge_attempt_count=0`, clears the kind, records the head, posts a `<!-- final-merge-auto-resume:<sha> -->` tracking comment, and the caller runs `mark_validation_complete` in the same tick. Any failed lookup skips with the state unchanged. State parked before this change has no marker and is never resumed.
