<!-- agents: section="Workflow architecture" -->
- **Plan-granted `.github/ai/<file>` writes (issue #9920, plan Phase 5 / R3 of `docs/plans/pipeline-human-wait-elimination-plan.md`).** The only grant source is the automation-path grant `build_automation_grant` (`scripts/files_touched_scope_guard.py --emit-automation-grant`) builds: the record must be `trusted == true` and not `open`, and only literal direct children of `.github/ai/` count (three segments; no `*`, `?`, `[`, `..`, trailing `/`, backslash, CR or LF).
  - *Implement.* After the self-repo `IMPLEMENT_SELF_REPO_GITHUB_AI_ADD` block (kept as is), `scripts/implement_commit_changes.sh` reads `${AUTOMATION_PATH_GRANT_FILE:-${RUNTIME_DIR}/automation_path_grant.json}` in every repository and `git add`s each granted regular, non-symlink file. `add_o_excludes` keeps `':!.github/ai'`. With `ALLOW_WORKFLOW_EDITS` not `true` it stages nothing (`outcome=skipped reason=workflow_edits_disabled`), because the automation-path guard would otherwise fail the run. The deletion, automation-path and files_touched guards still check every staged path.
  - *Sandbox.* `scripts/review_untrusted_workspace.py snapshot ... [--granted-paths-file <path>]` (an optional trailing pair, stripped before the argc checks) validates the list (one bad entry rejects all) and freezes it in the `<manifest>.github_ai_grants.json` sidecar; `transfer`, `refresh` and the heal repro classifier `cmd_scope` read only that sidecar, so a later caller cannot widen it. The review and heal jq filters keep only direct children (`^\.github/ai/[^/]+$`), so a nested entry in the grant is dropped instead of rejecting the whole list. `allowed(..., granted=frozenset())` admits a granted name after the EXCLUDED/`.env`/secret/credential filters and the `pr_merge_status_guard.py` deny; every other caller passes no set. In heal scope a granted name skips only the `.github/ai/` denial and must still match the scope file.
  - *Heal.* `scripts/heal_isolated_implement.sh` derives `${root}/github_ai_grants.json` from the automation grant before its snapshot; the gate and repro `manifest.json*` copy loops carry the sidecar, and the heal commit stages through `implement_commit_changes.sh`.
  - *Review.* `scripts/review_collect_pr_metadata.sh` adds `author{login} authorAssociation` to its existing linked-issue GraphQL calls and persists `author_login` / `author_association` in `linked_issues_raw.json`. `_review_github_ai_grant_prepare` in `scripts/review_untrusted_sandbox.sh` (`prepare` only, never `prepare-ephemeral`) runs only for exactly one linked issue with status `ok` whose body mentions `.github/ai/`, takes the pipeline login from `REVIEW_GITHUB_AI_GRANT_PIPELINE_LOGIN`, runs the trusted guard, and exports the list as `REVIEW_GITHUB_AI_GRANT_PATHS_FILE` (its own runner-temp directory). `scripts/review_commit_changes.sh` then keeps a granted creation out of the `pipeline artifact` removal (it still goes through the pre-editor untracked check) and, in consumer repos, stages it exactly despite the `':!.github/ai'` exclusion. Any failure falls back to no grant. The prepare step has no GitHub token, so the login is the GH_PAT identity implement uses: `review_collect_pr_metadata.sh` resolves it in the token-holding "Collect PR metadata" step (`id: collect_pr_metadata`) with the same one-issue/body pre-filter, publishes it as the step output `github_ai_grant_pipeline_login` (never `GITHUB_ENV`), and the `deps_prepare` step's `env:` passes it in. The helper's own lookup runs only when the variable is unset, and logs `reason=no_credentials` when no token is present either.
  - *Switch / rollback.* `GITHUB_AI_PLAN_GRANT_WRITE_ENABLED` defaults to `true` in every script and in the workflow-level `env:` of `implement.yml` and `review_autofix.yml`, which read it from the `AI_PLAN_GRANT_WRITE_ENABLED` repository variable (GitHub does not allow configuration variable names that start with `GITHUB_`); `false` (any case) restores the old behaviour and any other value is off with a warning. Tests: `tests/test_github_ai_plan_grant_write.py`.
