Stale auto-close of held heal issues (issue #8808). A run-sourced workflow-heal issue held at `ai:awaiting-approval` by the heal counterfactual gate (#8249) used to stay open forever, because the hold counts no recovery attempt. In the `heal_counterfactual_hold` branch of `_plan_auto_approval_gate`, before `_heal_counterfactual_hold_notify`, the poller now calls `_heal_stale_close_check` (`scripts/orchestrate_poll_process.sh`). `scripts/workflow_failure_heal.py heal-stale-decision --stage target|resolve|decide` (`python3 -I -B`; exit 0 for every decision, 2 when the issue or comments file cannot be read) closes the issue only when all of these hold:
- the issue is open, labelled `ai:workflow-heal` and `ai:awaiting-approval`, not `ai:orchestrator-managed` (`skip orchestrator_managed`), and has a trusted author;
- its body has `workflow-failure-heal:source=<repo>#run` (`#<n>` sources give `skipped not_run_sourced`; PR-sourced heals keep `workflow_failure_heal_pr_reconcile.sh`);
- a trusted `ai:heal-counterfactual-hold:v1 issue=<n> plan_comment=<latest plan id>` marker exists;
- no open same-repository PR with head `ai/issue-<n>` cross-references the issue (`open_issue_branch_pr` in the batched details map, read from the same `timelineItems` query whatever the link keyword, so a `Refs`-linked PR counts; `"unknown"` when the timeline was not returned, or when it has more than the last 50 cross-references (`pageInfo.hasPreviousPage`, same query) and none matched, gives `linked_pr_unknown`), and the map's `linked_pr` (or else `STALL_MANAGED_LINKED_PR_CACHE`) is not an open PR, where a missing entry gives `linked_pr_unknown`. Pipeline-created PRs always cross-reference their issue, because `implement.yml` writes `Automated implementation. Refs|Closes <issue url>` into the body. A hand-made `ai/issue-<n>` PR that never mentions the issue is not seen. This residual is accepted: issue #8808 condition 3 reuses the cross-reference cache, and finding such a PR would need a PR search outside the batched details query;
- the anchor (the later of the issue `created_at`, now in the batched details map, and its newest trusted `<!-- workflow-failure-heal:occurrence -->` comment) is at least `HEAL_STALE_MIN_AGE_HOURS` old;
- the newest `HEAL_STALE_GREEN_RUNS+10` completed `push` runs of the workflow on the target branch hold at least `HEAL_STALE_GREEN_RUNS` runs created after the anchor, and each one concluded `success`. Only that one page is read: when it neither reaches the anchor (holds a run created at or before it) nor holds every run the API's `total_count` reports, it must itself hold at least `HEAL_STALE_GREEN_RUNS` runs after the anchor, or the issue is kept (`runs_window_incomplete`). A long-held issue on a busy branch therefore closes once the newest page is green; a failure that comes back posts a trusted occurrence comment, which moves the anchor.

The plan's file list is never read. The workflow file comes from the body marker `<!-- workflow-failure-heal:workflow=.github/workflows/<file>.yml -->`. The intake writes it as an optional sixth header line for `workflow_run` sources from the verified run's `.path` (`compose-issue --workflow-path`), and `validate_heal_issue_body_routing` accepts exactly one fully matched line there. Older issues instead make one `GET actions/runs/<id>` read of the first source-repository run in the `ai:workflow-heal-scope:v1 runs=` marker. API budget per tick: at most one `GET repos/<src>/actions/workflows/<file>/runs` per (repo, workflow, branch) (`HEAL_STALE_RUNS_CACHE_JSON`), one cached run lookup per run (`HEAL_STALE_RUN_LOOKUP_CACHE_JSON`), and on close one comment plus one `PATCH state=closed state_reason=completed`. Labels are left as they are. Any API error or malformed response, including a single run entry that is not an object or has no parseable `created_at`, keeps the issue open (`kept runs_unavailable`). On close it posts one comment ending `<!-- ai:heal-stale-close:v1 issue=<n> workflow=<file> branch=<b> green_runs=<k> newest_run=<id> -->` (none when a trusted one exists, so a failed PATCH is retried alone next tick), sends a Telegram `DEBUG` (the pipeline handled it) and skips the hold notice. A recurrence files the next lineage generation through the intake (cap unchanged). No automation reopens heal issues, so partial-delivery tracking needs no guard. Flags, defaulted in the script and on the five `orchestrate_poll.yml` steps that set `HEAL_COUNTERFACTUAL_GATE_ENABLED`:
- `HEAL_STALE_AUTO_CLOSE_ENABLED` (`true`; `false` turns it off, any other value warns and is treated as `true`);
- `HEAL_STALE_GREEN_RUNS` (`5`, an integer of at least 1; above 90 it warns and uses 90, because one runs read returns at most 100 runs);
- `HEAL_STALE_MIN_AGE_HOURS` (`24`, an integer of at least 0).

Invalid integers warn and use the default. Tests: `tests/test_workflow_failure_heal.py` (`heal_stale` cases) and `tests/test_orchestrate_poll_process.py` (stale-close fixtures).
