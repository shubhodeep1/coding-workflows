Integration-sync conflict preparation (`scripts/review_conflict_prepare.sh`) reads the newest complete `ORCHESTRATOR_STATE_V2` chain by the pipeline login first, the same way `_resolver_test_repair_context` in `scripts/review_conflict_resolve.sh` does. It runs `orchestrate_state_v2.py extract` from `${SUPPORT_SCRIPTS_DIR}` or `${GITHUB_WORKSPACE}/.codex-workflow-src/scripts/` (absolute paths only, never a symlink, `python3 -I -B`) and falls back to the V1 comment only when there is no V2 state. The merged sub-issue list and `merged_issue_fingerprints` in the resolver prompt now come from current state, so the resolver's fingerprint check runs again: it skips a fingerprints file of 2 bytes or less, and the old V1-only read always produced `{}` because the poller never writes V1. Missing or unreadable state still fails open with an empty list and `{}`. Switch `CONFLICT_INTEGRATION_V2_STATE_ENABLED` (default `true`, forwarded from the repository variable by the prepare step in `.github/workflows/review_autofix.yml`): unset, empty or `true` in any case is on, `false` keeps the V1-only read, and any other value keeps the V1-only read with a `::warning::`.
