- **Security dependency hold escalation and unmerged release (stuck-states P8c, Refs #8291).** The standalone poller's security-dependency branch in `run_standalone_stall_recovery` (`scripts/orchestrate_poll_process.sh`) now ages and releases holds; it still runs only for standalone (not orchestrator-managed) follow-ups.
  - **Switch.** `DEPENDENCY_WAIT_RESUME_ENABLED` (default `true`, parsed once per sweep and exported). `scripts/security_dependency.py` reads the same variable with its own `true` default, and `clarify.yml` ("Decide clarify route") and `implement.yml` ("Validate approval phase label", "Recheck security dependency before edits") forward it. When on, a predecessor closed without `ai:merged` returns `status=ready` with the unchanged reason `dependency closed without ai:merged`; `false` restores the `held` verdict and every write below is skipped.
  - **State keys.** The `AI_STANDALONE_STALL_STATE_V1` comment carries optional integer keys `security_dependency_depends_on`, `security_dependency_held_since_ts` (UTC epoch seconds) and `security_dependency_escalated_ts`. `_extract_standalone_state_json_from_comments` keeps them only when present (unparsable values become 0); the ordinary `updated_state` write drops them, which ends the hold episode once the issue is no longer held.
  - **Aging.** Only a verified `dependency open` verdict ages the hold (`_security_dependency_hold_age_check`). `held_since` is recorded once (reset when missing, invalid, in the future or for a different `depends_on`). The hold keys and the state comment written back are read only from `AI_STANDALONE_STALL_STATE_V1` comments by the pipeline login (`unblock_trusted_login`, one cached `/user` read per tick; unavailable logs `security_dependency_identity_unavailable` and writes nothing), so a forged state comment cannot mark a hold escalated. After `DEPENDENCY_WAIT_ESCALATE_DAYS` (default `7`, 1-9999, else `7`) the poller posts a latch comment ending `<!-- ai:needs-human-latch reason=security_dependency_wait depends_on=<M> held_since=<ts> -->` and then adds `ai:needs-human`; `escalated_ts` is written only after the label lands. A failed comment or label write logs `security_dependency_escalation_failed` and leaves `escalated_ts` at 0, so the next tick retries; when this episode's latch comment (same `held_since`) already exists from the pipeline login, it only adds the label (`reason=security_dependency_escalated detail=marker_present`). A latch comment from an earlier episode does not match. Escalation is skipped when the label is present or `escalated_ts` is set. The hold stays in place.
  - **Unmerged release.** For `ready` + `dependency closed without ai:merged` the poller posts one `/reclarify\n<!-- AI_SECURITY_DEPENDENCY_RELEASED_V1 reason=predecessor_unmerged issue=<n> depends_on=<M> -->`, deduplicated on that marker written by the pipeline login (`unblock_trusted_login`); no post when the login or the complete comment history is unavailable. The merged release (`ai:security-dependency-released:<n>`, author_association trust) is unchanged.
  - **Latch removal.** On either release the poller removes `ai:needs-human` only when the latest pipeline-login latch comment is `reason=security_dependency_wait` and the newest `labeled` event for `ai:needs-human` (one paginated `issues/<n>/events` read) was made by the pipeline login; other latches stay, and a label a person re-added later is kept (`reason=security_dependency_latch_kept detail=labeled_by_other`, the release still posts). An unreadable events list counts as a failed removal. A failed removal posts no release marker (`reason=security_dependency_retrigger_failed detail=latch_clear_failed`), so the next tick retries the removal and the release together.
  - **Log reasons** (existing `STALL_SKIP issue=<n> reason=... action=...` line, no new prefix): `security_dependency_hold_recorded`, `security_dependency_escalated`, `security_dependency_escalation_failed`, `security_dependency_released_unmerged`, `security_dependency_latch_cleared`, `security_dependency_latch_kept`, `security_dependency_identity_unavailable`, plus the existing `security_dependency_comments_unavailable` / `security_dependency_retrigger_failed`.
  - **API budget.** Steady state adds the verdict read plus one cached `/user` read per tick. One state write per hold episode; at escalation one label edit, one comment and one state write; on a release one `/reclarify` plus, when `ai:needs-human` is present after this hold's latch, one paginated events read and at most one label edit. A paginated comments read runs only when a write is due and the cached 100-comment window is incomplete.
