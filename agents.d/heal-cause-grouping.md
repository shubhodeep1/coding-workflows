Heal cause grouping (P5 / decision D3 of `docs/plans/heal-evidence-reproduction-and-trends-plan.md`, Refs #8434): behind `WORKFLOW_HEAL_CAUSE_GROUPING_ENABLED` (default `false`; only the literal `true` turns it on, defaulted in `scripts/workflow_failure_heal_intake.sh` and in both the `intake` and `recovery-scan` jobs of `.github/workflows/workflow-failure-heal-intake.yml`). `cause_key(workflow, failing_step, shape)` in `scripts/workflow_failure_heal.py` is the sha256 of the workflow name (the `[cycle:N]` suffix stripped exactly as `fingerprint()` does), the failing step and the `classify_failure_shape` class (unknown shapes count as `other`); `fingerprint()`, `root=` and the five existing markers are unchanged. The intake's `_heal_cause_key` runs the pure `cause-key` subcommand after the fingerprint, only for `workflow_run` and `phase_failure` reports that are not recovery replays (`REPORT_AUTH=reconstructed`), have a failing step and have a signature from real error lines (not empty, `no-error-lines`, `phase:*` or `label:*`); the job conclusion (`timed_out` from the current run's saved jobs JSON) and the failing tests (`heal-scope failing-tests` over the saved job logs) are the same inputs the run-time trend uses. New heal issues then carry an optional sixth header line `<!-- workflow-failure-heal:cause=<64 lowercase hex> -->` right after `classification=`; `validate_heal_issue_body_routing` accepts exactly that line as line 6 (`_HEAL_CAUSE_MARKER_LINE_RE`, fullmatch) and still rejects a seventh marker, a malformed `cause=` line or `<!--` anywhere else with `marker`. `build_issue_payload`'s trusted-lineage check (`startswith` over the five keys) is unchanged. `budget_decision(cause=, cause_window_days=)` (`budget --cause --cause-window-days`, window clamped 1..30, default `WORKFLOW_HEAL_CAUSE_GROUPING_DAYS=3`) matches an open listed heal issue whose `cause=` marker equals the key and whose `created_at` is inside the window (a missing `created_at` never matches); decision order is fingerprint duplicate, source duplicate, re-issue duplicate, lineage-cap escalation, **cause duplicate** (`match: cause`, plus the report's own `lineage_source`), budget caps, open. A cause match still runs the re-issue lookup (which outranks it) and is skipped by heal-scope recovery, so another fingerprint's heal issue is never replaced. The heal-scope recovery budget re-run drops `--cause` and `--cause-window-days`, so an unrelated same-cause heal issue never blocks a replacement, and a `phase_failure` report that cause-matches its own heal issue escalates (`heal_issue_failed_itself`) exactly as a fingerprint self-match does. The occurrence comment (`compose-occurrence --signature-file --cause-shape [--evidence-pack-file]`) adds a `Matched by` line, the neutralised signature (backticks removed) and, with `WORKFLOW_HEAL_EVIDENCE_PACK_ENABLED=true`, an `## Evidence pack` rendered from the failed-run JSON already saved (`--failed-run` only, no linked runs, no `_heal_fetch_evidence_pack_api`). The heal-issue lists the intake already reads are the only input: zero new GitHub reads, and the only write is the existing occurrence POST. With the switch off no `cause` line is logged, no `--cause` is passed (existing `cause=` markers are ignored) and bodies and comments are byte-identical.
