Heal intake runner-wait credit (alerts of 2026-11-13; intake runs 43439048054, 43496779526, 43498856864): the intake job waited 1h54m to 3h25m for a GitHub-hosted runner, while the heal queue step (`HEAL_INTAKE_QUEUE_WAITED_SECONDS`) had waited seconds, so `verify-report-identity` rejected valid reports as `identity_stale` against the 3600-second limit. For a `repository_dispatch` report that carries an identity, or an `engine_fallback` report, `scripts/workflow_failure_heal_intake.sh` now reads its own run attempt once (`repos/<self>/actions/runs/<GITHUB_RUN_ID>/attempts/<GITHUB_RUN_ATTEMPT>`, `.run_started_at`) and, when the elapsed time is larger than the queue wait, adds that instead (clamped to 0..86400). The limit therefore applies at the report's arrival; a re-run attempt starts its own clock. A failed read logs `report_age_credit outcome=unavailable` and keeps the queue-only credit.

Sandbox-excluded escalation counts top-level bullets only (PRs #9453, #9390): `scripts/review_autofix_step_post_editor_summary.sh` counts an "Ignored suggestions" bullet as a declined `sandbox-excluded path` finding only when it has at most one leading space and no tab. An indented sub-bullet that explains a sandbox-only test failure and happens to end with "a sandbox-excluded path" no longer writes the `review_editor_sandbox_path_excluded` marker, so it no longer caps the head or gets `ai:needs-human` from the heal intake.

Single-issue security gate `head_unpushed` hold (PRs #9338, #9283; review runs 43385072188, 43161924339): the conflict resolver commits `[ai-merge-resolve]` locally and the job pushes it after the review-blocked judge, so the judge's merge gate saw a checkout `HEAD` one commit ahead of the PR payload head and held as `extensions_unverifiable`, which paged "will not clear on its own". `single_pass_gate` in `scripts/review_single_issue_security_pass.sh` now holds as `head_unpushed` (status mode: `unverifiable`) when the checkout `HEAD` differs from the PR head and descends from it. The merge still holds, since that head is unaudited, but the "Telegram review-blocked judge decision" step treats `security_hold_head_unpushed` like `audit_dispatched`: the deferred push starts the review whose gate audits the new head. A checkout that does not descend from the PR head still holds as `extensions_unverifiable`.
