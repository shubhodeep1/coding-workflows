**Transient CI and stale check-triage recovery (#8671).**
- `scripts/ci_cancelled_rerun.py` `classify_runner_shutdown` has a third transient class, `checkout_fetch`. A failed non-`lint` job counts when `job_failed_at_checkout` holds (the first failed step is `Checkout repository` or `Run actions/checkout*`, only a successful `Set up job` ran before it, and every later step is skipped or `Post *` / `Complete job`) and `checkout_fetch_annotations` holds (every failure annotation fully matches `CHECKOUT_FETCH_MESSAGES`, at least one matches `CHECKOUT_FETCH_STRONG`). Any run with such a job, mixed only with shutdown or action-resolution jobs, returns `checkout_fetch` and is re-run once. The off switch is `CI_CHECKOUT_FETCH_RERUN_ENABLED`, forwarded by `review_autofix_sweep.yml`. The class makes no extra reads.
- `scripts/check_triage_resolution.py` `verify_resolution` hands an open, unmerged PR to `_verify_open_head`. That function resolves only for a same-repository PR whose current head differs from the trusted header's `Head SHA`, as follows:
  - check-run triage: the latest runs of the check on the head all succeeded;
  - workflow-run triage: the newest `pull_request` run of the workflow on the head (no status filter) is `completed`/`success`, and `shard_jobs_resolved` holds for the triaged run's failed jobs.
  
  The gate JSON gains `path` (`merged` | `open_head`, only when resolved), `pr_state` and, on the open path, `triage_head_sha`. The marker's `sha` is the current head.
- `scripts/check_failure_triage.sh` dedup (normal mode only) widens its existing listing projection with `labels`, `user_login`, `user_type` and `author_association`. `triage_supersede_candidate` lets the run continue when exactly one open issue matches and that issue:
  - is `ai:blocked`;
  - passes the `_author_trusted` rule;
  - starts with the canonical fp header;
  - has one unfenced `Head SHA` on another commit, while the new failure is on the PR's current head.
  
  The candidate goes into `triage_metadata.json` (`supersede_issue`, `supersede_old_head_sha`, `supersede_new_head_sha`). Before the new issue is created, `triage_supersede_old_issue_eligible` runs the account and state check below with the posting token: the new `CHECK_TRIAGE_STAGE=supersede-check` in `check_failure_triage.yml`'s post step, run only when `triage_metadata.json` records a `supersede_issue` (exit 10, or any non-zero exit, skips the create; the post step logs `op=supersede outcome=skip_create rc=<n>`, plus a `::warning::` for an exit other than 10; with `CHECK_TRIAGE_SUPERSEDE_STALE_ENABLED` off the stage logs `reason=disabled` and exits 10), or stage `all` right before its own create. A failed check logs `skip reason=duplicate_open_issue`, so a stale issue another account opened never ends up next to a second open issue with the same fingerprint. After the new issue exists, `triage_supersede_stale_issue` reads the token's login (one `GET /user`; unreadable logs `reason=identity_unavailable`) and re-reads the old issue (one GET; the login must have opened it, else `reason=not_own_issue`, and it must still be open and `ai:blocked`, else `reason=old_issue_stale|old_issue_unreadable`), then comments (marker `<!-- check-failure-triage:superseded-by=<n> -->`), closes the old issue as `not_planned` and only then adds `ai:closed`, so a failed close never leaves the terminal label on an open issue. It runs from stage `all` after its own create, or from the new `CHECK_TRIAGE_STAGE=supersede`, which `check_failure_triage.yml`'s post step calls with `CHECK_TRIAGE_SUPERSEDE_NEW_ISSUE_URL` and its Issues-scoped token (`|| true`). The off switch is `CHECK_TRIAGE_SUPERSEDE_STALE_ENABLED`.
- Unblock judge hold kind `pr_check_green` (`HOLD_KINDS` in `scripts/unblock_ledger.py`):
  - ref `<pr>@<percent-encoded check name>` (`~` as `%7E`, at most 120 characters; the check name is 1-100 characters with no control characters, `,`, backtick, `<` or `>`). The hold-marker ref class in both parsers includes `%`.
  - `unblock_hold_condition` reads the check-triage gate verdict that `unblock_check_triage_resolved` cached in `${RUNTIME_DIR}/triage_resolution.json` (only when `.issue` equals the item), else one `gate --dry-run`. The mapping is:
    - `resolved` / `already_resolved` → `met`;
    - `pr_state` `open` → `unmet`;
    - `closed` / `merged`, `not_triage`, or a PR or check mismatch → `impossible`;
    - anything else → `unknown`.
  
  Both judge prompt copies say re-running a check is never an operator step.

- `CI_CANCELLED_RERUN` also logs `action=rerun reason=checkout_fetch` (#8671, `scripts/ci_cancelled_rerun.py`) when every non-`lint` failed job of a current-head `failure` run is a checkout-fetch job (mixes with runner-shutdown or action-resolution jobs included).
- `CHECK_TRIAGE_RESOLVED` also logs `path=merged|open_head` (#8671, `scripts/check_triage_resolution.py` `_cmd_gate`; empty when not resolved). New unverified reasons on the open-head path: `open_head_unreadable`, `triage_head_unavailable`, `open_head_unchanged`, `open_head_checks_unreadable`, `open_head_check_<outcome>`, `open_head_run_unreadable`, `open_head_run_missing`, `open_head_run_pending`, `open_head_run_not_success`, `open_head_run_jobs_unreadable`.
- `CHECK_TRIAGE` also logs `op=supersede outcome=candidate old=<n> fp= pr=`, `op=supersede outcome=skip reason=disabled|multiple_open|not_blocked|untrusted_author|header_mismatch|old_head_unreadable|same_head|not_current_head|new_issue_invalid|metadata_missing|metadata_invalid|identity_unavailable|not_own_issue|old_issue_stale|old_issue_unreadable old=<n>` (with `stage=pre_create` before the create, `new=<m>` after it), `op=supersede outcome=skip_create rc=<n> pr=<n>` (post step), `op=supersede outcome=closed old=<n> new=<m>` and `op=supersede outcome=warn reason=supersede_close_failed|supersede_label_failed old=<n> new=<m>` (#8671, `scripts/check_failure_triage.sh`).
- `UNBLOCK_JUDGE` also logs `op=hold hold=pr_check_green ref=<pr>@<encoded check>` with the existing hold outcomes (#8671, `scripts/unblock_judge.sh`).
