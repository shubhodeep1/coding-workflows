- **Judge-decision lease grant (issue #9987).** When the review-blocked judge decides `merge`, `merge_with_followup` or the terminal `fix` merge and `_pr_base_fresh_for_merge` returns `PR_BASE_FRESHNESS_OUTCOME=lease_wait`, `rb_judge_mark_merge_pending <decision>` (`scripts/review_rb_judge.sh`, block `# BEGIN/END rb-judge judge-decision lease mark (#9987)`) calls `_pr_judge_merge_pending_mark <pr> <head> <merge|merge_with_followup|terminal>` (`scripts/pr_checks_lib.sh`) at most once per run. That posts one `success` status under `MERGE_LEASE_JUDGE_DECISION_CONTEXT` (`ai-review/judge-merge-pending`, a fixed name, not an env input) on the judged head; it posts nothing with `MERGE_LEASE_REVOKE_ENABLED=false` or on invalid input, and a failed POST only warns. `ai-review/head-gate` is still posted only right before a merge request ("gates first"). The `merge_with_followup` `lease_wait` branch keeps `judge_skip_reason=base_freshness_unknown`.
  - `_merge_lease_pr_eligible` reads the newest status of that context from the statuses response it already fetched (no extra call). For a waiter only, when head-gate is absent or pending from the trusted login, a `success` created by the trusted login makes it eligible; a head-gate `failure`/`error`, or any head-gate state from another login, still wins (`no_head_gate`), and holders are unchanged. It sets `MERGE_LEASE_ELIGIBLE_GATE=head_gate|judge_decision` (empty when eligibility did not rest on a status, e.g. fail-open).
  - Both tick loops (`_mt_merge_lease_tick`, `_mt_merge_lease_tick_multi`) dispatch a `judge_decision` grant through `_mt_dispatch_rb_judge <pr> <head>` (`scripts/review_merge_train.sh`): one `gh workflow run review_rb_judge_dispatch.yml -f pr_number=<pr>` (force_rb_judge, so no reviewer/editor round). When that dispatch fails (the `core` profile ships no such wrapper) it dispatches `ai-review.yml`, then `internal-review.yml`, with `-f pr_number=<pr> -f force_rb_judge=true -f allow_workflow_edits=false` (`internal-review.yml` defaults that input to `true`; a judge-only run never gets workflow-edit capability), and only when neither can be dispatched falls back to `_mt_dispatch_review` (a degraded last resort: a plain review round, as before #9987).
  - A `lease_wait` deferral writes no `[judge-fix]` commit, so it never counts against `MAX_REVIEW_BLOCKED_RETRIES` (`RETRY_COUNT` comes only from `JUDGE_FIX_COUNT`).
