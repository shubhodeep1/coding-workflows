- **Merge lease (2026-11-17, follow-up to #9642; on the stable line from v1.47.4).** Approved PRs into `main` were still updated up to six times without merging (#9367 update 6, #9368 update 5): each update head needed a final CI run that took 1.5-2.5 hours on the congested runner pool, and `main` moved under a shared file before it finished. GitHub's merge queue is not available here (user-owned repository), and the `main` ruleset does not require up-to-date branches (`strict_required_status_checks_policy: false`), so freshness is the pipeline's own rule. The change:
  - **Merge lease** (`scripts/pr_checks_lib.sh`, "Merge lease"). `_pr_base_fresh_for_merge` calls `_merge_lease_gate <pr> <base> <head> update` before it requests a branch update, and `... merge` before a fresh or clean merge proceeds. One lease per base, the ref `MERGE_LEASE_REF_PREFIX<base>` (default `refs/merge-lease/<base>`) pointing at a commit whose message is the record (`merge-lease v1`, `state=held|released`, `pr=`, `head=`, `expires=`, `paths:` then one path per line or `*`). Every write is a child of the record read, moved by a fast-forward-only PATCH, so concurrent writers cannot both win (a loser re-reads and decides again, at most twice). Update mode: a live lease held by another PR, or a free lease with an earlier waiter in queue order (priority label from `MERGE_TRAIN_PRIORITY_LABELS` on the PR, then the lowest number), means wait: no update, label `MERGE_LEASE_WAIT_LABEL` (`ai:merge-lease-wait`), `PR_BASE_FRESHNESS_OUTCOME=lease_wait`, return 1. Otherwise the PR takes or renews the lease (`expires` = now + `MERGE_LEASE_TTL_MINUTES`, default 240; the record keeps `acquired=` from the first take) and updates as before. A holder past `MERGE_LEASE_MAX_HOLD_MINUTES` (default 720, never below the TTL) since `acquired` stops renewing (`reason=max_hold_reached`), so a holder whose update keeps failing frees the base at its next expiry. Merge mode waits only when another PR holds a live lease and shares a path with it. Callers (`deterministic-skip-merge`, `scripts/review_enable_auto_merge.sh`, `scripts/review_rb_judge.sh`) report `reason=merge_lease_wait`; standalone stall recovery in `scripts/orchestrate_poll_process.sh` does not count a lease wait as a recovery attempt (`attempt_merge_skipped_merge_lease_wait`). Every lease read or write failure proceeds as before with `MERGE_LEASE ... outcome=unavailable` (fail-open; the lease only ever delays). `MERGE_LEASE_ENABLED=false` turns it off.
  - **Lease hand-off** (`_mt_merge_lease_tick` in `scripts/review_merge_train.sh`, run by `release` after the queued-PR loop, so on every poll tick and every PR close). It lists lease refs (`git/matching-refs`), writes `state=released` for a holder that is not in the open-PR list or whose expiry passed, (a holder missing from the list is confirmed closed with one live `pulls/<n>` read first), then reserves a free lease for the first waiter on that base, removes its wait label and dispatches its review (`_mt_dispatch_review`); the review's merge path then finds itself the holder and updates at once. The review sweep (`review_autofix_sweep.yml`) skips `ai:merge-lease-wait` PRs (`AUTOFIX_SWEEP_SKIP ... reason=merge_lease_wait`) only while both the lease and the merge train are enabled, since the train's release step is what re-dispatches waiters. A holder whose review run never comes back blocks only overlapping PRs, and only until its expiry.
