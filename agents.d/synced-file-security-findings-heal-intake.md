Workflow failure heal, synced-file security findings (Phase 1 of `docs/plans/synced-file-security-findings-heal-intake-plan.md`, tracking #7604): the report kind `synced_security_finding` carries one finding a consumer's `scripts/security_audit.sh` kept out of its queue as `upstream_managed` (the cited file is byte-identical to the coding-workflows release copy). `workflow_failure_heal.py build-synced-security-finding-payload` is the trusted builder the Phase 2 sender will call; `validate_payload` re-checks every field (finding id and category patterns, severity `critical|high|medium|low`, confidence 1-10, a positive line, an ASCII repo-relative path, a 40-hex `wrapper_sha`, no `run_refs`) and strips scope markers, routing keys and `<!--` from the model-written exploit scenario and recommendation (each cut to 600 characters and redacted). The intake (`scripts/workflow_failure_heal_intake.sh`) skips the kind unless `WORKFLOW_HEAL_SYNCED_SECURITY_FINDING_ENABLED=true` (default off in the script and in `workflow-failure-heal-intake.yml`; any value other than unset, empty, `true` or `false` warns), requires a verified OIDC identity bound to `security-audit.yml` (`REPORT_IDENTITY_WORKFLOW_BY_KIND`) even while `WORKFLOW_HEAL_REQUIRE_REPORT_AUTH=false`, and maps the consumer path with `synced-security-finding-scope` before diagnosis: `.github/workflows/<name>.yml` to `workflow-templates/<name>.yml`, `.claude/commands/<name>.md` to its template, audit-gate targets to `workflow-templates/audit-gate/<source>`; `.claude/hooks/**` (`live_safety_hook`), other `.claude/**`, `CLAUDE.md` and unmanaged or missing sources skip as `synced_security_finding_unmappable`. The fingerprint is `fingerprint("synced-security-finding", <source path>, <category token>)`, so the same file and finding class from every consumer and run share one lineage. The frozen scope is the mapped file plus `tests/**` and `changelog.d/*.md`, with the run ref `<consumer>:<verified reporter run id>` taken from the token, never the payload; `_heal_report_claimed_no_runs` excludes the kind, so an unresolved scope keeps the CRITICAL `scope_marker_unverified` refusal. Every classification other than `workflow-defect`, `inconclusive` and a verified `already-fixed` is remapped to `workflow-defect` (`reason=synced_security_finding_upstream_owned`), so the heal issue is always filed in this repository; the reason `synced_file_security_finding` is deterministic. No new log prefix: all lines use `WORKFLOW_HEAL`. Tests: `tests/test_workflow_failure_heal_security_finding.py`.
