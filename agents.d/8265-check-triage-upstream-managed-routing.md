Check-failure triage upstream routing (issue #8265, Refs #8066, #8176). `prompts/mode-check-failure-triage.txt` (and its identical `_templates/` copy) asks the diagnosis to end "Affected files" with one block: `AFFECTED_FILES_BEGIN`, an optional `cause: <path>` line, one `- <path>` line per file (at most 20, repository-relative, no globs, no `..`), `AFFECTED_FILES_END`.
- **Classification.** The diagnose stage of `scripts/check_failure_triage.sh` (`triage_upstream_classify`, before neutralisation) runs `workflow_failure_heal.py check-triage-route` from trusted support with no credentials. `parse_check_triage_affected_files` reads the block as untrusted data. `scripts/build_sync_manifest.py` `classify_paths` / `classify_managed_path` (subcommand `classify-paths`) hashes each path's git blob at the failing head SHA in the PR checkout, never the working tree, against the `managed-digests` map: `unmanaged`, `unmodified` (a listed digest, or for `.github/workflows/` the pin-normalised digest) or `modified` (anything else, symlinks and missing files included). The security audit keeps its inline copy of the same rule; `tests/test_build_sync_manifest.py` pins the two together.
- **Decision.** The decision is `route` when every path is `unmodified`, or when `cause` is an `unmodified` `.github/workflows/` path; only the unmodified paths are reported. Any `modified` path files the consumer issue. The decision lands in `${RUNTIME_DIR}/upstream_route.json`.
- **Sending.** The workflow's "Stage workflow support files" step builds `${RUNNER_TEMP}/check-triage-managed-digests.json` from the SHA-verified pinned `.codex-workflow-src` before pruning it. It exports `CHECK_TRIAGE_UPSTREAM_MANAGED_DIGESTS_FILE`, and `CHECK_TRIAGE_WRAPPER_SHA` only for a 40-hex pin outside this repository. The new step "Route upstream-managed check failure" (`id: upstream_route`, `continue-on-error`, env `GH_TOKEN` = `GH_PAT`, `TG_BOT_SECRET`, `CHECK_TRIAGE_STAGE=route`) runs between diagnose and post. It also receives `WORKFLOW_HEAL_ENABLED` (`vars.WORKFLOW_HEAL_ENABLED || 'true'`), so a consumer's heal opt-out stops the report, and it does not run in this repository. A diagnosis that fell back to the CI-log body never routes (`reason=fallback_diagnosis`), because that text is untrusted log output. It sends one `repository_dispatch` (`workflow-failure-heal`) with an OIDC report identity and writes `routed=true`. "Post check-failure triage issue" runs only when `routed != 'true'`. A direct `all`-stage caller routes just before its own `gh issue create`.
- **Switch.** `CHECK_FAILURE_TRIAGE_UPSTREAM_ROUTING_ENABLED` is defaulted in the script and the workflow: unset, empty or `true` (any case) means on, `false` means off, and any other value means off with a `::warning::`. `CHECK_TRIAGE_UPSTREAM_REPOSITORY` defaults to `shubhodeep1/coding-workflows`. This repository, historical mode, an unpinned wrapper and `WORKFLOW_HEAL_ENABLED=false` never route; in this repository the diagnose stage does not start the classify helper at all and only logs `upstream_route outcome=file reason=self_repo`.
- **Logs** (existing `CHECK_TRIAGE` prefix):
  - `upstream_route outcome=file reason=disabled|self_repo|historical_mode|fallback_diagnosis|no_block|malformed_block|no_paths|manifest_unavailable|classify_failed|head_sha_unavailable|helper_missing|consumer_modified|unmanaged_paths`
  - `upstream_route outcome=candidate reason=all_unmodified_managed|managed_wrapper_cause paths= heal_fp=`
  - `upstream_route outcome=fail_open reason=disabled|support_unpinned|workflow_heal_disabled|token_missing|helper_missing|payload_invalid|identity_unavailable|dispatch_envelope_failed|dispatch_failed|metadata_missing|metadata_invalid`
  - `skip reason=upstream_managed fp= pr= check= paths= route_reason=`
  - `upstream_route outcome=routed heal_fp=<64 hex> upstream=<repo>`

Heal kind `synced_check_failure` (`scripts/workflow_failure_heal.py`; reporter workflow `check_failure_triage.yml` in `REPORT_IDENTITY_WORKFLOW_BY_KIND`) carries only these fields:
- `pr_number`;
- `check_name`, reduced to `[A-Za-z0-9 ._:/()-]` and 100 characters;
- `check_run_ids`: up to 3 Actions run ids from a same-repository `details_url`, used as links and never read;
- `paths`: 1-20 safe relative paths, plus an optional `cause_path` that must be one of them;
- 40-hex `head_sha` and `wrapper_sha`, and the reporter run.

`run_refs` must be empty. In `scripts/workflow_failure_heal_intake.sh` the kind needs a verified identity whose `job_workflow_ref` ends in `@<wrapper_sha>` (`identity_required`, `release_mismatch`). A report from this repository is skipped (`skip reason=synced_check_self_repo`). `_synced_check_failure_intake` runs before provenance and reads no log:
1. It runs the shared `_synced_release_prepare`, factored out of the `synced_security_finding` branch without behaviour change. That covers the release fetch, `compare/<sha>...stable` (`release_not_on_stable`), `managed-digests` at the release and the retired lists.
2. `synced-check-check-paths` (`unmanaged_path`).
3. `skip reason=retired_file`.
4. `skip reason=release_superseded` when a mapped template source appears in the compare response's `files`; a page of 300 files counts as unknown.
5. One fingerprint, `synced-check-fingerprint`: the sha256 of the sorted paths.
6. The usual `budget` decision. A duplicate becomes `compose-synced-check-occurrence`. An open renders a heal scope from the template sources plus the reporter run and passes the scope guard, then `compose-synced-check-issue` and `gh issue create --label ai:workflow-heal`.

It logs `WORKFLOW_HEAL received kind=synced_check_failure paths=N outcome=opened|occurrence|skipped [reason=] fp=`. Tests: `CheckFailureTriageUpstreamRoutingTests` in `tests/test_check_failure_triage_workflow_security.py`, the `synced_check` cases in `tests/test_workflow_failure_heal.py` and `tests/test_workflow_failure_heal_synced_security.py`.
