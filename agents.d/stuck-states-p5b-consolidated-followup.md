<!-- agents: section="Workflow architecture" -->
- **Single-issue security pass consolidated follow-up (stuck-states P5b, Refs #8291).** Switch: `SINGLE_ISSUE_SECURITY_PASS_CONSOLIDATE_ENABLED` (default `true` in `scripts/security_audit.sh` and in the `security-audit.yml` row; `false` restores one follow-up issue per finding).
  - **When.** `scripts/security_audit.sh` sets `SECURITY_AUDIT_CONSOLIDATE_ACTIVE=true` only in issues mode with `SECURITY_AUDIT_TARGET_REF` set, `SECURITY_AUDIT_PASS_PR_NUMBER` matching `^[1-9][0-9]{0,9}$` (`security-audit.yml` step "Run security audit" exports `inputs.pr_number`; an invalid value warns and is dropped) and the switch truthy. It logs `security-audit: followup_mode=<consolidated|per_finding> pr=<n|none>`. A finding ID that cannot sit on its own marker line falls back to the per-finding path for the run. Scheduled and `ref`-only audits never consolidate.
  - **Body.** One `<!-- ai:security-finding:<id> -->` line per new finding (the leading marker block), `Refs #<tracker>`, `- Pull request: #<pr>`, `- Audited head:`, `- Integration branch:`, then `## Findings`. Title `[security-audit] PR #<pr>: <k> findings at <head12>`. Over 60,000 characters the per-finding prose is truncated; marker lines are always kept. `followups_created` counts issues (0 or 1); the summary line format is unchanged.
  - **Depends on.** The consolidated `followup-index.tsv` row has file key `multi:<k1>+<k2>...`; the create loop appends exactly one `- Depends on: #<n>` (`scripts/security_dependency.py` holds an issue with repeated lines): the highest open predecessor across those files (`LAST_OPEN_FOLLOWUP_BY_FILE`, filled from existing rows whose title column is `open` and from issues filed in the run), or the highest closed one when none is open (`LAST_ANY_FOLLOWUP_BY_FILE`, a per-file maximum; `LAST_FOLLOWUP_BY_FILE` keeps the last-listed row for the unchanged per-finding chain), then records the new number for every file. A closed `ai:merged` predecessor would release the hold while another file's predecessor is still open. Known limit: with open predecessors in several files only the highest-numbered one is depended on, so merging it releases the hold while a lower-numbered one is still open. In consolidated mode the tracker's `New follow-up issues planned this run:` line counts issues (0 or 1), and the `Follow-up mode: consolidated` line appears only when an issue is planned.
  - **Readers (unconditional).** The audit dedupe adds every ID in a body's leading marker block to today's first-match ID, and `single_pass_open_followup_ids` in `scripts/review_single_issue_security_pass.sh` compares against the leading marker block instead of line 1. A marker further down the body never counts. Legacy one-marker bodies give identical results.
  - **Known limit.** `unblock_actions.py` / `unblock_judge.sh` read only the first marker, so an unblock re-issue of a consolidated follow-up carries one ID; the gate then holds with `followups_missing` (fails closed) and the `state=all` dedupe still prevents refiling.
