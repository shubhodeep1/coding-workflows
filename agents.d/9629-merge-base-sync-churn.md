- **Merge-base sync churn (2026-11-17).** Approved PRs were updated from `main` up to five times without merging: the overlap was almost always `.github/workflows/ci.yml` (18 of 19 sampled updates), and each update head waited for a fresh single-issue security audit, then a review run, then its full final CI run, while `main` moved again. Three changes:
  - **No per-file `ci.yml` wiring for Python tests.** `tests/test_ci_wires_every_test_file.py` counts a `tests/test_*.py` file as wired while `tests-system-python` collects all of `tests/` (`python3 -m pytest --collect-only -q -p no:cacheprovider tests`, with `pyproject.toml` collecting `test_*.py` and no `collect_ignore` in `tests/conftest.py`); `test_the_catch_all_collects_every_python_test_file` fails when that stops holding. `tests/test_*.sh` files must still be named in a workflow. `UNWIRED_ALLOWLIST` is empty.
  - **Security-pass inheritance.** `scripts/review_single_issue_security_pass.sh` (`gate` and `status`) treats a head with no security-pass marker as clean when it is a verified freshness update of a head with a trusted `status=clean` marker. Verification is `review_head_gate_freshness_sync` from `scripts/review_head_gate.sh`, sourced in a subshell from `SUPPORT_SCRIPTS_DIR` (never the PR head), which now also sets `REVIEW_HEAD_GATE_FRESHNESS_SYNC_FROM` to the verified approved head. Chains of updates are walked back at most `SINGLE_PASS_INHERIT_MAX_HOPS` (10) hops, two API reads each; a hop that fails verification, or reaches a head whose latest marker is pending, findings or failed, audits the head as before. A head that already has its own marker is decided by that marker. Log: `SINGLE_ISSUE_SECURITY_PASS mode=gate ... outcome=clean reason=freshness_sync_inherited from=<sha> hops=<n>`. No marker comment is posted for an inherited result.
  - **Final CI at the update.** After a verified update `_pr_base_fresh_for_merge` calls `_pr_base_sync_dispatch_final_ci <pr> <approved head> <update head>` (`scripts/pr_checks_lib.sh`), which dispatches the update head's final CI run at once through `_pr_ensure_final_ci`, so the next review run finds it in flight. It needs `REVIEW_FINAL_CI_WORKFLOW`, a same-repository head branch, and `mergeable: true` for the update head (the observe read, then up to `MERGE_BASE_SYNC_MERGE_REF_POLL_ATTEMPTS` more PR reads, default 3, 0-10); otherwise it skips and the required-checks wait dispatches later, as before. `MERGE_BASE_SYNC_FINAL_CI_ENABLED` (default `true`) turns it off.
  - **Sync-quick final CI.** When every overlap path is a CI-wiring file (`scripts/ci_sync_quick.sh classify`: `.github/workflows/ci.yml` and the tests that pin it) and the approved head has a successful full final run (`ci_sync_quick.sh full-ci-green`: a `workflow_dispatch` ci.yml run named exactly `CI [pr:<n>]`), the dispatch passes `sync_quick=true`. `MERGE_BASE_SYNC_QUICK_CI_ENABLED` (default `true`) turns it off. In that run ci.yml skips the seven gated test jobs and `tests-sync-quick` runs `ci_sync_quick.sh verify` on `refs/pull/<n>/merge` (depth 3), then `ci_sync_quick.sh run-tests` (the PR's changed `tests/test_*.py` / `.sh` files plus the CI-structure tests). The run is named `CI [pr:<n>] [sync-quick]`, so it never counts as a full run for a later update. `lint` accepts the gated jobs' `skipped` only when `tests-sync-quick` succeeded; in every other run it accepts `tests-sync-quick`'s `skipped`. A refused `sync_quick` dispatch (a branch whose ci.yml predates the input) retries once with the full suite.
  - Failure modes: a wrong `sync_quick=true` fails `tests-sync-quick` and with it `lint` (the PR goes back to review through `final-ci-failed`); a PR test that needs deeper history than depth 3 fails the same way, and a re-run of the final CI without `sync_quick` covers it.
