- Check-failure triage has a `transient-rerun` stage (#9387). The `check_failure_triage.yml` step `transient_rerun` ("Re-run transient check failure") runs after collect when `ready == 'true'` and not in historical mode, with `GH_TOKEN: ${{ secrets.GH_PAT }}` and `continue-on-error: true`; it never sees `CHECK_TRIAGE_ISSUES_TOKEN`. `scripts/check_failure_triage.sh` reads the run id only from a details URL under `<server>/<repo>/actions/runs/<id>`, checks the run (same id, head SHA and repository, `completed` / `failure`, `run_attempt == 1`), and imports `classify_runner_shutdown` and `rerun_failed_jobs` from the trusted-dir copy of `scripts/ci_cancelled_rerun.py` (staged as an optional support file). Only the `shutdown`, `action_resolution`, `checkout_fetch` and `abandoned` verdicts get one `rerun-failed-jobs` POST. It logs `CHECK_TRIAGE op=transient_rerun outcome=<requested|skip|fail_open> reason=<...> run=<id> verdict=<...>` and always exits 0; the triage issue is still posted. Switch: `CHECK_TRIAGE_TRANSIENT_RERUN_ENABLED` (default `true`; `false` turns it off, any other value turns it off with a warning). The CI_ACTION_RESOLUTION / CI_CHECKOUT_FETCH / CI_ABANDONED_JOB re-run switches are forwarded to the step.
- `scripts/check_triage_resolution.py` `_verify_open_head` resolves an open PR whose head still equals the trusted header's Head SHA through `path=open_head_rerun` (#9387): workflow-run triage needs the newest `pull_request` run on that head to be the triaged run itself (same run id), `completed` / `success` with `run_attempt > 1`, and its latest jobs all completed with none failed (`success` / `skipped` / `neutral`, at least one `success`); a passing re-run of another run on that head never counts; check-run triage needs every latest check run of the name on that head to be `success`. Any miss on that head keeps the reason `open_head_unchanged`. No new trigger re-runs the gate when the re-run finishes: the issue closes the next time an existing gate caller (clarify, plan or the unblock judge) runs. The evidence comment says the PR is still open on the same head and a re-run passed; the resolved marker format is unchanged.
- The plan auto-approval gate grants an extensionless plan path only when `os.lstat` in the planning checkout (the guard's current directory) shows a regular file (`_plan_grant_checkout_state`, #9387); a directory, a symlink or a path under a symlinked parent directory never. A listed extensionless file missing from the checkout, nested under an existing top-level directory (`_plan_grant_missing_path`, `extract_plan_missing_file_paths`) or a root-level name that leads a top-level (column 0) Files bullet, backticked or bare (a bare token only in upper case, never `NONE` / `TBD` / `TODO`; a `None` entry never counts), alone or followed by a dash, colon or parenthesis, while the guard runs in a git checkout (`_plan_grant_missing_root_path`; prose naming a root token or an indented sub-bullet never counts), holds the plan with `path_not_granted`, the missing paths denied and `replannable: true` (not replannable on the heal route, on both the pipeline-plan-grant proposal and the ordinary approval path), and no grant body is written.
