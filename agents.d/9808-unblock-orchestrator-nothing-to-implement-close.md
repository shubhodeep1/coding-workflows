- **Unblock judge closes orchestrator sub-issues that planning found nothing to implement for (#9808).** `unblock_nothing_to_implement_close` in `scripts/unblock_judge.sh` used to resume any item with a tracking issue, so an orchestrator sub-issue whose work was already on the integration branch looped: planning stopped again with `work is already on the planning ref; nothing to implement` (#9769, tracking #9421). It now hands items with a tracking issue to `unblock_nothing_to_implement_orchestrator_close`. That function closes the issue only when every check passes: `ITEM_KIND=issue`, stop `blocked`, a digits-only tracking issue, the `ai:orchestrator-managed` label, and `unblock_nothing_to_implement_blocked` (the newest trusted "Planning blocked" comment gives that reason, and no trusted implementation plan came after it). It then posts one comment that names the project, adds `ai:closed` and closes the issue as completed. These writes go through the shared `unblock_nothing_to_implement_write` helper, so the marker `<!-- ai:unblock-nothing-to-implement:v1 item=<n> fixup=<f|none> -->` is posted only once. It runs in two places. One is after a done fix-up, where the wait is marked `done`. The other is on `unblock_main`'s main path right after the #9659 triage check, with no fix-up wait: marker `fixup=none`, no round and no model call. On its next tick the orchestrator poller sees the sub-issue closed with `ai:closed` and treats it as an adjudicated close without a merge. A failed write keeps the wait open, so the next scan retries. `UNBLOCK_ORCHESTRATOR_NOTHING_TO_IMPLEMENT_CLOSE_ENABLED` is read from the script environment only (`.github/workflows/unblock_judge.yml` does not forward it). Unset, empty or `true` in any case keeps the close on, and `false` restores the resume. Any other value also restores the resume, with a `::warning::` and an `outcome=skip reason=invalid_flag` log line. The standalone path, and its `UNBLOCK_NOTHING_TO_IMPLEMENT_CLOSE_ENABLED` switch, are unchanged. Cost: at most three writes (comment, label, close) plus the wait update, and no reads.

- `UNBLOCK_JUDGE` also logs `item= kind= stop= fixup= tracking= op=nothing_to_implement_orchestrator outcome=closed|skip reason=comment_failed|label_failed|close_failed|invalid_flag` (`scripts/unblock_judge.sh`, #9808). `outcome=closed` means an orchestrator sub-issue that planning found nothing to implement for was closed as completed with `ai:closed`; `fixup=none` means the close happened on the main path without a fix-up. A `*_failed` reason means a write failed and the item stays open for the next scan. `invalid_flag` means `UNBLOCK_ORCHESTRATOR_NOTHING_TO_IMPLEMENT_CLOSE_ENABLED` held a value other than `true` or `false`, so the item resumed; that line carries no `fixup=` or `tracking=`.
