- **Check-triage completion on a merge into the failing PR's branch (`check_triage_pr_branch`).** An `ai:check-triage` issue's fix PR merges into the head branch of the PR named by its `<!-- check-failure-triage:pr=<N> -->` marker. `issue_pr_status.yml` ("Update linked issue labels when PR closes") and `close_merged_issues_sweep` (`_pr_json_base_is_target_merge` sixth argument) count that merge as completion with `target_merge_reason` / `_TARGET_MERGE_REASON` `check_triage_pr_branch`, only after the existing `default_branch` / `declared_integration_branch` / `managed_no_child_metadata` rules rejected it. Trust rules (shared parser `check_triage_target_branch`, CLI `orchestrate_lib.py check-triage-target-pr`): the issue carries `ai:check-triage`, its author equals the pipeline login (case-insensitive; `resolve_unmerged_close_login` in the workflow, `unblock_trusted_login` in the poller), the body has exactly one marker (`CHECK_TRIAGE_PR_MARKER_RE`, identical to `check_triage_resolution.PR_MARKER_RE`), and PR `<N>`'s head is in the same repository with `head.ref` (from the API, never issue text) equal to the merged PR's base. The workflow also requires the merged PR to be same-repository and bound to the issue (`ai/issue-<n>` head) and `<N>` to differ from the merged PR. API budget: one `pulls/<N>` read per candidate issue, only after the existing rules rejected the merge; every failure leaves the issue unchanged. The sweep adds one `gh issue list --label ai:check-triage` per tick (`origin=check_triage`, after `merged_label` and `ready_label` in precedence): no merged PR is a silent pending skip, and an accepted merge applies `ai:merged` through `set_issue_phase_label` before closing. Standalone stall recovery keeps the five-argument call. Issue #8955.
