- **Protected-path handoff after a merged fix-up (#7287).** With `UNBLOCK_PROTECTED_HANDOFF_ENABLED=true`, the merged-fix-up arm of `scripts/unblock_judge.sh` checks the `protected-rejection` result before running `unblock_actions.py followup`. When that result is `ok`, it first runs `unblock_try_regrant`; a grant the current guard accepts resumes the item and marks the wait done (`outcome=followup_regrant`); a failed regrant actuation (`UNBLOCK_REGRANT_RESULT=failed`) leaves the wait open (`outcome=skip reason=followup_regrant_failed`). Otherwise, on a `scope-blocked` issue whose newest trusted guard comment is an automation-path rejection: a pending hold marker marks the fix-up wait done and skips (`outcome=skip reason=operator_handoff_pending fixup=<N>`); otherwise, when the output's `prior_handoff_verdict` (the newest pipeline-authored `scope-blocked` verdict marker after the rejection, only `descope` / `operator_step`, else null) is set, `unblock_actions.py followup-handoff --fixup <N> --verdict <v>` produces the #7060 handoff ops (operator step under its own key `unblock-handoff-<item>`, so the original `unblock-<item>` entry and its placeholder are kept, hold comment, WARNING with `handoff_retry: true`) instead of a resume, and the wait is marked done (`outcome=followup_handoff`). A failed write leaves the wait open for the next run (`reason=followup_handoff_failed`, WARNING "the next judge run retries it"). Flag off, or any other case, keeps the existing follow-up resume.
