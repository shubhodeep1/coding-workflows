<!-- agents: section="Workflow architecture" -->
- **Unblock re-issue own-PR guard (issue #10121, `UNBLOCK_REISSUE_OWN_PR_GUARD_ENABLED`, default on; `false`/`0`/`no`/`off` turns it off, as the registry's on_values, and an invalid value keeps it on).** For an item of kind `issue`, `unblock_resolve_own_prs` in `scripts/unblock_judge.sh` runs just before the model is asked: one `gh api graphql` `pullRequests(headRefName: "ai/issue-<item>", states: OPEN)` read (owner, name and head ref passed as variables). It keeps only nodes with `isCrossRepository == false`, head repository equal to `REPOSITORY`, head ref exactly `ai/issue-<item>` and author equal to the pipeline login (case-insensitive, `[bot]` stripped), and merges `own_prs: {status: ok|unknown, prs: [{number, head_sha, head_ref, mergeable_state, head_gate, ci_final, lease_wait}]}` into `context.json`; the judge context gets it as `own_pull_requests`. `head_gate` counts only a pipeline-created `ai-review/head-gate` on the current head oid; `ci_final` accepts `github-actions` or the pipeline login. A failed or malformed read is `unknown`, never "none"; so is a `totalCount` above the 10 listed nodes (`OWN_PR_MAX` in `scripts/unblock_actions.py` is the same 10).
  - `scripts/unblock_actions.py` validates `own_prs` again (`_own_prs`; a malformed value is `unknown`, a missing key `disabled`). `own_pr_refusal` refuses a `reissue` with `own_pr_unknown`, `own_pr_green` (head-gate success) or `own_pr_lease_wait` (`ai:merge-lease-wait`); `plan` then returns one comment and nothing else. The CLI `own-pr-refusal --context-file` prints `{refuse, reason, pr, body}`.
  - For a `reissue` verdict `unblock_main` runs `unblock_resolve_own_prs` again after the model (the model call can take minutes; a failed merge skips with `own_pr_refresh_failed`), so the refusal and the retire ops use fresh facts. It then calls `own-pr-refusal` before the round marker is written: a refusal with a pull request number (and waits on) becomes a `wait` verdict with `hold_kind: item_closed`, `hold_ref: <pr>` (the existing hold path, no round); otherwise only the refusal comment is posted and no marker is written, so the next run judges again; that run does not post the same refusal text while it is still the newest pipeline-login comment on the item (`outcome=refusal_already_posted`).
  - A `reissue` that goes ahead and closes the source issue also plans, for each listed own pull request, a `comment` with `created_ref: true` (`unblock_run_ops` replaces `{created}` with the number this run's `create_issue` returned and fails the op when there is none) and a `close` with `pr: true`; on the tracking-issue path the comment text is static and names the request id. Kind `pr` re-issues are unchanged.

<!-- agents: section="Isolated Codex agents" -->
- **Merge-lease source-issue guard (issue #10121, `MERGE_LEASE_SOURCE_ISSUE_GUARD_ENABLED`, default on; `false`/`0`/`no`/`off` turns it off).** `_merge_lease_source_issue_orphans <rows>` in `scripts/pr_checks_lib.sh` takes a tick's base rows (the `_mt_list_open_prs` projection), picks non-draft labelled waiters whose same-repository head is `ai/issue-<n>`, and makes one GraphQL query per 50 distinct issue numbers (aliases `i<n>: issue(number: <n>) { state stateReason }`). It sets `MERGE_LEASE_SOURCE_ISSUE_ORPHANS` (PR numbers whose issue is `CLOSED` / `NOT_PLANNED`) and `MERGE_LEASE_SOURCE_ISSUE_READ=none|ok|failed`; a failed read is fail-open. `_mt_merge_lease_tick` and `_mt_merge_lease_tick_multi` call it once per base before the grant loop (only when the staged library has it), add each orphan to the excluded list, and leave its wait label in place. Holders are not revoked by this check and the update-mode gate does not use it.
