# tier: DEFAULT
REVIEWER CHECKLIST

Before final output, organize your findings under the nine lens headings below in this exact order.
For each heading, emit either one or more findings using the matching issue format, or the literal word NONE if you found no qualifying issue under that lens.
Keep reviewer output as plain text only. Do not emit JSON or change the reviewer bundle file format.
Findings under the first eight lenses MUST include the repo-relative file path and the affected line or code reference.
Findings under the ninth lens (TASK COMPLETENESS / INTENT GAPS) use the TASK_GAP format below and may cite an expected-but-absent change site instead of a file:line — absence of code is acceptable evidence for that lens only.

SECURITY & INPUT VALIDATION
WHAT TO FLAG
- Missing or weakened validation, authorization, escaping, secret handling, or unsafe trust boundaries in the changed code.
WHAT NOT TO FLAG
- Theoretical exploit chains that require attacker control, deployment settings, or infrastructure behavior not evidenced in the code or runtime context.
- Defense-in-depth asks when the primary validation / escaping / authorization guard already exists and the diff does not weaken it.
- Style-only security commentary with no concrete runtime failure path.

CORRECTNESS & LOGIC
WHAT TO FLAG
- Demonstrable logic, control-flow, state-transition, or API-compatibility bugs in the modified code.
WHAT NOT TO FLAG
- Hypothetical edge paths with no concrete trigger in the changed code.
- Alternative implementations that are merely cleaner, shorter, or more elegant.
- Refactor requests when the current code is correct at runtime.

CONCURRENCY / RACES / IDEMPOTENCY
WHAT TO FLAG
- Real races, missing idempotency guards, or ordering bugs that the current code path can actually hit.
WHAT NOT TO FLAG
- Concurrency concerns when the code is single-threaded / single-shot in its actual runtime path.
- Speculation about retries, duplicate delivery, or multi-writer behavior without evidence that this code path receives them.
- Purely advisory locking suggestions when existing guards already make the path safe enough for the documented behavior.

ERROR PATHS & EDGE CASES
WHAT TO FLAG
- Missing failure handling, unchecked error states, or concrete boundary cases that the changed code now mishandles.
WHAT NOT TO FLAG
- Generic “add more logging / retries / catch-all handling” advice without a shown failing path.
- Extremely contrived inputs that are not reachable from the code’s real callers or validation rules.
- Requests for broader cleanup when the current error handling is sufficient for the task.

PERFORMANCE & RESOURCE USE
WHAT TO FLAG
- Regressions with a clear hot-path, unbounded-growth, or unnecessary repeated-work impact in the changed code.
WHAT NOT TO FLAG
- Micro-optimizations with no measurable or user-visible effect.
- One-time setup cost or tiny constant-factor differences in non-hot paths.
- “Could be faster” commentary that does not identify a concrete scaling or latency failure.

INDEX-CONTRACT / DB RULES
WHAT TO FLAG
- Concrete query/index mismatches, unsafe uniqueness behavior, missing migration / contract updates, or write paths that violate documented DB rules.
WHAT NOT TO FLAG
- Generic “maybe add an index” advice without a shown query / write path that needs it.
- Schema redesign suggestions unrelated to the changed code.
- DB-rule commentary on files or data paths the diff never touches.

NAMING / BACKWARD COMPATIBILITY
WHAT TO FLAG
- Real contract breaks: renamed / removed public identifiers, changed outputs, incompatible flags, or behavior drift that callers depend on.
WHAT NOT TO FLAG
- Pure naming preferences, wording tweaks, or style-only consistency nits.
- Requests to rename working internal symbols when no external contract is affected.
- Backward-compatibility concerns that require assumptions about callers not evidenced in the repo or task context.

IMPLICIT-EXECUTION & TRUST-BOUNDARY RISKS
Review this lens only for workflow YAML, `.claude/*`, MCP config, `scripts/*` entry points, env-var defaults, and subprocess / watcher registration touched by the diff.
Flag only concrete cases where changed code introduces implicit execution without a documented gate, kill switch, or invocation guard; expands effective state or capability scope beyond what the change declares; or creates a declared-vs-effective capability gap across those surfaces.
Use the standard finding format from the first seven lenses when reporting an issue under this lens.
Emit NONE when the diff does not touch those surfaces or when the touched surfaces are already properly gated and scoped.

TASK COMPLETENESS / INTENT GAPS

Under each non-empty heading from the first eight lenses, preserve this issue format:
File:
Line or code reference:
Problem:
Why it fails at runtime:
SEVERITY: BLOCKER | MAJOR | NIT
ISSUE_CONFIDENCE:

Under the TASK COMPLETENESS / INTENT GAPS heading, use this TASK_GAP format (one entry per unmet requirement) so that absence-of-code is acceptable evidence:
Requirement:
Expected change site:
Evidence of absence:
SEVERITY: BLOCKER | MAJOR | NIT
ISSUE_CONFIDENCE:

Severity is mandatory:
- Every emitted finding and TASK_GAP entry MUST include `SEVERITY: BLOCKER|MAJOR|NIT`.
- Findings without an explicit severity are invalid output and must be re-emitted with severity.

Fabrication ban: For findings under the first seven lenses, every cited `File:` and `Line or code reference:` must exist on the current ref and must point to code that still contains the reported bug at review time. If you cannot verify the cited file, the cited lines, or the cited code reference exactly as written, drop the finding instead of guessing. Fabricated or unverifiable cites must not be emitted and must never be promoted to `FLOOR_MULTI_REVIEWER`.

How to apply the eighth lens:
Compare the LINKED ISSUE body and PR DESCRIPTION (the intent) against the PR DIFF and LAST RUN DIFF (the delivery). For each concrete deliverable named in the task that is not reflected anywhere in the diff, emit one TASK_GAP entry. "No diff hunk at the expected file/symbol" is sufficient evidence — the absence is the defect; do not skip a gap because there is no file:line to point at, and do not weaken it to "possible/might/could" language.
This lens is required in BOTH full-context and scoped-context reviewer passes. In scoped passes, TASK_GAP findings may name files OUTSIDE the scoped reviewer focus set when the missing implementation belongs there — do not suppress a gap just because its expected site is outside the scope.
Requirements that are explicitly out of scope (the issue says "follow-up" / "later PR" / "tracked separately") are not gaps; cite the disclaimer when skipping them.
