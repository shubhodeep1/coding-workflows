Role: validate-discover. Goal: infer runtime validation hints for this repository and output a single `.ai/validate.yml` document.

Goal:
- Produce practical, minimal hints that improve harness generation accuracy.
- Keep output deterministic and safe for local CI execution.

Hard constraints:
- Output YAML only (no markdown, no fences, no prose).
- Do not edit files.
- Do not use real credentials.
- Prefer concrete values found in the repo over guesses.
- If uncertain, omit optional keys instead of inventing values.
- Fallback on empty discovery: if the primary detection (build manifest,
  Dockerfile, package.json, pyproject.toml) returns empty, try at least
  one fallback (Makefile rules, README's "Getting Started", existing
  test-runner config) before omitting a required slot.

Expected YAML shape (top-level `type` and `slots` are REQUIRED; everything else is optional):
- `type` (REQUIRED): one of the renderer-supported template families — `python-mongo-flask` | `python-mongo-repo-checks` | `python-repo-checks` | `node-hardhat-solidity`. Pick the closest match for the repo; do not invent other values (the renderer rejects unknown families with `FamilyResolutionError`).
- `slots` (REQUIRED, mapping):
  - `project_name` (REQUIRED, non-empty string): short identifier used by rendered compose/test files (e.g. the repo or service slug).
  - `canary_tools` (REQUIRED, non-empty list of strings): tools the canary test must verify are runnable inside the harness container (e.g. `["python", "pip"]` for Python repos, `["node", "npx"]` for Node repos).
  - `tap_plan` (optional, positive integer): expected TAP test count when known.
- `entry`: entrypoint path or command target
- `port`: app port number (for network services)
- `health_check`: health route/path when available
- `services`: list of required local services (e.g. `postgres:16`, `redis:7`, `mongo:7`)
- `env_overrides`: safe test-only env values needed for startup
- `custom_tests`: optional existing test commands worth reusing
- `skip_tests`: optional list of clearly non-applicable categories

Guidance:
- Keep values compatible with `validation/docker-compose.test.yml` and local Docker networking.
- Include only env vars necessary to start and smoke-test the app.
- Favor stable defaults for unknown versions (`postgres`, `redis`, `mongo`) when service detection is clear.
- For `env_overrides`, prioritise fail-fast env vars — those read during module import or service `__init__` in a way that raises when absent/empty (patterns such as `raise RuntimeError("<VAR> is not configured")`, bracket access `os.environ["<VAR>"]`, `Fernet(...)` / crypto constructors fed from env, settings modules that dereference env at import). Missing any of these is the most common cause of validation `harness_error`. Record format hints in YAML comments adjacent to `env_overrides` keys (or as explicit placeholder values when comments are impractical), e.g. `TFA_ENCRYPTION_KEY: ""  # format: Fernet urlsafe-b64 32 bytes`, so the generate phase can emit format-valid synthetic values rather than arbitrary strings.
