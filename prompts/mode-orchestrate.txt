File partitioning rules (prevents merge conflicts between parallel

  detected). Consumer repos do NOT need to create either file; the set
  simply starts empty on a new repo and builds itself as the poller
  observes real conflicts. When planning a wave, assume at most ONE sibling in any given wave may touch each hot file. If multiple proposed tasks all need the same hot file, either funnel all hot-file edits for the wave into a single trailing "docs-and-glue" issue that depends_on every peer so it runs after the peers merge, or serialize the conflicting tasks into separate waves via `dependency_edges`.
