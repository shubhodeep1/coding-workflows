Docker Compose variable interpolation rules (CRITICAL):
- Docker Compose interpolates `$VAR` and `${VAR}` in string values at config-render time, BEFORE the container shell ever runs.
- Any `$` that is meant for the in-container shell (POSIX shell variables, command substitution, parameter expansion) MUST be escaped as `$$` in the compose file. Compose collapses `$$` to a literal `$` after rendering, and the container shell then evaluates it normally.
- This rule applies to EVERY Compose string field — including `healthcheck.test`, `command`, `entrypoint`, `environment` values, `labels`, etc. The healthcheck case is the most common foot-gun because the command often uses temp shell variables.
- CORRECT (in-container shell variable, doubled `$`):
    healthcheck:
      test:
        - "CMD-SHELL"
        - "RESP=$$(curl -sf http://localhost:8545 || true); [ -n \"$$RESP\" ] || exit 1"
- WRONG (Compose eats `$RESP` and `$(...)` at render time, leaving the container shell with empty strings):
    healthcheck:
      test:
        - "CMD-SHELL"
        - "RESP=$(curl -sf http://localhost:8545 || true); [ -n \"$RESP\" ] || exit 1"
- Preferred alternative: avoid in-shell temp variables entirely in healthchecks. Use a single self-contained command, e.g. `curl -sf --max-time 2 http://localhost:8545 >/dev/null` or a one-shot `curl ... | jq -e '...'` pipeline. This eliminates the `$$` escaping requirement.
- After generating the compose file, mentally render every string field and confirm that no unescaped `$` references a shell variable that should be evaluated in the container.
- The same rule applies to any Compose `${VAR}` you want passed through literally (e.g. `$${VAR}`), but prefer rewriting to avoid this whenever possible.

        "phase": os.environ["PHASE"],
        "total_tests": int(os.environ["TOTAL_TESTS"]),
        "passed_tests": int(os.environ["PASSED_TESTS"]),

      local test_name="$1" error_msg="$2" log_file="${3:-/dev/null}"
      append_failure "$test_name" "$error_msg" "$log_file"
      FAILED_TESTS=$((FAILED_TESTS + 1))
      RESULT="fail"
      emit_result
      exit 1
    }
    # Belt-and-braces: also emit on any unexpected EXIT before normal path runs.
    on_exit() {
      local rc=$?
      teardown
      if [ "$RESULT_EMITTED" != "1" ]; then
        RESULT="fail"
        emit_result
      fi
      exit $rc
    }

CRITICAL — robust service-state detection in canary:
- NEVER parse human-readable `docker compose ps` text output (columns, status words) to determine whether a service container is running. Output formatting varies across Docker Compose versions and produces false negatives when the service is actually healthy.
- ALWAYS resolve the container ID first with `docker compose ps -q <service>` and then use `docker inspect` for machine-readable state fields.
- Recommended pattern for the canary "service is running" check (this should be the FIRST TAP assertion, i.e. `ok 1` / `not ok 1`; subsequent checks increment sequentially):
    SERVICE="${SERVICE_NAME:-app}"
    # The canary script uses set -e / set -euo pipefail. Use || true so that a
    # transient docker compose ps failure is caught by the empty-CID guard below,
    # which emits a proper TAP "not ok" message instead of aborting the script
    # before any TAP output is written.
    CID=$(docker compose ps -q "$SERVICE" 2>/dev/null | head -n1 || true)
    if [ -z "$CID" ]; then
      echo "not ok 1 - $SERVICE service is not running (no container id returned by docker compose ps -q)"
      exit 1
    fi
    RUNNING=$(docker inspect -f '{{.State.Running}}' "$CID" 2>/dev/null || echo "false")
    STATUS=$(docker inspect -f '{{.State.Status}}' "$CID" 2>/dev/null || echo "unknown")
    if [ "$RUNNING" = "true" ] || [ "$STATUS" = "running" ]; then
      echo "ok 1 - $SERVICE service is running"
    else
      echo "not ok 1 - $SERVICE service is not running (Status=$STATUS Running=$RUNNING)"
      exit 1
    fi
- The "service is running" check must always be TAP assertion #1. All subsequent checks (endpoint reachability, tool presence, etc.) use sequentially increasing numbers (ok 2, ok 3, …).
- Endpoint reachability (`curl`) and in-container tool checks are corroborating signals that should be emitted as separate TAP assertions (for example `ok 2 - app port is reachable`, `ok 3 - required tools present`). CRITICAL — shell-mode parity between canary tool checks and test invocations:
- A canary assertion that proves a CLI tool is present in the container (for example `command -v forge`) MUST be run under the **same shell invocation mode** as the subsequent test command that relies on that tool (for example `npm run test:forge`, `npx hardhat test`, `forge test`, `pytest`). Mismatched modes produce the false-positive failure pattern where canary reports `ok` but the test reports `command not found`.
- Concretely: `docker compose exec -T <svc> /bin/sh -lc '...'` (login shell) is NOT equivalent to `docker compose exec -T <svc> /bin/sh -c '...'` (non-login). Tools installed under `/root/.foundry/bin`, `/root/.local/bin`, `/home/*/bin`, etc. therefore disappear from PATH inside login shells even though the Dockerfile appears to add them.

Never mix `-c` for canary with `-lc` for tests or vice versa.

CRITICAL — grep-safe TAP counting under `set -e` / `pipefail`:
- `grep` exits with code 1 when zero lines match. Under `set -e` or `pipefail`, this kills the script even when zero matches is the expected (all-pass) outcome.
- When counting TAP `ok` / `not ok` lines, always use patterns that return exit code 0 on zero matches. Preferred approaches:

CRITICAL — Ethereum / Hardhat JSON-RPC health checks:
- Hardhat JSON-RPC (and any standard Ethereum node) returns a **JSON object**, not a JSON array.
- Response shape: `{"jsonrpc":"2.0","id":1,"result":"0x1"}`.
- NEVER index the response with a number (`jq '.[0]'`, `jq '.[1]'`, etc.) — that causes:
    `jq: error (at <stdin>:1): Cannot index object with number`
- ALWAYS read `.result` and validate it is a non-null string before asserting.
- ALWAYS guard against non-JSON or empty responses before piping into `jq`.
- Recommended startup probe pattern (use inside a retry loop):
    RPC_URL="${RPC_URL:-http://localhost:8545}"
    PAYLOAD='{"jsonrpc":"2.0","method":"eth_chainId","params":[],"id":1}'
    CHAIN_ID=""
    RESP=""
    for attempt in $(seq 1 30); do
      RESP="$(curl -sf --max-time 2 -H 'Content-Type: application/json' \
               -d "$PAYLOAD" "$RPC_URL" 2>/dev/null || true)"
      if [ -z "$RESP" ]; then
        echo "attempt $attempt: no response, retrying..."
        sleep 1
        continue
      fi
      if ! printf '%s' "$RESP" | jq -e 'type == "object"' >/dev/null 2>&1; then
        echo "attempt $attempt: non-JSON or not a JSON object: $RESP"
        sleep 1
        continue
      fi
      CHAIN_ID="$(printf '%s' "$RESP" | jq -r 'if has("result") and (.result != null) and (.result | type == "string") and (.result | length) > 0 then .result else empty end')"
      if [ -z "$CHAIN_ID" ]; then
        echo "attempt $attempt: missing/invalid .result; raw response: $RESP"
        sleep 1
        continue
      fi
      echo "RPC healthy: chainId=$CHAIN_ID"
      break
    done
    if [ -z "${CHAIN_ID:-}" ]; then
      echo "RPC did not become healthy within timeout; last response: ${RESP:-<none>}"
      exit 1
    fi

CRITICAL — graceful shutdown container resolution:
- After `docker compose stop <service>`, the container moves to `exited` state.
- `docker compose ps -q <service>` only returns RUNNING containers and will return empty after stop.
- To resolve a stopped container's ID, use: `docker compose ps -q --status exited <service>` or `docker compose ps -aq --filter "status=exited" <service>`.
- To check the exit code, use: `docker inspect --format='{{.State.ExitCode}}' <container_id>`.
- A harness-initiated `docker compose stop` sends SIGTERM to PID 1. Any of the following outcomes is a graceful shutdown and MUST be treated as pass:
    1. Exit code 0 — PID 1 handled SIGTERM and returned cleanly.
    2. Exit code 143 (= 128 + SIGTERM) — PID 1 was terminated by SIGTERM without a custom handler; this is the documented signal-exit convention.
    3. Exit code 1 when PID 1 is an `npm` / `yarn` / `pnpm` wrapper AND the compose log contains a wrapper SIGTERM marker (for example `npm ERR! signal SIGTERM` or `Command failed with signal "SIGTERM"`) for the wrapped command. npm translates signal-termination of its child into exit code 1 instead of propagating 143; this is a wrapper artifact, NOT an application crash.
- NEVER hardcode a strict `EXIT_CODE == 0` check when the service is launched via an `npm` / `yarn` / `pnpm` script — you will get false failures on every clean `docker stop` because of (3) above.
- Recommended pattern:
    COMPOSE_FILE="validation/docker-compose.test.yml"
    COMPOSE_LOG="validation/logs/compose.log"
    docker compose -f "$COMPOSE_FILE" stop -t 5 app
    CID=$(docker compose -f "$COMPOSE_FILE" ps -q --status exited app | head -n1 || true)
    if [ -z "$CID" ]; then
      CID=$(docker ps -aq --filter "status=exited" --filter "label=com.docker.compose.service=app" | head -n1 || true)
    fi
    if [ -z "$CID" ]; then
      echo "not ok - app container id unavailable after stop"
      exit 1
    fi
    EXIT_CODE=$(docker inspect --format='{{.State.ExitCode}}' "$CID" 2>/dev/null || echo unknown)
    docker compose -f "$COMPOSE_FILE" logs --no-color app > "$COMPOSE_LOG" 2>&1 || true
    NPM_SIGTERM=0
    if [ "$EXIT_CODE" = "1" ] && [ -f "$COMPOSE_LOG" ] \
       && grep -qiE '((npm|yarn|pnpm).*signal.*SIGTERM|Command failed with signal.*SIGTERM)' "$COMPOSE_LOG"; then
      NPM_SIGTERM=1
    fi
    if [ "$EXIT_CODE" = "0" ] || [ "$EXIT_CODE" = "143" ] || [ "$NPM_SIGTERM" = "1" ]; then
      echo "ok - app shut down gracefully (exit=$EXIT_CODE npm_sigterm=$NPM_SIGTERM)"
    else
      echo "not ok - app exited with code $EXIT_CODE (expected 0, 143, or npm-wrapped SIGTERM)"
      exit 1
    fi

CRITICAL — robust synthetic env-var assertions in env_var_validation tests:
- Docker Compose services declare synthetic test credentials with an override-or-default expression:
    environment:
      VALIDATION_TEST_API_KEY: "${VALIDATION_TEST_API_KEY:-validation-api-key}"
- This means the container sees EITHER the value injected by the CI job environment OR the compose
  default fallback. A test that hardcodes one fixed expected value will produce a false negative
  whenever the other branch is active.
- When asserting env var values inside the container, the test MUST accept BOTH branches:
  1. An explicitly provided CI env override (the outer value of $VALIDATION_TEST_API_KEY if set), OR
  2. The default fallback value defined in the compose file (e.g. `validation-api-key`).
- NEVER hardcode a single expected string — that creates brittle false negatives.
- Recommended pattern for a robust synthetic env-var assertion (POSIX-safe, set -euo pipefail compatible):

    # Single quotes around the printf command are intentional: they prevent the
    # host shell from expanding ${VALIDATION_TEST_API_KEY:-} before passing the
    # argument to /bin/sh -c; expansion happens inside the container's shell.
    actual="$(docker compose -f "$COMPOSE_FILE" exec -T "$APP_SERVICE" \
                /bin/sh -c 'printf "%s" "${VALIDATION_TEST_API_KEY:-}"')"
    # Compute expected: honour the CI override when present, otherwise use the compose default.
    # This mirrors exactly what Compose does with "${VALIDATION_TEST_API_KEY:-validation-api-key}".
    if [ -n "${VALIDATION_TEST_API_KEY:-}" ]; then
      expected="${VALIDATION_TEST_API_KEY}"
    else
      expected="validation-api-key"
    fi
    if [ "$actual" = "$expected" ]; then
      echo "ok $ASSERTION - synthetic validation env vars are configured as expected"
