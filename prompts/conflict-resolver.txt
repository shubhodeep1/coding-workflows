Repository task: Resolve merge conflicts.

The repository currently contains files with Git merge conflict markers.

A Git merge conflict marker block is the standard output `git merge` writes
into a conflicted file: a start line consisting of seven less-than characters
followed by a space and the name HEAD, then the lines from HEAD, then a
separator line consisting of seven equals characters, then the lines from the
other branch, then an end line consisting of seven greater-than characters
followed by a space and the name of the other branch. These start, separator,
and end lines are what you must look for and remove; this prompt deliberately
does not reproduce them literally so a repository-wide scan for conflict
markers does not match this file.

Conflicted files reported by `git diff --name-only --diff-filter=U` ({{CONFLICTED_FILES_COUNT}} total):
{{CONFLICTED_FILES_LIST}}

Your task:
Resolve merge conflicts safely.

Rules:
- You MUST resolve EVERY conflicted file listed above in this single run. Do not stop after fixing only one file or a subset.
- Before declaring success, re-scan every file in the repository to confirm no Git conflict markers (the seven-character lines git inserts at the start, separator, and end of each conflict hunk) remain anywhere. If any remain, keep resolving until none are left.
- Only resolve conflicts.
- Do not introduce new functionality.
- Do not refactor unrelated code.
- Do not modify files that do not contain conflict markers.
- Prefer preserving behavior from both sides when possible.
- If both sides are incompatible, choose the version consistent with surrounding code.
- Remove all conflict markers.
- Ensure the final code compiles logically.
- You may read repository files as needed.
- You may modify repository files directly.
- Do not generate patches.
- Do not generate scripts.
- Do not modify GitHub workflow files except when resolving merge conflicts.
- Do not access the network.

EDIT TOOL DISCIPLINE (prevents announce-without-editing stalls):
- `apply_patch` is the preferred write tool for surgical edits to existing
  source files. ("Do not generate patches" above means do not output a
  textual unified-diff as your final response — invoking the `apply_patch`
  tool to write to disk is exactly what we want.)
- If `apply_patch` does not land on a particular hunk, fall back to your
  best judgment: a different `apply_patch` shape, a shell heredoc /
  `printf '...content...' > path/to/file` (substitute the actual content
  and path) for fully-specified plain-text files, or any other write
  tool available. What matters is that the file actually changes on disk
  this turn.
- Avoid `sed -i`/`perl -i`/`awk` regex substitutions — they exit 0 even
  when the regex misses, leaving the file unchanged. After ANY shell write,
  verify with `git diff --stat -- path/to/file` (substitute the actual
  path); if zero lines changed, switch tools.
- Returning an empty completion or a final assistant message that only
  describes the fix ("I will apply_patch …", "the resolution is
  straightforward") is a FAILURE. The retry loop counts these as
  no-actionable-output and bails after 3 attempts without a commit. You
  MUST invoke a write tool — the file is unchanged until the tool call
  executes.
- Known model bug: `gpt-5.3-codex` reliably narrates an `apply_patch`
  invocation without emitting the tool call on some inputs
  (openai/codex#11151). The fallback paths above exist for that case.

Your edits are diff-checked against the set of files that actually had merge conflicts. Any file you modify that did NOT contain conflict markers will abort the run with no commit. Do not "improve" surrounding code, rewrite unrelated sections, or add helper scripts, env vars, or workflow steps — if a file has no conflict markers, leave it alone.

Before finalizing, verify every file path you reference in your edits (including paths mentioned in shell commands, sourced scripts, or workflow steps) exists in the repository by reading it.
