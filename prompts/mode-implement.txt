Dependency / lockfile discipline: if your patch edits a dependency manifest

`requirements*.txt`, `go.sum`, `Cargo.lock`). Regenerate via the canonical
tool for the ecosystem (`npm install`, `uv lock`, `go mod tidy`,
`cargo update -p <pkg>`). Never split manifest and lockfile across commits.
If the regenerator tool is unavailable in the runner, record the blocker in
your output instead of committing a partial change.

Code-style hints:
- Prefer descriptive function and variable names over abbreviations unless the
  surrounding code has an established convention you must preserve. Avoid 1-2
  character names except in tight scopes (loop indices, lambda params,
  single-statement comprehensions).
- Avoid inline comments unless the task explicitly asks for them or the
  non-obvious "why" would otherwise be lost.
- Always read each file completely before the first `apply_patch` on that
  file; the exploration log from the discovery pass is the authoritative
  checklist.
- Run independent operations in parallel; serialise only when there is an
  explicit dependency between the results.
- Never make surprise edits affecting more than three files outside the
  plan's `files_touched` set without flagging the scope expansion in the
  post-implementation summary.
- Preferred flow: discovery pass -> brief todo/plan (and note divergence if
  present) -> short status update -> batch tool calls for edits -> reconcile
  touched files against the approved scope -> final summary. Do not start
  editing before the discovery pass completes.
- During the discovery pass, record the exploration log and ensure every file
  to be edited appears in it before the first `apply_patch`.

Data-file output discipline: when writing files under `db/contracts/` or any
other YAML/JSON path, emit raw YAML or raw JSON only. Never wrap the file
body in markdown code fences (` ``` ` or ` ```yaml ` / ` ```json `), and
never include language tags, fence markers, or surrounding prose in the
file. The file's first byte must be valid YAML/JSON, and its last byte
must be valid YAML/JSON — anything else is a syntax error that breaks the
post-Codex validation step.

YAML reserved-indicator quoting: when writing or editing `*.yml` / `*.yaml`
files, any scalar (list item or mapping value) whose first non-whitespace
character is one of `` ` ``, `@`, `*`, `&`, `|`, `>`, `!`, `%`, `#`, `?`,
`,`, `[`, `]`, `{`, or `}` MUST be wrapped in double quotes. Plain (unquoted)
scalars starting with these characters are reserved indicators in YAML 1.2
and cause `yaml.scanner.ScannerError: ... found character 'X' that cannot
start any token` at parse time. This is enforced by
`scripts/validate_changed_files_syntax.sh` and a single failure burns a
post-Codex repair attempt. Common cases: prose-heavy invariants in
`db/contracts/*.yml` mentioning backticked technical terms, list items
beginning with `@username` mentions, or a `*` glob pattern.

## Commit discipline

- One logical change = one commit. Treat the approved task as one atomic,
  task-scoped commit: every edited file in the final change set must be
  required by the approved plan, and every required edit should land together.
- Use commit message format: `<verb>: <change> (plan task <N.M>)` when
  `PLAN.md` or the approved plan names a task ID; omit the parenthetical when
  no task ID is available.
- Bulk style edits or auto-format passes go in a separate trailing commit
  titled `chore: auto-format pass`.
- Failed test fix-ups roll into the commit that introduced the failure; use
  `--amend` only on commits from the current `implement` run that have not yet
  been pushed.
- Do not split the approved task across unrelated commits or bundle
  opportunistic follow-up changes into the same task commit.
- This implement-phase guidance does not change review-autofix's existing
  `[ai-autofix]` commit convention.
