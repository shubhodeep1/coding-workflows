Repository task: Resolve merge conflicts on an orchestrator integration branch.

The repository currently contains files with Git merge conflict markers.
The PR head is an orchestrator-managed integration branch
(`{{INTEGRATION_BRANCH}}`) carrying the work of {{MERGED_SUB_ISSUE_COUNT}}
merged sub-issue(s) belonging to project #{{TRACKING_ISSUE_NUMBER}}.

A Git merge conflict marker block is the standard output `git merge` writes
into a conflicted file: a start line consisting of seven less-than characters
followed by a space and the name HEAD, then the lines from HEAD, then a
separator line consisting of seven equals characters, then the lines from the
other branch, then an end line consisting of seven greater-than characters
followed by a space and the name of the other branch. These start, separator,
and end lines are what you must look for and remove; this prompt deliberately
does not reproduce them literally so a repository-wide scan for conflict
markers does not match this file.

Files in scope for this resolver run ({{CONFLICTED_FILES_COUNT}} total):
{{CONFLICTED_FILES_LIST}}

Most entries in the list above are files `git merge` left with
unresolved conflict markers.  Some entries may instead be files
`git merge` auto-merged cleanly (no markers) but whose current
content already fails a captured sub-issue fingerprint — i.e. the
auto-merge silently reverted a merged sub-issue's intent.  For
those entries there will be nothing to remove; your job is to
edit the file so every `must_contain` pattern in INTENT_FINGERPRINTS
re-matches and every `must_not_contain` pattern stops matching,
typically by restoring the HEAD-side content the auto-merge
discarded.  Both kinds of entry are in-scope for edits; anything
NOT in the list above is out-of-scope and will cause the run to
abort.

=== INTEGRATION PROJECT CONTEXT ===

Tracking issue title:
{{TRACKING_ISSUE_TITLE}}

Tracking issue body (project intent — preserve at all costs):
{{TRACKING_ISSUE_BODY}}

Merged sub-issues already on this integration branch (their work MUST
survive your resolution intact):
{{MERGED_SUB_ISSUES_LIST}}

=== INTENT FINGERPRINTS ===

The orchestrator captured intent fingerprints when each sub-issue's PR
merged into this integration branch. These are the authoritative
acceptance criteria for your resolution. Two lists per sub-issue:

- `must_contain`: regex patterns the post-resolve tree MUST still
  match. They were derived from lines the sub-issue ADDED. If your
  resolution removes any of these, your work has silently reverted
  the sub-issue's intent and will be rejected.

- `must_not_contain`: regex patterns the post-resolve tree MUST NOT
  match. They were derived from lines the sub-issue REMOVED. If your
  resolution reintroduces any of these, your work has resurrected
  code that the sub-issue intentionally deleted and will be rejected.

Fingerprints (JSON, may be empty for sub-issues merged before
fingerprinting was enabled):
{{INTENT_FINGERPRINTS_JSON}}

=== YOUR TASK ===

Resolve the merge conflicts in a way that satisfies ALL of these
constraints simultaneously:

1. Every file in the in-scope list above that currently has Git
   conflict markers must be free of them after your edits.  Files
   in the list that have no markers (fingerprint-violation entries)
   still need edits — see constraints 2 and 3.
2. Every `must_contain` pattern in INTENT_FINGERPRINTS must still
   match somewhere in its file in the post-resolve tree.
3. No `must_not_contain` pattern in INTENT_FINGERPRINTS may match
   anywhere in its file in the post-resolve tree.
4. The post-resolve tree must compile/parse logically.

If the only way to keep both sides of a conflict hunk is to SYNTHESIZE
a new hunk that combines them — i.e. the conflict is between two
independent rewrites of the same code, where neither side standalone
preserves all merged sub-issue intents — then synthesize. Do not
default to "pick side A or pick side B" when synthesis is possible.
The integration-branch ("HEAD") side typically carries the merged
sub-issue's intent; the default-branch (other) side typically carries
unrelated maintenance fixes that you should layer in additively.

=== HARD RULES ===

- You MUST handle EVERY file in the in-scope list above in this single
  run.  Do not stop after fixing only one file or a subset.
- Before declaring success, re-scan every file in the repository to
  confirm no Git conflict markers (the seven-character lines git
  inserts at the start, separator, and end of each conflict hunk)
  remain anywhere. If any remain, keep resolving until none are left.
- Only resolve conflicts and fix the fingerprint violations listed
  via INTENT_FINGERPRINTS.  Do not introduce new functionality.
- Do not refactor unrelated code.
- Do not modify files that are not in the in-scope list above.
- Remove all conflict markers.
- Ensure the final code compiles logically.
- You may read repository files as needed.
- You may modify repository files directly.
- Do not generate patches.
- Do not generate scripts.
- Do not modify GitHub workflow files except when they appear in the
  in-scope list above.
- Do not access the network.

Edit-tool discipline (apply_patch first with fallbacks, verify-after-write,
no `sed -i`/`perl -i`/`awk` for multi-line edits) is defined in
`unattended_system_instructions.md` §4. Apply it; don't restate it.

Note: "Do not generate patches" above means do not output a textual
unified-diff as your final response — invoking the `apply_patch` tool to
write to disk is exactly what we want.

Your edits are diff-checked against the in-scope list above. Any file you modify that is NOT in that list will abort the run with no commit. Do not "improve" surrounding code, rewrite unrelated sections, or add helper scripts, env vars, or workflow steps. If you find yourself wanting to edit a file not in the list, leave it alone — even if you believe it relates to a fingerprint violation. Fingerprint-violating files are expanded into the in-scope list by `scripts/review_conflict_prepare.sh` before this prompt renders; if a path you need is missing, that is a plumbing bug to report, not one to route around.

Before finalizing, verify every file path you reference in your edits (including paths in shell commands, sourced scripts, or workflow steps) exists in the repository by reading it. If you cannot read a referenced file, your resolution is wrong — revert that edit and choose a resolution that does not invent new files, scripts, or invocations. The most common failure mode is hallucinating a plausible helper script (e.g. build_repo_overview.sh) and wiring it into the bootstrap loop; the downstream existence check will catch this and abort the merge-resolve commit.

Sub-issue intent is load-bearing. The orchestrator merges sub-issues in strict dependency order; each was reviewed and merged on its own merits. If you silently revert a sub-issue's intent, downstream sub-issues that build on it will fail in confusing ways one or more waves later. Treat every `must_contain` and `must_not_contain` fingerprint pattern as a hard test case your resolution must pass. When choosing between two valid synthetic resolutions, pick the one that keeps MORE merged sub-issue intent verbatim.

Do NOT pick the default-branch side verbatim. The single most common failure mode is "pick the default-branch (other) side of every hunk and drop the integration (HEAD) side". That wholesale-revert pattern fails fingerprint verification by dropping every `must_contain` line the merged sub-issues added and reintroducing every `must_not_contain` line they deleted. Whenever INTENT_FINGERPRINTS has a non-empty entry for a conflicted file, the correct resolution is almost never "pick the other side" — it is "pick HEAD" or "synthesize a hunk that layers the other side's unrelated maintenance fix on top of HEAD's sub-issue content". Before writing the resolved hunk, look up the file in INTENT_FINGERPRINTS and reconcile against every `must_contain` / `must_not_contain` pattern.

Per-file fingerprint pre-flight: for every conflicted file that has fingerprint entries in INTENT_FINGERPRINTS (even just one), before you finalize that file:
1. Read the post-resolve content of that file.
2. For each `must_contain` regex listed for that file across all
   sub-issues: confirm the pattern still matches the post-resolve
   content. If it does not, your resolution regressed that
   sub-issue's intent — revise the hunk to re-introduce the matching
   content (usually by keeping the HEAD side or synthesizing).
3. For each `must_not_contain` regex listed for that file across
   all sub-issues: confirm the pattern does NOT match the post-
   resolve content. If it does, your resolution resurrected a line
   a sub-issue intentionally deleted — revise the hunk to drop that
   line (usually by keeping the HEAD side or synthesizing).
4. Repeat until every fingerprint for that file is satisfied, THEN
   move on to the next file. Do NOT leave this check "for the end".

Final output must be plain text.

  there wastes the entire run and stalls the integration branch
