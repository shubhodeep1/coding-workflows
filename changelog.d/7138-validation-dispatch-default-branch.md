- **The orchestrator now dispatches runtime validation from the default branch's wrapper.** A stale validation wrapper on an integration branch can no longer fail every validation run, and projects it already parked recover once on their own.

The poller used to dispatch the validation wrapper with `--ref <integration branch>`, so GitHub ran the integration branch's copy of `ai-validate.yml`. That copy keeps whatever `validate.yml` pin the branch had when it was cut, and the poller deliberately does not sync `main` into a branch while it is validating. A stale pin then failed every re-dispatch with `raw_status=harness_error`, as on binance-blessings#249. The poller now sends no `--ref`. GitHub runs the default branch's wrapper, and `validate.yml` still checks out the integration branch it resolves from the `tracking_issue` input.

A project already parked by that failure is re-dispatched once from the default branch: the last failed run used a branch other than the default branch, or, for state written before this fix, the project has a separate integration branch. The validation counters are kept, and the tracking issue gets a "🔁 Validation re-armed after stale workflow pin" comment. The pipeline handles this itself, so the Telegram notice is DEBUG and pages nobody. Set `VALIDATION_STALE_PIN_AUTO_RECOVER_ENABLED=false` to keep such projects parked until `/revalidate`.

What this means for consumer repos: validation runs use the `ai-validate.yml` on your default branch, so keep that wrapper synced. A tracking issue must carry its `Integration branch:` line, which the orchestrator writes when it creates the issue.

### For contributors

The recovery block sits right after the `/revalidate` block in `scripts/orchestrate_poll_process.sh`, so an operator `/revalidate` on the same tick wins. It fires at most once per project: the state flag `validation_stale_pin_recovered_ref` (default-branch SHA) and a `<!-- validation-stale-pin-recovery:<sha> -->` comment by the pipeline login both stop it. Nothing is dispatched until the state flag is written: a failed state write or an unreadable default-branch head skips the recovery for that tick (`reason=state_write_failed` / `default_sha_unavailable`). Each decision logs `VALIDATION_STALE_PIN_RECOVERY tracking_issue=<N> outcome=recovered|skip reason=<r>`. New state fields: `validation_last_dispatch_workflow_ref`, `validation_last_run_head_branch`, `validation_last_run_id`.
