- **The consumer updater's pull request is now checked against the attested release before it can auto-merge.** When `UPDATER_PR_DELIVERY_ENABLED` is `true`, a new `verify` job in `update_workflows.yml` runs after the update job opens or refreshes the pull request. It checks the PR head out as data, downloads and attests the release manifest again, and compares every file the PR changes with what that release produces: wrappers are re-rendered at the release SHA, `.claude/` files and `CLAUDE.md` must match the manifest hashes, deleted files must be retired files with an attested hash, and audit-gate and changelog output must match a re-run of the attested scripts on the PR's parent. Any other file is rejected. The check is the new `scripts/verify_release_manifest.py verify-pr-tree` command.

The job posts the commit status `ai-update-workflows/verify` on the PR head and is now the only place that enables auto-merge. The "Commit and push updates" step records `auto_merge=pending_verify` instead of merging. Auto-merge still needs `UPDATER_VERIFY_RELEASE_MANIFEST` to report `verified=true`. Any error posts a `failure` status, leaves auto-merge off, and logs `UPDATER_PR_VERIFY outcome=rejected reason=<token>`.

What this means for consumers: nothing changes while `UPDATER_PR_DELIVERY_ENABLED` is unset; the updater still pushes straight to the default branch. The `ai-update-workflows.yml` template now grants `pull-requests: write` and `statuses: write` and describes pull-request delivery; it reaches consumers on the next `@stable` sync and passes no new inputs. The verify job runs the release's own copy of the verifier, so it rejects every PR until a stable release ships `verify-pr-tree`. The job id, status context and log prefix are provisional names, because the project plan could not be read when this was built.
