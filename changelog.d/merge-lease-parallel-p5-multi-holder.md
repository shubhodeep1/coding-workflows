- **The merge lease can let several approved PRs update from their base at once (`MERGE_LEASE_MAX_HOLDERS`, default `1`).** Before, one PR per base branch held the merge lease, so approved PRs that changed unrelated files still updated and ran their final CI one after another. Now `MERGE_LEASE_MAX_HOLDERS` (1-5) sets how many PRs may hold the lease for a base at the same time, as long as their changed paths are pairwise disjoint (the `MERGE_LEASE_SOFT_PATHS` probe applies). A PR that shares a path with a holder waits on that holder (`reason=holder_shares_paths`, `MERGE_LEASE_BLOCKER` is that holder); at the cap a newcomer waits `held`. The merge-train tick releases, revokes and grants each holder on its own, and a released primary hands the record to the holder that acquired first. With 2+ holders the lease record gains `holder=` and `holder_path=` lines before `paths:`, `expires=` carries the latest holder expiry so older readers see a stricter lease, and the `MERGE_LEASE` line ends with `holders=<n>`. A value that is not a whole number of at most three digits (for example `abc` or `1000`) uses 1 with a warning; 0 gives 1 and 6-999 give 5.

What this means for consumer repos: nothing changes with the default of `1`: the lease record, the log lines and the GitHub API calls are the same as before. To try parallel holders, set the repo variable `MERGE_LEASE_MAX_HOLDERS` to `2` only after the `@stable` sync that ships this change has reached every workflow that runs the lease; an older staged script that releases a holder rewrites the record with one holder, and the others acquire again on their next update.
