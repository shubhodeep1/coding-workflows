- **Release and consumer-sync gaps no longer reach an operator step when the model leaves out their condition, and the poller's operator-step resolve step can no longer hold the poll job.** Activation verification now sends an `operator` gap that has no `dormant_until`, is titled as a release or consumer sync (for example "Promote main to stable"), and names no secret, token, setting or similar, to the release path instead of the `ai:operator-step` issue. The resolve classifier in `scripts/operator_step_issue.py` already treated that kind of gap as a release step. The poller's "Resolve released operator steps" step now has `timeout-minutes: 5`, so a hung `gh` call becomes a warning instead of using up the poll job's 360-minute limit.

`activation_normalise_verdict` in `scripts/activation_verify.sh` now uses `RELEASE_STEP_TITLE_RE` and `HUMAN_OBJECT_TITLE_RE`, copied from the writer, and a test checks that both copies match. Before this change, only an `@stable contains` condition rerouted a gap, so the rule that a release "never reaches a person" depended on the model following the prompt. A gap whose title names a secret or setting stays an operator step. So does a gap that carries its own condition. New contract tests cover the resolve CLI: with the kill switch off it makes no API call, and an API error on the listing or on a tick post exits 2 and closes nothing. Log keys, env vars and identifiers are unchanged.

What this means for consumer repos: after the next `@stable` sync, an activation verdict that lists promoting `main`, tagging `stable` or the consumer sync as an operator step without a condition shows that gap in the verdict comment as shipping with the next release, and opens no operator step for it.

Refs #9393. Refs #8291.
