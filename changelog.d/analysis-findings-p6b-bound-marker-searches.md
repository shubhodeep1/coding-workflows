- **The apply-analysis doc scan is now bounded, so a growing `analysis/` backlog can no longer stall the daily promote cycle.** `scripts/apply_analysis_on_main.sh` used to run one `search/issues` call (plus up to 20 comment reads) for every unlisted analysis doc, in both list-only and dispatch mode, and one failed lookup skipped the run as `guard_unavailable`. The newest-first scan now stops once it has found `APPLY_ANALYSIS_MAX_CANDIDATES` unprocessed docs (default `3`, raised to `PROMOTE_CYCLE_MIN_DOCS` when that is larger, logged as `APPLY_ANALYSIS_CANDIDATE_CAP raised_to=<n> reason=promote_cycle_min_docs` on stderr), or once it has skipped `APPLY_ANALYSIS_MAX_MARKER_SEARCHES` docs for a trusted dispatch marker (default `20`) with older docs still unexamined. List-only mode then appends ` capped_behind_markers=true` to its `APPLY_ANALYSIS_CANDIDATES` line; dispatch mode with no doc found logs `APPLY_ANALYSIS_SKIPPED reason=scan_capped_behind_markers searches=<n>` instead of `all_docs_processed`; and `scripts/promote_main_cycle.sh` skips a capped count below `PROMOTE_CYCLE_MIN_DOCS` as `PROMOTE_CYCLE_SKIPPED reason=scan_capped_behind_markers available=<n> required=<m>`, with the same text as a `::warning::`. An uncapped low count still skips as `insufficient_docs`. At the defaults a run makes at most 3 + 20 = 23 `search/issues` calls; no new API calls were added, and a failed lookup still fails closed. When abandoned marker docs fill the front of the scan, record them in the processing report (which also lets the log analysis purge remove them) or raise `APPLY_ANALYSIS_MAX_MARKER_SEARCHES`.
