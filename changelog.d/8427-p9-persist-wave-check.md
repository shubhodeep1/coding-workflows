- **Check between waves, behind `PERSIST_ORCH_WAVE_CHECK_ENABLED` (default off).** With the repo variable on, a cleanly completed orchestrator wave no longer advances straight away: the poller holds the boundary for one tick (the head it read predates that tick's merges), then reads the check runs on the integration PR's head (one call, no extra PR read). Only failures of the checks the final merge requires (`ORCH_FINAL_MERGE_REQUIRED_CHECKS`) count, and a newer run of the same name hides only a cancelled one. Passing checks advance the wave as before; pending checks hold the wave (recorded once in `wave_check_wait_since`) for up to `PERSIST_ORCH_WAVE_CHECK_MAX_WAIT_MINUTES` (default 90); failing checks, or checks still pending after the wait, send the wave to the existing wave judge with a fenced `UNTRUSTED WAVE CHECK` block (failing checks, one log tail of at most 8 KiB, unmet done-checks). A missing final PR, an unknown head or unreadable checks fall back to today's behaviour. At most two API reads per tick. With the variable off nothing changes, apart from removing a leftover wait field. Phase P9 of the persistent unattended workflows plan; Refs #8427.
