- **`implement.yml` is back under the workflow size ceiling.** The "Preflight destructive-commit guard" and "Attempt post-Codex syntax repair" step bodies moved word for word into `scripts/implement_step_preflight_destructive_guard.sh` and `scripts/implement_step_post_codex_syntax_repair.sh` (#9678). The file drops from 447,636 to about 400,000 bytes, well under the 480,000-byte guard.

Both steps run after the editor's writes are copied back, so each one sources its script only from the trusted pre-editor copy in `IMPLEMENT_STAGED_SUPPORT_RUN_DIR` and fails closed when that copy is missing or a symlink; a workspace copy never runs. Step names, ids, conditions, env, outputs (`destructive_commit_*`, `scope_violation_*`, `staged_support_rebase_conflict*`, `repaired`) and log lines are unchanged. Both scripts are new required support files, so a support ref that predates them fails the implement run until the next `@stable` release carries them, except on the legacy `main`-snapshot fallback described below. With the default unified staging (`SUPPORT_SCRIPTS_UNIFIED_ENABLED=true`), staging copies only what that ref's own `stage_support_for_phase.sh` lists and stays green; the run then fails at the "Preflight destructive-commit guard" wrapper, after the editor has run, with `::error::Trusted pre-editor copy of implement_step_preflight_destructive_guard.sh is missing`. The legacy staging loop first falls back to the `main` snapshot in `.codex-workflow-src-main`, which is checked out only when `SCRIPT_REF` is `stable`; when that snapshot carries the scripts, staging installs them from it and the run proceeds. It fails at staging itself (`::error::Missing required support script`) only for a pinned `SCRIPT_REF`, or when the `main` snapshot is missing or does not carry the scripts either.
