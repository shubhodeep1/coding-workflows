- **The workflow log analysis report now arrives through a pull request.** The `Commit and push report` step of `workflow-log-analysis.yml` no longer pushes the new `analysis/workflow-optimization-<date>(-N).md` report straight to the dispatch branch.

The step now keeps the purge, the commit and the retry-with-rename loop as they were, but pushes to a run-unique `auto/workflow-log-analysis-report-<run_id>-<attempt>` branch. It opens a PR against the dispatch branch (the body is linted by `scripts/lint_pr_body_auto_close.py` first), then tries a squash merge with `--match-head-commit`, then `--auto`, and otherwise leaves the PR open with a warning. It never uses `--admin`, so branch protection still applies. Before any merge call it drops the old-report purge from the PR, so a purge decided now cannot land hours later (through auto-merge or a merge queue) after an apply-analysis project started reading one of those reports. PR mode therefore no longer purges old reports; apply-analysis deletes the docs it processes, and push mode still purges. If the purge cannot be dropped, the PR is left open with a warning and is neither merged nor set to auto-merge. After either merge call it waits up to `WORKFLOW_LOG_ANALYSIS_REPORT_MERGE_WAIT_MINUTES` (default 10, 0 to 20) for the report to reach the branch, polling with git only, and counts only a landed report as `pr_merged`, so a PR that merely joined a merge queue keeps its branch. Before choosing the report path it also checks the other pending `auto/workflow-log-analysis-report-*` branches, so two same-day reports never add the same file. The run-branch push uses `--force-with-lease`. The step writes new outputs `delivery`, `report_pr_number`, `report_pr_url` and `report_branch` next to the unchanged `committed` and `report_file`, and logs one `WORKFLOW_LOG_ANALYSIS_REPORT_DELIVERY` line. The analyze step's report path now reaches the shell through `env:` and must match the dated report pattern. `analyze-commit-notify` gets a job-level `pull-requests: write` grant, `deep-audit` runs only when the report reached the branch, and the Telegram message links the PR while the report waits in it (at WARNING only when the PR is left open, since an armed auto-merge needs nobody), or reports a failed or cancelled delivery at WARNING instead of linking a report that is not on the branch. The merge wait never runs past 55 minutes after the job started.

| The numbers that matter | Value |
| --- | --- |
| GitHub API calls per committed run | at most 3 (`gh pr create`, `gh pr merge`, `gh pr merge --auto`), plus 1 `gh pr list` only when the PR already exists |
| New repo variable | `WORKFLOW_LOG_ANALYSIS_REPORT_VIA_PR` (default `true`) |
| New repo variable | `WORKFLOW_LOG_ANALYSIS_REPORT_MERGE_WAIT_MINUTES` (default `10`) |

What this means for consumer repos: after the next `@stable` sync, each dispatched log analysis run opens a report PR. Where branch protection refuses the direct merge, the report lands when auto-merge completes or someone merges the PR, and that run skips the deep audit and the API-redundancy audit, with a warning. When the report does land in the run, the deep audit and API-redundancy sections are still not delivered yet: each section job logs a warning and `outcome=skipped reason=no_report_branch`. A caller that reads the newest report from the branch right after a successful run (for example Phase 2 of `comprehensive-test-and-release.yml`) then sees the previous report. Each report PR is a normal pull request, so it runs PR CI and the review pipeline like any other; a report under `analysis/` usually takes the docs-only review skip. A report PR with auto-merge set up is reported at DEBUG, because GitHub merges it once its checks pass. If a required check on it then fails, the PR stays open and nobody gets a Telegram alert, only the run-log warning, so look for open `auto/workflow-log-analysis-report-*` pull requests when a report is missing. Set `WORKFLOW_LOG_ANALYSIS_REPORT_VIA_PR=false` to keep the direct push.
