- When the release gate gives up waiting for a child run it dispatched, it now cancels that run. In release run 43590943288 the `validation-refresh`, `validate` and `orchestrate` children stayed queued for 3 to 4.7 hours with no runner, the watches timed out, and the children ran hours later anyway: the orchestrate child then created a smoke tracking issue and Wave 1 issues that the gate's cleanup could not see. Every dispatch step of `test-and-mark-stable.yml` that waits for its child to complete ("Dispatch & watch — validation-refresh", "Dispatch internal-orchestrate.yml with multi-issue project", "Dispatch internal-validate.yml standalone", "Dispatch & watch — update_workflows (allow_workflow_edits=false)", "Dispatch & watch — internal-memory-maintenance") now reads the timed-out child's jobs once, prints a `::warning::` with the number of jobs and how many are queued with no runner (`unknown` when the jobs read fails or returns no jobs list), and cancels the child. Both calls only warn when they fail, and the step still fails with the watcher's exit code. Set the `DISPATCH_WATCH_CANCEL_ON_TIMEOUT` repository variable to `false` to skip the cancel (the three jobs that own these steps map it into their environment, defaulting to `true`). Unset, empty or `true` (any letter case) cancels; any value other than `true` or `false` also skips the cancel and logs a `::warning::` that does not print the value, following the repository's boolean-variable convention. The switch gates only this timeout cancel: the orchestrate job's `if: always()` "Cleanup orchestrate test issues" step still cancels its dispatched run through `scripts/stable_orchestrate_cancel_dispatched_run.sh` whatever the switch says, so a queued bootstrap cannot create a project after the gate's cleanup has run. The cause of that run was most likely runner starvation, so re-run the release gate once the runner queue clears. Refs #9532.
