- **The isolated implement sandbox can include Solidity compilers.** A new opt-in repo variable, `SANDBOX_SOLC_VERSIONS` (default empty: off), lists up to 5 `solc` versions, for example `0.8.24, 0.8.20`. `scripts/codex_isolated_exec.sh` validates the value. When it is set, the sandbox image build downloads each version from `binaries.soliditylang.org`, checks its sha256 against the official `linux-amd64/list.json`, and fails the build on a mismatch. The versions are installed as `/usr/local/bin/solc-<version>`, with `/usr/local/bin/solc` pointing at the first one. They also go into a Hardhat `compilers-v2` cache that the agent container links into `$HOME/.cache`, so Hardhat compiles with no network. An invalid value logs `::warning::CODEX_ISOLATION solc_versions_invalid reason=<format|too_many>` and the image is built without solc; on a runner that is not x86-64 the warning says `reason=unsupported_arch` and the image is built without solc too. `.github/workflows/implement.yml` passes the variable at workflow level, so `prepare`, `run`, `run --engine claude` and the pre-push gate's `image` call all build the same image.

What this means for consumer repos: nothing changes unless you set `SANDBOX_SOLC_VERSIONS`. Empty or invalid, the image build context and build args are byte-identical to before, so the prebuilt `codex-isolated-codex` and `codex-isolated-claude` images are still pulled. When set, the image is built locally on x86-64 runners, and the build needs `binaries.soliditylang.org` to be reachable. The checksum catches a corrupt, truncated or wrong file. It does not protect against a compromise of soliditylang.org itself.
