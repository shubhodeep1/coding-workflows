- **Automated merges and stable releases now refuse protected `.claude` changes unless the repository owner approved the exact PR head.** This closes security finding #4919 (`template-variant-authorization-bypass`, high).

The template parity test from #4775 could not tell who changed a consumer-variant command. An unattended agent could therefore edit the command and its pinned SHA-256 in one PR, pass CI, auto-merge, and reach every consumer on the next `@stable` sync. Now every unattended `gh pr merge` runs through `scripts/protected_path_gate.sh`. That covers review auto-merge, the review-blocked judge, and the orchestrator. A PR that changes a protected-equivalent path merges only after the owner posts an unedited comment whose whole body is `/authorize-protected-paths <head sha>`. Comments from Claude sessions carry the `claude` GitHub App attribution and never count. The gate also binds every merge it lets through to the head it checked, and turns off an auto-merge pending on a PR it refuses. GitHub keeps auto-merge enabled across pushes by anyone with write access, so a protected change pushed after auto-merge was enabled cannot ride on it. The release workflows and the manual `scripts/mark-stable.sh` apply the same check to every protected change since the previous `stable` tag before the tag moves. That includes a protected edit made inside a merge commit, such as a conflict resolution.

| The numbers that matter | Value |
| --- | --- |
| Protected-equivalent paths | `.claude/**`, `workflow-templates/.claude/**`, `tests/test_claude_template_parity.py`, and the gate's two scripts |
| Merge calls gated | 22 `gh pr merge` calls in `scripts/review_enable_auto_merge.sh` (2), `scripts/review_rb_judge.sh` (5), and `scripts/orchestrate_poll_process.sh` (15, at 9 sites) |
| Release check | "Verify protected-path changes are authorized (issue #4919)" in the `validate` job of `test-and-mark-stable.yml` and `mark-stable.yml`, and in `scripts/mark-stable.sh` (exit 6 on a refusal) |
| Extra API cost per merge attempt | 2 REST reads for an unprotected PR (PR + files); comments are read only for a protected PR; one GraphQL mutation only when a refused PR has auto-merge pending (at most 3 when it fails, each retry after one PR read) |

What this means for operators: a PR that touches the protected set now stays open after a clean review. It carries one comment naming the head to approve. Post `/authorize-protected-paths <sha>` yourself from the GitHub web UI or app, then merge it, or let the orchestrator retry. A new push needs a new approval. If a release stops at the new step, post the command with the merged head SHA on each PR it lists and re-run the release. Changes merged before the gate existed are grandfathered. Consumer repos get the gate with the next `@stable` release, and it applies there only to PRs that touch the same paths.

### For contributors

`scripts/protected_path_authorization.py` holds the rules and prints one JSON line. The `pr` mode exits 0 to allow, 3 to block, and 2 on a read error. The `release` mode exits 0 to pass and 3 to block. It needs the full history (a shallow checkout fails) and git 2.36 or later for `--remerge-diff`. `scripts/mark-stable.sh` pushes `stable` and the major-version tag with `--force-with-lease` on the values it read before the check, and exits 8 rather than roll back a release that moved them meanwhile. Wrap any new unattended merge as `protected_path_guarded_merge gh_retry gh pr merge …`. `tests/test_protected_path_authorization.py` fails on an unwrapped `gh pr merge` in `scripts/*.sh`, and on any protected path that `review_autofix.yml`'s deterministic-skip guard (`PROTECTED_SKIP_SUPPRESSED`) would let skip review. The wrapper binds an authorized merge with `--match-head-commit`. Every failure, a missing checker included, returns 3 so the caller's existing "merge failed" branch runs.
