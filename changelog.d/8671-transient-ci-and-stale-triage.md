<!-- changelog: fixed -->
- **A CI job that failed only because `actions/checkout` could not fetch is now re-run once by the review sweep.** CI run 40999073395 on PR #8430 failed in its checkout step with `RPC failed; HTTP 408`, `expected 'packfile'` and git exit code 128, and no test ran. `scripts/ci_cancelled_rerun.py` now treats such a job as transient (log reason `checkout_fetch`) when the checkout step is the first failed step, nothing ran after it and every failure annotation is a fetch error. The run's failed jobs get the existing single re-run, under the same once-per-head cap and read caps, with no extra API reads. `CI_CHECKOUT_FETCH_RERUN_ENABLED=false` turns this class off. Refs #8430, Refs #8433.
- **A check-triage issue whose failure a later push fixed now closes while its pull request is still open.** The already-resolved gate (`scripts/check_triage_resolution.py`) only resolved after the PR merged, so an issue filed against an orchestrator integration PR stayed open until the project ended. It now also resolves when the PR is open, its head has moved past the issue's `Head SHA`, and the newest run on the current head passed every job that failed (`path=open_head`). A pending or missing run stays unverified. Refs #8427, Refs #8433.
- **A new failure on a newer head of the same PR and check is triaged instead of being skipped behind a stale blocked issue.** Before filing, `scripts/check_failure_triage.sh` checks that the old `ai:blocked` issue was opened by the account that posts triage issues and is still open and blocked; otherwise it keeps skipping the failure as a duplicate. It then files the new issue, checks the old one again, comments on it, closes it as `not_planned` and labels it `ai:closed` (marker `<!-- check-failure-triage:superseded-by=<n> -->`). Lineage and the generation cap are unchanged. `CHECK_TRIAGE_SUPERSEDE_STALE_ENABLED=false` turns this off.
- **The unblock judge no longer turns "re-run a check" into an operator step.** Both judge prompts gain a rule against it and a new `wait` condition, `pr_check_green`, which holds an `ai:check-triage` item until the check passes on its pull request's current head. The judge reads that condition from the check-triage gate it already runs, so it makes no extra API calls.
- **The `CI_RERUN_PR_8430_UNSET_OPERATOR_STEP` operator step is withdrawn; no operator action is needed.** An earlier note (fix-up #8439) recorded a re-run of CI on PR #8430 as a step for a person. The failure was a one-off checkout timeout on `fd967e4`, later CI on PR #8430 passed, and nothing ever read the placeholder. This correction does not change any behaviour. Refs #8430, Refs #8433.
