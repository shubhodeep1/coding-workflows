- **When a Claude session rejects every review finding on a `claude/*` pull request, a GPT judge in the review workflow now decides, instead of the pull request waiting on a human.** The judge rules on each finding and merges the pull request, fixes what it upholds, or holds it for a person.

Until now, a Claude-fixer pull request whose findings the Claude session judged invalid could only converge through a dedicated GitHub App bot posting a ledger-bound verdict. `CLAUDE_FIXER_VERDICT_BOT_LOGIN` was never configured, and a Claude Code on the web session cannot post as a bot anyway, so six pull requests (#4602, #4594, #4609, #4611, #4638, #4596) sat on hold on 2026-09-27. Now the session posts its rejection reasons in one comment and dispatches `review_autofix.yml` (or the consumer's `ai-review.yml`) with `claude_fixer_judge_head=<sha>`. The gate accepts that only for the head's newest findings hand-off, the reviewers are skipped, and the review-blocked judge runs in a new Claude mode on `WORKFLOW_EDITOR_MODEL`: it reads the reviewer ledger from the hand-off run's verified `claude-fixer-evidence-*` artifact, treats the session's comment as an argument rather than evidence, and rules on each finding. Nothing upheld enables auto-merge bound to the head once its checks are green. Upheld findings are fixed by the judge in a `[judge-fix] claude-fixer round <r>: …` commit, which starts a normal review round. At the judge-fix cap the pull request merges with a follow-up issue for the upheld findings, unless one of them is a security or data-loss defect, which labels it `ai:needs-human`; the follow-up issue is opened only when the pull request is set to merge on that run, so a failing check hands off without one. A later round's finding that repeats one the judge ruled invalid (same file, within 3 lines) is listed as non-blocking instead of starting another round.

| The numbers that matter | Value |
| --- | --- |
| Judge fixes per pull request (`CLAUDE_FIXER_JUDGE_FIX_CAP`) | 2, counted on the pull request's own commits, never reset |
| Sticky-ruling window | same file, start line within 3 lines, same claim, newest 3 judge runs |
| Reviewer model calls per judge run | 0 (one judge call, plus one writer call for a fix) |
| API calls to prepare a judge run | 3 or 4 REST reads for the hand-off evidence, plus 3 per earlier judge run (at most 3) |
| New repository variables | `CLAUDE_FIXER_JUDGE_ENABLED` (default `true`), `CLAUDE_FIXER_JUDGE_FIX_CAP` (default `2`) |
| New dispatch input | `claude_fixer_judge_head` on `review_autofix.yml` and the `ai-review.yml` wrapper |

What this means for operators: a Claude-fixer pull request no longer needs a human when the Claude session and the reviewers disagree; look for the `## Review round <r>: GPT judge verdict` comment and the `AUTOFIX_GATE_CLAUDE_FIXER_JUDGE` and `CLAUDE_FIXER_JUDGE` lines in the review run logs. A pull request labelled `ai:needs-human` by the judge is waiting on you. Set `CLAUDE_FIXER_JUDGE_ENABLED=false` to reject every judge dispatch; sessions then fall back to the verdict bot or the hold. The verdict-bot path and `claude_fixer_converged_head` are unchanged. Consumer repos get the change on the next `@stable` release; until their `ai-review.yml` wrapper carries the new input, the dispatch is refused and sessions hold as before.

### For contributors

The gate reads the hand-off's run id from its run link (a pointer only) and exports `claude_fixer_judge`, `claude_fixer_judge_run`, `claude_fixer_judge_round` and `claude_fixer_judge_ledger`; an accepted judge dispatch bypasses the terminal same-head skip, and the retrigger guard forces `max_iterations_reached=true` with `skip_judge=false`. "Prepare Claude-fixer judge" (`scripts/review_autofix_step_claude_fixer_judge.sh`) verifies the hand-off run's evidence with `review_claude_fixer_evidence.py verify --expect-ledger --ledger-out`, and `scripts/review_claude_fixer_judge.py` holds the decision table, the sticky-ruling demotion, the prior-ruling loader (`verify --require-judge`), and the verdict and follow-up text. A judge run uploads its evidence in "Upload Claude-fixer judge evidence" after the judge, and the earlier upload step skips judge runs so the artifact name stays unique. A judge that reaches no decision leaves `judge_handled=false`, so "Label Claude-fixer PR review-blocked" labels the pull request `ai:review-blocked`; that covers no usable ruling (`claude_fixer_no_rulings`), a failed decide helper (`claude_fixer_decide_failed`), and a judge-fix count neither git nor the API could read (`claude_fixer_fix_count_unreadable`), which is never treated as the cap. When the model rules on a finding twice, the most cautious ruling is kept. Until PR #4596 merges, the hand-off step adds its own `=== NON-BLOCKING FINDINGS ===` block for sticky findings. Tests: `tests/test_review_rb_judge_claude_mode.py`, the judge cases in `tests/test_review_autofix_claude_fixer_mode.py`, and `tests/test_review_claude_fixer_evidence.py`.
