- **Self-repo implement runs no longer fail after a successful edit because the editor's own test run wrote into the workflow's staged-support ledger, and a repeated implementation failure on one issue now reaches the workflow failure heal intake.**

Implement runs 35614385686, 35628923735, 35642366131 and 35656715219 (issues #4227 and #4242, project #4139) each produced a complete change set and then died in the post-editor `reinstall` with `IMPLEMENT_STAGED_SUPPORT_BASE_MISSING path=scripts/helper.sh`. `implement.yml` exports `STAGED_SUPPORT_EDITOR_HEAD_LEDGER` into the job environment, the codex editor inherits it, and when the editor validated its change with `pytest tests/test_implement_post_codex_recovery.py` the staged-support round-trip test ran `scripts/implement_staged_support_workspace.sh restore` with an environment copied from `os.environ`. The helper prefers that inherited variable over its ledger-relative default, so the test appended its fixture path `scripts/helper.sh` to the live run's editor-head ledger, failed its own ledger assertion, and left an entry the workflow could not reinstall. The stall poller retried twice, the stall judge closed #4227 and re-issued it as #4242, and the replacement failed the same way. Nothing reached the heal path: the implement workflow had no heal reporter, and stall recovery never applied an escalation label.

Three changes close this. `tests/conftest.py` strips the four staged-support runtime variables for the whole pytest session, the same way it already strips `GIT_DIR` / `GIT_WORK_TREE`. `scripts/implement_staged_support_workspace.sh reinstall` acts only on editor-head ledger entries that are also in `STAGED_SUPPORT_LEDGER` and logs any other entry as `IMPLEMENT_STAGED_SUPPORT_EDITOR_HEAD_LEDGER_UNKNOWN_PATH` instead of failing closed, which takes effect for every branch as soon as `main` carries it. And `implement.yml` gains a failure-path reporter, `scripts/workflow_failure_heal_implement_report.sh`, that sends an `implement_failure` report to the heal intake once `WORKFLOW_HEAL_IMPLEMENT_FAILURE_STREAK` (default 2) implementation runs in a row failed on the same issue, counted from the workflow's own failure comments.

| The numbers that matter | Value |
| --- | --- |
| Failed implement runs on the same defect | 4 (35614385686, 35628923735, 35642366131, 35656715219) |
| Variables stripped per session | `STAGED_SUPPORT_LEDGER`, `STAGED_SUPPORT_BASE_DIR`, `STAGED_SUPPORT_EDITOR_HEAD_LEDGER`, `IMPLEMENT_STAGED_SUPPORT_RUN_DIR` |
| Implement failure streak before a heal report | `WORKFLOW_HEAL_IMPLEMENT_FAILURE_STREAK` = 2 |
| Run references per heal report | this run plus up to 2 runs linked from the issue's failure comments |
| Stall recovery cost before the re-issue | 2 retries, 1 stall-judge run, 127 minutes in `ai:implementing` |

What this means for operators: a self-repo implement run whose editor runs the staged-support tests completes instead of failing after the edit, an editor-head ledger entry that is not a staged copy no longer kills the run, and when an implementation still fails twice in a row on one issue the heal intake opens an `ai:workflow-heal` issue with the job logs of the whole streak instead of leaving the failure to the retry and re-issue loop. Consumers need no new wrapper: the reporter ships inside `implement.yml` and is staged fail-open from the pinned release, with `WORKFLOW_HEAL_ENABLED=false` as the kill switch.

### For contributors

Tests that exercise `scripts/implement_staged_support_workspace.sh` or `scripts/implement_commit_changes.sh` may still set the ledger variables explicitly; the session fixture only removes values inherited from the launching workflow. `WORKFLOW_RUNTIME_ENV_VARS` in `tests/conftest.py` is the combined list. The reporter's streak counter (`count_implement_failure_streak` in `scripts/workflow_failure_heal.py`) treats plan, `/approved` and stall-recovery comments as neutral and ends the streak at a BLOCKED verdict, a pathspec halt or a no-op comment, because those paths already route the issue elsewhere. A re-issued issue starts a fresh streak; the parent's failures are not carried over.
