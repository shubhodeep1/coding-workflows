- **A CI-failure re-issue whose PR merged into a non-default branch now runs on that branch.** `scripts/resolve_integration_ref.sh` resolves an unblock-judge re-issue to the base branch of its owning PR when that PR merged into a non-default branch of the same repository (for example an orchestrator integration branch). Before this, the re-issue planned and implemented against the default branch, which does not hold the failing code.

The unblock judge (`scripts/unblock_actions.py`) writes a re-issue for a CI failure whose owning PR has been verified with only a `<!-- check-failure-triage:pr=<n> -->` lineage marker: no `ai:check-triage` label and no `Integration branch:` line. The resolver used to skip such bodies. It now routes only the exact shape the unblock judge writes: the marker on line 1, `Re-issued by the unblock judge from #N.` on line 2, a trusted author (`OWNER`, `MEMBER` or `COLLABORATOR`), no `ai:orchestrator-managed` label and no tracking line. It reads the PR once through the rate-limit-aware `gh_api_retry`. If the PR merged, both sides are this repository, its `base.ref` passes the head-ref safety rules and is not `base.repo.default_branch`, and the branch still exists, the resolver prints it and logs the existing `CI_TRIAGE_PR_BRANCH_ROUTING ... outcome=routed` line. A PR that did not merge, or that merged into the default branch, keeps today's default-branch result. Anything the resolver cannot verify keeps the default branch, as the re-issue did before this change, and logs one `::warning::CI_TRIAGE_PR_BRANCH_ROUTING ... outcome=skipped reason=<token>` line: a failed PR read (`pr_lookup_failed`, with gh's error text echoed first), a mismatched PR number (`pr_association_mismatch`), a cross-repository PR (`pr_cross_repository`), an unsafe base ref (`base_ref_invalid`), or a branch read that fails (`branch_lookup_failed`) or names another ref (`branch_missing`). The resolver never stops the phase with exit 3 for this shape. When the base branch no longer exists, the resolver asks `scripts/retarget_merged_base.sh` where that branch's own merged PR went: if it was merged into the default branch and then deleted (orchestrator finalize uses `--delete-branch`), the re-issue keeps the default branch, which now holds the code, and logs `::notice::CI_TRIAGE_PR_BRANCH_ROUTING ... outcome=skipped reason=base_branch_merged_into_default`. The resolver always runs that helper with `RETARGET_MERGED_BASE_ENABLED=true`, so plan and implement give the same answer whatever the repository variable says. If the helper's lookup fails (or the helper is missing), the skip reason is `branch_lookup_failed`; any other deleted base branch skips with `branch_missing`. A rate-limited read exits 75. The routing runs only while the existing `CI_TRIAGE_PR_BRANCH_ROUTING_ENABLED` (default `true`) is on, and a new switch, `CI_TRIAGE_REISSUE_BASE_BRANCH_ROUTING_ENABLED` (default `true`; `false` turns it off, any other value turns it off with a `::warning::`), turns off this routing alone (`outcome=skipped reason=flag_off`) without touching the labelled `ai:check-triage` routing. The clarify, plan, implement, orchestrate_clarify_respond and validate workflows forward the repository variable `CI_TRIAGE_REISSUE_BASE_BRANCH_ROUTING_ENABLED` (default `true`) to the resolver in their "Resolve integration ref" step.

| The numbers that matter | Value |
| --- | --- |
| New GitHub API calls per eligible re-issue | 2 (one PR read, one branch read), plus 2 when the base branch is gone (one closed-PR search, one ref read per followed hop); none on any other issue |
| New refusal reasons | 0 (every unverifiable reissue keeps the default branch with an `outcome=skipped` warning) |
| New environment variables | 1 (`CI_TRIAGE_REISSUE_BASE_BRANCH_ROUTING_ENABLED`, default `true`, forwarded from the repository variable by clarify, plan, implement, orchestrate_clarify_respond and validate; setting the repository variable to `false` turns the re-issue routing off, `reason=flag_off`) |

What this means for operators: no re-issue is stopped by this routing. When a run logs `CI_TRIAGE_PR_BRANCH_ROUTING ... outcome=skipped reason=<token>` as a warning, the re-issue ran on the default branch. If it should have run on the merged PR's base branch (for example an abandoned integration branch, `reason=branch_missing`, or a failed API read, `reason=branch_lookup_failed`), add an `Integration branch:` line to the re-issue, or recreate the branch, and re-run. Setting the repository variable `CI_TRIAGE_REISSUE_BASE_BRANCH_ROUTING_ENABLED=false` turns the re-issue routing off (`outcome=skipped reason=flag_off`) and leaves the labelled `ai:check-triage` routing unchanged.
