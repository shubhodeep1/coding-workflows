- **Workflow log analysis now reports which repositories it could not collect, or collected only in part.** `scripts/collect_workflow_logs.py` adds a top-level `coverage` object to `workflow_log_report.json` (and `summary.json`), and the collect step logs it, annotates it and alerts on it.

`coverage` holds `repositories_requested`, `repositories_failed` (`{"repository", "message"}`, with the message sanitized and capped at 300 characters), `repositories_truncated` and `page_limit_reached`. A repository whose run listing failed is `failed`; one whose listing hit `--max-runs`, the page limit, or (on the daily PAT-budget run) lost one of its per-workflow listings is `truncated`. The two lists never overlap. Exit codes are unchanged: the collector still exits 1 only when every repository failed, and the existing `errors[]` entries are unchanged. The `Collect workflow logs` step now prints one `WORKFLOW_LOG_COLLECT_COVERAGE` line, one `::error` annotation per failed repository and one `::warning` per truncated repository, even when the collector exits 1, then exits with the collector's own code. A new `Alert on workflow log collection gaps` step sends one Telegram alert at WARNING (so `ALERT_MSG_LEVEL=SILENT` holds it back), is `continue-on-error`, and is skipped on the 06:00 PAT-budget run. Only validated `owner/repo` names and counts are printed or sent, never error text. The analyze step copies `coverage` into `analysis_context.json`, and the analysis prompt now asks for every failed or truncated repository to be named in `## Executive Summary`.
