- **Stall recovery no longer auto-approves a plan while its base CI is red.** Before this change, `plan.yml` held `/approved [auto-approved-by-plan]` on a red base, but the poller's stall-recovery `auto_approve` (and `retrigger_implement` in `ai:awaiting-approval`) could approve the same plan on the next tick. That started implement runs whose PRs inherited the red base (Refs #9421, Phase 2 step 4 of the stuck-backlog plan).

`_plan_auto_approval_gate` in `scripts/orchestrate_poll_process.sh` now runs the same `red_base_approval_hold_check` from `scripts/plan_base_ci_gate.sh` before any other check. For orchestrator-managed issues it checks the project's integration branch; for all other issues it checks the default branch. On a red base it logs `STALL_SKIP ... reason=base_ci_red_hold`, posts nothing, and counts no recovery attempt. Results are cached once per branch per poller step, so a tick adds at most one runs read per configured workflow and one heal-issue listing per branch. Every read fails open. `.github/workflows/orchestrate_poll.yml` stages the helper from the pinned workflow source the same way `plan.yml` does.

What this means for consumer repos: after the next `@stable` sync, the hold also covers stall recovery. A consumer whose CI file is not `.github/workflows/ci.yml` sets `RED_BASE_HOLD_WORKFLOWS` to its path. `RED_BASE_APPROVAL_HOLD_ENABLED=false` turns the hold off in both places.
