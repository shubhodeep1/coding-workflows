- **The single-issue security pass no longer dispatches a second audit for a head that is already clean, and never reuses a cycle number.** The gate decided on the comments snapshot taken when the review job started, so a run that reached it later saw none of the markers an audit had posted since, dispatched again and posted `cycle=1` a second time (PR #10175). Before it dispatches an audit or posts a marker, and whenever the snapshot is unusable, the gate now reads the PR's comments once more, fresh. A clean marker in that view ends the gate `clean`; other new markers are decided on that view; a failed fresh read, or an empty one while the PR reports comments, holds with `hold_reason=markers_unverifiable` (`detail=fresh_read_failed|fresh_read_empty`) and dispatches nothing, posts nothing and counts no cycle. A new marker is always numbered above every trusted cycle already on the PR. New `SINGLE_ISSUE_SECURITY_PASS ... outcome=markers_read` log line (comments, markers, author, snapshot source, age and whether the signing shim is active), and the signing shim now logs the reason (and HTTP status) for every fallback to the PAT. Switches `SECURITY_PASS_MARKER_REREAD_ENABLED` and `SECURITY_PASS_CYCLE_REUSE_GUARD_ENABLED`, both default `true`. Why the failing runs posted unsigned comments is not confirmed; the new log fields show it on the next occurrence. Refs #10176, #10104.
