- **The single-issue security pass no longer dispatches a second audit for a head that is already clean, and numbers a new marker above every cycle already on the PR.** The gate decided on the comments snapshot taken when the review job started, so a run that reached it later saw none of the markers an audit had posted since, dispatched again and posted `cycle=1` a second time (PR #10175). Before it dispatches an audit or posts a marker, and whenever the snapshot is unusable, the gate now reads the PR's comments once more, fresh. A clean marker in that view ends the gate `clean`; other new markers are decided on that view; a failed fresh read, or an empty one while the PR reports comments, holds with `hold_reason=markers_unverifiable` (`detail=fresh_read_failed|fresh_read_empty`) and dispatches nothing, posts nothing and counts no cycle. A new pending or failed marker is numbered above every trusted cycle in the fresh view; two review runs that overlap on one PR can still both read before either posts and pick the same number (a race that predates this change; the fresh read only narrows it). New `SINGLE_ISSUE_SECURITY_PASS ... outcome=markers_read` log line (comments, markers, author, snapshot source `cache_hit|cache_miss|fallback|direct|synthesized|fresh`, age and whether the signing shim is on PATH), also before a `markers_unverifiable` hold, and the signing shim now logs the reason (and HTTP status) for every fallback to the PAT. Switches `SECURITY_PASS_MARKER_REREAD_ENABLED` and `SECURITY_PASS_CYCLE_REUSE_GUARD_ENABLED`, both default `true`. Cause (change 4): the repository-code part is confirmed and fixed here: the gate decided on the job-start snapshot, and an empty or unreadable comments file looked the same as "no markers". Why the failing runs' comments read came back without the markers and their posts fell back to the PAT is not recoverable from their logs (they did not record a fallback reason); the code paths that post without a signature line are the shim fallbacks now logged, and the one the evidence points to (a job-token refusal or the repository-wide job-token rate limit) is an external limit, so changes 1 to 3 stand on their own and the new log fields name it on the next occurrence. Refs #10176, #10104.
