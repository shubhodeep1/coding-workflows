- **The review-blocked judge now acts only on the pull request head it evaluated.**

Previously, a push during the judge call could cause two problems. The `fix` path could post the head-gate success status and apply `ai:ready-to-merge` for a head the judge never saw. A reissue could also keep unjudged code as its baseline. Now, after the judge runs, `scripts/review_rb_judge.sh` compares the live head with the head named in the judge prompt. The live head comes from the PR read the script already makes. When the head moved during the judge call, the judge skips every action before any comment, label, status or close (`judge_skip_reason=stale_head`, log line `RB_JUDGE_STALE_HEAD pr= judged_head= live_head= action=`). A force-push back to an older commit counts as moved. The one exception is the head this run checked out, sitting behind the run's own unpushed commit. When the live head cannot be read, `fix` and `close_and_reissue` are refused (`judge_skip_reason=head_unverified`). The same refusal applies to a merge that open security findings convert to `fix`. Merge actions are otherwise unchanged, because `--match-head-commit` already binds them. A spot-fix reissue uses the evaluated head as its baseline, which saves one `gh pr view` call. When the evaluated head is the run's own unpushed commit, the reissue uses the PR head the run checked out, because `implement.yml` ignores a baseline the closed PR never carried.

What this means for operators: a review-blocked PR that receives a push while the judge is running is left for a later review or judge run, and its linked issue no longer reaches `ai:ready-to-merge` from a verdict on an older head.
