- **A project parked after its final merge ran out of attempts now resumes on its own once the blocker clears.** The poller retries the final merge once per final PR head SHA when that PR is open, not a draft, mergeable with `mergeable_state=clean`, its required checks are green, and the integration branch is still ahead of the default branch; a head other than the one that passed validation is re-validated before the merge.

Before, after `MAX_FINAL_MERGE_ATTEMPTS` failed merges a project stayed `failed` with `ai:blocked` and every tick logged `Project already failed, skipping.`, even after the final PR went green (shubhodeep1/fun-token-multi-chain#579: final PR #596 was green and clean four days before a person merged it by hand). The exhaustion path now records `final_merge_failure_kind=final_merge_exhausted` and `final_merge_failure_head_sha`. The retry restores `ai:validated` (dropping `ai:blocked` and `ai:needs-human`), resets `final_merge_attempt_count`, posts one tracking comment and runs through `mark_validation_complete`, so the security pass, required-checks gate and head-bound merge still apply. If the retry fails the project parks again until the final PR's head changes. A new head is never merged on the strength of an older validation pass: the poller first sends the project back to runtime validation for that head and merges only once it passes. Projects whose comprehensive cycle was already aborted, or that failed validation after the park, are not retried. Every decision is logged as `FINAL_MERGE_AUTO_RESUME`. Set `FINAL_MERGE_AUTO_RESUME_ENABLED=false` to keep the old behaviour. Projects that failed for any other reason, or that parked before this change, are left alone.
