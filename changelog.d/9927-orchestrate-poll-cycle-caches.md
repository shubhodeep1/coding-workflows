- **The orchestrator poller reads less from the GitHub API per cycle (GH_PAT budget, part D).** In `scripts/orchestrate_poll_process.sh`, `_fetch_pr_json` now serves repeat reads of the same PR within one run from a per-run cache (a 0700 temp directory, removed on exit, 60-second TTL set by `ORCH_POLL_PR_JSON_CACHE_TTL_SECS`; `0` turns it off). Every `gh_retry` call that is not a read invalidates the cache through a new default-off `GH_RETRY_AFTER_CALL_HOOK` in `scripts/gh_helpers.sh`: only that PR's entry for an issue/PR-numbered write, the whole cache for merges, update-branch and other writes. `git push`, the PR-body PATCH and unwrapped merges invalidate it explicitly, and the review-blocked race-guard, post-judge and standalone-stall mergeability-retry reads always go live. The post-review-blocked and implementation-failed label re-reads use one `_fetch_issue_labels_batch_graphql` call (REST only for numbers the batch did not return). The 17 default-branch reads reuse the existing `_review_run_default_branch` memo once it is resolved, and the first successful read seeds it, so a run normally makes one GET for it; a failed read keeps the site's own fallback and costs no second GET. `ORCH_POLL_CYCLE_SUMMARY` gains `cache_hits_pr_json`, `cache_hits_default_branch` and `cache_hits_labels`. The noop force-merge sweep's second comment read is unchanged, because it is Gate B's fail-closed fresh snapshot. Poller decisions do not change. Refs #9927, #9887.
