- **The merge lease no longer revokes a holder whose review or CI run is still waiting for a runner.** Since the Phase 2 revocation rules reached `main` (#9804), seven lease holders in a row were released with `merged=false`: a granted PR's branch is updated, so it needs a new review and final CI run, and both waited 60-100 minutes for a runner, past `MERGE_LEASE_IDLE_MINUTES`. The tick now keeps a holder while a run that works on it is queued or in progress. Past the head-gate grace it reads the review and CI runs on the head once. Past the idle time it also checks the merge train's active-run listing for a run on the head or a `<workflow> [pr:<n>]` review dispatch, read once per tick. Such holds log `MERGE_LEASE ... outcome=held reason=holder_runs_active`. A queued run older than `ZOMBIE_RUN_MAX_QUEUED_HOURS` (default 24, the #9473 rule) is wedged and does not count. The TTL and the maximum hold still end every hold, and a failed run read keeps the holder.
- Skip entries now record why they were written: `skip=<pr>:<head>:<reason>`. An entry written for `revoked_no_head_gate`, or an old entry with no reason (every entry in the record today), stops blocking once the PR's pipeline head-gate is `success` on that head, so the PRs parked by the old rule are released once. Other reasons still block until the head changes. No new variable; `MERGE_LEASE_REVOKE_ENABLED=false` keeps the old behaviour. Operators have nothing to do; the stopgap `MERGE_LEASE_IDLE_MINUTES=180` repository variable can go back to its default once this is on `main`.

Refs #9983, Refs #9781.
