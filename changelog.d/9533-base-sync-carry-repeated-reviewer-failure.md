- **A pipeline base sync keeps the clean security audit, and a reviewer crash that repeats on one head stops instead of retrying.** PR #9356 waited more than a day after its fix was audited clean: a base sync forced a fresh audit, and a deterministic reviewer crash was retried as if it were transient.

`scripts/review_single_issue_security_pass.sh` now treats a head as clean when it is the pipeline's own freshness update of a clean head. The shared `review_head_gate_freshness_sync` verifier must accept the update commit, the newest trusted marker for `from=` must be `status=clean`, and over the PR's changed files the merge must change nothing of its own (matching `-U0` patch-ids). It logs `outcome=clean reason=base_sync_carry from=<sha>`. Anything unverifiable audits the head as before (`outcome=carry_skipped reason=<token>`). `SECURITY_PASS_BASE_SYNC_CARRY_ENABLED=false` turns the carry off.

A second `reviewers_failed` failure with the same fingerprint on the same head now blocks: the gate's identical-failure cap trips at `REVIEW_FAILURE_FINGERPRINT_MAX_IDENTICAL_REVIEWERS_FAILED` (default 2) for that reason only, the codex-agent job posts no "will retry" comment (`AUTOFIX_REVIEWERS_FAILED_REPEATED`), labels `ai:review-blocked` and posts one comment naming the fingerprint and the first error, and the poller's issue-less retry pass skips the head (`reason=repeated_reviewer_failure`). A single failure still retries. The reviewer step's stderr is now kept, so a shell crash such as `render_prompt.sh: line 306: 1abc: invalid variable name` fills `AUTOFIX_FAILURE_FIRST_ERROR` and the fingerprint.

What this means for consumer repos: after the next `@stable` sync, fingerprints of reviewer crashes that print a bash diagnostic change once; no action is needed.
