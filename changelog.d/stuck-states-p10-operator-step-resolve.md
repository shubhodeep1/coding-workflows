- **Activation verification no longer asks a person to do automated release steps, and the poller ticks and closes the operator-step issue once a release ships (stuck-states P10, Refs #8291).** Work that only takes effect once the next `@stable` release ships it is now reported as a release-pending `code` gap (`dormant_until` `@stable contains <merge commit>`). `scripts/activation_verify.sh` shows it in the verdict comment only: it opens no fix issue and writes no operator step, and a model `operator` gap with that condition is rerouted to such a code gap, so promoting `main`, tagging `stable` and the consumer sync never land in the `ai:operator-step` issue. A new poller step, "Resolve released operator steps" in `.github/workflows/orchestrate_poll.yml`, runs `scripts/operator_step_issue.py resolve` on every tick. It ticks an entry whose steps only wait for the release once `stable` contains its merge commit (`compare/<sha>...stable` reports `ahead` or `identical`, at most 10 compares per tick), and closes the tracker as completed when no unticked step is left. It never ticks an entry that also holds a real human step (a step whose own dormant condition is not the release counts as one, whatever its title), and it never closes a tracker a person reopened. If an operator step is written while the tracker is being closed, the poller or the writer reopens the tracker so the step is not lost; if that check itself cannot read GitHub, the poller reopens the tracker anyway and the writer reports the write as failed.

  What this means for operators: nothing needs to be run by hand. Release-only operator entries tick themselves after the nightly promote, and the operator-step issue closes itself when it is empty. To turn the poller step off, set the repository variable `OPERATOR_STEP_AUTO_RESOLVE_ENABLED=false`.
