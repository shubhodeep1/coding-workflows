- **Operator steps are only filed for real human work, and the `ai:operator-step` issue now ticks its entries and closes itself (stuck-states P10, Refs #8291).** Activation verification used to be able to file "wait for the `@stable` release" as an operator step or as a code gap for the pipeline to build. A gap whose only condition is `@stable contains <sha>` is now recorded as a release wait: it is shown in the verdict comment and opens neither a fix issue nor an operator step. The poller also runs a new `operator_step_issue.py resolve` step on every tick. It ticks an entry whose only condition is `@stable contains <sha>` once the `stable` commit contains the merge it came from (GitHub compare status `ahead` or `identical` only, at most 10 compares per tick) and closes the tracker as completed once no unticked box is left. A new entry that lands around the close reopens the tracker.

  What this means for operators: nothing needs to be run by hand. Steps that only wait for a release disappear on their own, and the tracker closes when every step is ticked. Steps for real human work (a secret, a repository setting) and steps without a merge commit (for example unblock-judge steps) still need a person to tick them. To go back to the old behaviour, set the repository variable `OPERATOR_STEP_AUTO_RESOLVE_ENABLED=false`.
