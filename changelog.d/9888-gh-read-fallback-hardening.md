- **A failing job-token read now always falls back to `GH_PAT`.** Before this, when a polling read made with the job's `GITHUB_TOKEN` (`gh_read` in `scripts/gh_helpers.sh`) failed with a 5xx or a network or other non-HTTP error, it went back to the caller's `gh_retry`, which retried the job token five times and never tried the PAT. That could fail the promote cycle's gate polls, the heal intake queue and the reviewer/editor PR-state watchdog even though the PAT would have answered. `gh_read` now drops the job-token output and runs the read once with the PAT on any job-token failure, and logs `GH_READ_FALLBACK reason=error caller=<script>` (no latch, so the next read tries the job token again). If the PAT fails too, the job token's error is returned, so `gh_retry` backs off and retries instead of raising a PAT rate-limit alert and waiting for the PAT reset. The release-gate twin `gh_api_safe_job_token_read` already handed every failure to the PAT loop; it now logs the same `reason=error` line. New tests in `tests/test_gh_read.py` run every call site that a `GH_READ_TOKEN` step reaches (`dispatch_and_watch_workflow_run.sh`, `stable_e2e_step_wait_review.sh`, `stable_orchestrate_cancel_dispatched_run.sh`, the promote cycle, the heal queue and `gh_review_pr_state`) under `set -euo pipefail` with the job token failing with HTTP 403, a rate limit, HTTP 502 and a non-HTTP error, and check that the PAT's answer is used, the caller exits 0 and no token is printed. Refs #9888.
