- **`gh_retry` reports a non-zero status again when the reader closes before a successful response is delivered on ubuntu-26.04 runners.** The CI test `tests/test_gh_retry_stdout_isolation.py::test_closed_reader_does_not_rerun_a_successful_command` passes again on the new image.

`gh_retry` in `scripts/gh_helpers.sh` buffers each attempt's stdout and copies only the successful attempt to the caller. It used to return the exit status of the external `cat` that did the copy. On the `ubuntu-26.04` image, `cat` comes from Rust coreutils, and that `cat` exits 0 when the reader closes the pipe early, so a caller could not tell that the output never arrived. The copy now uses bash's builtin `printf` in a subshell. When the reader is gone it returns 141 (SIGPIPE), or 1 when SIGPIPE is ignored, whichever coreutils the runner ships. The output is still byte-exact, including trailing newlines. `cat` is used only when the response holds a NUL byte, which a shell variable cannot store. A command that succeeded is still never re-run, and the temp files are still removed on every path. A new test swaps in a `cat` that always exits 0, so the regression now shows up on every host, not only on ubuntu-26.04.

What this means for operators and consumer repos: no action is needed. After the next `@stable` sync, scripts that pipe `gh_retry` output into an early-exiting reader (such as `head`) see the same non-zero status on every runner image.
