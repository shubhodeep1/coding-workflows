- **Plan no longer fails when the integration-ref lookup is rate-limited on a CI-triage issue.** When the integration-ref resolver hits a GitHub rate limit (exit 75) while CI-triage routing is on, plan still refuses to fall back to the default branch, but it now defers the run instead of failing it. The step writes no ref, sets `SKIP_PLAN=true`, skips every setup step (so the default branch is never checked out), replays the resolver's rate-limit line as a `::warning::`, logs `INTEGRATION_REF_RESOLVE outcome=deferred reason=rate_limited` and writes one line to the run summary. It makes no GitHub call. No label changes: stall recovery re-posts `/answer` after the limit resets for an issue in `ai:planning` or `ai:clarification`, while an `ai:blocked` issue stays as it was and needs `/answer` re-posted by hand. Before this, each rate-limited run failed the job and filed a `plan_failed` heal report for a cause that clears by itself. Exit 2, exit 3 and the routing-off fallback are unchanged. Refs #9599.

  What this means for operators: a rate-limited plan run on a CI-triage issue is now green. On installs without standalone stall recovery (the `core` profile, or `ENABLE_STANDALONE_STALL_RECOVERY=false`), or when the issue was in `ai:blocked`, nothing re-triggers planning; the run summary says so, and posting `/answer` again after the limit resets resumes it.

  For contributors: `test_plan_rate_limited_refusal_defers_without_failing` and `test_plan_setup_steps_skip_on_rate_limited_defer` in `tests/test_workflow_checkout_integration_ref_audit.py` cover the new path.
