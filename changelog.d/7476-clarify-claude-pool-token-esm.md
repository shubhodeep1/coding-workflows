- **Clarification no longer loses its Claude credential in consumers whose root `package.json` sets `"type": "module"` (#7476).** In such a repository Node loaded the `claude-pool-token` action's CommonJS `main.js` and `post.js` as ES modules, so they crashed on `require`, no account pool was written, and every clarify run ended with `AI_ENGINE_FALLBACK_REFUSED role=CLARIFY reason=no_credential` (`shubhodeep1/multi-user-ai-agent#266`). `clarify.yml` now runs the same "Pin claude-pool-token action module type" step that `plan.yml` gained in #7434, right before "Resolve Claude credential" and only when the role resolves to Claude. It writes `{"type":"commonjs"}` as `package.json` into the action directory of the support checkout, never overwrites an existing `package.json` or follows a symlink, logs `CLAUDE_POOL_MODULE_PIN outcome=written|skip|failed reason=present|action_dir_unavailable|write_failed`, and does nothing once the action ships its own `package.json`. Plan and clarify are now covered; implement, review, the poller judges, validate, clarify-respond and the other Claude roles still fail the same way in those consumers until a separately scoped issue commits `.github/actions/claude-pool-token/package.json`. The refusal of `no_credential` is unchanged. After this reaches a stable release and the consumer syncs, a stuck issue clarifies again on `/reclarify` or the stall poller's next retry.
