- **The security-audit tracker no longer gets pulled into the AI pipeline.** The poller treats an issue labelled `ai:security-audit` as what it is: a long-lived results log, not a work item (Refs #3576).

Standalone stall recovery had auto-answered a clarification on the tracker, planning then blocked with "nothing to implement", and the unblock judge kept picking it up. Now standalone stall recovery also lists `ai:security-audit` in its existing label batch, so a tracker left with only `ai:blocked` is found. It strips `ai:blocked` and any pipeline phase label from the tracker and logs `STALL_RECOVERY_SKIP ... reason=security_audit_tracker`, without closing it, editing its body or posting a command. `scripts/unblock_scan.py` skips it as `security_audit_tracker` (a failed project is still judged), and the unrouted-blocked-comment detector and the unblock scan's PR-dependency filter skip it too. Handling of `ai:orchestrator-tracking` is unchanged.

What this means for consumer repos: after the next `@stable` sync, a security-audit tracker stops collecting pipeline labels and judge comments. Setting `SECURITY_AUDIT_TRACKER_PIPELINE_EXCLUDE_ENABLED=false` (or `0`/`no`/`off`) in the poller's environment restores the previous behaviour; the orchestrate-poll workflow does not forward it from a repository variable yet.
