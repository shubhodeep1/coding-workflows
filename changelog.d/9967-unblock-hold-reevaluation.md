- **Unblock-judge holds that could never end on their own now end.** Two hold kinds are re-checked each time the judge looks at a held item (Refs #9967):

  - A `pr_on_branch` hold counts as met when the pull request's squash commit already has a patch-equivalent commit on the target branch, for example a hotfix that carried the fix to `stable` as a different commit. The judge fetches the branch and the commit into a scratch bare repository and runs `git cherry` limited to that one commit. A merge commit, a fetch failure or a commit not yet on the branch keeps the hold. Switch: `UNBLOCK_HOLD_PATCH_EQUIVALENCE_ENABLED` (default `true`).
  - A `placeholder_retired` hold on a standalone `ai:workflow-heal` issue closes the issue as completed when its failure did not come back. This uses the same green-run window and age as the poller's heal stale close (`HEAL_STALE_GREEN_RUNS`, `HEAL_STALE_MIN_AGE_HOURS`); a `#<n>`-sourced issue closes once its source item is closed. An open `ai/issue-<n>` pull request, a red run or any unreadable input keeps the hold, and a failed close is retried on the next run. Switch: `UNBLOCK_PLACEHOLDER_RECURRENCE_CHECK_ENABLED` (default `true`).

`workflow_failure_heal.py heal-stale-decision` gains `--purpose unblock_placeholder` and `--source-closed`; their defaults keep the poller's behaviour unchanged, and the `target` stage adds a `source_number` key. What this means for consumer repos: after the next `@stable` sync, these holds stop waiting out `UNBLOCK_JUDGE_WAIT_MAX_DAYS`. Setting either repository variable to `false` restores today's behaviour; `unblock_judge.yml` forwards both.
